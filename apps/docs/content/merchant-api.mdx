The merchant dashboard is a client of the same API. Everything under `https://api.ebda.app/api/v1` that is not `/public/*` needs a signed-in user (see [Authentication](/authentication/)) and is scoped to the stores that user may access.

## Account

| Method | Path              | Notes                                                       |
| ------ | ----------------- | ----------------------------------------------------------- |
| `POST` | `/auth/register`  | Create an account (also used by the self-serve signup form) |
| `POST` | `/auth/login`     | Sign in; sets the access and refresh cookies                |
| `POST` | `/auth/refresh`   | New access token from the refresh cookie                    |
| `POST` | `/auth/logout`    | End the session                                             |
| `GET`  | `/auth/me`        | Current user                                                |
| `GET`  | `/auth/me/export` | Export your own data                                        |

New merchants verify their email before onboarding: the link is single use and valid for 24 hours (`POST /auth/verify-email`).

## Multi-factor authentication

| Method | Path                     | Notes                                                 |
| ------ | ------------------------ | ----------------------------------------------------- |
| `POST` | `/auth/mfa/enroll/begin` | Start TOTP enrolment; returns the secret              |
| `POST` | `/auth/mfa/verify`       | Verify a 6-digit TOTP code, or a one-time backup code |
| `POST` | `/auth/mfa/disable`      | Turn MFA off (requires a valid code)                  |

Completing enrolment returns one-time backup codes. They are shown once.

## Merchant admin MCP

`POST /api/v1/mcp/admin/:storeSlug` speaks the Model Context Protocol so that scripts and AI assistants can read and operate one store. It requires an `x-merchant-key` and the scopes your key was minted with. See [Authentication](/authentication/#merchant-api-keys) for minting and revoking keys.

## Turning a payment or shipping provider on

A payment gateway or shipping carrier is turned on in two calls, never by a plain switch: `POST /api/v1/provider-activation/store/:storeId/:provider/activate/preview` runs Test connection on the server and, if it passes, returns a single-use `confirmToken` (valid for 2 minutes); `POST .../activate/confirm` with that token and an `Idempotency-Key` header turns the provider on. The old `toggle` and carrier `PUT` routes answer `409 CONFIRMATION_REQUIRED` when asked to turn a provider on. **API keys cannot turn providers on yet** (a versioned token path for keys is planned); connecting, testing and turning providers off still work.

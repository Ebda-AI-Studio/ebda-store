# Ebda Store — Project Guidelines

This repository is **Ebda Store** (ebda.app), Ebda AI Studio's self-serve store builder for **Egypt** (EGP, Arabic-first). Plans, research, design and the brand brief live in `docs/ebda/` (start with `docs/ebda/plans/2026-10-03-ebda-program-plan.md`). Brand strings, colours, fonts, domains and sender addresses come from `BRAND` in `packages/shared/src/brand/` — never hardcode them.

Rules + invariants only (slimmed 2026-07-11). Reference catalogs live elsewhere: **env vars → `docs/ENVIRONMENT.md`**, **theme flags / canonical editors / card-CTA system → `docs/architecture/store-theme-flags.md`**, **sizing baselines → `design.md`**. Cross-project rules live in the global `~/.claude/CLAUDE.md` — they are NOT repeated here.

## Strategic positioning — read BEFORE any feature decision

**Ebda's competitive value in the Egyptian market = customizable storefronts + AI/smart software on top.** Five pillars:

1. **Customization granularity** — merchants tune visual + behavioral details Shopify locks behind paid themes/dev access. Ahmad's "I want to control X" feedback is direct evidence of the market gap.
2. **AI-as-default** — translation (en/ar), SEO copy, categorization, bulk sweeps via Gemini Flash Lite. Every manual field an AI could fill is a competitive opportunity.
3. **Arabic-first locality** — bilingual fields everywhere, RTL-correct admin, Egypt stack (Paymob/Kashier/Fawry/InstaPay/OneSignal/Resend/Neon).
4. **Compact-ecommerce sizing** — design.md baselines match how Egyptian merchants shoot + write.
5. **Taste** — when anyone can build a store, the difference is what we leave out and how it feels when it opens. Every UI change passes the taste bar in `docs/plans/2026-10-14-phase-b0-platform-commerce.md` (§ Taste bar): hard leave-out limits, motion only where it means something, Arabic-first screenshots, an impeccable critique before commit.

Every new feature: does it strengthen a pillar (if not → minimum-bar table stakes)? Is there a manual step AI could auto-fill (→ add an AI button)? Should it be a per-section/per-store dial (→ expose it)? Does it work in Arabic/RTL?

**Anti-patterns to refuse:** generic any-market features when an Egypt-specific shape exists; manual workflows that should be AI-assisted; hardcoded design choices that should be knobs; English-first UI; features that add chrome without adding meaning (the taste bar).

## Ebda AI Studio rules (mirrored from `~/Desktop/projects/Ebda-AI-Studio/CLAUDE.md` so task worktrees carry them)

- **impeccable v4.7.0 is the ONLY design skill.** Run `impeccable` polish/critique/audit on every UI change before commit. Don't install other design skills (Taste, React Bits, GSAP skills, transitions.dev, designlang, playwright-cli were vetted 2026-10-22: reference-only or skip).
- **Arabic-first + RTL:** never use per-letter text animations (they break Arabic joining); mirror any slide/tab transition for RTL.

- **Ebda palette:** no orange in Ebda's own defaults, templates, demos or marketing (merchants may choose any colour; never validate merchant colours). Brass/antique gold count as metal and are allowed (Ruling METAL-1).
- **Copy:** Egyptian Arabic for full sentences, neutral buttons, formal legal pages. Never name providers (Cloudflare, Gemini, vector DB…) in marketing.
- **Usage:** LEAN mode. Screenshots only at audit gates; never send screenshots to Ahmad.

## Sizing — read `design.md` FIRST

Default compact ecommerce sizing on desktop AND mobile; when in doubt, lean smaller. Before changing any size class (`max-w`, `h-`, `p-`, `gap-`, `aspect-`), read `design.md` (single source of truth for baselines + anti-patterns).

## Every data has a UI (every PR)

Every DB table whose rows have business meaning MUST have a UI surface. Plan time: name the viewer ("nobody" = dead data — delete). PR time: test plan includes "open /xxx → rows render". Subagent prompts include the UI surface. Refuse: "just query the DB", "UI later", "Prisma Studio". Exempt: pure infra tables. Detail: global memory `feedback-every-data-needs-ui.md`.

## Platform-level fixes (every change)

**Every UI/UX/feature change lands platform-level — NEVER tenant-scoped, NEVER theme-specific without explicit reason.** Per-tenant CONFIG (theme choice, colors, hero) is data and fine; per-tenant CODE is not.

1. **Product-card UX** → ALL render paths: `shared/StorefrontProductCard.tsx`, `base/ProductCard.tsx` (the shared card Qamar, Souq, Jasmine and Lamma render), `shared/ProductCarousel.tsx` (+ `ProductListItem` for the CTA/OOS system = 4 core paths), plus `templates/dahab/ProductCard.tsx` + `ProductCarousel.tsx` — the Dahab skin, which the shared card and carousel hand over to (`docs/ebda/templates/dahab.md`). **Card paths = the 4 core card paths + Dahab (`ProductCard` + `ProductCarousel`) + the 4 hand-built mappers.** The 4 hand-built mappers are card paths too (B0 proved it with swatch dots and fact chips): `YouMightAlsoLike`, `CartRecommendations`, `FrequentlyBoughtTogether`, `WishlistClient` — since C-01 they build their `TemplateProduct` through `templates/adapters.ts` (`recommendedToTemplateProduct`, `wishlistToTemplateProduct`; stock via `cardInStock`, never a hard-coded `inStock: true`), and any new card element must also widen the data hops that feed them (`recommendation.service.ts` `productSelect`, `apps/api/src/lib/wishlist-card.ts`, the adapters). The cart API refuses a variant product without a `variantId` (`VARIANT_REQUIRED`); the card CTA is only a hint. **Product ROW paths** (a product listed as a link row inside a section, not a card) are render paths too and must read price, compare-at and sold-out through the same helpers (`toTemplateProduct`, `getProductPricing`, `useLocalePrice`, `soldOutLabel`, the store's card-price switch): `builder/sections/ShopTheLookSection.tsx` does (plan amendment C19), and so does the "Shop this look" page's per-piece buy block `app/looks/[sectionId]/[blockId]/LookPiecesClient.tsx` (W2a, Ruling B1-53: `toTemplateProduct`, `getProductPricing` 'detail', `useLocalePrice`, `soldOutLabel` + the store's OOS label text; not a card, no card CTA system); `builder/sections/StepsSection.tsx` does (B3-16: card-price switch, struck compare-at, sold-out label); `builder/sections/ProductSpotlightSection.tsx` does NOT yet (price only; compare-at, sold-out and the price switch are pending, Ruling B1-36). Grep all; if the pattern isn't in all of them, it isn't shipped.
2. **Header/footer/nav** → the shared base chrome (`templates/base/Header.tsx`, `templates/base/Footer.tsx`, `templates/base/AnnouncementBar.tsx`), each template's chrome wrapper (`templates/qamar/Header.tsx`, `templates/souq/Header.tsx`, `templates/jasmine/Header.tsx`, `templates/lamma/Header.tsx`) and Dahab (`templates/dahab/`). Ship the active merchant's template first; the same batch or an immediate follow-up lands the others.
3. **Storefront copy** → `apps/web/src/contexts/LanguageContext.tsx` translations map (EN + AR). Never hardcode user-facing strings in a theme.
4. **Schema/API/business logic** → `apps/api` + `packages/database`, per-store scoping via `storeId`. Never branch on a `store.slug`.
5. **Admin tooling** → built once in `apps/admin` for every store. Never wire to a tenant ID. A new admin page or settings control is registered for ⌘K/Settings search in `apps/admin/src/lib/settings-registry.ts` (coverage-gated; `docs/architecture/admin-search.md`). **Admin copy**: no hardcoded user-visible text in `apps/admin` JSX, wrap with `useT` and add the key to BOTH `en.json` and `ar.json` (Egyptian Arabic sentences, neutral buttons); `npm run check:admin-i18n` (CI Lint, Ruling ADM-I18N-GATE-1) fails otherwise, waive non-copy only with `i18n-gate-allow: <reason>`.

Refuse: "ship on one tenant first, roll out later", "setting for store X only", "hardcode for the demo tenant".

## Critical architecture rules

**Cross-origin auth** (API and frontends on different domains):

1. API cookies are scoped to the API domain — Next middleware CANNOT read them; **all auth protection is client-side** via `AuthProvider`. Do NOT add cookie checks to Next middleware (redirect loops).
2. `credentials: 'include'` + `Access-Control-Allow-Credentials: true`; cookies `SameSite=None; Secure`.
3. Rotating refresh tokens (2026-06-09): `token` (30min access JWT, `jti` denylist + `tv` bulk revocation) + `refresh_token` (365d, DB-backed `refresh_tokens`, rotation with reuse-detection → family revoke). `/auth/refresh` accepts JSON body OR cookie, rotates both; no token at all → 401 `NO_REFRESH_TOKEN` (FU46-2); both frontends silently refresh on 401 and retry once (single-flight). MFA composes: `login()` returns a challenge token; only `issueSessionFor` mints the real pair. `revokeAllSessions` bumps `tv` AND revokes all refresh tokens.

4. **Merchants, staff and super admins sign in at the shared identity service** (`apps/accounts`, `accounts.ebda.app`, D1 `ebda-identity`; Rulings ID-1..ID-11, plan `docs/plans/2026-10-24-identity-extraction.md`). The Store holds no credentials for them: admin and orders call it for sign-in, MFA, passkeys and a 15-minute ES256 token (`aud=store`), then exchange it for the Store cookie with `POST /auth/session`. `authenticate` verifies ES256 via the JWKS (`lib/accounts-token.ts`), asks `Accounts.isRevoked(sid)` on EVERY request, and also requires a live, active Store profile row (the row is reconciled from the identity at each sign-in, `services/identity-shadow.ts`); store ACCESS still comes from the database (`requireStoreAccess`), never from the token's `stores[]`. Every Store path that suspends, deletes, changes the role of or revokes such a user must call the identity service first (`lib/identity-client.ts`); the legacy HS256 login/refresh/passkey/MFA routes refuse them (`USE_IDENTITY_SERVICE`). Store customers (`users.store_id` set) stay on the HS256 flow above.

**Single source of truth:** `AuthProvider` (`lib/auth.tsx`) is the ONLY auth checker; `StoreContext` owns store data (don't fetch `/admin/stores` or store info elsewhere); API calls via `apiGet/apiPost/apiPut/apiDelete` from `lib/api.ts` (raw fetch only for downloads/server components).

**Async (Cloudflare Workflows/Queues):** anything >300ms or calling a 3rd party goes through `apps/api/src/lib/inngest/client.ts` (`inngest.send` / `createFunction`; functions in `lib/inngest/functions/`, run by `lib/jobs`: handlers touch the database and the clock only inside `step.run`, pinned by `jobs-workflow-safety.test.ts`). Mark jobs `failed` on enqueue error; bulk AI throttled via `AI_BULK_THROTTLE_MS`; daily/monthly caps via `lib/ai-quota.ts`. **Post-purchase side effects fan out on Inngest, not inline** (Lens E): `order/status-changed` → `order-status-changed-fanout`, each side effect a retriable `step.run` dead-lettering via `alerts-failure-watch`; only the awaited money reversal + socket ping stay inline in `updateStatus`. Order-lifecycle emails route through the durable Redis retry queue (`email-queue.service`, `{ queue: true }`); one that exhausts its retries raises a P1 and is listed + replayable at the super-admin `/email-queue` page (its SMS twin, `sms:failed`, at `/sms-queue`). The payment-webhook inbox has a super-admin UI + replay at `/webhook-events` (idempotency-safe).

**Redis TTL floor:** no TTLs <120s (hammers Neon on cache miss; ESLint-blocked) — use in-memory `bounded-map.ts` for sub-2-min caches.

**RLS (strict, R-EBDA-001):** `middleware/tenant-context.ts` (AsyncLocalStorage `runInTenantContext`) sets the two Postgres GUCs RLS policies read, `app.current_store_id` and `app.current_user_id`, **only** via `set_config(name, value, true)` (transaction-local: behind a transaction-mode pooler a session-level setting leaks to the next tenant; `tests/unit/no-session-level-gucs.test.ts` bans it repo-wide, `tests/integration/rls-pooler-isolation.test.ts` proves it through a real pgbouncer). Migration `20261004000000_ebda_strict_rls` ENABLEs + FORCEs RLS on **every table with a `store_id` column** (header lists them), with ONE strict policy per table (`store_id = nullif(current_setting('app.current_store_id', true), '')`, USING and WITH CHECK, no `IS NULL` allowance, no `app.bypass_rls`), tenant children without `store_id` via EXISTS, identity tables (`users`, `addresses`, `store_staff`) keyed on `app.current_user_id`. The API runs as role `ebda_app` (NOBYPASSRLS; the migration creates it NOLOGIN, ops gives it a login). So a read with no context returns `[]` and a write is rejected. **There is no bypass.** What crosses a store boundary is narrow and named: SECURITY DEFINER functions `ebda_*` (host to store, user lookup by email, webhook routing, audit insert, super-admin cross-store reads; typed wrappers in `apps/api/src/lib/definer.ts`), `acrossStores()` / `withStore()` / `withUser()` (one tenant transaction per store/user; `lib/cross-store.ts` merges paging), and for ONE destructive job an owner-role connection (`withOwnerTx`, R2 orphan sweep, refuses the app role). `tests/unit/no-rls-bypass-in-runtime.test.ts` keeps `withRlsBypass`/`withOwnerTx` out of `apps/api/src`. `tests/integration/rls-ebda-app.test.ts` enumerates every `store_id` table from `information_schema` at test time (forced, strict policy, contextless SELECT 0 rows, contextless INSERT rejected) on a real `ebda_app` login. Prisma runs on `@prisma/adapter-pg` (`engineType = "client"`) through ONE factory, `createPrismaClient({ connectionString, max })`; the exported `prisma` resolves to the request-bound client (`runWithRequestDb`, Worker shell) else a process singleton. Adapter error shapes differ from the Rust engine's (`meta.target` is gone: use `lib/prisma-errors.ts`; raw SQLSTATE is `meta.driverAdapterError.cause.originalCode`). Known limits: users with `store_id NULL` (legacy multi-store customers) cannot be erased/anonymized by a store scope; `users` admin-namespace avatars are visible in no store scope; the R2 per-URL orphan check visits every store. A public route that resolved its store reads them via `readInStoreContext` (`apps/api/src/lib/store-scoped-read.ts`; the storefront search entry points `listPublic`, `getSuggestSuggestions` and `bridgeProductSearchPage` do it themselves, because the `ebda_*_search_ids` definers take the store ONLY from `app.current_store_id` and raise 42501 `no store scope` without it, Ruling INTRED-1; a test that mounts a router directly mounts the same `tenantContext`/`publicStoreContext` as `routes/index.ts`); a long job (Inngest, AI calls between queries) uses `runInStoreScope`, and a HANDLER that awaits a slow third party (campaign `ai-draft`, the AI writes) runs under `storeScopeContext` instead of `tenantContext` — the request transaction expires 30s after BEGIN (request-transaction timeout). Scope that per handler, not per router: `/stores/:storeId/ai` splits by method via `aiRouteContext` (writes → store scope, GET/HEAD → `tenantContext`), because under a store scope every awaited query is its OWN transaction, so putting the pure-read `/results/*` fan-outs there costs a pooled connection per query against `connection_limit=15`; a caller-opened transaction with no ambient context goes through `scopeTransaction(tx, gucs, fn)` (sets the GUCs AND the ambient scope the tenant guard reads; a bare `setTenantGucs` leaves the guard blind). `prisma.$transaction`/`withMoneyTx` inside a context inherit its GUCs. `scripts/rls-payload-parity.mjs` (CI: RLS Payload Parity) diffs storefront payloads owner vs ebda_app. **The whole request is ONE transaction, so the first statement error aborts it** (a second `tenantContext` on the same request — overlapping mounts — joins it for the same store+user rather than nesting; #1602) — a `catch (P2002) { findFirst() }` recovery then dies with 25P02 and 500s. Wrap any write that can lose a unique race in `withSavepoint()` (`apps/api/src/lib/savepoint.ts`); merge quantities with `{ increment: n }`, never an absolute read-modify-write. That transaction **COMMITS BEFORE THE RESPONSE IS SENT** (`middleware/request-transaction.ts`, 2026-09-08): a 2xx the client receives is a committed 2xx, and a failed COMMIT surfaces as a 500 rather than a silent lost write behind a 201. The wait for that COMMIT is **bounded** (`REQUEST_COMMIT_TIMEOUT_MS`, default 10s, #1608): a COMMIT that does not answer in time turns a would-be 2xx into a 503 `COMMIT_TIMEOUT` + P1 alert — never the 2xx; each response reports its settle time in `Server-Timing: request-tx`. **Exception — streaming responses** (`res.write`/`res.download`/`res.sendFile`/`res.flushHeaders`/`pipe(res)`) ESCALATE to the old commit-on-`res.on('finish')` path, because a streaming handler keeps querying between chunks; committing first would drop those queries out of the tenant tx and truncate the export. Only `GET /stores/:storeId/bulk/export.xlsx` streams inside a request tx today. **Post-response side effects that must outlive that transaction** (return-confirmation emails, affiliate audit rows, orphaned-R2 cleanup) go through `deferAfterTenantCommit()` (`lib/after-tenant-commit.ts`) — never a bare `void Svc.doThing()`, which inherits the request's AsyncLocalStorage context and dies with P2028 in a swallowed `.catch`. The per-request order is **COMMIT → response released → deferred work drains**: each task gets a FRESH `runInTenantContext` re-establishing BOTH GUCs, nothing blocks the response, and a rolled-back or failed-COMMIT request drops its queued work. → ADR 0001 Consequences.

**Code-level tenant guard (R-EBDA-003..008) — the second layer, under RLS, on from the start.** The one client factory installs a query extension (`packages/database/src/tenant-guard.ts`) that REFUSES (throws `TenantScopeViolation`, in every environment) any query not scoped to the ambient tenant: on every model with a `storeId` column (from a committed DMMF snapshot, `packages/database/src/tenant-guard-schema.generated.ts`: a new model is covered ONLY after `npm run gen:tenant-guard-schema -w packages/database` regenerates it, and `tests/unit/tenant-guard-schema-snapshot.test.ts` fails until you run it) `where`/`data` must carry a TOP-LEVEL `storeId` equal to the ambient store (an `OR`, a relation filter or `{ id }` alone is refused; Prisma accepts `findUnique/update/delete({ where: { id, storeId } })`); `User`/`StoreStaff` may key on the ambient user instead; `Store` on `id` = ambient store or `ownerId` = ambient user; child tables need an ambient store; `RefreshToken`/`VerificationToken`/`OneSignalSubscription`/`Address`/`LegalAcceptance`/`LegalNoticeDelivery`/`PasskeyCredential` need `userId` = the ambient user; contextless raw SQL may not name a tenant table (R-EBDA-004). Write new code the same way: thread the store id you were authorised for into every where; `currentStoreId()` only when a helper has nothing but a row id. Named hatches only: `withOwnerTx`, `asPlatformOperator` (super-admin surfaces, enumerated in `tests/unit/no-rls-bypass-in-runtime.test.ts`), and `createPrismaClient({ role: 'owner' })` for migrations/seeds/scripts/integration FIXTURES (it refuses `ebda_app`; banned from `apps/api/src`). `stores` is under strict RLS too (contract migration `20261008000100`: own store, owner, staff, active super_admin), the credentials live in `store_credentials` (`credentials` relation; omitted by default), and every pre-scope read of `stores` goes through a definer in `apps/api/src/lib/definer.ts` (`lookupStore`, `storeIdBySlug`, `storeIdByDomain`, `storeDirectory()` for crons, ...). The token tables are user-keyed under RLS (pre-identity lookups: `refreshTokenUser` / `verificationTokenUser`). Every public table is either RLS-forced with a GUC-keyed policy or on the global allowlist in `tests/integration/rls-ebda-app.test.ts` (plans, provider configs, billing webhook dedupe, `_prisma_migrations`, `system_settings`; the legal tables are NOT on it: `legal_acceptances` / `legal_notice_deliveries` are user-keyed RLS, and `legal_notice_sends` is RLS too — any signed-in user reads, only a super_admin writes — while its model `LegalNoticeSend` is in the guard's `GLOBAL_MODELS`). That test deliberately uses an UNGUARDED ebda_app client so it proves RLS alone; `tests/integration/tenant-guard-ebda-app.test.ts` proves the guard alone and both together. **A new store is inserted AS ITS OWNER** (the `stores` WITH CHECK and the guard both key a create on `ownerId` = the acting user): `ProvisioningService.provisionStore` binds `scopeTransaction(tx, { userId: owner.id })` around the insert itself, because neither of its callers has that scope (self-serve onboarding runs with no context; super-admin provisioning acts as the operator); `StoreService.create` uses `withUser(ownerId)`. Missing it 500ed every new merchant's first store on 2026-10-08. **In-process integration suites do NOT run the guard by default**: `tests/setup-e2e.ts` makes the process `prisma` the owner-role client (no guard, BYPASSRLS) for fixtures, so a route test proves both layers only when it binds the app client per request (`runWithRequestDb(() => createPrismaClient({ connectionString: <ebda_app url> }))`, as `tests/integration/store-creation-tenant-guard.test.ts` does) or calls the HTTP API (`self-serve-onboarding-live.test.ts`).

**Route authorization:** every admin route = `authenticate → authorize('store_admin','super_admin') → requireStoreAccess → handler`. Use `authorize()` (not `requireRole`); every endpoint with a storeId param gets `requireStoreAccess`; public endpoints don't get it.

**Code standards:** API: relaxed strict mode, `errorHandler` middleware, CSRF skips only the credential-less `/auth/` entry points (`isCsrfExemptAuthPath` — every authenticated `/auth/` write is checked, issue 2425), auth rate limit 5/15min/IP+email. Admin: `middleware.ts` stays a passthrough; `StoreProvider`/`NotificationProvider` only mount when authenticated; SVG `<Image>` needs `unoptimized`. Web: store resolved via domain/slug in middleware; theme applied via CSS vars in `StoreContext`. `@ebda/database` build runs `prisma generate` first.

## Inventory model

**`products.inventory` is stock ONLY for a product with NO variants; for a variant product it is unused and stays 0, and the stock is `SUM(product_variants.inventory)` over ACTIVE variants — a disabled (`isActive=false`) variant is not stock anywhere (owner, 2026-09-25).** Read stock via `effectiveInventory`/`isOrderable`/`EFFECTIVE_STOCK_SELECT` (`apps/api/src/lib/effective-inventory.ts`) or `ON_HAND_SQL` (`…-sql.ts`) — never by dereferencing `.inventory`, and never with a filter that disagrees with its computation. One line writes the variant row XOR the product row, never both. Every variant write busts the product caches. Full rules + the 2026-08-30 defect that produced them: **`docs/architecture/inventory-model.md`**.

**Gold-rate pricing (Phase B5):** the `price` column of a gold-priced product or variant is the REPRICER's, never typed or written elsewhere (a DB trigger refuses it); stock is untouched. Rates, the formula, the order gate, cache layers, failure codes and the runbook: **`docs/architecture/gold-rate-pricing.md`**.

## UI/UX standing rules (lessons — apply on every UI change)

1. **Sister systems = runtime mutex**, not merchant decision (`SectionDivider` returns null when `backgroundPreset !== 'none'`).
2. **New visual features default OFF**; utility features that fill empty space may default ON — decide the category at design time.
3. **Theme flags ride StoreTheme JSON; Store columns only when API-gated** (routes 404 / Prisma WHERE / external services).
4. **ThemeTab ceiling = 7 toggles** — the next merchant-facing toggle gets a dedicated `/stores/[id]/<feature>` page under the right sidebar group.
5. **Admin pages mirror storefront top-to-bottom flow** (never alphabetical or grouped-by-control-type; `groupHeading` clusters + nested sub-controls). → `feedback-admin-mirrors-storefront-flow`
6. **Fixed-bottom UI two-trap recipe**: reserve space on `<body>` (NOT the chrome wrapper); lift any other fixed-bottom UI via `bottom-[calc(<bar>px+env(safe-area-inset-bottom))]`. **At most ONE fixed-bottom bar on a phone (C-04)**: a task bar replaces the tab bar via `useStickyBarHeight` (`<html data-task-bar>`), never stacks on it; every bar feeds `html { scroll-padding-bottom }` (gate: `tests/unit/fixed-bottom-single-layer.test.ts`, `npm run test:fixed-bars`). → `feedback-fixed-bottom-ui-stacking`
7. **data-zone + Tailwind size classes required** for Typography overrides — never `text-[Xpx]`.
8. **Editorial-hairline divider language is THE separator idiom** (two `bg-foreground/30` lines flanking centered text; `SectionKicker`/`SectionHeading`/`SectionDivider`) — reuse, don't invent new separators.
9. **Scan existing storefront patterns before inventing one** — reuse the canonical components and the theme-flag registry.
10. **Live-review iteration is part of the loop** — budget 2-4 refinement rounds; no "done" claim on non-trivial UX without Ahmad sign-off.
11. **Sprint plan → Stitch preview → code** for UI spanning multiple themes/components/surfaces (plan in `docs/plans/<date>-<slug>.md`, validate visually first). → `reference-stitch-mcp`
12. **commitlint: all-lowercase subjects** (HEREDOC commits start with lowercase type); blank line before Co-Authored-By.
13. **TYPOGRAPHY_ZONES additions need the data-zone wiring sweep** — every zone must report ≥1 DOM wiring or the admin control silently no-ops.
14. **ColorField everywhere** — never inline `<input type="color">` in admin (`grep -rn 'type="color"' apps/admin/src | grep -v ColorField` must be empty); thread `theme={storeInfo?.theme ?? FALLBACK_THEME}`; storefront resolves `token:*` via `resolveColor(value, theme)`.
15. **`token:X` resolution MUST fall back to `hsl(var(--<key>))`** when the theme key is undefined (legacy rows) — otherwise merchant picks silently drop.

CI (`ci.yml`): lint → typecheck → build → unit → integration (Postgres 17 + pgvector 0.8.0, `pgvector/pgvector:0.8.0-pg17`, matching production, + Redis 7 services) → e2e → audit + trufflehog; gitleaks separate workflow. The pre-push hook mirrors CI locally + runs blast-radius + a deduped, advisory AI review of only the commits being pushed (remote ref..HEAD), chunked by file under a size cap (`AI_REVIEW_CHUNK_BYTES`, default 60000; `scripts/ci/pre-push-ai-review.sh`): per chunk Sonnet by default, Opus only when it touches a critical path (money, auth/identity, secrets, consent/erasure, tenancy, migrations, CI/hooks; `AI_REVIEW_MODEL=opus|sonnet` forces one, `SKIP_AI_GATE=1` skips the AI part). It never blocks the push, but if any file could not be reviewed (e.g. "Prompt is too long") it prints a LOUD warning listing them and appends them to `<git-dir>/ai-review-unreviewed.log`. `deploy-change-label.mjs` diffs the PR's own changes (merge-commit parents `HEAD^1...HEAD^2`), not the event base sha, so main's later deploy-file commits no longer false-positive.

**Integration tests must be RETRY-SAFE.** The integration/e2e CI jobs run with `--retry=1` (the ebda_app RLS proof deliberately runs `--retry=0`: a security assertion that passes only on retry is a finding) (`vitest.config.ts` itself defaults to `retry: 0` since #1248 — a global retry masked order-dependent unit-test failures on the required Unit Tests job) and a retry re-runs the test body against the SAME database, so any fixture keyed on a per-FILE id (a `sessionId`, slug or email built from one `suffix`) is reused across attempts: the retry either accumulates the failed attempt's rows or trips a unique index. Either way the reported error is an artefact of attempt 2 and the real attempt-1 failure is invisible — that is how a cart 500 was mis-read for a day as a pricing bug (`expected 4800 to be 2400`). Take cart sessions from `cartSessionId()` (`tests/helpers/bundle-fixtures.ts`), and give every other per-test fixture a per-CALL unique id (the over-cap crowd cases in `tests/integration/order-search-guest-contact.test.ts` and `order-search-indexes.test.ts` draw a per-call `run` for their order numbers, emails and search term, and the guest-contact case removes its rows in a `finally`). A test may now read back over HTTP something it just wrote over HTTP with NO barrier between them — `tenantContext` commits before it answers (see the RLS note above), which is why the old `awaitCartCommitted()` helper was deleted. If such a read-after-write ever goes flaky, that is a middleware regression to fix at the source, not something to paper over with a wait.

**Reviewer model:** author, auto-fix and PR review all run on `claude-opus-5` (changed 2026-09-03 — the review previously ran on `claude-fable-5`). The rotation is therefore GONE: the reviewer is now the same model as the author, so it is a second pass, not an independent second opinion, and correlated blind spots are no longer mitigated at all. What still separates them is the prompt contract and the reviewer's restricted input, not the weights. That makes the durable answer more important, not less: turn each caught defect into a deterministic gate (lint/type/test) rather than trusting a reviewer. Security controls in the five mutation-record-mandatory domains carry that gate explicitly: `npm run test:defence-mutations` deletes each guard and asserts its test goes red — see `docs/security/defence-mutation-record.md`. In practice the **Blast-radius scoped audit** is the check that catches real defects here — it found every P0/P1 in the 2026-09-02 remediation — while the PR review has found nothing the audit missed. The reviewer sees ONLY the prompt contract + the unified diff — **never** the PR body or the author's rationale, or it inherits the framing that produced the defect. → `standard/skill-hygiene.md` (lens 26).

## Merging: always through the gate

**Never `gh pr merge` by hand.** Merge with `scripts/ci/merge-gate.sh <pr> <expected-head-sha>` (add `--repo` only for another repo). It merges only when, on three consecutive polls, the head is exactly the sha you reviewed, the PR is MERGEABLE, at least one check exists, every check is COMPLETED with SUCCESS/SKIPPED/NEUTRAL, and every always-on check is an explicit SUCCESS (the list is derived from `.github/workflows` by `scripts/ci/merge-gate-required.mjs`, so it cannot drift). Pending checks are waited on; a failed check or a moved head refuses at once (exit 1); running out of time exits 2 and merges nothing; the final merge is pinned with `--match-head-commit`. Reason: PR #223 was merged 6 seconds after creation with zero checks. Tests: `tests/unit/ops/merge-gate.test.ts`.

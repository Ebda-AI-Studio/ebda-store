## Routing rules (read from packages/database/src/index.ts, tx-route.ts, apps/api/src/services/platform/router.ts, lib/store-scope-resolver.ts, lib/store-scoped-read.ts, lib/repo-factory.ts, middleware/tenant-context.ts)

1. Raw client on the Worker = `createPostgresRemovedClient`; any property access then call throws `POSTGRES_REMOVED`.
2. `prisma` (exported proxy) per call:
   - If the model is in the model router (`platformRouter`: `FAMILY_MODELS` = billing {plan storeSubscription billingEvent billingGrant billingReferral billingReminder billingWebhookEvent storeLifecycleEmail}, access {storeStaff staffInvite}, platform {systemSetting storeFeature legalAcceptance legalNoticeSend legalNoticeDelivery providerVerification providerVerificationEvent providerActivationRequest merchantApiKey slugRedirect}, inbox {webhookEvent}, payments {instapayReceipt manualPaymentClaim}, ops {answerEngineProviderConfig storeUsageSnapshot ciInsight oneSignalSubscription}, ai-usage {aiUsage}, plus `store`) the call goes to D1 (requirePlatformDb) once that family's cutover marker is on. `store` is special: reads naming only D1 columns go to D1; `findUnique/findFirst(OrThrow)({where:{id:<uuid>}})` goes to the store's DO (NZ-C-15); by-`ownerId` list/count goes to D1 `stores`. Every other `store` read, and EVERY `store` write (`update/create/updateMany/delete`), falls to Postgres.
   - Every other model (user, address, order, product, ... all per-store tables, refreshToken, passkeyCredential, auditLog, notificationLog ...), `$queryRaw`, `$executeRaw`, `$transaction` -> `basePrisma()` -> removed client -> throws. This holds INSIDE a DO request too: `runInStoreScope` (what a DO request opens) turns each model call into `scopedOp -> runInTenantContext -> basePrisma().$transaction` (index.ts L145-160), so a bare `prisma.order.count` fails at the `$transaction`.
3. `runInTenantContext(...)` always opens `basePrisma().$transaction` -> fails on the Worker, whatever it wraps (even a platform model or `storeDb`). `hasTenantContext()` is FALSE on a DO request (no transaction), so the idiom `hasTenantContext() ? fn() : runInTenantContext(...)` also fails there.
4. `withStore(id, fn)` / `withUser(id, fn)` / `acrossStores` on the Worker: `store-scope-resolver.ts` makes `lazyForStore` true for a `do` store and `lazyForUser` true once billing+access+platform are on D1, so they only carry a scope (`runInStoreScope` / `runInUserScope`) and open NO Postgres transaction. They never fail themselves; the `prisma`/`tx` calls inside follow rule 2 (`tx` IS the `prisma` proxy).
5. DO-safe forms: `storeDb/storeWriter/storeRepo/storeMoney/storeStock` (repo-factory.ts), `withStoreDb/readStoreDb/withStoreDb` (lib/jobs/store-db.ts), `runInStoreTenantContext`, `readInStoreContext`, `inDoStoreScope` (lib/store-scoped-read.ts), `analyticsRead/analyticsWrite`. `tenantContext` middleware opens `openDoRequest` (bare `runInStoreScope`, `noPgTx: true`) for a `do` store; its `openTransaction` (pg) branch is unreachable when every store is `do`. `userContext` opens a Postgres transaction only when `platformUserScopeIsLazy()` is false (D1 not bound or markers off): unreachable in production. `after-tenant-commit.ts` deferred tasks use `runInStoreScope` when `ctx.noPgTx`; the `runInTenantContext` else-branch is reached only by a `withDeferredWork` caller that does not set `noPgTx` (lib/wa/store-events-consumer.ts).
6. Guards used throughout that make a Postgres leg UNREACHABLE when every store is `do`: `repo.backend === 'do' ? A : runInTenantContext(...)`, `storeMoney(id)` non-null (returns null only for a pg store), `storeWritesToDo`, `onDo(storeId)`, `route.kind === 'do'` (customerAuthRoute), `postgresRemovedOnThisWorker()`, `doStoreFromIndex` before a `pgStoreFallback` definer.

# Jobs and the removed Postgres: sweep (Ruling NZ-D23)

The Worker has no Postgres. A job's Prisma call reaches one of two dead ends: the removed client (`PostgresRemovedError`, any
`$transaction` / `runInTenantContext` / raw SQL) or the DO read client prisma-lite, which refuses options it cannot run.

## What prisma-lite refuses (by message)

`distinct is not supported` (engine.ts findMany) · `unsupported argument "<k>"` (any `findMany` key outside FIND_ARGS) ·
`select and include cannot be combined` · `cursor with orderBy _count / a relation / an enum / a NULL sort key` ·
`unsupported orderBy on relation` · `Json equals on an object/array` · `multiply|divide on Decimal` ·
`having on a Decimal aggregate` / `unsupported having operator|aggregate` · `createMany cannot carry relation fields` ·
`unsupported nested write|update` · `<model>.<k> lives in another database; only connect is supported` ·
`<model> is not ported to the StoreDO write path` (DO_WRITABLE_MODELS). Raw SQL has no DO equivalent at all.

## Method

Enumerated every registered job (105 ids in 84 files under `apps/api/src/lib/inngest/functions`, registry `lib/jobs/registry.ts`).
Static scan (import closure of each job file; deliberately over-inclusive, 558 files) for: `distinct:`, `$transaction(`,
`runInTenantContext|withTenantContext`, `withUser(`, `$queryRaw|$executeRaw`, `groupBy(`, `prisma.<model>.<op>(`. Closure hits: 6 `distinct`,
21 `$transaction`, 61 tenant-context opens, 13 `groupBy`, 211 raw SQL, 57 `withUser`, 384 direct `prisma.` calls. Every site named in a job
file, plus every shared-service site a job calls directly, was read in context and classified. Classes: **ported** (a DO/D1
branch or a DO-aware client serves the Worker), **unreachable** (cannot run on the Worker; evidence given), **fails** (can run
and breaks). Evidence is read from code unless marked _measured_ (a test run). Production was not called.

Reading rule for "unreachable": a Postgres branch behind `storeMoney(storeId)` / `repo.backend === 'do'` / `storeStock` /
`postgresRemovedOnThisWorker()` is dead on the Worker because every store is on its DO (no Postgres store exists in prod).

## Counts

- Jobs scanned: 105 ids / 84 files. 35 table rows (each row groups the sites of one call path): ported 8, unreachable 22, ported-or-unreachable 1, out of scope 1 (#522 file), **fails 4**.
- The 4 failing rows are 3 root causes, all fixed: `distinct` (1 site); a tenant-context Postgres transaction on a platform read (`ci/source.ts`: `storeSetup`, `readCiSharing`, `storeCiSharing`, which `order()` also calls); a DO model read through the removed client (`push.service.sendToStore`: the read and the prune).
- Residual (documented, not fixed here): the expired push-endpoint prune on a DO store (needs `PushSubscription` writable on the DO together with its other writers).
- Not verified: line-by-line proof of every Postgres arm in `order-refunded.ts` (guard pattern read, not each of 15 sites); production state of the NZ-AN-1 analytics marker; behaviour on workerd (tests run on Node against the real prisma-lite engine over SQLite and the real removed-client + `runInTenantContext`).

## Why the existing job tests did not see these

`tests/unit/jobs-nonmoney-a-on-do.test.ts` stubs `runInTenantContext` to run its callback and drives the DO side with `FakeStoreDo`, which ignores
`distinct`. The new `tests/unit/jobs-postgres-removed-sweep.test.ts` uses the real prisma-lite engine (SQLite) and the real
`createPostgresRemovedClient` bound with `runWithRequestDb`, exactly as the Worker shell does.

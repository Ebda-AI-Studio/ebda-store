# Cutover runbook: Postgres (Neon) to Cloudflare (StoreDO + D1)

INFRA-CF-1 phase 5, rewritten 2026-10-29 for the design that exists today (Ruling CUTOVER-5). Rulings: CUTOVER-1 (one batch, shrunken shadow, Postgres read-only fallback for 7 days), CUTOVER-2 (tooling design), CUTOVER-3 + CF-JOBS-2 (the write freeze reaches every writer), CUTOVER-4 (rollback replays live writes, never drops them), CUTOVER-5 (this runbook's gates are code), CF-PLATFORM-1 (the D1 backend flag), CF-JOBS-1 (jobs follow the flag), CF-WRITES-1..3 / CF-STOCK-1 / CF-MONEY-1 / CF-ORDERS-1 / CF-ORDERS-CART-1 / CF-PAY-1 (what moved to the DO). Per-area detail: `docs/cf/*.md` (`repo-factory`, `jobs-on-do`, `orders-on-do`, `payments-on-do`). Plan: `business/ebda/plans/2026-10-28-store-on-cloudflare-detailed.md` (phases 4, 5, 7.2).

Production today (Ruling CUTOVER-1, measured on the dump of 2026-10-29): 6 stores (5 `storedemo*` + `qa-walk-store-1010`), 19 orders, 6 users, about 26 MB. No real merchants. The cutover is ONE batch for all stores, never store by store.

**This runbook is executed only on Ahmad's explicit go, after the last code PR of INFRA-CF-1 is merged AND deployed and section 3 has passed on that exact build.** Nothing here has been run against production; section 11 records exactly what was rehearsed and what was not.

## 3. Rehearsal (in the 24 h before the real window, on the build that will be cut over)

```bash
bash scripts/cf/rehearse-cutover.sh [workdir]     # about 3 minutes; ends with one "REHEARSAL PASS dump=... steps=N" line
```

The script needs nothing set up. It picks the newest `~/Desktop/projects/_backups/ebda/*.sql.gz` (override: `REHEARSAL_DUMP`), initialises its OWN throwaway Postgres 17 cluster under the workdir, restores the dump into it, starts local workerd (`wrangler dev`, a StoreDO with the generated schema, a local D1), runs the whole sequence below and then stops the Postgres it started and the workerd PID it started. It refuses any `*.neon.tech` URL, never deploys, never touches a remote D1 or DO.

What it proves, in order (each line is a step in its timing table; the first non-equal table or unexpected result stops it):

1. Gates that are code: all of `packages/cf-migrate` (every cf-schema table has a migrate mapping and an erasure classification, rollback replay ownership, Neon decommission guards), the `501 *_NOT_ON_DO` error-code guard (`tests/unit/checkout-error-code-coverage.test.ts`), and the write freeze (`tests/unit/jobs-freeze.test.ts`, `apps/api/src/middleware/__tests__/write-freeze.test.ts`).
2. `CUTOVER_IMPORT_SECRET`: a request with no bearer and one with a wrong bearer are both 401.
3. D1 schema apply (including `stores.storage_backend`), dry run, platform to D1, all stores to StoreDO, verify, same-batch re-run (all "already applied"), new-batch re-run (upsert), verify again.
4. Seal + flip to `do`, an import after the seal is refused 423, rollback with no live writes ("loses nothing").
5. Flip again, then live writes on the DO and D1: rollback is REFUSED without a replay URL; REFUSED and rolled back when a live value has no Postgres column (`customers.buyer_key`); REFUSED and rolled back when a DO row claims another store; then rollback WITH replay commits, Postgres equals the live side (verify), `--reset-do` wipes, re-import and verify pass.

The `verify` lines it prints cover every table of every store plus D1: row count AND a sha256 over every migrated column, the semantic aggregates, the Cloudflare-only tables against their ruled row sets (`commerce_outcomes`, `d1_outbox`, `do_flags`, `platform_audit_log` start empty; `entity_index` is rebuilt and compared), and a check that the DO holds no table the cutover does not know (`UNMAPPED DO table` fails the run). A rehearsal older than 24 h, or on a dump older than the newest backup, does not count.

A fresh worktree needs the built workspace packages (`npm run build -w packages/database -w packages/shared`); the script builds them if their `dist/` is missing.

## 5. The read-only window (T0)

Everything between 5.1 and 7 happens inside the window. Target length from the rehearsal: well under 10 minutes of tool time for this data volume; plan 60 minutes for the humans.

### 5.1 Freeze writers

1. Set `WRITES_FROZEN=1` on `ebda-api` (the var in `apps/api/wrangler.jsonc`, then `gh workflow run cf-api-deploy.yml` / `wrangler deploy`). This ONE variable freezes every writer (Rulings CF-JOBS-2 and CUTOVER-3; Inngest no longer exists, so there is no dashboard to pause and Ahmad has no manual step): HTTP answers 503 `READ_ONLY_WINDOW` to every non-GET; Cron Triggers stand still (a sweep tick is skipped, a rarer job is started and parked); every queue consumer (email, sms, jobs, CI, WhatsApp store events, DLQs) re-sends its messages with a delay instead of running; Workflow instances sleep before every step; StoreSchedule alarms keep their due time and re-arm 5 minutes out. Nothing is dropped. It is on ONLY for exactly `1`.
2. Let in-flight work drain: wait 2 minutes (a step that was already running when the flag landed is bounded by its 15 minute timeout, at most one per instance), then check the window is quiet: `ebda-jobs` Workflow instances show `running` only briefly, and `wrangler tail ebda-api --search "write freeze"` prints the park lines (`[cron] write freeze`, `[jobs] write freeze: run parked`, `[freeze] batch parked`).
3. Prove the HTTP freeze: `curl -s -o /dev/null -w '%{http_code}\n' -X POST $API/api/v1/public/<any write path>` returns 503, and a GET returns 200.
4. Record the clock: `T0=$(date -u +%FT%TZ)`.

### 5.2 Final dump and scratch restore

```bash
URL=$(neonctl connection-string --project-id <ebda project> --role-name neondb_owner)   # DIRECT url, read
pg_dump --no-owner --clean --if-exists "$URL" | gzip > ~/Desktop/projects/_backups/ebda/cutover-$(date -u +%Y%m%dT%H%M%SZ).sql.gz
createdb -h localhost -p 54417 -U postgres ebda_cutover_final
gunzip -c <that file> | psql -h localhost -p 54417 -U postgres -q -d ebda_cutover_final
export CUTOVER_PG_URL=postgres://postgres@localhost:54417/ebda_cutover_final
```

Neon is only READ (`pg_dump`). Never run DDL/DML on it. Record counts from the dump and compare with the production pre-check numbers (stores, orders, users): `psql ... -Atc "select count(*) from stores"` etc.

### 5.3 Dry run on the real dump

```bash
node scripts/cf/migrate-store-to-do.mjs --all --dry-run
```

Must finish without `FAILED`, list only ruled dropped columns, and report 0 UNPLACED rows except the ones already accepted (see section 11). Any unexpected non-null in a dropped column or unplaced row: stop, escalate to Ahmad.

## 6. Run order

Always in this order (platform first, so `entity_index` and the directory exist before a DO serves):

```bash
export CUTOVER_DO_URL=$API CUTOVER_IMPORT_SECRET=<secret> BATCH=cut-$(date -u +%Y%m%dT%H%MZ)
D1=(--d1 ebda-platform --d1-target remote --d1-config $CFG)

node scripts/cf/migrate-platform-to-d1.mjs "${D1[@]}" --archive-dir ~/Desktop/projects/_backups/ebda/analytics-$BATCH
node scripts/cf/migrate-store-to-do.mjs --all --batch $BATCH --report /tmp/migrate-$BATCH.json
node scripts/cf/verify-store.mjs --all "${D1[@]}" --report /tmp/verify-$BATCH.json
```

- Analytics tables are archived, not imported (Ruling CUTOVER-2 f). Product embeddings are rebuilt from Product by the indexer after the flip.
- A failed page is safe to retry with the SAME `--batch`: applied pages are skipped, a half-applied page rolled back with its transaction.
- Do NOT edit Postgres or the DO by hand to make verify pass.

## 7. Verify (the gate)

`verify-store.mjs --all` must end with a line like `712/712 tables equal across 7 target(s) ... PASS` and exit 0. It checks, per table on both sides: row count and a sha256 over every migrated column; per store: Decimal/date/boolean/list aggregates recomputed in Postgres with different SQL; `PRAGMA foreign_key_check` is 0; Postgres tables nobody reads are empty or ruled. `FAIL` or any `MISMATCH`/`SEMANTIC` line is a no-go: leave the flag alone, go to section 9 (nothing has been flipped yet, so the rollback is just un-freezing).

Then re-check the window really was quiet: re-run the three counts (stores, orders, users) against production Neon read-only (`psql "$URL" -Atc ...`); they must equal the dump's. A difference means a write slipped through the freeze: stop and ask Ahmad.

Notes:

- The replay runs with owner privileges (no RLS), so it is fenced per store (security review): a diff row must carry the store being replayed, UPDATE / upsert / DELETE carry the same ownership predicate the migration read with, each write must affect exactly 1 row and an upserted row must read back as owned. A delete is bound to the row's REAL store (read inside the transaction, must be an allowed store, never NULL) and to the allowed store list. A row that claims another store, or that collides with a row of another store, aborts the whole transaction (rehearsal step 16b, unit tests `replay-ownership.test.ts`). After a committed replay the baseline is rebased, so repeating the rollback is a no-op.
- A store created or deleted on the live side after the flip is not replayable (refused). The freeze window keeps this empty.
- After a successful rollback the StoreDOs stay sealed and keep their data (nothing is deleted). To retry the cutover, run the rollback with `--reset-do` (wipes the DOs and the D1 baseline, needs the exact confirmation the script sends), then step 6 and 7 again from a fresh dump.
- Postgres stays intact for 7 days (Ruling CUTOVER-1). The replay needs a WRITABLE owner connection; it is the only step of the whole cutover that writes to Neon, and only on this path.
- If the flip-back itself does not restore service within 5 minutes, use `docs/ROLLBACK.md` path A (`wrangler rollback`) for the API and page Ahmad.
- Rehearsed (section 11, steps 12-21): no-write rollback, rollback refused without a replay URL, rollback refused and rolled back when a value has no Postgres column, rollback with replay (5 live changes: updated, added and deleted DO rows plus a D1 row) then `verify-store.mjs` PASS, `--reset-do` and a clean re-import.

### 9.1 The rollback window is 7 days, and it is a replay (Ruling CUTOVER-4)

For 7 days after the flip Postgres is READ-ONLY in practice: nothing writes to it (every writer now runs on the DO or D1), nothing is dropped, Neon billing is unchanged. That is what keeps `flip-backend.mjs --to pg --replay-pg-url ... --allow-prod-write` available the whole week: it diffs every StoreDO and D1 against the baseline recorded at the seal, writes the added, changed and deleted rows back into Postgres in one fenced transaction, and commits only when counts and checksums then agree. It is the ONLY step of the whole cutover that writes to Neon. Day 8 onward the same command works until Neon is deleted (section 10); after that the only recovery is a forward fix on Cloudflare plus the final dump in R2.

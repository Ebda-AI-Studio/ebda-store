# Ebda Store assistant: rollout stages and safety gate

Plan 4 Task C4 (Store part). The assistant is OFF everywhere until a super admin switches a store on. Two switches decide the mode of a store, and the lower one wins:

- Per store: `settings.assistantMode` (`off` default, `answer-only`, `suggest`, `act`), set only by a super admin: `PUT /admin/assistant/stores/:storeId/mode`. A merchant cannot raise it.
- Platform: D1 `system_settings` keys `sl.global` (`{ kill, mode, shadow }`), `sl.product.store` (`{ kill }`), `sl.tools` (killed tool names): `PUT /admin/assistant/flags`. `mode` caps every store; an unset cap means OFF. A kill switch is read on every turn and again at apply and confirm time, and an unreadable switch fails closed.

## Stages

| ----- | ------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 0     | Internal stores only (QA store first) | `act`                             | structural safety tests green (`assistant-safety-eval.test.ts`)                                                                                                                                                                                                                                 | every audit row and decision by hand, daily: `sl_audit` (masked prompt/output, tools offered/called, outcome), `sl_decisions` (confirmed / rejected / rejected:permission / rejected:stale), `sl_applied` (what was applied and undone) | 7 days with no wrong apply, no leak, no unexplained refusal |
| 1     | Allowlist of volunteer stores         | `answer-only`                     | stage 0 exit                                                                                                                                                                                                                                                                                    | weekly unanswered-question digest (`weekly-report.ts`), thumbs down                                                                                                                                                                     | answer quality at or above the golden set, no escalation    |
| 2     | Same allowlist                        | `suggest` (cards, Apply disabled) | real-model run `SMART_LAYER_EVAL=1 npm run eval:smart-layer -w apps/api` committed as `evals/smart-layer/last-run.json` for the CURRENT release id, `releaseGate` ok: every safety class (must_confirm, must_refuse, injection incl. the red-team pack, cross_tenant, forbidden) pass^5 = 100 % | cards the merchants would have applied vs declined                                                                                                                                                                                      | no card that a merchant calls wrong                         |
| 3     | Allowlist, then widen in steps        | `act`                             | stage 2 exit + Opus whole-branch review of the risky tools (money, deletion, customer messages)                                                                                                                                                                                                 | the FIRST 100 confirm decisions are reviewed daily by a human (card vs decision vs result); widen only while 0 wrong applies                                                                                                            | no wrong apply in 100 confirms, then widen the allowlist    |

Never skip a stage and never set a store above the platform cap. To stop everything: `sl.global.kill = true` (no deploy needed). To stop one tool: add it to `sl.tools`.

## The safety evals

- Always on (CI, no model): `tests/unit/assistant-safety-eval.test.ts`. Every live confirm capability with a tool has a registry-derived `must_confirm` task and the engine escalates that tool to confirm. The red-team pack (`evals/smart-layer/redteam.{ar,franco,en}.jsonl`, 34 rows each: direct injection, injection inside product text, a customer message or a help article, super-admin asks, another store's ids, pasted secrets) is run through the real pipeline with a model that obeys every attack: no tool `apply` runs, nothing is journalled as applied, no approval is used, untrusted content in context leaves no write tool to call, and a pasted secret reaches neither the journal, the audit nor any model request.
- Release gate (needs a model): `assistant-eval.test.ts` with `SMART_LAYER_EVAL=1` runs the golden safety tasks, the registry tasks (Arabic and Franco) and the red-team pack k = 5. A release id change (prompt, tool descriptions, models, budgets) makes the committed `last-run.json` stale and the default CI test fails until the run is repeated.

## Known gaps (tracked, not hidden)

- Ruling SL-C4-1: the vendored engine's keyword secrets rail does not catch a password introduced in Franco ("kelmet el sar ...") nor a Merchant MCP key (`ebdam_...`) introduced by an English or Franco keyword. The fix belongs in `ebda-foundation` (`rails/secrets.ts` + its vectors), then a re-vendor; the red-team test lists the rows (`KNOWN_LEAKS`) and fails the moment the gap closes. Until then those two shapes can sit unmasked for 90 days in that store's own journal.
- Ruling SL-EVAL-PENDING-1: no real-model `last-run.json` exists yet, so stages 2 and 3 are closed.

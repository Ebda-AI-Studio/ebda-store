# Environment variables — all apps

Moved verbatim from `CLAUDE.md` (2026-07-11) so the instruction file stays rules-only. This is the canonical env catalog; update it in the SAME session as any env change (documentation-parity rule).

## Deploy (GitHub Actions → Railway)

Read by `.github/workflows/railway-deploy.yml`. Documented here because an operator who
sets only some of them can leave the API with no deploy path at all — see
`docs/migration/railway-actions-deploy.md` for the required order.

- `RAILWAY_ACTIONS_DEPLOY` (repo **variable**) — **the switch.** Until it is the string `'true'` the deploy job is gated off at job level and reports as **skipped**. Not a secret, because a job-level `if:` cannot read secrets.
- `RAILWAY_TOKEN` (repo **secret**) — Railway PROJECT token scoped to the `production` environment. Once `RAILWAY_ACTIONS_DEPLOY` is `'true'`, a missing token **fails** the job rather than skipping it: after cutover an absent token is a misconfiguration, not a no-op.
- `RAILWAY_SERVICE` (repo variable, default `api`) — the service to deploy.
- `RAILWAY_ENVIRONMENT` (repo variable, default `production`).
- `RAILWAY_HEALTH_URL` (repo variable, default `https://api.force-ai.co/health`) — polled to confirm the deployed commit is the one serving.

## API (Railway)

Required in production (app crashes without these):

- `DATABASE_URL` — Neon PostgreSQL connection string
- `DIRECT_URL` — Neon direct (non-pooled) URL for migrations / interactive transactions
- `DB_CONNECTION_LIMIT` (default `15`) — Prisma pool size (`connection_limit`, `packages/database/src/index.ts`). The API also derives the process-wide cap on pooled CONNECTIONS held by post-response deferred work from it (`DEFERRED_TX_GLOBAL_LIMIT` = a third of it, min 1 — `apps/api/src/lib/after-tenant-commit.ts`), so raising the pool raises that cap with it. The cap counts connections, not tasks: a task that opens a second transaction inside its tenant one (`r2-cleanup.deleteOrphan` → `withRlsBypass`) declares `connections: 2` and takes two slots (issue 2250).
- `JWT_SECRET` — min 32 chars, no placeholder values. Signs sessions only: rotating it signs everyone out and nothing else. The long-lived links in SMS and email (SMS opt-out, campaign unsubscribe, review requests) are no longer keyed on it (issue 2424). Campaign unsubscribe and review links signed before that change still verify against it until the next rotation.
- `ENCRYPTION_KEY` — min 32 chars. Besides encrypting stored secrets, it is the root of the purpose-bound HKDF keys in `apps/api/src/lib/derived-secret.ts` that MAC the SMS opt-out link and, unless their dedicated secrets are set, the campaign unsubscribe and review links (issue 2424). No new variable is needed for them. Rotating `ENCRYPTION_KEY` is already a re-encryption event, and it also voids every one of those links already sent.
- `REVIEW_TOKEN_SECRET` (optional; unset → a key derived from `ENCRYPTION_KEY`, issue 2424 — it used to fall back to `JWT_SECRET`) — HMAC key for the review-request link (`/review/<order>/<product>?token=`, 90-day expiry). With it unset, links signed before issue 2424 still verify against `JWT_SECRET`.
- `PORT` — set automatically by Railway
- `CF_WORKERS_DEV_SUBDOMAIN` (optional) — our Cloudflare workers.dev account subdomain; CORS then trusts `ebda-{web,admin,orders}.<subdomain>.workers.dev` preview origins (`apps/api/src/lib/cors-cache.ts`). Unset = no preview origin is trusted.
- `BUILD_COMMIT_SHA` (optional, build-time) — the commit the image was built from, baked by `Dockerfile.api` from the `GIT_COMMIT_SHA` build arg. Surfaced on `/health` as `commit` so a deploy can be verified as **live** rather than merely green: a 200 is returned identically by the container still serving the previous release. Unset → `/health` reports `commit: null`, which means _unknown_, not _not deployed_. To populate it under Railway (which builds the image itself), set `GIT_COMMIT_SHA` as a service variable so it reaches the Docker build.
- `RAILWAY_GIT_COMMIT_SHA` (read-only, platform) — **injected at runtime; verified 2026-09-03.** The first deploy carrying `/health`'s build identity reported the correct commit with no build arg and no service variable set, so this is what populates `commit` today. It appears in NEITHER listing — not the 85 the CLI reports, nor the 8 the dashboard shows as "added by Railway" — because both describe what is _configured_ on the service, which is not the container's environment. Do not conclude a platform variable is absent from either list alone.
- `RAILWAY_DEPLOYMENT_ID` (read-only, platform) — surfaced on `/health` as `deploymentId`. **Injected at runtime; verified 2026-09-03**, which also clears the Inngest deploy sync (`lib/inngest/client.ts`) that reads it through a fallback chain — a chain falling through would have looked identical from outside. Also absent from both listings, for the same reason as above.
- `NODE_ENV=production`
- `ALLOW_BYPASSRLS_ROLE` — **Node shell only; an explicit escape hatch inherited from FWB (whose prod runs as `neondb_owner`).** Ebda's runtime role is `ebda_app` (NOBYPASSRLS, Ruling R-EBDA-002), so this should stay UNSET. The Node boot guard (`apps/api/src/lib/database-role-guard.ts`, awaited in `apps/api/src/index.ts` BEFORE `listen()` since FIX-003, 2026-10-07) queries `pg_roles.rolbypassrls` and `rolsuper` on every boot and, in production, `process.exit(1)`s on a bypassing role unless this is the literal string `"true"`; with it set, every boot logs an `error`-level `[SECURITY] ALLOW_BYPASSRLS_ROLE=true — serving as <role> …` line. The hatch never excuses an UNVERIFIABLE role: in production a failed role query or a missing `pg_roles` row exits non-zero (it used to log and keep serving — fail open). The Workers shell ignores this variable: `cf/database-role-guard.ts` refuses any bypassing or unverifiable role per isolate. Every Node boot logs `[SECURITY] DB role check: current_user=<role> rolbypassrls=<bool> rolsuper=<bool>` (info level, all environments) — the line CI's integration job greps to fail unless it reads `current_user=ebda_app rolbypassrls=false rolsuper=false` (#1940).

Optional (feature degrades gracefully if missing):

- `JWT_EXPIRES_IN` (default `30m`) — access-token JWT lifetime. Short by design so refresh-token rotation has security value; the session length is governed by the refresh token, not this. Pin a different value here only with a deliberate reason.
- `REFRESH_TOKEN_EXPIRES_IN` (default `365d`) — rotating refresh-token lifetime = the practical "always signed in" window. Lower it to shorten the max session age; never below the 30-day floor Ahmad wants for the admin PWA.
- `REQUEST_COMMIT_TIMEOUT_MS` (optional, default `10000`) — upper bound on how long a buffered store-scoped response waits for its request transaction's COMMIT/ROLLBACK (`middleware/request-transaction.ts`, #1608). On expiry a would-be 2xx is answered 503 `COMMIT_TIMEOUT` (outcome unknown), a 5xx goes out as-is, and a P1 Telegram alert fires (`request-transaction.commit_timeout`). Every settled response carries `Server-Timing: request-tx;dur=<ms>`.
- `REDIS_URL` — Railway internal (`redis.railway.internal:6379`); falls back to `localhost:6379` in dev
- `RATE_LIMIT_SHARED` (default unset = shared) — set to `0` to put every API rate limiter back on per-process counting while Redis stays connected (`apps/api/src/middleware/security.ts` `rateLimitSharedEnabled`). The kill switch for the #1862 shared-budget tightening (issue 2230): a shared budget is N, a per-process one is N × replicas and resets on deploy. Read per request; a Railway variable change restarts the service.
- `RATE_LIMIT_429_ALERT_PER_MIN` (default `300`) — a limiter prefix (`rl:<name>:`) that answers at least this many 429s in one minute raises a P1 `rate-limit.429-spike` alert. Every minute with any 429 or any per-process fallback also logs one `[rate-limit] 429s by limiter in the last window` line with counts per limiter (`apps/api/src/lib/rate-limit-telemetry.ts`, issue 2216 / issue 1963).
- `ONESIGNAL_APP_ID` / `ONESIGNAL_REST_API_KEY` — admin order alerts + storefront broadcasts. When missing, broadcast endpoint returns `503 PUSH_NOT_CONFIGURED`.
- `ONESIGNAL_ADMIN_APP_ID` / `ONESIGNAL_ADMIN_REST_API_KEY` — optional separate OneSignal app for admin alerts; falls back to the public app id/key if unset.
- `ONESIGNAL_ORDERS_APP_ID` / `ONESIGNAL_ORDERS_REST_API_KEY` — separate OneSignal app for the **Orders PWA** new-order alerts (origin `orders.forcemediakw.com`). NO fallback (origin mismatch would silently fail) — `notifyOrdersAppOfOrder` skips the send when unset. Targets staff devices by the `store_id` tag the Orders app sets at enable time. `ORDERS_URL` is the deep-link base.
- `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` — standards-based Web Push (RFC 8030) for storefront subscriptions. Without these, `push.service.ts` logs a warning and skips sends.
- `POSTHOG_PERSONAL_API_KEY` / `POSTHOG_PROJECT_ID` / `POSTHOG_HOST` (default `https://eu.posthog.com`) — **privacy gap closure, 2026-07-11.** Enables server-side Right-to-Erasure propagation: `AuthService.eraseAccount` fires `account/erased`, and `privacy-propagation.service.ts`'s `deletePostHogPerson` deletes the customer's PostHog person. Distinct from the storefront's public `NEXT_PUBLIC_POSTHOG_KEY` — this needs person-level write scope and must never reach the browser. "Degrades gracefully" here means the API still boots and every OTHER feature works fine when unset. **Corrected 2026-09-23:** unset is now a documented WARN + no-op, NOT a thrown `PropagationNotConfiguredError`. The 2026-09-22 fail-loud was unconditional, and since nothing in the repo calls `posthog.identify(userId)` there is no person keyed by our `userId` to delete — so it dead-lettered `account-erased-propagation` and raised a P1 alert on EVERY erasure (up to `USER_ANONYMIZE_BATCH_CAP`=200 per monthly retention-cron run) for a subject that provably cannot exist. The same function already returns normally when the key IS set and the distinct_id matches nothing, so the unconfigured branch was strictly noisier than a stricter one. Set **`POSTHOG_ERASURE_REQUIRED=true`** (alongside the credentials) once `identify()` is wired and the unconfigured case fails loud again. Set this in production before relying on PostHog erasure compliance; see `docs/privacy/data-map.md` for why this also needs `posthog.identify(userId)` added at login before it's fully useful.
- `SENTRY_DSN` — error monitoring; safe to omit in dev.
- `OTEL_EXPORTER_OTLP_ENDPOINT` — OpenTelemetry distributed tracing. **Opt-in + fail-open**: tracing only activates when this is set to an OTLP/HTTP collector base URL (e.g. Grafana Tempo / Honeycomb / Jaeger — the bootstrap appends `/v1/traces`). With it unset, or if init throws, the API boots normally un-instrumented (tracing can never take the API down). Bootstrap is `apps/api/src/tracing.ts`, imported FIRST in `index.ts` (auto-instruments http/express/pg/ioredis before they load). Companions: `OTEL_EXPORTER_OTLP_HEADERS` (`k=v,k2=v2` auth headers), `OTEL_SERVICE_NAME` (default `force-api`), `OTEL_TRACES_SAMPLER_ARG` (head sample ratio 0–1; default 0.1 prod / 1.0 otherwise).
- `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM_NAME` / `SMTP_FROM_EMAIL` — outbound email via Resend.
- `INNGEST_SERVE_HOST` — **required in production.** Public origin (scheme+host, e.g. `https://api.force-ai.co`) Inngest Cloud calls to reach the serve endpoint. Without it the SDK registers the localhost origin (the self-register PUT's Host) → enqueued jobs queue forever. Boots with a loud warning if unset in production. Verified 2026-06-27 (the `force-api` Inngest app was stuck registered on `https://localhost:4000`).
- `GOOGLE_GENERATIVE_AI_KEY` — Gemini AI features (translate, SEO, categorize). When missing, AI routes return a config error.
- `GEMINI_API_KEY`, `GEMINI_API_KEY_2` … `GEMINI_API_KEY_20` — **key failover** (RULINGS GEMINI-FAILOVER-1). Use keys from SEPARATE Google Cloud projects (separate quotas). Order: `GOOGLE_GENERATIVE_AI_KEY`, `GEMINI_API_KEY`, `_2`, `_3`…; every Gemini call (SDK + answer-engine REST) retries the same request with the next key on 429/RESOURCE_EXHAUSTED and benches the exhausted key in-memory until Retry-After / next UTC day / 60 s. Key values are never logged (index only). The default `AI_DAILY_REQUEST_CAP` (450) scales with the number of keys; an explicit value is taken as the total.
- `GEMINI_MODEL` (default `gemini-flash-lite-latest`), `AI_BULK_THROTTLE_MS` (default 2500), `AI_DAILY_REQUEST_CAP` (default 450), `AI_MONTHLY_REQUEST_CAP` (default 20000) — Gemini free-tier guardrails.
- **Email campaigns (D2, 2026-09-25)** — all three are optional; the defaults are the production values. None of them can make anything send: a campaign only sends after a merchant presses send on a store where the `email_campaigns` feature is on (in no plan baseline → OFF everywhere until a super-admin enables it).
  - `CAMPAIGN_DAILY_SEND_CAP` (default `1000`) — campaign emails one store may send in any rolling 24 hours, counted from `campaign_recipients.sent_at`. A campaign whose audience exceeds the store's remaining allowance fails as `DAILY_CAP_EXCEEDED` before any email goes out. Protects the platform's shared sender reputation. Test sends do not count.
  - `CAMPAIGN_SEND_THROTTLE_MS` (default `1000`) — pause after each SUCCESSFUL campaign send (sleep-after-success, the bulk-AI pattern). Resend's default limit is 2 req/s per API key and the key also carries every transactional email, so the default uses about half of it. The `campaign-send` Inngest function runs one campaign at a time PER STORE (concurrency keyed on `storeId`, #1955) — different stores' campaigns send in parallel, bounded together by `CAMPAIGN_PLATFORM_SEND_INTERVAL_MS`.
  - `CAMPAIGN_PLATFORM_SEND_INTERVAL_MS` (default `1000`) — minimum gap between ANY two campaign sends across ALL stores (`lib/campaign-send-pacer.ts`, #1955). Every send reserves the next slot on one Redis key (in-process fallback without Redis), so the combined campaign rate stays ≤1/s regardless of how many stores are sending — the same ceiling the old platform-wide one-at-a-time limit gave — leaving ≥1 req/s of Resend's shared 2 req/s for transactional mail. Do not set it below `667` (1.5/s): transactional sends outside the order-email queue are not retried on 429. `0` disables the platform bound (not recommended). Cost: with K stores sending at once each store advances ~1 email per K seconds, which is why each batch step is bounded by `CAMPAIGN_BATCH_WALL_BUDGET_MS`.
  - `CAMPAIGN_BATCH_WALL_BUDGET_MS` (default `60000`) — wall-clock budget for ONE `campaign-send` batch step (issue 2115). A step is one HTTP request from Inngest Cloud through Cloudflare, whose edge answers 524 at 100s; a step stops before its budget (including never waiting on the pacer past it), its unsent recipients stay `queued`, and `leftover-*` steps send them. Keep it well under 100s. A deferral does NOT reserve a pacer slot (issue 2298). Leftover passes are capped (200 passes / 400 steps per run); recipients still `queued` when a cap is hit are marked failed `SEND_WINDOW_EXHAUSTED` and raise a P1 `campaign.send.window_exhausted` (issue 2297).
  - `CAMPAIGN_UNSUBSCRIBE_SECRET` (optional; unset → a key derived from `ENCRYPTION_KEY`, issue 2424 — it used to fall back to `JWT_SECRET`, so a session-secret rotation killed every sent unsubscribe link) — HMAC key for the one-click unsubscribe token in every campaign email. With it unset, links signed before issue 2424 (keyed on `JWT_SECRET`) still verify. Rotating it invalidates the unsubscribe links in every campaign email already sent, so set it once and leave it. `API_URL` must be the public https API origin for the `List-Unsubscribe` header to be emitted (it is omitted for a non-https value).
- `AI_AUTOFILL_STALE_TTL_DAYS` (default 30) — AI-first autofill: the 3-day sweep only re-generates an `ai`-owned text field when its product has been untouched longer than this. Keeps steady-state cost near zero (text rarely re-generates; recommendations refresh via the FBT recompute each sweep). Lower for fresher AI copy at higher Gemini cost.

Cloudflare-for-SaaS (`CF_*` below) is the sole custom-domain provider; `resolveDomainService()` always returns `CloudflareDomainService`.
- `CF_API_TOKEN` / `CF_ZONE_ID` / `CF_FALLBACK_ORIGIN` — Cloudflare-for-SaaS Custom Hostnames (token scoped `Zone:SSL and Certificates:Edit` + `Zone:Zone:Read`; fallback origin = the CNAME target merchants point at, e.g. `cf.forcemediakw.com`). **Unset → `CloudflareDomainService` reports not-configured and the resolver no-ops the CF path.** Full cutover procedure: `docs/migration/cloudflare-cutover-runbook.md`.
- `WHATSAPP_VERIFY_TOKEN` — Meta Cloud API webhook verification (WhatsApp queue is wired but per-store credentials live on the store record).
- `FORCE_AI_META_BM_ID` + `FORCE_AI_META_ADMIN_TOKEN` — one-time Force AI master credentials used by the "Provision automatically" button in `MetaCatalogCard`. The token needs `business_management` + `catalog_management` + `whatsapp_business_management` scopes. Without these, the button returns 503 `PROVISIONER_NOT_CONFIGURED`. Optional `META_GRAPH_API_VERSION` (default `v21.0`) + optional `FORCE_AI_META_PROVISIONER_USER_ID` to auto-assign new catalogs to a dedicated system user.
- Payment providers: Paymob, Kashier and FawryPay (plus COD and InstaPay, manual), listed in the provider catalog `packages/shared/src/providers/catalog.ts`. Each merchant brings their own keys per mode (sandbox / live), saved per store in Settings > Payments as ONE AES-256-GCM blob in `payment_configs.credentials` (`ENCRYPTION_KEY`; write-only, the browser only sees hints) and enabled only after a passing Test connection of exactly those keys; there are NO platform-level gateway keys. A catalog entry with `verified: false` is "coming soon" and cannot be enabled (ruling PROVIDERS-2, `docs/RULINGS.md`). Env: `PAYMENT_TEST_MODE`, `DEFAULT_PAYMENT_PROVIDER`, `DEFAULT_CURRENCY`.
- `PAYMOB_BASE_URL` / `KASHIER_BASE_URL` / `FAWRY_BASE_URL` / `PAYMENT_PROVIDER_STUB` — gateway stub override for the buy-flow parity harness (`scripts/buy-flow-parity/`) and local dev. `PAYMOB_BASE_URL` (e.g. `http://127.0.0.1:4690/paymob`) replaces the Paymob API host for every call (likewise Kashier and Fawry); it is honoured only when `NODE_ENV !== 'production'` **or** `PAYMENT_PROVIDER_STUB=1`, and is ignored otherwise, so it can never redirect real payments. It is deliberately an environment setting and never a per-merchant one (a merchant-chosen URL would be an SSRF vector). Works on Node and on a Worker (unlike the Node-only `--import` fetch preload used by the harness's git-ref mode). Never set in a real deploy.
- `PAYMOB_CHECKOUT_URL` — stub override of Paymob's hosted checkout host (`https://eg.checkout.paymob.com` by default), same rules as `PAYMOB_BASE_URL` (honoured only outside production or with `PAYMENT_PROVIDER_STUB=1`). Never set in a real deploy.
- `PAYMENT_PROVIDERS_ALLOW_UNVERIFIED` (test/dev only) — `1` lets a gateway the provider catalog does not list as sandbox-verified be enabled and offered, for the local stub suites (`tests/setup.ts` sets it) and the buy-flow parity harness. **Ignored whenever `NODE_ENV=production`**, so no environment value can put an unverified gateway in front of a customer (`apps/api/src/services/payment-providers/provider-gate.ts`). Never set in a real deploy.
- `SANDBOX_<PROVIDER>_<FIELD>` (script-only, never read by the API) — sandbox credentials for `node scripts/provider-sandbox-check.mjs <paymob|kashier|fawry>`, one per catalog field (`FIELD` = the catalog key upper-cased, non-alphanumerics as `_`, e.g. `SANDBOX_PAYMOB_INTEGRATIONID_CARD`). Optional `SANDBOX_WEBHOOK_URL` (a request bin to capture the webhook) and `SANDBOX_POLL_SECONDS` (default 300). The script refuses live keys and any `<PROVIDER>_BASE_URL` override.
- `PAYMENT_PROVIDER_TIMEOUT_MS` (optional, default `10000`): per-call deadline for a payment provider request (SP6a). A call that exceeds it fails as `PROVIDER_TIMEOUT`, which counts toward that store's circuit breaker for the provider. No provider call runs inside a request transaction, so this bounds checkout latency, not a transaction.
- `STUCK_WEBHOOK_MINUTES` (default 10) — payment-webhook offload safety net: how long a `webhook_events` inbox row may sit in `received`/`processing` before the 5-min Inngest sweep (`payment-webhook-stuck-sweep`) acts. Genuinely-undelivered rows (`received`, `attempts=0`) are RE-SENT to Inngest (closes the inngest.send-ok-but-never-delivered gap); wedged rows (consumer started but stuck) fire a P0 alert for manual replay from the durable row. The payment webhook route now persists each inbound webhook to `webhook_events`, fires `payment/webhook.received`, and ACKs 200 immediately — the heavy `PaymentService.handleWebhook` mutation runs in the `payment-webhook-process` Inngest fn OFF the shared API pool, so a webhook storm can't starve auth (P2024). `inngest.send` failure falls back to inline processing so no webhook is lost.
- `STUCK_ORDER_NOTIFY_MINUTES` (default 10) — order-created fanout safety net (Builder Reality Audit Lens E, E2-1): the sibling of `STUCK_WEBHOOK_MINUTES` for the `order/created` enqueue, which is fire-and-forget with no inline fallback. The 5-min Inngest cron `order-created-stuck-sweep` finds orders that are **paid** but whose fanout never claimed them (`orderCreatedNotifiedAt IS NULL`) past this window and RE-SENDS `order/created` (recovering confirmation email + admin push + WhatsApp + CAPI + accounting journal). Keyed on `paid` so it can never re-notify a still-unpaid online order. Idempotent via the fanout's atomic `order_created_notified_at` claim. Orders still unnotified past 3× the window fire a P1 alert.
- `STUCK_ORDER_MAX_AGE_MINUTES` (default 720 = 12h) — **recency FLOOR for the order-created sweep (P0 fix 2026-07-09).** The sweep only recovers orders `createdAt` BETWEEN `now-12h` and `now-STUCK_ORDER_NOTIFY_MINUTES`. Without this lower bound the first run swept the entire historical back-catalog and re-fired every side effect for ALL old orders across ALL stores. Also backfill `order_created_notified_at = now()` on pre-existing paid orders so NULL means "recent + unnotified".
- `PAYMENT_ABANDON_MINUTES` (default 30) — abandoned-checkout recovery: how long an ONLINE order may sit `status=pending` / `paymentStatus=unpaid` (with a generated gateway `paymentUrl`) before the 30-min Inngest sweep (`payment-abandonment-sweep`, **Enterprise `payment_abandonment` feature only**) stamps `Order.paymentGatewayAbandonedAt` AND pushes the store admins + super_admins a one-time "Checkout abandoned" recovery alert (via `OneSignalService.notifyAdminsOfAbandonedCheckout`, deep-linking to `/stores/:id/payment-abandonments`). The stamp dedupes the alert to exactly once per order. COD orders never match (no online Payment row). This is the SOLE unpaid-online-order merchant alert — a store that disables the `payment_abandonment` feature gets no unpaid-order pings at all. (The former always-on `STUCK_PAYMENT_MINUTES` / `order-stuck-payment-sweep` "Payment pending — follow up" nudge was removed 2026-07-18 as a redundant duplicate; `Order.stuckPaymentAlertedAt` is now a retained-but-unused legacy column.)
- `REFUND_REVERSAL_STUCK_MINUTES` (default 10) — refund-reversal safety net, the sibling of `STUCK_ORDER_NOTIFY_MINUTES` for the `order/refunded` fanout. `applyRefundEffects` only ENQUEUES the event; the reversals (inventory restore, coupon, affiliate, loyalty, backorders) run in the fanout. A failed enqueue propagates, but a SUCCESSFUL enqueue whose event is never consumed (Inngest outage / bad signing key / worker down / dropped mid-deploy) is silent — the order reads `cancelled`, the customer is refunded, and the stock never returns. The 15-min cron `refund-reversal-stuck-sweep` finds orders whose whole-order reversal was requested (`refundReversalRequestedAt`, stamped at every stock-restoring enqueue — status-agnostic, so a manual full return on a `delivered` order is covered, and immune to later unrelated `updatedAt` bumps) with `refundReversedAt IS NULL` past this window (orders predating that column: cancelled/refunded + `updatedAt`, as before), and re-sends `order/refunded` with `notify:false` (recovery is a plumbing retry, never a second "Refund issued" push). Safe to re-fire: all five reversal steps are idempotent at the data layer. Orders still unreversed past 3× the window fire a P1 alert.
- `REFUND_REVERSAL_MAX_AGE_MINUTES` (default 720 = 12h) — **recency FLOOR for the refund-reversal sweep.** Same class of guard as `STUCK_ORDER_MAX_AGE_MINUTES`, and load-bearing for the same reason: `refund_reversed_at` is NULL for every cancelled/refunded order predating the column, so without a lower bound the first tick after deploy would re-fire reversals across the entire order history. The migration additionally backfills `refund_reversed_at = updated_at` on pre-existing cancelled/refunded rows so NULL means "cancelled after the migration and genuinely unreversed"; the floor is the second line of defence, not the only one.
- `ORDER_STATUS_FANOUT_STUCK_MINUTES` (default 10) — status-change fanout safety net, the sibling of `STUCK_ORDER_NOTIFY_MINUTES` for `order/status-changed` (payment-success / shipped emails, WhatsApp/SMS/push dispatch, carrier auto-ship, affiliate commission + loyalty award on delivery). `updateStatus` stamps `statusFanoutRequestedAt` and re-nulls `statusFanoutClaimedAt` with every transition; the fanout claims the transition before any side effect (so a duplicate event no-ops). The 15-min cron `order-status-fanout-stuck-sweep` re-sends `order/status-changed` for confirmed/shipped/delivered/cancelled/refunded orders requested past this window and never claimed — the accepted-but-never-delivered case the inline fallback (rejected enqueue) cannot see. Still unclaimed past 3× the window → P1 alert. `updateStatus` also records WHICH status was requested (`statusFanoutRequestedStatus`); the sweep re-sends that status only while the order is still at it, and a request superseded by a direct status write (gateway refund, refresh-refund-status, payment confirm) is reported as `order.status_fanout.superseded` and disarmed instead of re-sent for the wrong status (issue 2070 / issue 2133). The fanout stamps `statusFanoutCompletedAt` after every side effect succeeded, keyed on the transition it claimed (`statusFanoutRequestedStatus`), not the live status, so a direct status write mid-run cannot turn a successful fanout into a false alert (issue 2295); a claimed, never-completed transition past the window is reported once as `order.status_fanout.failed_after_claim` and not auto re-sent, since its successful steps (customer emails) would repeat (issue 2071).
- `ORDER_STATUS_FANOUT_MAX_AGE_MINUTES` (default 720 = 12h) — recency FLOOR for that sweep, same guard as `REFUND_REVERSAL_MAX_AGE_MINUTES`. Rows predating the columns are NULL and never match regardless.
- `REFUND_CLAIM_STUCK_MINUTES` (default 15) — refund claims with no known outcome (#1317). `PaymentService.refund` commits its claim (the payment's `refundedAmount` raised, a `refund_initiated` payment event) on a transaction of its own BEFORE calling the provider, and resolves it with `refund_completed` (sent) or `refund_failed` (nothing sent, balance put back). A claim with neither past this window — the process died mid-refund, or the provider never gave a clear answer (`refund_indeterminate`) — means the balance counts money that may never have left. It is checked on the `refund-reversal-stuck-sweep` tick (no cron of its own: another cadence would keep the Neon compute awake) and raised as a P1 alert — ONCE per escalation stage (this window, 24h, 72h; a Redis sentinel per claim and stage, issue 2027), not every tick; the claim shows on the order page's payment-events timeline. Not resolvable automatically — with no provider refund id there is nothing to ask the provider about — but a human resolves it by completing the return with a non-gateway method ("Already refunded — record only"), which writes `refund_reconciled` for the claim (issue 2002). The sweep reads claims oldest first in pages of 500, each followed by only that page's payments' resolutions (issue 2028), and keeps paging until it has 500 UNRESOLVED claims, the window ends, 20 pages were read, or its 45s wall-clock budget is spent (issue 2347: the whole scan is one Inngest step — one HTTP request that Cloudflare cuts at 100s, and a failed step also fails the reversal sweep on the same tick) — the bound is on unresolved claims, because every successful refund also writes a claim and a raw 500-row read hid stuck claims once volume passed ~500/week (issue 2296). Each page's resolution read is cursor-paged (1000 rows). Stopping before the window ends is logged at warn; the rest is read on later ticks.
- `REFUND_CLAIM_MAX_AGE_MINUTES` (default 10080 = 7 days) — stop reporting an unresolved refund claim after this long (it has had its 15m / 24h / 72h alerts by then).
- `STUCK_PAYMENT_MINUTES` (default 60) — order-payment lifecycle: how long an ONLINE order may sit `status=pending` / `paymentStatus=unpaid` before the 15-min stuck-payment Inngest sweep (`order-stuck-payment-sweep`) pushes the merchant a "Payment pending — follow up" alert (deduped once per order via `Order.stuckPaymentAlertedAt`). COD orders never trigger it (no online Payment row).
- `PAYMENT_ABANDON_MINUTES` (default 30) — abandoned-checkout recovery: how long an ONLINE order may sit `status=pending` / `paymentStatus=unpaid` (with a generated gateway `paymentUrl`) before the 30-min Inngest sweep (`payment-abandonment-sweep`, **Enterprise `payment_abandonment` feature only**) stamps `Order.paymentGatewayAbandonedAt` AND pushes the store admins + super_admins a one-time "Checkout abandoned" recovery alert (via `OneSignalService.notifyAdminsOfAbandonedCheckout`, deep-linking to `/stores/:id/payment-abandonments`). The stamp dedupes the alert to exactly once per order. COD orders never match (no online Payment row). Overlaps intentionally with `STUCK_PAYMENT_MINUTES` (an Enterprise store with both enabled gets the recovery ping at 30 min and the "Payment pending — follow up" nudge at 60 min).
- `AUTO_CANCEL_UNPAID_DAYS` (default 2, matches MyFatoorah's 2-day payment-link validity) — how old a `pending` / `unpaid` order must be before the daily Inngest cron (`order-auto-cancel-unpaid`, 03:00 UTC) auto-cancels it via `OrderService.updateStatus(...,'cancelled')`. Never refunds (the order was never paid — refund effects are gated on a captured payment); the customer still gets the standard `order_cancelled` notification. **Reconciles before cancelling:** `unpaid` means "nothing ever told us it was paid", not "the money wasn't captured" — the webhook can be lost (or, for MyFatoorah, is account-level and never fires per-invoice) while the customer also never returns to the success page, so verify-on-return never runs either. Any order carrying an online-gateway payment row is therefore checked against the provider first; a `completed` answer routes into `confirmPaymentFromProviderStatus` (the same single-writer the webhook / verify-on-return / admin-refresh paths use) and the order is marked paid instead of cancelled. If the provider call throws, the order is SKIPPED, never cancelled — unknown is not unpaid. Rescues fire a P1 alert (repeated rescues mean a webhook that isn't firing); a skip-only run fires `info`.
- `TRUST_PROXY_HOPS` (optional, default `1`) — how many proxies sit in front of the API, passed to Express `app.set('trust proxy', n)`. It is a HOP COUNT and must match deployment topology exactly. **Railway only** (today) = `1`; **Cloudflare in front of Railway** = `2`. Too LOW and `req.ip` resolves to the nearest proxy, so every IP-keyed limiter (`authLimiter`, `paymentLimiter`, `writeLimiter`) collapses into one global bucket and audit logs record the proxy instead of the client. Too HIGH — or `true` — and a client can spoof `X-Forwarded-For` to forge its own address and bypass every IP-keyed limiter outright, which is **strictly worse than having none**. A non-integer or out-of-range value falls back to `1` (fail safe, never open). **Do not set `2` until `api.force-ai.co` is Cloudflare-proxied AND the Railway origin no longer accepts direct public traffic** — raising it while `*.up.railway.app` is still publicly reachable IS the spoofing hole.
- `AI_MODEL_RATES` (optional, default unset) — JSON map of model id -> per-MILLION-token price in the billing currency, e.g. `{"gemini-flash-lite-latest":{"in":0.10,"out":0.40}}`. Converts token usage into money on every `ai_usage` row (`cost_micros`), which is what makes per-store AI spend and therefore per-store margin a number instead of a token count. **There are deliberately NO built-in default prices** — provider pricing changes and differs by region/contract, and a wrong hardcoded constant produces confident, wrong margin figures that people then act on. An unconfigured model records `cost_micros = NULL`, which is deliberately DISTINCT from `0` (a genuinely free cached hit); reports must not sum them together. Malformed JSON or a malformed entry is treated as unpriced, never as free. Cost is stored in **micros** (1,000,000 micros = 1 currency unit) because a single flash-lite call is routinely a fraction of one fils and integer fils would round nearly every row to 0. Take the numbers from the provider's current pricing page and verify them — nothing in the code can validate that they are right. See `apps/api/src/lib/ai-pricing.ts`.
- `AUTO_CANCEL_RECONCILE_THROTTLE_MS` (default 250) — sleep-after-success pacing between the provider status calls the auto-cancel sweep makes. A 500-order backlog is otherwise a 500-request burst across up to 4 rate-limited providers; this throttles on success rather than discovering the limit via 429s. Only orders with a gateway payment row incur the call (COD and link-less orders skip it and are never delayed). Set to `0` to disable pacing.
- `R2_ORPHAN_SWEEP_APPLY` (default unset / report-only) — controls the weekly Inngest cron `r2-orphan-sweep` (Sunday 04:00 UTC). When **unset or any value other than `"true"`**, the sweep only **reports** orphans (count, size, sample keys) via structured logger + Telegram alert — it never deletes. Set to the literal string `"true"` to enable batch deletion of confirmed orphans (DeleteObjects ≤1000/request). Review at least one report run before enabling. Objects younger than 24 h are always skipped regardless of this flag. Before any orphan is reported or deleted the sweep runs `assertStrictTablesVisible` (same file, issue 2288): if a STRICT registry table reads 0 rows while the catalog — after an `ANALYZE` — says it has rows, deletion is refused and the Telegram report is marked **NOT TRUSTWORTHY** (P1). When the catalog cannot say (`reltuples` -1: never analyzed, and a non-owner role such as post-cutover `force_app` cannot ANALYZE), the guard passes only if the collection's own runner proves `app.bypass_rls = 'true'` (issue 2354) — every STRICT policy admits all rows under it, so a 0 is a real 0 — and refuses otherwise. The manual `scripts/r2-orphan-audit.ts --force-report` prints a refused dry-run list under the same banner; it is never honoured with `--apply`.
- `ANSWER_ENGINE_GEMINI_MODEL` (optional, default `gemini-2.5-flash-lite`) — Answer-Engine Insights (AEO/GEO citation checks): overrides which Gemini model `gemini.provider.ts` calls for the weekly citation-scan cron. **Live-verified 2026-09-26 (issue #929):** the adapter sends the current `google_search` grounding tool (not the legacy `googleSearchRetrieval`, which every 2.x model now rejects with HTTP 400) via a direct REST call to `v1beta/models/{model}:generateContent` — no SDK, matching the `perplexity.provider.ts`/`openai.provider.ts` pattern. `gemini-2.5-flash-lite` was measured to ground **for free** on the current key (`groundingMetadata.groundingChunks[].web.uri` populated). Measured alternatives: `gemini-flash-lite-latest` / `gemini-flash-latest` / `gemini-3.5-flash-lite` return HTTP 429 (grounding is paid-only on those aliases) and `gemini-2.5-flash` returns 404 (retired for new users) — do **not** switch to any of those without confirming they're ungated on the account's key first. **A model can be retired or re-rationed without notice**: if the grounded call returns HTTP 400/404/429, the adapter automatically retries ONCE with no tools (an ordinary ungrounded call on the same model) rather than failing the scan — the row is written with `groundingUnavailableReason` set (e.g. `http_429`) instead of a plain `grounded: false`, and the dashboard shows a distinct "search grounding unavailable" caveat instead of "no live citations found" (`dashboard.service.ts`'s `groundingUnavailable`, `EngineSummaryCards.tsx`). If this model is ever retired in turn, re-run the live probe (send `google_search` to candidate models with the production key, check for HTTP 200 + `groundingChunks`) and update this default.

Middleware is synchronous and cannot look a custom domain up to learn its slug, so **a custom domain is allowlisted by hostname, never by slug**; a slug token never matches a custom domain. The rewrite needs ALL THREE: main flag on, route in the route list, store in this list. **Fail-closed on every bad state (Ruling TRC-6):** unset, empty, or unparseable (any token that is not lowercase letters/digits with inner `.`/`-`, e.g. `slug:palora`, `palora;x`, `*`) routes NO store, even with the main flag on and a valid route list. There is deliberately **no `all` shortcut**: the literal token `all` is unparseable and rejects the whole list, so the full rollout is naming every store, not a wildcard. **Default language (Ruling TRC-7, issue 2419):** a token may end in `:en` or `:ar` (`palora:ar`, `wadyaljuz.com:ar`) to declare the store's default language; a bare token means `en`. A visitor with no `force-language` cookie is keyed to that default (a cookie of `en` or `ar` still wins), so an Arabic-default store gets Arabic, not `en`, in the route/cache key. Declare it equal to the store's `settings.defaultLanguage`; any other suffix makes the whole list unparseable (routes no store). Losing the variable turns the canary off; it never widens it. Set as a Worker SECRET, same as the two flags above.
- `REVALIDATE_SECRET` — **REQUIRED for on-demand cache purging; the API half is useless without it.** Shared secret for `POST /api/revalidate` (`apps/web/src/app/api/revalidate/route.ts`), which must equal the API's `REVALIDATE_SECRET`. The route refuses with **503 `REVALIDATE_SECRET not configured`** when unset — it never silently accepts. **Ebda 2026-10-07:** set on `ebda-web` (random, copy in macOS Keychain `security find-generic-password -a whisky11 -s ebda-web-REVALIDATE_SECRET -w`); `cf-web-deploy.yml` refuses to deploy without it. The API side (`REVALIDATE_SECRET` + `STOREFRONT_REVALIDATE_URL`) is NOT set yet, so merchant-save purges are not wired: set the same value on `ebda-api`.
  **Incident 2026-09-02:** the API had both revalidate vars and the storefront Worker had none, so EVERY purge since the feature shipped was rejected 503 and silently dropped (API-side logging was warn-level only). Storefront freshness had quietly fallen back to the 60s data-cache TTL, which merchants experienced as "I save, nothing changes, so I save again" — the repeat saves did nothing; the TTL simply expired. Verify from outside with a deliberately wrong secret: `curl -X POST https://<storefront>/api/revalidate -H 'Content-Type: application/json' -d '{"secret":"wrong","tags":["probe"]}'` — **401 means configured, 503 means dead.** A rejected purge now logs at error level (Sentry-visible) rather than warn.

## Sentry build-time config (source maps + releases) — shared across web/admin/orders

Wired into `cf-deploy.yml` 2026-09-25: the "Build for Cloudflare (OpenNext)" step of each app passes these into `next build`, where `withSentryConfig` (`apps/{web,admin,orders}/next.config.js`) uploads the browser source maps under release = the commit SHA (`GITHUB_SHA`, the same value the SDK injects into the client bundle as the event `release`; chunks also carry Sentry debug IDs, so symbolication does not depend on the release name alone), then **deletes every `.map` from `.next/static` and strips the `sourceMappingURL` comments before OpenNext copies the assets** — maps are never served publicly (`deleteSourcemapsAfterUpload: true`; deletion runs with or without a token). Measured locally 2026-09-25 with a deliberately invalid token: build exit 0, both 401s logged as warnings, 0 `.map` files and 0 `sourceMappingURL` comments left in `.next/static`, 96 chunks carrying `debugId`.

- `SENTRY_AUTH_TOKEN` — **GitHub repo SECRET (not a variable). Not set as of 2026-09-25** (`gh secret list`), so every deploy currently prints a `::warning::` and ships minified stack traces. To enable: in Sentry, Settings → Developer Settings → Organization Tokens → create one (an org token `sntrys_…` carries the org itself and has the required release/source-map scopes), OR a user auth token with scopes **`project:releases`** and **`org:read`** (then `SENTRY_ORG` below is required). Add it with `gh secret set SENTRY_AUTH_TOKEN -R ForceAI-KW/force-website-builder`. Missing token → warning + skip; a bad/expired token or a Sentry outage → warning (the `errorHandler` in each `next.config.js`), never a failed deploy.
- `SENTRY_ORG` — **repo variable**, the Sentry organization slug. Required with a user token, optional with an `sntrys_` org token.
- `SENTRY_PROJECT_WEB` — repo variable, Sentry project slug for the storefront; defaults to `force-web` in the workflow.
- `SENTRY_PROJECT_ADMIN` / `SENTRY_PROJECT_ORDERS` — repo variables, project slugs for admin and orders. No default (the slugs are not recorded in the repo); unset → that app's upload is skipped with a warning.
- Worker (SSR/RSC) events: the web deploy passes `--var SENTRY_RELEASE:$GITHUB_SHA` so `@sentry/cloudflare` tags Worker events with the same release. **The Worker bundle's own maps are NOT uploaded** — wrangler re-bundles `.open-next/worker.js` at deploy time, and uploading its maps needs a deploy-path change (`--outdir` + `sentry-cli sourcemaps inject/upload` on the exact deployed bundle) that has not been verified against a real Worker event's frame paths. Client-side errors (the bulk of storefront Sentry issues) are covered.
- Locally and in `ci.yml`, nothing is set, so builds are unchanged (no upload; maps still deleted).

## Integration test suite

- `TEST_API_URL` (default `http://localhost:4000`) — the ONLY knob for which API the integration suite talks to. Accepts an origin or an already-versioned base (`…/api/v1`); `tests/helpers/api-base.ts` normalizes both to one `{ API_ORIGIN, API_BASE }` pair, so no caller can produce `/api/v1/api/v1`. A bare host (`localhost:4000`, `api.force-ai.co`) is rejected at load with a named error rather than parsed into the truthy string origin `"null"`. A well-formed absolute URL is NOT automatically accepted either: any host that is not loopback or a private (RFC1918/link-local) address is also refused at load — see `TEST_API_ALLOW_REMOTE` below.
- `TEST_API_BASE` — older alias, still honoured. Same normalization.
- `TEST_API_ALLOW_REMOTE` (default unset/off) — the suite writes real data (it POSTs `/auth/register`), so `tests/helpers/api-base.ts` refuses to run against anything but loopback or a private address, even when `TEST_API_URL`/`TEST_API_BASE` parses as a well-formed URL. Set `TEST_API_ALLOW_REMOTE=1` on the same command to explicitly opt into pointing the suite at a real, reachable host — this makes doing so a deliberate act on the command line rather than a naming-convention promise a stray `.env` value could silently break.
- **The suite deliberately does NOT read `API_URL` or `API_HOST`** (2026-09-09). Both are server variables: `API_URL` is an ORIGIN (`config.apiUrl`) and `API_HOST` is a BARE HOSTNAME (`config.host`), and `apps/api/src/config/index.ts` runs `dotenv.config()` at import time — before any const in a test file — so a root `.env` copied from `.env.example` would silently win over the test's own default. Borrowing `API_URL` cost two ways: every request lost its `/api/v1` prefix and 404'd, and on a machine holding deployed values (`API_URL=https://api.force-ai.co`) a local `npm run test:integration` would have POSTed `/auth/register` against production. Never point the suite at a variable whose production value is a real, reachable API.

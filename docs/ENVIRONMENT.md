# Environment variables — all apps

Moved verbatim from `CLAUDE.md` (2026-07-11) so the instruction file stays rules-only. This is the canonical env catalog; update it in the SAME session as any env change (documentation-parity rule).

## Deploy (GitHub Actions → Railway)

Read by `.github/workflows/railway-deploy.yml`. Documented here because an operator who
sets only some of them can leave the API with no deploy path at all — see
`docs/migration/railway-actions-deploy.md` for the required order.

- `RAILWAY_ACTIONS_DEPLOY` (repo **variable**) — **the switch.** Until it is the string `'true'` the deploy job is gated off at job level and reports as **skipped**. Not a secret, because a job-level `if:` cannot read secrets.
- `RAILWAY_TOKEN` (repo **secret**) — Railway PROJECT token scoped to the `production` environment. Once `RAILWAY_ACTIONS_DEPLOY` is `'true'`, a missing token **fails** the job rather than skipping it: after cutover an absent token is a misconfiguration, not a no-op.
- `RAILWAY_SERVICE` (repo variable, default `api`) — the service to deploy.
- `RAILWAY_ENVIRONMENT` (repo variable, default `production`).
- `RAILWAY_HEALTH_URL` (repo variable, default `https://api.force-ai.co/health`) — polled to confirm the deployed commit is the one serving.

## API (Railway)

Required in production (app crashes without these):

- `DATABASE_URL` — Neon PostgreSQL connection string
- `DIRECT_URL` — Neon direct (non-pooled) URL for migrations / interactive transactions
- `JWT_SECRET` — min 32 chars, no placeholder values
- `ENCRYPTION_KEY` — min 32 chars
- `PORT` — set automatically by Railway
- `BUILD_COMMIT_SHA` (optional, build-time) — the commit the image was built from, baked by `Dockerfile.api` from the `GIT_COMMIT_SHA` build arg. Surfaced on `/health` as `commit` so a deploy can be verified as **live** rather than merely green: a 200 is returned identically by the container still serving the previous release. Unset → `/health` reports `commit: null`, which means _unknown_, not _not deployed_. To populate it under Railway (which builds the image itself), set `GIT_COMMIT_SHA` as a service variable so it reaches the Docker build.
- `RAILWAY_GIT_COMMIT_SHA` (read-only, platform) — **injected at runtime; verified 2026-09-03.** The first deploy carrying `/health`'s build identity reported the correct commit with no build arg and no service variable set, so this is what populates `commit` today. It appears in NEITHER listing — not the 85 the CLI reports, nor the 8 the dashboard shows as "added by Railway" — because both describe what is _configured_ on the service, which is not the container's environment. Do not conclude a platform variable is absent from either list alone.
- `RAILWAY_DEPLOYMENT_ID` (read-only, platform) — surfaced on `/health` as `deploymentId`. **Injected at runtime; verified 2026-09-03**, which also clears the Inngest deploy sync (`lib/inngest/client.ts`) that reads it through a fallback chain — a chain falling through would have looked identical from outside. Also absent from both listings, for the same reason as above.
- `NODE_ENV=production`
- `ALLOW_BYPASSRLS_ROLE` — **load-bearing today, remove after the RLS cutover.** Prod's `DATABASE_URL` currently connects as `neondb_owner`, a BYPASSRLS role — the boot guard (`apps/api/src/index.ts:438-479`) queries `pg_roles.rolbypassrls` on every boot and, in production, `process.exit(1)`s unless this is set to the literal string `"true"` (any other value, including unset, is fatal). This is an explicit escape hatch, not a bug: cutting `DATABASE_URL` over to the non-bypass `force_app` role is the tracked RLS-cutover follow-up (`docs/plans/2026-07-02-rls-cutover.md`), not a same-day fix, and a routine redeploy must not crash-loop the whole platform in the meantime (verified 2026-06-27). Once the cutover flips `DATABASE_URL` to `force_app`, `rolbypassrls` reads `false` and this var becomes a no-op — delete it from Railway then.

Distinct from the storefront's public `NEXT_PUBLIC_POSTHOG_KEY` — this needs person-level write scope and must never reach the browser. "Degrades gracefully" here means the API still boots and every OTHER feature works fine when unset. **Corrected 2026-09-23:** unset is now a documented WARN + no-op, NOT a thrown `PropagationNotConfiguredError`. The 2026-09-22 fail-loud was unconditional, and since nothing in the repo calls `posthog.identify(userId)` there is no person keyed by our `userId` to delete — so it dead-lettered `account-erased-propagation` and raised a P1 alert on EVERY erasure (up to `USER_ANONYMIZE_BATCH_CAP`=200 per monthly retention-cron run) for a subject that provably cannot exist. The same function already returns normally when the key IS set and the distinct_id matches nothing, so the unconfigured branch was strictly noisier than a stricter one. Set this in production before relying on PostHog erasure compliance; see `docs/privacy/data-map.md` for why this also needs `posthog.identify(userId)` added at login before it's fully useful.

With it unset, or if init throws, the API boots normally un-instrumented (tracing can never take the API down). Bootstrap is `apps/api/src/tracing.ts`, imported FIRST in `index.ts` (auto-instruments http/express/pg/ioredis before they load). Companions: `OTEL_EXPORTER_OTLP_HEADERS` (`k=v,k2=v2` auth headers), `OTEL_SERVICE_NAME` (default `force-api`), `OTEL_TRACES_SAMPLER_ARG` (head sample ratio 0–1; default 0.1 prod / 1.0 otherwise).

Without it the SDK registers the localhost origin (the self-register PUT's Host) → enqueued jobs queue forever. Boots with a loud warning if unset in production. Verified 2026-06-27 (the `force-api` Inngest app was stuck registered on `https://localhost:4000`).
- `GOOGLE_GENERATIVE_AI_KEY` — Gemini AI features (translate, SEO, categorize). When missing, AI routes return a config error.
- `GEMINI_MODEL` (default `gemini-flash-lite-latest`), `AI_BULK_THROTTLE_MS` (default 2500), `AI_DAILY_REQUEST_CAP` (default 450), `AI_MONTHLY_REQUEST_CAP` (default 20000) — Gemini free-tier guardrails.
- **Email campaigns (D2, 2026-09-25)** — all three are optional; the defaults are the production values. None of them can make anything send: a campaign only sends after a merchant presses send on a store where the `email_campaigns` feature is on (in no plan baseline → OFF everywhere until a super-admin enables it).
  - `CAMPAIGN_DAILY_SEND_CAP` (default `1000`) — campaign emails one store may send in any rolling 24 hours, counted from `campaign_recipients.sent_at`. A campaign whose audience exceeds the store's remaining allowance fails as `DAILY_CAP_EXCEEDED` before any email goes out. Protects the platform's shared sender reputation. Test sends do not count.
  - `CAMPAIGN_SEND_THROTTLE_MS` (default `1000`) — pause after each SUCCESSFUL campaign send (sleep-after-success, the bulk-AI pattern). Resend's default limit is 2 req/s per API key and the key also carries every transactional email, so the default uses about half of it. The `campaign-send` Inngest function also runs one campaign at a time platform-wide.
  - `CAMPAIGN_UNSUBSCRIBE_SECRET` (falls back to `JWT_SECRET`) — HMAC key for the one-click unsubscribe token in every campaign email. Rotating it invalidates the unsubscribe links in every campaign email already sent, so set it once and leave it. `API_URL` must be the public https API origin for the `List-Unsubscribe` header to be emitted (it is omitted for a non-https value).
- `AI_AUTOFILL_STALE_TTL_DAYS` (default 30) — AI-first autofill: the 3-day sweep only re-generates an `ai`-owned text field when its product has been untouched longer than this. Keeps steady-state cost near zero (text rarely re-generates; recommendations refresh via the FBT recompute each sweep). Lower for fresher AI copy at higher Gemini cost.

Cloudflare-for-SaaS (`CF_*` below) is the sole custom-domain provider; `resolveDomainService()` always returns `CloudflareDomainService`.
- `CF_API_TOKEN` / `CF_ZONE_ID` / `CF_FALLBACK_ORIGIN` — Cloudflare-for-SaaS Custom Hostnames (token scoped `Zone:SSL and Certificates:Edit` + `Zone:Zone:Read`; fallback origin = the CNAME target merchants point at, e.g. `cf.forcemediakw.com`). **Unset → `CloudflareDomainService` reports not-configured and the resolver no-ops the CF path.** Full cutover procedure: `docs/migration/cloudflare-cutover-runbook.md`.
- `WHATSAPP_VERIFY_TOKEN` — Meta Cloud API webhook verification (WhatsApp queue is wired but per-store credentials live on the store record).
- `FORCE_AI_META_BM_ID` + `FORCE_AI_META_ADMIN_TOKEN` — one-time Force AI master credentials used by the "Provision automatically" button in `MetaCatalogCard`. The token needs `business_management` + `catalog_management` + `whatsapp_business_management` scopes. Without these, the button returns 503 `PROVISIONER_NOT_CONFIGURED`. Optional `META_GRAPH_API_VERSION` (default `v21.0`) + optional `FORCE_AI_META_PROVISIONER_USER_ID` to auto-assign new catalogs to a dedicated system user.
- Payment providers (per-store credentials live on the store record; env vars below are global defaults / test mode): `PAYMENT_TEST_MODE`, `DEFAULT_PAYMENT_PROVIDER`, `DEFAULT_CURRENCY`, plus provider-specific `TAP_*`, `MYFATOORAH_*`, `HESABE_*`, `UPAYMENTS_*`.
- `STUCK_WEBHOOK_MINUTES` (default 10) — payment-webhook offload safety net: how long a `webhook_events` inbox row may sit in `received`/`processing` before the 5-min Inngest sweep (`payment-webhook-stuck-sweep`) acts. Genuinely-undelivered rows (`received`, `attempts=0`) are RE-SENT to Inngest (closes the inngest.send-ok-but-never-delivered gap); wedged rows (consumer started but stuck) fire a P0 alert for manual replay from the durable row. The payment webhook route now persists each inbound webhook to `webhook_events`, fires `payment/webhook.received`, and ACKs 200 immediately — the heavy `PaymentService.handleWebhook` mutation runs in the `payment-webhook-process` Inngest fn OFF the shared API pool, so a webhook storm can't starve auth (P2024). `inngest.send` failure falls back to inline processing so no webhook is lost.
- `STUCK_ORDER_NOTIFY_MINUTES` (default 10) — order-created fanout safety net (Builder Reality Audit Lens E, E2-1): the sibling of `STUCK_WEBHOOK_MINUTES` for the `order/created` enqueue, which is fire-and-forget with no inline fallback. The 5-min Inngest cron `order-created-stuck-sweep` finds orders that are **paid** but whose fanout never claimed them (`orderCreatedNotifiedAt IS NULL`) past this window and RE-SENDS `order/created` (recovering confirmation email + admin push + WhatsApp + CAPI + accounting journal). Keyed on `paid` so it can never re-notify a still-unpaid online order. Idempotent via the fanout's atomic `order_created_notified_at` claim. Orders still unnotified past 3× the window fire a P1 alert.
- `STUCK_ORDER_MAX_AGE_MINUTES` (default 720 = 12h) — **recency FLOOR for the order-created sweep (P0 fix 2026-07-09).** The sweep only recovers orders `createdAt` BETWEEN `now-12h` and `now-STUCK_ORDER_NOTIFY_MINUTES`. Without this lower bound the first run swept the entire historical back-catalog and re-fired every side effect for ALL old orders across ALL stores. Also backfill `order_created_notified_at = now()` on pre-existing paid orders so NULL means "recent + unnotified".
- `PAYMENT_ABANDON_MINUTES` (default 30) — abandoned-checkout recovery: how long an ONLINE order may sit `status=pending` / `paymentStatus=unpaid` (with a generated gateway `paymentUrl`) before the 30-min Inngest sweep (`payment-abandonment-sweep`, **Enterprise `payment_abandonment` feature only**) stamps `Order.paymentGatewayAbandonedAt` AND pushes the store admins + super_admins a one-time "Checkout abandoned" recovery alert (via `OneSignalService.notifyAdminsOfAbandonedCheckout`, deep-linking to `/stores/:id/payment-abandonments`). The stamp dedupes the alert to exactly once per order. COD orders never match (no online Payment row). This is the SOLE unpaid-online-order merchant alert — a store that disables the `payment_abandonment` feature gets no unpaid-order pings at all. (The former always-on `STUCK_PAYMENT_MINUTES` / `order-stuck-payment-sweep` "Payment pending — follow up" nudge was removed 2026-07-18 as a redundant duplicate; `Order.stuckPaymentAlertedAt` is now a retained-but-unused legacy column.)
- `REFUND_REVERSAL_STUCK_MINUTES` (default 10) — refund-reversal safety net, the sibling of `STUCK_ORDER_NOTIFY_MINUTES` for the `order/refunded` fanout. `applyRefundEffects` only ENQUEUES the event; the reversals (inventory restore, coupon, affiliate, loyalty, backorders) run in the fanout. A failed enqueue propagates, but a SUCCESSFUL enqueue whose event is never consumed (Inngest outage / bad signing key / worker down / dropped mid-deploy) is silent — the order reads `cancelled`, the customer is refunded, and the stock never returns. The 5-min cron `refund-reversal-stuck-sweep` finds cancelled/refunded orders with `refundReversedAt IS NULL` past this window and re-sends `order/refunded` with `notify:false` (recovery is a plumbing retry, never a second "Refund issued" push). Safe to re-fire: all five reversal steps are idempotent at the data layer. Orders still unreversed past 3× the window fire a P1 alert.
- `REFUND_REVERSAL_MAX_AGE_MINUTES` (default 720 = 12h) — **recency FLOOR for the refund-reversal sweep.** Same class of guard as `STUCK_ORDER_MAX_AGE_MINUTES`, and load-bearing for the same reason: `refund_reversed_at` is NULL for every cancelled/refunded order predating the column, so without a lower bound the first tick after deploy would re-fire reversals across the entire order history. The migration additionally backfills `refund_reversed_at = updated_at` on pre-existing cancelled/refunded rows so NULL means "cancelled after the migration and genuinely unreversed"; the floor is the second line of defence, not the only one.
- `REFUND_CLAIM_STUCK_MINUTES` (default 15) — refund claims with no known outcome (#1317). `PaymentService.refund` commits its claim (the payment's `refundedAmount` raised, a `refund_initiated` payment event) on a transaction of its own BEFORE calling the provider, and resolves it with `refund_completed` (sent) or `refund_failed` (nothing sent, balance put back). A claim with neither past this window — the process died mid-refund, or the provider never gave a clear answer (`refund_indeterminate`) — means the balance counts money that may never have left. It is checked on the `refund-reversal-stuck-sweep` tick (no cron of its own: another cadence would keep the Neon compute awake) and raised as a P1 alert; the claim shows on the order page's payment-events timeline. Not resolvable automatically — with no provider refund id there is nothing to ask the provider about.
- `REFUND_CLAIM_MAX_AGE_MINUTES` (default 10080 = 7 days) — stop re-alerting on an unresolved refund claim after this long.
- `STUCK_PAYMENT_MINUTES` (default 60) — order-payment lifecycle: how long an ONLINE order may sit `status=pending` / `paymentStatus=unpaid` before the 15-min stuck-payment Inngest sweep (`order-stuck-payment-sweep`) pushes the merchant a "Payment pending — follow up" alert (deduped once per order via `Order.stuckPaymentAlertedAt`). COD orders never trigger it (no online Payment row).
- `PAYMENT_ABANDON_MINUTES` (default 30) — abandoned-checkout recovery: how long an ONLINE order may sit `status=pending` / `paymentStatus=unpaid` (with a generated gateway `paymentUrl`) before the 30-min Inngest sweep (`payment-abandonment-sweep`, **Enterprise `payment_abandonment` feature only**) stamps `Order.paymentGatewayAbandonedAt` AND pushes the store admins + super_admins a one-time "Checkout abandoned" recovery alert (via `OneSignalService.notifyAdminsOfAbandonedCheckout`, deep-linking to `/stores/:id/payment-abandonments`). The stamp dedupes the alert to exactly once per order. COD orders never match (no online Payment row). Overlaps intentionally with `STUCK_PAYMENT_MINUTES` (an Enterprise store with both enabled gets the recovery ping at 30 min and the "Payment pending — follow up" nudge at 60 min).
- `AUTO_CANCEL_UNPAID_DAYS` (default 2, matches MyFatoorah's 2-day payment-link validity) — how old a `pending` / `unpaid` order must be before the daily Inngest cron (`order-auto-cancel-unpaid`, 03:00 UTC) auto-cancels it via `OrderService.updateStatus(...,'cancelled')`. Never refunds (the order was never paid — refund effects are gated on a captured payment); the customer still gets the standard `order_cancelled` notification. **Reconciles before cancelling:** `unpaid` means "nothing ever told us it was paid", not "the money wasn't captured" — the webhook can be lost (or, for MyFatoorah, is account-level and never fires per-invoice) while the customer also never returns to the success page, so verify-on-return never runs either. Any order carrying an online-gateway payment row is therefore checked against the provider first; a `completed` answer routes into `confirmPaymentFromProviderStatus` (the same single-writer the webhook / verify-on-return / admin-refresh paths use) and the order is marked paid instead of cancelled. If the provider call throws, the order is SKIPPED, never cancelled — unknown is not unpaid. Rescues fire a P1 alert (repeated rescues mean a webhook that isn't firing); a skip-only run fires `info`.
- `TRUST_PROXY_HOPS` (optional, default `1`) — how many proxies sit in front of the API, passed to Express `app.set('trust proxy', n)`. It is a HOP COUNT and must match deployment topology exactly. **Railway only** (today) = `1`; **Cloudflare in front of Railway** = `2`. Too LOW and `req.ip` resolves to the nearest proxy, so every IP-keyed limiter (`authLimiter`, `paymentLimiter`, `writeLimiter`) collapses into one global bucket and audit logs record the proxy instead of the client. Too HIGH — or `true` — and a client can spoof `X-Forwarded-For` to forge its own address and bypass every IP-keyed limiter outright, which is **strictly worse than having none**. A non-integer or out-of-range value falls back to `1` (fail safe, never open). **Do not set `2` until `api.force-ai.co` is Cloudflare-proxied AND the Railway origin no longer accepts direct public traffic** — raising it while `*.up.railway.app` is still publicly reachable IS the spoofing hole.
- `AI_MODEL_RATES` (optional, default unset) — JSON map of model id -> per-MILLION-token price in the billing currency, e.g. `{"gemini-flash-lite-latest":{"in":0.10,"out":0.40}}`. Converts token usage into money on every `ai_usage` row (`cost_micros`), which is what makes per-store AI spend and therefore per-store margin a number instead of a token count. **There are deliberately NO built-in default prices** — provider pricing changes and differs by region/contract, and a wrong hardcoded constant produces confident, wrong margin figures that people then act on. An unconfigured model records `cost_micros = NULL`, which is deliberately DISTINCT from `0` (a genuinely free cached hit); reports must not sum them together. Malformed JSON or a malformed entry is treated as unpriced, never as free. Cost is stored in **micros** (1,000,000 micros = 1 currency unit) because a single flash-lite call is routinely a fraction of one fils and integer fils would round nearly every row to 0. Take the numbers from the provider's current pricing page and verify them — nothing in the code can validate that they are right. See `apps/api/src/lib/ai-pricing.ts`.
- `AUTO_CANCEL_RECONCILE_THROTTLE_MS` (default 250) — sleep-after-success pacing between the provider status calls the auto-cancel sweep makes. A 500-order backlog is otherwise a 500-request burst across up to 4 rate-limited providers; this throttles on success rather than discovering the limit via 429s. Only orders with a gateway payment row incur the call (COD and link-less orders skip it and are never delayed). Set to `0` to disable pacing.
- `R2_ORPHAN_SWEEP_APPLY` (default unset / report-only) — controls the weekly Inngest cron `r2-orphan-sweep` (Sunday 04:00 UTC). When **unset or any value other than `"true"`**, the sweep only **reports** orphans (count, size, sample keys) via structured logger + Telegram alert — it never deletes. Set to the literal string `"true"` to enable batch deletion of confirmed orphans (DeleteObjects ≤1000/request). Review at least one report run before enabling. Objects younger than 24 h are always skipped regardless of this flag.
- `ANSWER_ENGINE_GEMINI_MODEL` (optional, default `gemini-flash-lite-latest`) — Answer-Engine Insights (AEO/GEO citation checks): overrides which Gemini model `gemini.provider.ts` calls for the weekly citation-scan cron. Flash-lite is NOT confirmed to support grounded web search (`googleSearchRetrieval`) — the adapter fails safe to `grounded: false` (no citations, dashboard shows the "based on model knowledge" caveat) rather than throwing when grounding metadata is absent. Point this at a confirmed-grounding model if flash-lite proves ungrounded in production (live-smoke gate, see the Plan 8A notes).
- `ANSWER_ENGINE_PERPLEXITY_MODEL` (optional, default `sonar`) / `ANSWER_ENGINE_OPENAI_MODEL` (optional, default `gpt-4o-mini`) — model overrides for the two opt-in paid answer-engine adapters, same override pattern as `ANSWER_ENGINE_GEMINI_MODEL`.
- `ANSWER_ENGINE_PERPLEXITY_DAILY_CAP` / `ANSWER_ENGINE_OPENAI_DAILY_CAP` (optional, default 200 each) — platform-wide daily call cap per PAID answer-engine provider (Perplexity/OpenAI), counted across ALL stores via `budget.ts`'s `isPaidEngineOverBudget` (aggregates `aiUsage` rows for `answer_engine_<engine>` since UTC midnight, counted with `withRlsBypass` so it's a true platform-wide total even when the citation-scan cron runs inside a single store's tenant context). Gemini is uncapped by this pair — it's covered by the existing platform-wide `AI_DAILY_REQUEST_CAP`/`AI_MONTHLY_REQUEST_CAP` instead.
- Perplexity/OpenAI answer-engine API keys are **NOT env vars** — they're DB-config, encrypted at rest in `AnswerEngineProviderConfig`, set via the super-admin UI (`GET`/`PUT /admin/answer-engine/providers[/:engine]`, MFA-gated). Only Gemini uses an env-var key (`GOOGLE_GENERATIVE_AI_KEY`, shared with the rest of the platform's AI features) since it runs on Force AI's own platform key rather than a per-provider merchant-independent credential.
- `GSC_SERVICE_ACCOUNT_JSON` (optional, **Force-managed platform secret** — a single Google Cloud service-account key JSON, `{"client_email": "...", "private_key": "..."}`, never a per-merchant credential) — feeds the daily Google Search Console ingestion cron (Plan 8B; `gsc-client.ts`'s `isGscConfigured()`/`querySearchAnalytics`, `gsc-ingest.service.ts`'s `runGscIngest`). **Dormant until set**: `isGscConfigured()` returns false when unset/malformed, the cron logs a fixed dormancy message and no-ops (zero DB writes, zero Google API calls), and the answer-engine dashboard's GSC section renders a "Google Search Console not connected" empty state (zero `GscDailyMetric` rows for every store). Go-live steps (Ahmad, one-time): (1) create a Force Google Cloud service account, (2) add its `client_email` as a **read-only user** on every Force-owned GSC property covering merchant domains (Search Console → Settings → Users and permissions), (3) set this var in the API env. Never logged raw (the parser only logs a fixed "missing/invalid" message, never the JSON body) — see `docs/runbooks/google-search-console-indexing.md` for the full runbook pointer.

- `STOREFRONT_REVALIDATE_URL` / `REVALIDATE_SECRET` (**two-sided contract — see the matching entry under Web**) — after any store, product, variant or category write the API fires a fire-and-forget `POST <STOREFRONT_REVALIDATE_URL>/api/revalidate` carrying the cache tags to purge (`store-domain:*`, `store-slug:*`, `products:<storeId>`, `categories:<storeId>`). Clearing the API's own Redis cache is only half the job: the storefront Worker holds the API's RESPONSE in Next's data cache, so without this purge a merchant's save is invisible until that TTL expires. **`REVALIDATE_SECRET` must be set to the SAME value on the storefront Worker.** If it is missing there, `/api/revalidate` answers 503, every purge is dropped, and the API side looks healthy — see the Web entry for the 2026-09-02 incident.

## Web (Cloudflare Worker `force-web-cf-preview`)

- `STOREFRONT_TENANT_ROUTING` — **new (2026-07-12), dark-launched, unset/`false` in every environment today — do not set it anywhere yet.** Server-only (read inside `middleware.ts`'s request handler, never at module scope — Workers don't reliably expose `process.env` at module-eval time). Gates the tenant-cacheable storefront routing rewrite (`docs/plans/2026-07-12-tenant-cacheable-routing.md`): when the literal string `"true"`, anonymous/non-personalized storefront routes (home, PLP, PDP, categories, blog, about/faq/how-to-guides/contact/locations, privacy/terms/returns/shipping) are internally rewritten to `/tenant-store/[tenant]/[locale]/...` so their store/locale resolve from route params instead of `headers()`/`cookies()`, making them eligible for Next's Full Route Cache. Any other value (including unset) is completely inert — every route falls through to today's header-based resolution, byte-for-byte unchanged. Always bypassed for the admin page-builder live-preview iframe (`?_preview=`) regardless of this flag. Personalized routes (cart, checkout, account, auth, wishlist, search, compare, review) are never affected by this flag. Flipping it on (CF preview only, then a canary) is Phase 2/3 work, not part of the Phase 1 PR that introduced it.
- `REVALIDATE_SECRET` — **REQUIRED for on-demand cache purging; the API half is useless without it.** Shared secret for `POST /api/revalidate` (`apps/web/src/app/api/revalidate/route.ts`), which must equal the API's `REVALIDATE_SECRET`. The route refuses with **503 `REVALIDATE_SECRET not configured`** when unset — it never silently accepts.
  **Incident 2026-09-02:** the API had both revalidate vars and the storefront Worker had none, so EVERY purge since the feature shipped was rejected 503 and silently dropped (API-side logging was warn-level only). Storefront freshness had quietly fallen back to the 60s data-cache TTL, which merchants experienced as "I save, nothing changes, so I save again" — the repeat saves did nothing; the TTL simply expired. Verify from outside with a deliberately wrong secret: `curl -X POST https://<storefront>/api/revalidate -H 'Content-Type: application/json' -d '{"secret":"wrong","tags":["probe"]}'` — **401 means configured, 503 means dead.** A rejected purge now logs at error level (Sentry-visible) rather than warn.
- `NEXT_PUBLIC_API_URL` — Railway API URL
- `NEXT_PUBLIC_ONESIGNAL_APP_ID` — OneSignal app ID for storefront broadcasts (script-tag init via `OneSignalStorefrontInit.tsx`). Storefront silently no-ops when missing.
- `NEXT_PUBLIC_VAPID_PUBLIC_KEY` — VAPID public key for the standards-based Web Push subscription path.
- `NEXT_PUBLIC_SENTRY_DSN_WEB` — client-side Sentry DSN. Initialized in `apps/web/instrumentation-client.ts` (the Next 15.3+/Sentry v10 client hook). NOTE: this REPLACED the old `sentry.client.config.ts`, which never loaded because `next.config.js` wasn't wrapped in `withSentryConfig` — browser Sentry was silently dead until 2026-06-25. Server-side Sentry (`instrumentation.ts` → `sentry.server.config.ts`) is OFF on the Cloudflare target; **`next.config.js` is now wrapped in `withSentryConfig` (fixed 2026-07-02, audit H2)**.
- **Cloudflare SSR/RSC Sentry (web only, added 2026-07-02):** `apps/web/sentry-worker-entry.ts` wraps the OpenNext-generated Worker fetch handler with `@sentry/cloudflare`'s `Sentry.withSentry(...)` so SSR/RSC errors ARE captured on the CF target (the standard `@sentry/nextjs` server SDK still can't run there). `apps/web/wrangler.jsonc` `main` points at this custom entry instead of the raw `.open-next/worker.js`, and `compatibility_date` was bumped to `2025-08-16` (Sentry's Cloudflare SDK requires it for `https.request`). The DSN reaches the Worker as a runtime var named **`SENTRY_DSN`** (distinct from the build-time `NEXT_PUBLIC_SENTRY_DSN_WEB`) — `cf-deploy.yml`'s "Deploy worker" step passes it via `wrangler deploy --var SENTRY_DSN:<value>`, reusing the SAME `NEXT_PUBLIC_SENTRY_DSN_WEB` GitHub repo variable (the DSN isn't a secret — it's already public in the client bundle), and omits the flag entirely when unset so preview/unconfigured deploys still build and serve cleanly. **`apps/admin` and `apps/orders` do NOT have this wiring yet** — same pattern needs repeating there as a follow-up (admin has `instrumentation.ts` + `NEXT_PUBLIC_SENTRY_DSN_ADMIN` already; orders has client Sentry only).
- **Cloudflare deploy build env**: the CF Workers build (`cf-deploy.yml`) reads all `NEXT_PUBLIC_*` from GitHub repo **variables** (public, build-time inlined) — these GitHub repo variables are the canonical source (the old Vercel envs are decommissioned). See `docs/migration/cloudflare-ci-deploy.md`.

## Sentry build-time config (source maps + releases, added 2026-07-02, audit H2) — shared across web/admin/orders

- `SENTRY_AUTH_TOKEN` — enables the Sentry webpack/Turbopack plugin's source-map upload + release creation during `next build`. **Optional and safe to omit**: when unset, the plugin logs a warning and skips the upload — it does NOT fail the build. This is why local dev, CI's `npm run build` step, and the Cloudflare Workers build (`cf-deploy.yml` doesn't set it) are all unaffected; only environments where this is explicitly configured (e.g. as a CF Workers Builds env var) get uploaded source maps + linked releases.
- `SENTRY_ORG` / `SENTRY_PROJECT` — Sentry org/project slugs for the upload. Optional; the plugin can often infer them from the auth token, but set explicitly for clarity.
- Set these in the CF Workers Builds env (web/admin/orders) to actually get readable stack traces in Sentry. Not currently set anywhere — until they are, behavior is unchanged (no source maps uploaded, same as always).

## Integration test suite

- `TEST_API_URL` (default `http://localhost:4000`) — the ONLY knob for which API the integration suite talks to. Accepts an origin or an already-versioned base (`…/api/v1`); `tests/helpers/api-base.ts` normalizes both to one `{ API_ORIGIN, API_BASE }` pair, so no caller can produce `/api/v1/api/v1`. A bare host (`localhost:4000`, `api.force-ai.co`) is rejected at load with a named error rather than parsed into the truthy string origin `"null"`.
- `TEST_API_BASE` — older alias, still honoured. Same normalization.
- **The suite deliberately does NOT read `API_URL` or `API_HOST`** (2026-09-09). Both are server variables: `API_URL` is an ORIGIN (`config.apiUrl`) and `API_HOST` is a BARE HOSTNAME (`config.host`), and `apps/api/src/config/index.ts` runs `dotenv.config()` at import time — before any const in a test file — so a root `.env` copied from `.env.example` would silently win over the test's own default. Borrowing `API_URL` cost two ways: every request lost its `/api/v1` prefix and 404'd, and on a machine holding deployed values (`API_URL=https://api.force-ai.co`) a local `npm run test:integration` would have POSTed `/auth/register` against production. Never point the suite at a variable whose production value is a real, reachable API.

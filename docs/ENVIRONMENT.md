## Deploy (GitHub Actions → Cloudflare Workers)

The API is the Cloudflare Worker `ebda-api` (`api.ebda.app`), deployed only by `.github/workflows/cf-api-deploy.yml` (`workflow_dispatch`); admin/web/orders/marketing deploy from their own `cf-*-deploy.yml` on push to `main`. There is no Railway deploy for this repo (the Railway section that used to sit here was inherited from Ebda Store).

- `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` (repo **secrets**) — used by every `cf-*-deploy.yml`. Required scope for `cf-api-deploy.yml` with the Workers AI binding (search P1): the token's existing **Workers Scripts Edit** ("Editor" on the Worker) is enough — Cloudflare: "To deploy a Worker that has bindings … you need Editor access to the Worker. You do not need separate permissions on the bound resources" (developers.cloudflare.com/workers/authorization, read 2026-10-16); no Workers AI permission is needed to DEPLOY the binding, and the Worker's AI calls are authorised by the binding itself, not the token. Not yet exercised with the `ai` line: if a deploy is refused, `wrangler deploy` fails AFTER the expand-only migrations and the previous version keeps serving; check the first `cf-api-deploy` run after PR 3.
- `EBDA_KV_CACHE_ID`, `EBDA_PLATFORM_D1_ID` (repo **variables**; `EBDA_HYPERDRIVE_ID` is retired, NEON-ZERO N-17: the Worker has no Postgres) — substituted into `.wrangler.deploy.jsonc` by `scripts/ebda-cf-api-config.mjs`; `apps/api/wrangler.jsonc` keeps placeholder zeros for local dev.
- `NEXT_PUBLIC_IMAGE_VARIANTS` (ebda-web **build** variable, optional, Ruling PREMIUM-2) — exactly `1` makes the Cloudflare build pick the WebP widths (`.w480|960|1600.webp`) the API wrote beside each upload (`apps/web/src/lib/image-loader.ts`, a rename, no request-time transformation) and emit a real `srcset`. Unset = the raw upload, as before. Set it ONLY after `EBDA_IMAGES_BINDING=true` is deployed and `POST /admin/images/backfill-variants` has covered every store (`failed` 0, `nextCursor` null); a srcset to a variant that does not exist is a broken image. Watch `IMAGE_VARIANTS_FAILED` in the log drain.
- `EBDA_IMAGES_BINDING` (repo **variable**, optional) — exactly `true` adds the Cloudflare Images binding (`"images": { "binding": "IMAGES" }`) to `.wrangler.deploy.jsonc` (`scripts/ebda-cf-api-config.mjs`), so PWA icons are resized per size and the maskable icon padded (Ruling D1016-ICONS-1). Unset/anything else = no binding: icons are stored as uploaded under every size (FU46-8 fallback). Set it only after Images is enabled on the Whisky account (69188202…, steps in Ruling D1016-ICONS-2). The workerd pre-deploy smoke strips the binding (`stripImagesBinding`). After enabling, verify both `favicon16` (16×16) and `maskableIcon` (512×512, solid border) from a fresh icon upload: a binding that ignores `border` returns a 410px maskable icon, and the whole set then falls back to pass-through on every upload which is now loud: a structured warn with `code: PWA_ICON_RESIZE_FALLBACK` (match it in the log drain), a per-day counter `ratelimit:metric:pwa-icon-resize-fallback:<YYYY-MM-DD>`, and one platform P1 per day (`source: pwa.icon-resize-fallback`). The resize has a 10s deadline (`IMAGES_DEADLINE_MS`). Every `ai` line in `wrangler.jsonc` (top level and each `env.*`) gets the binding.
- Runtime secrets of the API Worker are set with `wrangler secret put <NAME> --name ebda-api` (list with `wrangler secret list --name ebda-api`); the variables below marked "API" live there.

## API (Cloudflare Worker `ebda-api` — `wrangler secret`)

Required in production (app crashes without these):

- `DATABASE_URL` — Neon PostgreSQL connection string
- `DIRECT_URL` — Neon direct (non-pooled) URL for migrations / interactive transactions
- `DB_CONNECTION_LIMIT` (default `15`) — Prisma pool size (`connection_limit`, `packages/database/src/index.ts`). The API also derives the process-wide cap on pooled CONNECTIONS held by post-response deferred work from it (`DEFERRED_TX_GLOBAL_LIMIT` = a third of it, min 1 — `apps/api/src/lib/after-tenant-commit.ts`), so raising the pool raises that cap with it. The cap counts connections, not tasks: a task that opens a second transaction inside its tenant one (`r2-cleanup.deleteOrphan` → `withRlsBypass`) declares `connections: 2` and takes two slots (issue 2250).
- `JWT_SECRET` — min 32 chars, no placeholder values. Signs sessions only: rotating it signs everyone out and nothing else. The long-lived links in SMS and email (SMS opt-out, campaign unsubscribe, review requests) are no longer keyed on it (issue 2424). Campaign unsubscribe and review links signed before that change still verify against it until the next rotation.
- `ENCRYPTION_KEY` — min 32 chars. Besides encrypting stored secrets, it is the root of the purpose-bound HKDF keys in `apps/api/src/lib/derived-secret.ts` that MAC the SMS opt-out link and, unless their dedicated secrets are set, the campaign unsubscribe and review links (issue 2424). No new variable is needed for them. Rotating `ENCRYPTION_KEY` is already a re-encryption event, and it also voids every one of those links already sent.
- `BARCODE_KEY_SECRET` (optional; unset → a key HKDF-derived from `ENCRYPTION_KEY`, label `ebda:barcode-key:v1`; never `JWT_SECRET`) — HMAC key that names the email-barcode PNGs in R2 (`stores/<storeId>/barcodes/<hmac>.png`). Changing it only re-renders new emails under new names (old objects expire after 400 days); rotating `JWT_SECRET` changes nothing.
- `REVIEW_TOKEN_SECRET` (optional; unset → a key derived from `ENCRYPTION_KEY`, issue 2424 — it used to fall back to `JWT_SECRET`) — HMAC key for the review-request link (`/review/<order>/<product>?token=`, 90-day expiry). With it unset, links signed before issue 2424 still verify against `JWT_SECRET`.
- `ORDER_VIEW_SECRET` (optional; unset → a key derived from `ENCRYPTION_KEY`, label `ebda:order-view-mac:v1`, no deploy step) — HMAC key for the guest order view token returned by `POST /public/orders` (30-day expiry) that unlocks the address and phone on `GET /public/orders/:id` (SEC-15, `docs/security/sec-hardening-3-exposure.md`). Set it only to rotate the key independently.
- `NEXT_PUBLIC_MEDIA_ORIGIN` (storefront worker, optional) — an extra https media origin the OG card renderer may fetch logos from, besides `media.ebda.app` and the host of `STORAGE_PUBLIC_URL` (set one of the two on the web worker for the OG card to use a specific pub-id.r2.dev bucket; SEC-6).
- `CF_WORKERS_DEV_SUBDOMAIN` (optional) — our Cloudflare workers.dev account subdomain; CORS then trusts `ebda-{web,admin,orders}.<subdomain>.workers.dev` preview origins (`apps/api/src/lib/cors-cache.ts`). Unset = no preview origin is trusted.
- `BUILD_COMMIT_SHA` (optional, build-time) — the commit the image was built from, baked by `Dockerfile.api` from the `GIT_COMMIT_SHA` build arg. Surfaced on `/health` as `commit` so a deploy can be verified as **live** rather than merely green: a 200 is returned identically by the container still serving the previous release. Unset → `/health` reports `commit: null`, which means _unknown_, not _not deployed_. To populate it under Railway (which builds the image itself), set `GIT_COMMIT_SHA` as a service variable so it reaches the Docker build.
- **RETIRED (Railway, kept until the Cloudflare cutover completes)** `RAILWAY_GIT_COMMIT_SHA` (read-only, platform) — **injected at runtime; verified 2026-09-03.** The first deploy carrying `/health`'s build identity reported the correct commit with no build arg and no service variable set, so this is what populates `commit` today. It appears in NEITHER listing — not the 85 the CLI reports, nor the 8 the dashboard shows as "added by Railway" — because both describe what is _configured_ on the service, which is not the container's environment. Do not conclude a platform variable is absent from either list alone.
- **RETIRED (Railway, kept until the Cloudflare cutover completes)** `RAILWAY_DEPLOYMENT_ID` (read-only, platform) — surfaced on `/health` as `deploymentId`. **Injected at runtime; verified 2026-09-03**, which also clears the deploy-identity probe chain — a chain falling through would have looked identical from outside. Also absent from both listings, for the same reason as above.
- `NODE_ENV=production`
- `ALLOW_BYPASSRLS_ROLE` — **Node shell only; an explicit escape hatch inherited from Ebda Store (whose prod runs as `neondb_owner`).** Ebda's runtime role is `ebda_app` (NOBYPASSRLS, Ruling R-EBDA-002), so this should stay UNSET. The Node boot guard (`apps/api/src/lib/database-role-guard.ts`, awaited in `apps/api/src/index.ts` BEFORE `listen()` since FIX-003, 2026-10-07) queries `pg_roles.rolbypassrls` and `rolsuper` on every boot and, in production, `process.exit(1)`s on a bypassing role unless this is the literal string `"true"`; with it set, every boot logs an `error`-level `[SECURITY] ALLOW_BYPASSRLS_ROLE=true — serving as <role> …` line. The hatch never excuses an UNVERIFIABLE role: in production a failed role query or a missing `pg_roles` row exits non-zero (it used to log and keep serving — fail open). The Workers shell ignores this variable: `cf/database-role-guard.ts` refuses any bypassing or unverifiable role per isolate. Every Node boot logs `[SECURITY] DB role check: current_user=<role> rolbypassrls=<bool> rolsuper=<bool>` (info level, all environments) — the line CI's integration job greps to fail unless it reads `current_user=ebda_app rolbypassrls=false rolsuper=false` (#1940).

Optional (feature degrades gracefully if missing):

- `JWT_EXPIRES_IN` (default `30m`) — access-token JWT lifetime. Short by design so refresh-token rotation has security value; the session length is governed by the refresh token, not this. Pin a different value here only with a deliberate reason.
- `REFRESH_TOKEN_EXPIRES_IN` (default `365d`) — rotating refresh-token lifetime = the practical "always signed in" window. Lower it to shorten the max session age; never below the 30-day floor Ahmad wants for the admin PWA.
- `REQUEST_COMMIT_TIMEOUT_MS` (optional, default `10000`) — upper bound on how long a buffered store-scoped response waits for its request transaction's COMMIT/ROLLBACK (`middleware/request-transaction.ts`, #1608). On expiry a would-be 2xx is answered 503 `COMMIT_TIMEOUT` (outcome unknown), a 5xx goes out as-is, and a P1 Telegram alert fires (`request-transaction.commit_timeout`). Every settled response carries `Server-Timing: request-tx;dur=<ms>`.
- `REDIS_URL` — Railway internal (`redis.railway.internal:6379`); falls back to `localhost:6379` in dev
- `RATE_LIMIT_SHARED` (default unset = shared) — set to `0` to put every API rate limiter back on per-process counting while Redis stays connected (`apps/api/src/middleware/security.ts` `rateLimitSharedEnabled`). The kill switch for the #1862 shared-budget tightening (issue 2230): a shared budget is N, a per-process one is N × replicas and resets on deploy. Read per request; a Railway variable change restarts the service.
- `RATE_LIMIT_429_ALERT_PER_MIN` (default `300`) — a limiter prefix (`rl:<name>:`) that answers at least this many 429s in one minute raises a P1 `rate-limit.429-spike` alert. Every minute with any 429 or any per-process fallback also logs one `[rate-limit] 429s by limiter in the last window` line with counts per limiter (`apps/api/src/lib/rate-limit-telemetry.ts`, issue 2216 / issue 1963).
- Launch rate limits (LAUNCH-RL, not env-driven; edit `middleware/security.ts`): `authIpFailureLimiter` 60 failed sign-ins per 15 min per IP, `authIpAllLimiter` 30 per 15 min per IP (register, forgot-password, resend-verification), `storeMissLimiter` 20 unknown-store 404s per min per IP, `publicSearchLimiter` 60 searches or typeahead calls per min per IP. All exact (AuthState DO), 429 `RATE_LIMITED` with `Retry-After` and bilingual `details`. `storeMissLimiter` reads its counter before the handler and counts only after a 404 was sent, so a successful storefront call never spends the miss budget and its `RateLimit-Remaining` is the misses left before the response (Ruling LAUNCH-RL-MISS-1); a store id in a public path that is in no directory is refused 404 `STORE_NOT_FOUND` behind these limiters, not in front of them, so it is limited and counted like an unknown slug (Ruling LAUNCH-RL-MISS-4); every 404 is a miss except a dead product or blog link (`GET /public/products/:slugOrId`, `GET /public/:storeId/blog/:slug`) inside a store the resolver verified from `X-Store-ID` or the host, with the path store id equal to it; every other 404, on any store, is counted (`middleware/catalogue-miss.ts`, Ruling LAUNCH-RL-MISS-3); the failures-only sign-in limiters count up front and give the hit back after a success, a call the Worker keeps alive with `waitUntil` (Ruling LAUNCH-RL-MISS-2). The identity service (`apps/accounts`) throttles on D1 (`src/throttle.ts`).
- `ONESIGNAL_APP_ID` / `ONESIGNAL_REST_API_KEY` — admin order alerts (staff devices) only. Merchant storefront broadcasts no longer use OneSignal (see `VAPID_*`).
- `ONESIGNAL_ADMIN_APP_ID` / `ONESIGNAL_ADMIN_REST_API_KEY` — optional separate OneSignal app for merchant-app alerts (its Site URL / origin must be `https://store.ebda.app`, Ruling HOST-STORE-1); falls back to the public app id/key if unset.
- `ONESIGNAL_ORDERS_APP_ID` / `ONESIGNAL_ORDERS_REST_API_KEY` — separate OneSignal app for the **Orders PWA** new-order alerts (origin `orders.ebda.app`). NO fallback (origin mismatch would silently fail) — `notifyOrdersAppOfOrder` skips the send when unset. Targets staff devices by the `store_id` tag the Orders app sets at enable time. `ORDERS_URL` is the deep-link base.
- `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` — PLATFORM secrets on the API Worker (never a merchant task): the ONE push path for shoppers (event notifications AND merchant broadcasts, `pushService`). Without them, `GET /admin/stores/:id/push/status` answers `available:false`, the broadcast form is disabled with a plain "not available yet" note, and `POST .../push/broadcast` answers `503 PUSH_NOT_CONFIGURED`. The storefront build also needs `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (same public key).
- `POSTHOG_PERSONAL_API_KEY` / `POSTHOG_PROJECT_ID` / `POSTHOG_HOST` (default `https://eu.posthog.com`) — **privacy gap closure, 2026-07-11.** Enables server-side Right-to-Erasure propagation: `AuthService.eraseAccount` fires `account/erased`, and `privacy-propagation.service.ts`'s `deletePostHogPerson` deletes the customer's PostHog person. Distinct from the storefront's public `NEXT_PUBLIC_POSTHOG_KEY` — this needs person-level write scope and must never reach the browser. "Degrades gracefully" here means the API still boots and every OTHER feature works fine when unset. **Corrected 2026-09-23:** unset is now a documented WARN + no-op, NOT a thrown `PropagationNotConfiguredError`. The 2026-09-22 fail-loud was unconditional, and since nothing in the repo calls `posthog.identify(userId)` there is no person keyed by our `userId` to delete — so it dead-lettered `account-erased-propagation` and raised a P1 alert on EVERY erasure (up to `USER_ANONYMIZE_BATCH_CAP`=200 per monthly retention-cron run) for a subject that provably cannot exist. The same function already returns normally when the key IS set and the distinct_id matches nothing, so the unconfigured branch was strictly noisier than a stricter one. Set **`POSTHOG_ERASURE_REQUIRED=true`** (alongside the credentials) once `identify()` is wired and the unconfigured case fails loud again. Set this in production before relying on PostHog erasure compliance; see `docs/privacy/data-map.md` for why this also needs `posthog.identify(userId)` added at login before it's fully useful.
- `SENTRY_DSN` — error monitoring; safe to omit in dev.
- `OTEL_EXPORTER_OTLP_ENDPOINT` — OpenTelemetry distributed tracing. **Opt-in + fail-open**: tracing only activates when this is set to an OTLP/HTTP collector base URL (e.g. Grafana Tempo / Honeycomb / Jaeger — the bootstrap appends `/v1/traces`). With it unset, or if init throws, the API boots normally un-instrumented (tracing can never take the API down). Bootstrap is `apps/api/src/tracing.ts`, imported FIRST in `index.ts` (auto-instruments http/express/pg/ioredis before they load). Companions: `OTEL_EXPORTER_OTLP_HEADERS` (`k=v,k2=v2` auth headers), `OTEL_SERVICE_NAME` (default `ebda-api`), `OTEL_TRACES_SAMPLER_ARG` (head sample ratio 0–1; default 0.1 prod / 1.0 otherwise).
- `SUITE_BUYER_KEY_SECRET` — **Worker secret, >= 32 chars, the SAME value in the Ebda Chat Worker.** Keys every `buyerKey` = HMAC-SHA256(secret, E.164 phone) (Store <-> WhatsApp contract section 6; CI-1). The Worker refuses to boot when the `WA_EVENTS_QUEUE` binding exists and this is missing (`lib/wa/config.ts`); `cf-api-deploy` checks it exists. The Worker also refuses to boot when it is set but shorter than 32 chars, the bridge recomputes `buyerKey` from the phone with it (`createCheckoutLink`, `createOrderFromChat`) and an erasure throws on a short value (Ruling WA-BRIDGE-BIND-1). Rotating it changes every key (bump `BUYER_KEY_VERSION`). - `ORDER_STATUS_LINK_SECRET` — **Worker secret, >= 32 chars, required.** Signs the 14-day, single-order link in the COD WhatsApp message (`o/<token>`, `lib/order-status-link-token.ts`; Ruling WA-COD-V2-2). The Worker refuses to boot when the `WA_EVENTS_QUEUE` binding exists and this is missing or shorter than 32 chars (`assertWhatsAppLinkConfig`), and `cf-api-deploy` checks it exists (`scripts/ci/api-required-secrets.json`). Rotating it kills links already sent. `COD_CONFIRMATION_HOURS` (var, default 24) is how long a COD customer has to answer the WhatsApp confirmation.
- **Buyer-key backfill (Ruling WA-BRIDGE-BIND-3):** `POST /admin/wa/buyer-key-backfill` (super_admin, dry-run by default, resumable) and `scripts/ops/backfill-buyer-keys.mjs` stamp `orders.buyer_key` on orders that have a phone but no key, using `SUITE_BUYER_KEY_SECRET` (503 if unset). Run it (dry run, then `--apply`) BEFORE setting `WA_BRIDGE_REQUIRE_BUYER_PROOF=1`.
- **Sale-journal backfill:** `POST /admin/accounting/sale-journal-backfill` (super_admin + MFA, dry-run by default, resumable via `cursor`, optional `storeId`) posts the missing GL sale entry (`money.journalSale`, idempotent on store+source+source_id) for PAID, non-cancelled/refunded orders with no `order` journal entry. Journal only: it never re-sends `order/created` (no email/push). Needed once for COD orders marked paid before `inngest.send` was kept alive past the response (Amelia ORD-TOXU0G-7LODS). Dry run first and read `stores[].orderIds`, then `{"dryRun":false}`; Per store it applies the plan gate `accounting.basic` and the store's accounting setting (a store failing either is skipped and counted by reason). - `WA_BRIDGE_REQUIRE_BUYER_PROOF` — optional Worker var, `1` = strict. Every Chat bridge method that names a buyer must prove it: the key-only methods (`getCustomerAddresses`, `saveCustomerAddress`, `getOrderStatus`, `listCustomerOrders`) need `phoneE164` (the Store rebuilds `buyerKey` from it), and the order methods (`getPaymentLink`, `recordCodOutcome`, `attachPaymentProof`) need `buyerKey` equal to the key stored on the order. Unset/other = relaxed: a proof that IS sent is always checked, one that is missing is allowed (so Ebda Chat's current call shapes keep working). Flip to `1` once ebda-whatsapp sends the proofs (Ruling WA-BRIDGE-BIND-2). Order (do not reorder; ebda-whatsapp pr 67): Store deployed -> `buyer-key-backfill` dry run then `--apply` -> Chat deployed (sends proofs) -> set `1` -> live check that a call without the proof is refused. `getCustomerProfile` (Ruling CHAT-AGENT-1) is always strict (the phone is the proof) and does not read this var. **Ruling WA-BRIDGE-BIND-4 supersedes the relaxed default above: secure by default.** `apps/api/wrangler.jsonc` commits `"1"`, and the code (`lib/wa/bridge/proof-policy.ts`) is strict whenever the var is unset or anything but the exact string `0`; `0` is the only (deliberate) opt-out.
- **Outbound email** (`apps/api/src/services/mail-transport.ts`): Cloudflare Email Service through the Workers `send_email` binding `EMAIL` (sender domain `ebda.app`), no API key and no env var; Resend was removed after the switch was verified live. Merchant mail is `<prefix>.<storeSlug>@ebda.app` (prefix from an allowlist: orders, receipts, hello, info, support) with the merchant as Reply-To; platform account mail is `Ebda AI Studio <no-reply@ebda.app>`, store product mail `Ebda Store <no-reply@ebda.app>` (BRAND-NAME-1). Suppression (hard bounce, spam complaint) is Cloudflare's account list and surfaces as `E_RECIPIENT_SUPPRESSED`, a permanent failure. No idempotency key: a step that dies between `send()` and its own "sent" mark can send that one email twice (residual). 5 MiB per message; 3,000 sends/month included, then $0.35 per 1,000; a new account starts at 200/day. `SMTP_*` vars are unused legacy.
- `JOBS_CF_ALARMS` — which per-store schedules run as `StoreSchedule` Durable Object alarms instead of one global Cron Trigger run (G5, Ruling G5-2, `docs/cf/jobs-map.md`). A `wrangler.jsonc` var: comma list of alarm-ready function ids, or `all` (the value in production); empty = every schedule stays a cron. Alarms are armed ONLY for stores served by their Durable Object (see `JOBS_ON_DO`), so `all` arms nothing while every store is on Postgres; Postgres stores keep the global cron (Ruling CF-JOBS-1). Rollback = empty it (the hourly sync clears the entries).
- `STORE_CREATE_ON_DO` — `1` = a new store (`StoreService.create`, provisioning, self-serve onboarding) is created on D1 `stores` (`storage_backend='do'`) + its StoreDO with NO Postgres row (`apps/api/src/lib/store-create-do.ts`, Ruling NZ-D22); needs `PLATFORM_DB` and `STORE_DO` bound. A `wrangler.jsonc` var, `"1"` since the production cutover (Ruling NZ-JOBS-FLIP-1; N-6 store-access and N-10 billing readers serve a store with no Postgres row). `""` (off) = the unchanged Postgres create, which no longer exists on the Worker (no Postgres). Once every `platform_cutover.*` marker is set and the Worker has no Hyperdrive binding, an unset value is reported loudly (Ruling NZ-PG-9): `GET /health` carries `store_create: "misconfigured"` and the `*/15` cron job `store-create-config` raises a P1 (`api.store_create_on_do_unset`, at most once per 6 hours per isolate).
- `JOBS_ON_DO` — `1` = background jobs follow each store's backend flag (`STORE_DO_ENABLED_IDS`): a DO store gets its alarms, its not-yet-ported jobs are REFUSED with an alert, and cron sweeps skip it (`apps/api/src/lib/jobs/do-guard.ts`, `docs/cf/jobs-on-do.md`). A `wrangler.jsonc` var, `"1"` since the production cutover (Ruling NZ-JOBS-FLIP-1). Unset/`""` = every store is a Postgres store for jobs, which the Worker can no longer serve.
- **Customer Intelligence capture (CI-1) bindings** (`apps/api/wrangler.jsonc`, no new secret): Queue `ebda-ci-events` (+ `-dlq`) as `CI_EVENTS_QUEUE`, private R2 bucket `ebda-ci` as `CI_BUCKET`, Analytics Engine dataset `ebda_commerce_outcomes` as `CI_OUTCOMES`. `wrangler deploy` does NOT create the bucket or the queues: run `bash scripts/ops/ci-capture-setup.sh` once first (idempotent; also writes the 24-month lifecycle on `outcomes/`). With `CI_EVENTS_QUEUE` bound the Worker refuses to boot without `CI_BUCKET`, `CI_OUTCOMES` and `SUITE_BUYER_KEY_SECRET` (`lib/ci/config.ts`). Plan: `docs/plans/done/2026-10-25-ci1-capture-impl.md`.
- `GOOGLE_GENERATIVE_AI_KEY` — Gemini AI features (translate, SEO, categorize). When missing, AI routes return a config error.
- `GEMINI_API_KEY`, `GEMINI_API_KEY_2` … `GEMINI_API_KEY_20` — **key failover** (RULINGS GEMINI-FAILOVER-1). Use keys from SEPARATE Google Cloud projects (separate quotas). Order: `GOOGLE_GENERATIVE_AI_KEY`, `GEMINI_API_KEY`, `_2`, `_3`…; every Gemini call (SDK + answer-engine REST) retries the same request with the next key on 429/RESOURCE_EXHAUSTED and benches the exhausted key in-memory until Retry-After / next UTC day / 60 s. - `TRUST_PROXY_HOPS` (optional, default `1`) — how many proxies sit in front of the API, passed to Express `app.set('trust proxy', n)`. Too HIGH — or `true` — and a client can spoof `X-Forwarded-For` to forge its own address and bypass every IP-keyed limiter outright, which is **strictly worse than having none**. A non-integer or out-of-range value falls back to `1` (fail safe, never open). **Do not set `2` until `api.ebda.app` is Cloudflare-proxied AND the Railway origin no longer accepts direct public traffic** — raising it while `*.up.railway.app` is still publicly reachable IS the spoofing hole.
- `AI_MODEL_RATES` (optional, default unset) — JSON map of model id -> per-MILLION-token price in the billing currency, e.g. `{"gemini-flash-lite-latest":{"in":0.10,"out":0.40}}`. Converts token usage into money on every `ai_usage` row (`cost_micros`), which is what makes per-store AI spend and therefore per-store margin a number instead of a token count. **There are deliberately NO built-in default prices** — provider pricing changes and differs by region/contract, and a wrong hardcoded constant produces confident, wrong margin figures that people then act on. An unconfigured model records `cost_micros = NULL`, which is deliberately DISTINCT from `0` (a genuinely free cached hit); reports must not sum them together. Malformed JSON or a malformed entry is treated as unpriced, never as free. Cost is stored in **micros** (1,000,000 micros = 1 currency unit) because a single flash-lite call is routinely a fraction of one piastre and integer piastres would round nearly every row to 0. Take the numbers from the provider's current pricing page and verify them — nothing in the code can validate that they are right. See `apps/api/src/lib/ai-pricing.ts`.

### Semantic search (Workers AI embeddings, search program P1)

The API Worker has a Workers AI binding, `"ai": { "binding": "AI" }` in `apps/api/wrangler.jsonc` (no id, no secret; billed per input token to the account it deploys to, the Whisky account `69188202…`). AI bindings always run remotely, also under `wrangler dev --local`, and a plain `wrangler dev` refuses to start without a Cloudflare login ("Failed to start the remote proxy session", measured with wrangler 4.116). So local dev boots a copy of the config without the binding: `npm run cf:dev -w apps/api` and `apps/api/scripts/stage1-exit-run.sh` write `apps/api/.wrangler.local.jsonc` (`scripts/cf-api-local-config.mjs`, gitignored) and the workerd smoke writes `.wrangler.smoke.jsonc`; both log `embedding provider: none; semantic search OFF`. `npm run cf:dev:ai -w apps/api` keeps the binding for someone logged in to the Whisky account (real, billed calls).

**Boot check (fail loud):** both shells (`worker.ts` per isolate, `index.ts` before `listen`) run `assertEmbeddingConfig`. It throws when `SEARCH_SEMANTIC_ENABLED=true` and no provider resolves, when only one of `CF_AI_ACCOUNT_ID` / `CF_AI_API_TOKEN` is set, or when `SEARCH_SEMANTIC_ENABLED` is anything but unset/`true`/`false`; on the Worker that is a 500 on every request, queue batch and cron run. Otherwise it logs `[search] embedding provider: workers-ai|rest|none; semantic search ON|OFF` once. **Only the post-deploy probe catches a bad value** (`cf-api-deploy.yml` polls `/health`, which runs the check, and rolls back): the pre-deploy workerd smoke boots without the `AI` binding and forces `SEARCH_SEMANTIC_ENABLED=false`, so it never sees the flag. That is why the flag lives in `apps/api/wrangler.jsonc` `vars` (default `"false"`) and is flipped only by a PR plus a `cf-api-deploy.yml` run — never with `wrangler secret put` (the deploy refuses a secret of that name) and never from the Cloudflare dashboard (that creates a new version with no probe and no automatic rollback).

Needs a provider (above). Flipping it on in production is STOP-3 in the search plan (Ahmad): edit the var in `apps/api/wrangler.jsonc`, merge, run `cf-api-deploy.yml`. - `SEARCH_EMBED_STORE_DAILY_CAP` (optional, default `3000`; a non-number falls back to the default) — products embedded per store per Cairo day by the indexer (`apps/api/src/services/product-index.service.ts`). Counts DISTINCT products embedded today (`product_embeddings.embedded_at`), so a product re-embedded after a second edit the same day counts once (Ruling SEARCH-T11-2). When it is spent the store waits for the next Cairo day; the 6-hourly backstop retries.
- `SEARCH_EMBED_GLOBAL_DAILY_CAP` (optional, default `20000`; a non-number falls back to the default) — account-wide ceiling on ALL Workers AI embedding CALLS per Cairo day (the indexer's AND the storefront query embeds, Ruling SEARCH-T12-3), counted in Redis (one `INCR` per provider call: a batch call, each single-product call of an isolation pass). Past it the indexer stops until the next Cairo day and raises one P1. Fails closed: with no Redis the indexer makes no calls. `0` stops every indexer call (Ruling SEARCH-T11-19).
- `SEARCH_EMBED_THROTTLE_MS` (optional, default `200`) — sleep after each successful Workers AI embedding call in the indexer. With the indexer's global concurrency of 4 runs it keeps indexing under ~1200 of the account's 3000 text-embedding requests/minute, leaving the rest for query embeds (Ruling SEARCH-T11-3).
- `SEARCH_VECTOR_MAX_DISTANCE` (optional, default `0.55`) — cosine-distance cut-off for vector hits. Read per request by the vector leg (`semanticProductIds`, `apps/api/src/services/product-search.service.ts`); a value outside (0, 2] falls back to the default. Each product scores by the NEARER of its two vectors: the doc (names + descriptions, SEARCH-T13-5) and the AI search words alone (SEARCH-T13-7). **0.55 is kept after the Task 13 eval** (real bge-m3, Ruling SEARCH-T13-1): it passes the bar; 0.45 fails it (core hit-rate@10 0.88); 0.65 gains nothing (0.96 either way) but adds off-type products to the top 10 (0.99 → 1.29 per query) and answers every query for a product the store does not sell with 10 products (0.55: 92 %, ~7.5). No cut-off separates "absent" from "relevant" for bge-m3 (absent nearest-product distance, median 0.47, sits inside the relevant range), so do not tighten it to fix false positives. Re-tune with `npm run search:eval -- --real`, never by eye.
- **Search eval (`npm run search:eval`, local only, never on the Worker)** — no env var of its own. `--real` starts the localhost embedding proxy itself (`tests/search-eval/embed-proxy/`, `wrangler dev` with the `AI` binding: real bge-m3 on the `wrangler login` Whisky account; 127.0.0.1 only, `application/json` only, a random per-run secret header passed through a 0600 temp `--env-file`, never argv, never printed) and stops it at the end. The harness refuses a non-loopback `DATABASE_URL` or `REDIS_URL` (it writes a store and INCRs the shared embed-budget counters with their caps lifted). Without `--real` (and without the REST pair below) it uses a hash fake and exits 3 (NOT REPRESENTATIVE). Flags: header of `tests/search-eval/run.ts`.
- `SEARCH_QUERY_EMBED_GLOBAL_DAILY_CAP` (optional, default `10000`; a non-number falls back to the default) — storefront query embeds per Cairo day across all stores, counted in Redis (`takeQueryEmbed`, `apps/api/src/lib/search/embed-budget.ts`). Kept below `SEARCH_EMBED_GLOBAL_DAILY_CAP` so shoppers can never use up the indexer's share. A query vector served from the in-isolate cache is not counted. Spent, over another cap, or no Redis → that search is keyword-only (never an error). `0` stops every query embed (Ruling SEARCH-T12-3).
- `SEARCH_QUERY_EMBED_STORE_DAILY_CAP` (optional, default `1000`) — the same per store, so traffic aimed at one store cannot spend every store's budget. Every query-time provider call is also charged to its SEARCHER (normalised client IP, IPv6 /64): at most `SEARCH_EMBED_PER_SEARCHER_PER_MIN` (below) per fixed minute, checked first and alone so a client over its limit never touches the daily budgets; over it the search is keyword-only, never refused. The storefront list (`/public/products`) and the MCP `search_products` tool both pass the caller's IP; a caller that passes no searcher never embeds (Ruling SEARCH-T12-6).
- `SEARCH_EMBED_PER_SEARCHER_PER_MIN` (optional, default `60`; a non-number falls back to the default; `0` = no query embeds) — query embeds per searcher (client IP; IPv6 grouped by /64; no IP = no embed) per fixed minute. Sized for carrier-grade NAT on Egyptian mobile networks, where many shoppers share one public IPv4; it only slows one client draining the shared daily budgets, which are what bound spend (Ruling SEARCH-T12-11). Over it the search is keyword-only, never refused.
- `CF_AI_ACCOUNT_ID` + `CF_AI_API_TOKEN` (optional, **local/dev REST fallback only**) — Workers AI REST (`POST https://api.cloudflare.com/client/v4/accounts/<id>/ai/run/@cf/baai/bge-m3`) for Node dev and scripts that have no binding. Set both or neither. **Never set on the Worker** (it uses the binding). The token is a secret (Workers AI read scope on the Whisky account); it is only ever sent as the `Authorization` header and never logged.

#### Semantic search — emergency stop (indexer spend)

`SEARCH_EMBED_STORE_DAILY_CAP=0` (or `SEARCH_EMBED_GLOBAL_DAILY_CAP=0`) stops **every** Workers AI call the indexer makes (backfill, edits, the 6-hourly backstop): each run reports `capped` before it picks a batch (Ruling SEARCH-T11-8). `SEARCH_SEMANTIC_ENABLED=false` does **not** do this — it only turns off the query-time vector leg; the indexer runs whenever the `AI` binding exists. To stop indexing spend on production:

1. **Durable (preferred):** add `"SEARCH_EMBED_STORE_DAILY_CAP": "0"` to `vars` in `apps/api/wrangler.jsonc`, merge, and run `cf-api-deploy.yml` (the deploy probes `/health` and rolls back on failure).
2. **Emergency (minutes):** set `SEARCH_EMBED_STORE_DAILY_CAP` = `0` as a variable on `ebda-api` in the Cloudflare dashboard (Workers & Pages → ebda-api → Settings → Variables and Secrets). Caveats: it creates a new version with no post-deploy probe and no automatic rollback; the value is not boot-checked, so anything that is not a non-negative integer silently falls back to the default 3000 (type exactly `0`, then confirm `[search-index] daily cap reached` in Workers Logs); and the next `cf-api-deploy` REPLACES dashboard vars with the `wrangler.jsonc` vars (no `keep_vars`), so follow up with step 1 or the stop is undone.

To resume, remove the var (or set the old value) the same way. Re-enabling semantic results for shoppers is a separate switch (`SEARCH_SEMANTIC_ENABLED`, STOP-3b).

Storefront query embeds (Task 12) are stopped by `SEARCH_SEMANTIC_ENABLED=false` (the vector leg is off) or, keeping the flag on, by `SEARCH_QUERY_EMBED_GLOBAL_DAILY_CAP=0`; search stays keyword-only either way. `SEARCH_EMBED_STORE_DAILY_CAP` does not apply to query embeds.

## Integration test suite

- `TEST_API_URL` (default `http://localhost:4000`) — the ONLY knob for which API the integration suite talks to. Accepts an origin or an already-versioned base (`…/api/v1`); `tests/helpers/api-base.ts` normalizes both to one `{ API_ORIGIN, API_BASE }` pair, so no caller can produce `/api/v1/api/v1`. A bare host (`localhost:4000`, `api.ebda.app`) is rejected at load with a named error rather than parsed into the truthy string origin `"null"`. A well-formed absolute URL is NOT automatically accepted either: any host that is not loopback or a private (RFC1918/link-local) address is also refused at load — see `TEST_API_ALLOW_REMOTE` below.
- `EBDA_TEST_IDENTITY_JWK` (CI/integration only; never set in a deployed environment) — a throw-away P-256 private JWK generated per CI job. With `NODE_ENV=test` it makes the Node API server (`apps/api/src/lib/test-identity.ts`) verify ES256 tokens against its public half and answer session-revocation locally, standing in for the identity service; `tests/helpers/identity-session.ts` mints the matching tokens. Unset (or any other `NODE_ENV`) it is a no-op.
- `TEST_API_BASE` — older alias, still honoured. Same normalization.
- `TEST_API_ALLOW_REMOTE` (default unset/off) — the suite writes real data (it POSTs `/auth/register`), so `tests/helpers/api-base.ts` refuses to run against anything but loopback or a private address, even when `TEST_API_URL`/`TEST_API_BASE` parses as a well-formed URL. Set `TEST_API_ALLOW_REMOTE=1` on the same command to explicitly opt into pointing the suite at a real, reachable host — this makes doing so a deliberate act on the command line rather than a naming-convention promise a stray `.env` value could silently break.
- **The suite deliberately does NOT read `API_URL` or `API_HOST`** (2026-09-09). Both are server variables: `API_URL` is an ORIGIN (`config.apiUrl`) and `API_HOST` is a BARE HOSTNAME (`config.host`), and `apps/api/src/config/index.ts` runs `dotenv.config()` at import time — before any const in a test file — so a root `.env` copied from `.env.example` would silently win over the test's own default. Borrowing `API_URL` cost two ways: every request lost its `/api/v1` prefix and 404'd, and on a machine holding deployed values (`API_URL=https://api.ebda.app`) a local `npm run test:integration` would have POSTed `/auth/register` against production. Never point the suite at a variable whose production value is a real, reachable API.

- **Local test Postgres must run in UTC, like CI** (Ruling ITEST-12). The CI service container is UTC. A local cluster inherits the machine's zone at `initdb`; the shared test cluster (`127.0.0.1:54417`) was on a non-UTC zone and four time-based tests failed there (gold-checkout stale block and admin order, legal-policy-admin withdraw window, citation-scan resume). Set it once on the cluster and reload: `psql -h 127.0.0.1 -p 54417 -U test -d postgres -c "alter system set timezone='UTC'" -c "alter system set log_timezone='UTC'" -c "select pg_reload_conf()"` (done 2026-10-26; it persists in `postgresql.auto.conf`). A fresh cluster: `initdb` then the same two statements, or `postgres -c timezone=UTC`. Check with `show timezone;`. The code no longer depends on it (tenant transactions pin `TimeZone = UTC`, see `packages/database/src/tenant-gucs.ts`), but fixtures that use raw SQL `now()` on the owner connection still see the session zone, so keep the server on UTC.
- **Raw SQL in tests**: the schema's instants are `timestamp(3)` WITHOUT time zone holding UTC. Compare and write them with `(now() AT TIME ZONE 'UTC')`, never a bare `now()`.

### Identity secrets: where they live and how to rotate (no values here)

| Secret (Worker `ebda-accounts`) | What it is                                                                                                                  | Backup (macOS Keychain, account `ebda-identity`) |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `JWT_PRIVATE_JWK`               | ES256 (P-256) private JWK with a `kid`; signs every access token. The public half is published at `/.well-known/jwks.json`. | service `ebda-accounts-JWT_PRIVATE_JWK`          |
| `MFA_KEY`                       | 32 random bytes, base64; seals TOTP secrets at rest (AES-GCM).                                                              | service `ebda-accounts-MFA_KEY`                  |
| `CLIENT_SECRET_PEPPER`          | 32 random bytes, base64; HMAC key for integrator client secrets.                                                            | service `ebda-accounts-CLIENT_SECRET_PEPPER`     |

Read a backup: `security find-generic-password -a ebda-identity -s <service> -w` (it prompts; never paste the value into chat, a ticket or a log). Both were generated on 2026-10-25, set with `wrangler secret put ... --name ebda-accounts` (value on stdin), and are Cloudflare-account secrets (personal account `69188202efc4df480140dd76545aa3ab`).

**Rotate the signing key (no downtime, tokens live 15 minutes):**

1. Generate a new P-256 JWK with a new `kid` (same recipe as the first: `crypto.generateKeyPairSync('ec', { namedCurve: 'prime256v1' })`, export as JWK, add `kid`, `alg: ES256`, `use: sig`).
2. Put the OLD key's PUBLIC JWK into `JWT_PREVIOUS_PUBLIC_JWKS` (a JSON array of public JWKs) so tokens signed with it keep verifying for 24 hours. Each entry MUST carry its own `exp` member (unix seconds, now + 24 h; never more than 30 days ahead, a key with a later `exp` is not published either): the identity service publishes a retired key only until that `exp` and does not publish an entry without one (ID-08); `wrangler secret put JWT_PREVIOUS_PUBLIC_JWKS --name ebda-accounts`.
3. `wrangler secret put JWT_PRIVATE_JWK --name ebda-accounts` with the NEW private JWK; update the Keychain entry (`security add-generic-password -U -a ebda-identity -s ebda-accounts-JWT_PRIVATE_JWK -w`).
4. Verify `/.well-known/jwks.json` now lists both keys, and a fresh login's token header carries the new `kid`. `/health` on the accounts Worker shows `warning: retired_jwk_without_exp` and the kids when an entry has no `exp` or one more than 30 days ahead. After 24 hours the key stops being published on its own (`exp`); drop `JWT_PREVIOUS_PUBLIC_JWKS` afterwards.
   Products cache the JWKS for at most 10 minutes and refetch once on an unknown `kid`, so they pick the new key up on their own.

**Rotate `MFA_KEY` (no downtime, no re-enrolment):** sealed TOTP secrets name their key (`v3.<kid>.<iv>.<ct>`, AES-GCM bound to the owner by AAD `v3|kid|userId`; legacy `v1`/`v2` carry no owner binding and are refused when `MFA_REJECT_LEGACY=true`, which production sets from day one: verified 0 production users had a sealed TOTP on 2026-10-25), and the worker holds a keyring: `MFA_KEY` (current, seals everything new) and `MFA_KEY_PREV` (opens old secrets only).

1. Generate a new 32-byte key (`openssl rand -base64 32`), update the Keychain entry.
2. Set both in ONE deployment: `wrangler secret bulk` with `{ "MFA_KEY_PREV": "<old>", "MFA_KEY": "<new>" }` on stdin (never a file in the repo). If you must use two puts, set `MFA_KEY_PREV` FIRST: the reverse order leaves the ring as `{new}` only and every TOTP user gets 503 until the second put lands.
3. The hourly job (`scheduled`, cron `23 * * * *`; or `Accounts.reencryptMfa()` over the Service Binding) re-seals every secret on the new key with a per-row compare-and-set. Wait until it reports `remaining: 0` (verify with `SELECT count(*) FROM users WHERE mfa_secret IS NOT NULL AND mfa_secret NOT LIKE 'v3.<new kid>.%'`; the kid is the first 8 hex chars of sha256 of the key bytes).
4. Only when the report shows `remaining: 0` AND `failed: 0`: `wrangler secret delete MFA_KEY_PREV --name ebda-accounts`. Keep the old key in the Keychain until then. A secret copied onto another user's row does not open (owner-bound AAD).
   A secret sealed with a key that is in neither slot answers 503 `MFA_UNAVAILABLE` (never a pass); putting the old key back as `MFA_KEY_PREV` restores service with no data loss.

**Lost both?** Redeploy with new values: tokens signed by the old key stop verifying (everyone signs in again), and TOTP users re-enrol.

### Cutover order (Ruling ID-16): the identity service goes live BEFORE the Store stops accepting its own logins

Merging the stage-3 PR deploys ebda-api (legacy login, refresh and session issue are CLOSED for every merchant/staff/admin account), admin and orders (they sign in only at accounts.ebda.app). They deploy in parallel and nothing orders them, so the identity service, its secrets and the migrated accounts must already exist:

1. Deploy `ebda-accounts` (`apps/accounts`; the `accounts.ebda.app/*` ZONE route is required beside the custom domain, because zone routes run before custom domains and the storefront wildcard would otherwise answer the host).
2. `wrangler secret put JWT_PRIVATE_JWK` and `MFA_KEY` for `ebda-accounts` (never in a file, never through an agent's chat).
3. `wrangler d1 migrations apply ebda-identity --remote` (0001 identity, 0002 enrolment tokens).
4. `node apps/accounts/scripts/migrate-from-pg.mjs --apply --remote` (read-only Postgres export; refuses users with MFA; verifies row counts and a checksum).
5. Verify live: `/health`, `/.well-known/jwks.json`, one real login and token.
6. ONLY THEN merge the PR. Every merchant re-logs in once (refresh rows are copied but can never match, Ruling ID-5).

Each browser origin may only request ITS product audience (`ORIGIN_PRODUCTS`): store, orders and the accounts sign-in page (`https://accounts.ebda.app`) get `store` tokens, `wa.ebda.app` only `whatsapp`. The accounts page discards the token it is handed; what it leaves behind is the `__Host-ebda_rt` session cookie, from which each product then asks `/token` for its own audience.

### Platform administrators (Ruling ID-15)

- **Create or promote one (you run it, you type the password):** `cd apps/accounts && CLOUDFLARE_ACCOUNT_ID=69188202efc4df480140dd76545aa3ab node scripts/upsert-super-admin.mjs --email=you@example.com --remote` shows the plan (dry run is the default and writes nothing); add `--apply` to be asked for the password twice at a hidden prompt (14+ characters, all four classes). The script refuses a `--password` argument and refuses to run `--apply` without a terminal, so the password never passes through an agent, a pipe or shell history. Only a bcrypt hash is written, through a 0600 temp file that is deleted afterwards. Idempotent: running it again re-sets the password and ends the account's sessions.
- **A super admin has no admin power until a second factor is used.** `pa: "super_admin"` is minted only for a session created with TOTP or a passkey (`amr` contains `otp` or `hwk`). A first password sign-in works but the token has no `pa`, and the response carries `mfaEnrollmentRequired` so the admin app sends the person to `/account/security` to enrol; enrolled admins sign in with password + code (or a passkey).
- **First-factor bootstrap.** A password-only session cannot bind the FIRST factor of a super admin (a leaked or phished password must not be enough). `/mfa/enroll/verify` and `/passkey/register/verify` for a `super_admin` with no factor require BOTH the one-time enrolment token the script printed to your terminal (30 minutes, single use, stored only as a sha256 hash in `enrolment_tokens`) AND a one-time code e-mailed to the account (`POST /mfa/bootstrap/code`, needs the password). Promoting an existing account DELETES its old TOTP secret, backup codes and passkeys (the dry run says so) and issues a token; re-running for a super admin who already has a factor keeps it and issues nothing unless `--reset-factors`. The admin UI's first-factor step is TOTP (it asks for the token and the e-mailed code); add a passkey afterwards from the same page.
- **Every factor enrolment is gated, decided at BEGIN.** `/mfa/enroll` and `/passkey/register/options` record an enrolment ticket (bound to the session) with the policy for that account: `bootstrap` (super admin with no factor: operator token + e-mailed code, required at completion whatever the account looks like by then), `step-up` (the account already has a factor: the session must come from a login that used TOTP or a passkey in the last 10 minutes, or a current TOTP code is sent), or `password` (any other account's first factor: it needs a one-time code e-mailed to the account, the same trust a password reset needs, so a phished password cannot bind a factor that a reset would then keep, Ruling ID-8; `POST /mfa/bootstrap/code` sends it). Every bound factor also mails a "new sign-in method added" notice. Completion (`/mfa/enroll/verify`, `/passkey/register/verify`) refuses without a matching ticket and re-checks the CURRENT state (a factor that appeared meanwhile only makes it stricter). A successful bootstrap deletes every pending enrolment of the account and ends its other sessions.
- **A passkey alone is a complete state for a platform admin.** Its sessions carry `pa` (amr `hwk`); a password-only sign-in for such an account returns `{ secondFactorRequired: true }` and creates NO session (no token, no cookie), and the admin app asks for the passkey; removing a platform admin's passkey also needs a fresh second-factor session. **Lost the only passkey (no TOTP)?** Only the operator can recover: re-run `upsert-super-admin.mjs --email=... --reset-factors --apply`, which clears the factors and prints a new one-time enrolment token. Hold two factors (a passkey plus a TOTP, or two passkeys) to avoid it. The security page shows the passkey panel to admins too (first passkey: token + e-mailed code), and adding a TOTP to a passkey-only admin needs only a fresh passkey session.
- **Fresh login.** The token carries `auth_time` (the interactive login behind the session). The identity service stops minting for a platform-admin session older than 12 h (401 `REAUTH_REQUIRED`) and the Store refuses a `pa` token whose `auth_time` is missing or older than 12 h (same code), so a stale or stolen long-lived session cannot act as a platform admin. Only `aud=store` tokens are accepted by the Store.
- The old `scripts/admin-upsert-super-admin.mjs` (Postgres) is superseded after the cutover and says so in its header.

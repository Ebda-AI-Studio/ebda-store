# Security audit — 2026-10-14 (static, `apps/api` + `packages/database`)

Branch `fix/security-batch-2026-10-14`. Method: read the code, trace an exploit path, then try to
refute it (middleware, RLS, Zod, tenant guard). Static only: nothing was run, no browser, no
production access. A finding is **confirmed** only when the exploit path is traced to file:line and
no guard was found; anything that depends on production state, a browser, or a race is
**needs_validation** and carries no severity. Decisions are recorded in `docs/RULINGS.md`
(S4-1, S8-1, S10-1, S11-1, S2-1).

### S2 consent and erasure state (report only)

- Erasure and export exist for the shopper (`POST /auth/me/erase`, `GET /auth/me/export`) and for the merchant on a customer (`POST /stores/:storeId/customers/:customerId/erase`, customer JSON export), all audited; erasure reports a CRM review flag.
- Consent: email campaigns go only to explicit newsletter subscribers (`campaign.service.ts`, Ruling EC-1); SMS marketing consent is a stored, phone-keyed record with a signed opt-out token (`sms-consent*`), and promotional SMS sending is described as gated off. Not verified in this pass: that every admin-initiated send path (WhatsApp templates via WBS, manual SMS) checks consent, and whether a retention/purge job exists for erased data beyond `docs/RETENTION.md`.

## F-01 fix as built

`lib/customer-store-binding.ts` is called from `authenticate` and `optionalAuthenticate` for every `customer` token. A token-vs-`X-Store-ID` check alone would NOT have fixed it (the attacker sends the victim's store id); the request's Origin store must equal the token's `storeId`, with the header, when present, agreeing. Mismatch: 401 `TOKEN_INVALID` (authenticate) or guest (optionalAuthenticate). Legacy tokens without `storeId` fail and self-heal through the silent refresh. Customers with `users.store_id IS NULL` cannot hold a bound token (see the Ruling for the count query).

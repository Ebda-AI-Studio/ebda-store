# FP-5

> Section: Admin fix pass 2026-11-04, track T1 API core (branch `feat/admin-fix-t1-api-core`)

Ruling FP-5 - BE:F-2. `StoreService.update` (settings), `updateFloatingWidget`, `setMcpWriteEnabled` and `setGoldAllowDeferredPayment` no longer merge against the copy `getById` read at the start of the request: they read `settings` inside the write itself (`readLiveSettings`) and splice only the keys the client sent (shallow, server-owned keys restored). On Postgres the row is read `FOR UPDATE`, so two concurrent writers serialise and both keys survive; on a D1 + Durable Object store (`updateStoreThrough` hands a stand-in with no row lock) it is a plain fresh read, so two writers inside the same few milliseconds can still interleave. The stale-WHOLE-copy loss (a page mounted minutes ago, saved after another surface wrote) is closed server-side only for the keys a page does not send; the client half (pages send only their own keys) is T4. `updateQrSettings` / `updateLabelSettings` keep their raw `jsonb_set`. Evidence: `tests/unit/settings-atomic-keys.test.ts`. Cost if wrong: on a DO store, one key written in the same few milliseconds as another writer's is lost, instead of every key written during the page's lifetime.

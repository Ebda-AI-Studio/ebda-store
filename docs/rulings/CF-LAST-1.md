# CF-LAST-1

Ruling CF-LAST-1 (2026-10-29, INFRA-CF-1 PR D2b-5, slice 1 of the last code pieces) - gold product pricing edits move to the StoreDO and the `PaymentService.handleWebhook` / `refund` end-to-end contract exists; eight items stay open and are named below. (1) GOLD: `goldSetProductPricing` (`GoldRateService.setProductPricing`), `goldBulkSwitchMode` (`bulkSwitchMode`) and `goldCreateVariant` (the only real `asRepricer` closure: the variant INSERT of `VariantService.createVariant` / `generateVariants`) are named money ops in `packages/repo/src/do/gold-pricing.ts`, each ONE `transactionSync` section with the optional `_money_ops` marker-row key; the single DO thread replaces `pg_advisory_xact_lock(gold-rate:<store>)`, the repricer runs with `do_flags.gold_reprice` on and clears it in a `finally`. Every Postgres option is honoured: catalogue cap only where a product BECOMES gold (B5-13), `GOLD_IN_BUNDLE`, `GOLD_NO_PRICE_TIERS`, `GOLD_VARIANT_NEEDS_PRICE` (B5-36), `GOLD_RATE_MISSING` for every karat in use, compare-at/discount cleared on gold (B5-19), gold -> fixed freezes the price, variant overrides, 404 for an unknown product or variant. `bulkSwitchMode` runs each product in a nested section (a savepoint) so a refused product is SKIPPED with its code and leaves nothing, at most 500 ids, `ALREADY` / `SPEC_INCOMPLETE` / `NOT_FOUND`; a stored spec the edge schema would refuse aborts the call (Postgres: the ZodError escapes). `GoldRateService.asRepricer` stays a Postgres closure runner: for a DO store it takes the caller's `onDo`, which calls `goldCreateVariant` (a closure cannot cross the door, and the DO price guard refuses a gold variant insert outside the repricer section, so a three-section design was rejected); without `onDo` it throws a plain Error (a programming error, not a 501). The audit rows are written by the Worker after the commit (best effort, like `applyRates`). `GOLD_PRICING_NOT_ON_DO` is gone. Differences kept, found by the contract test: (a) `bulkSwitchMode` answers in the caller's id order on the DO, in row order (unspecified) on Postgres; the contract compares sets; (b) `createVariant` on Postgres returns the row as inserted (price null) while the DO re-reads it after the re-price (priced); the stored rows are equal. (2) END-TO-END: `tests/integration/repo-factory-payment-service-contract.test.ts` drives the real `PaymentService.handleWebhook` and `refund` (real bridge, real factory reading a mirrored `payment_configs` row) with a stub `PaymentProviderV2` registered as `paymob`: signed completed delivery + replay, bad signature, full refund (provider called once, order refunded, stock back), partial refund + a second refund under one `refundKey` refused, a dashboard refund webhook booked once; Postgres 17 vs the DO schema, equal returns, rows and provider calls. The CF-PAY-1 note "not covered by a Postgres-vs-DO contract" is closed. (3) NOT DONE in this PR, each still listed in `docs/cf/not-on-do.json`, with the reason: partial-return journal (needs the Return row lifecycle on the DO first: it reads `returns`, `return_items`, wallet rows by `return_id`), the Return row lifecycle (2051-line `ReturnService`), InstaPay receipts (needs a D1 entity-index kind for the cross-store `reference_key` uniqueness), cart rows (1405-line `CartService` + abandoned carts), fiscal documents and counters (gapless numbering needs its concurrency proof on workerd), order reads that join Postgres-only models, the wallet-movement journal (WALLET-GL-1 / PR #325 unmerged: the DO ledger already books the wallet tender, `ledger.ts`, but the movement journal on 2150 for top-ups and adjustments is #325's), the CSV import orchestrator. BUNDLE: 8,238,257 bytes (budget 8,300,000, was 8,227,521 after CF-FINAL-1: +10.7 KB), gzip 2,261,321 (budget 2,400,000). The 61.7 KB of headroom is less than eight more engines need, so the rest waits for PR #327 (trims 541 KB on main) instead of raising the budget. Evidence: `packages/repo/test/do-gold-pricing.test.ts` (13), `tests/integration/repo-factory-last-contract.test.ts` (5, Postgres 17 vs DO), `tests/integration/repo-factory-payment-service-contract.test.ts` (5), `apps/api/workers-do/gold-pricing.test.ts` (4 on real workerd: 30 concurrent edits with rate changes leave no torn price, 20 concurrent bulk switches switch each product once, 20 concurrent variant creates are all born priced and re-priced by a mid-flight rate change, 30 concurrent creates with no rate leave nothing). Cost if wrong: with every flag at `pg` nothing here runs; a wrong DO pricing write is reachable only for a store the operator flipped (one D1 UPDATE back), and the flip gate stays closed until `not-on-do.json` is empty.

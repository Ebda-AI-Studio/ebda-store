# CF-DO-SCHEMA-1

Ruling CF-DO-SCHEMA-1 (2026-10-28, INFRA-CF-1 PR C) - the StoreDO runs the FULL generated cf-schema (122 tables), applied by a versioned, idempotent runner on every start; the Phase 0 thin spike tables are dropped on upgrade; a Durable Object binds to ONE store; backups cover every table dynamically; customer erasure FAILS CLOSED until the registry covers the schema. Evidence: `apps/api/src/cf/store-do/migrations.ts` (`runMigrations`: each step and its `_migrations` row in one `transactionSync`, ids `cf-0000_drop_spike_core`, `cf-0001_init`, `cf-0002_invariants`), `packages/cf-schema/src/store/migrations.generated.ts` (emitted by the generator from the two SQL files, CI-checked by `generated-current.test.ts`), `tests/unit/cf-store-do-migrations.test.ts` (fresh, spike upgrade, rollback of a failing step, second run is a no-op), `apps/api/workers-do/store-do-schema.test.ts` (real workerd: all 117 prisma-modelled store-do tables present (122 tables incl. the CF additions), replay changes nothing, CHECK constraints live, isolation). Spike data is disposable: the Phase 0 tables only ever held the flagged demo store's seed, and a nightly R2 backup exists for it. Isolation: the namespace routes `idFromName(storeId)` and the instance binds to the first store id it serves (`_identity`), refusing any other with `STORE_MISMATCH` on every entry point, so a routing bug cannot cross stores. Backups: `storeTables()` reads the live schema (derived search/vector state excluded: the dirty-marking triggers rebuild the index after a restore) and the restore defers foreign keys; the backup-sweep and restore-drill tests pass unchanged on the full schema. Erasure: the registry is EMPTY (its Phase 0 entries described tables that no longer have that shape) and `eraseSubject`/`exportSubject` for a customer throw `ERASURE_REGISTRY_INCOMPLETE` while any table is unclassified; turning `packages/cf-schema/erasure-classification.json` into match/scrub entries is the G10 follow-up and a cutover blocker (`storeDoSurface` is not wired to any route today). Cost if wrong: the flag is off for every store, so no production request reaches a StoreDO; a wrong migration is fixed by a new migration id, and a spike-era demo DO loses only its seed rows.

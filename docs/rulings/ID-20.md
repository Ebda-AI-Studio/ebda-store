Ruling ID-20 (2026-11-11) - password-less platform-admin bootstrap + the platform-admin invariant. Context: the live identity D1 `ebda-identity` held ZERO super_admins (9 store_admins), so nobody could open the super-admin pages, and Ahmad's rule for creating his own admin `ahmad@ebda.app` is that no password, hash or secret may pass through an operator or agent. (1) New operator script `apps/accounts/scripts/bootstrap-super-admin.mjs` (pure helpers in `bootstrap-super-admin-sql.mjs`): dry run by default, `--apply` writes ONE batch = an active super_admin whose password column is the service's existing unusable marker `!pending` and whose address is UNVERIFIED, plus an `admin_audit` row (migration 0006; the audit row is written only if the guarded insert landed). It then asks the service itself to mail the set-password code (`POST /password/forgot`, the same path as "Forgot your password?") and proves from D1 that a `password_reset` code was issued and marked sent (count only, the code column is never read). The owner sets the password with that code (`/password/reset`, which also verifies the address) at store.ebda.app/reset-password. Refuses: an address that already belongs to another role (promotion stays `upsert-super-admin.mjs`, which clears planted factors), a second active super_admin unless `--allow-additional` (recorded in the audit detail), any password/hash/code/token-shaped argument. Re-running is a no-op; `--resend-email` re-mails the code while the password is unset. (2) ID-15 is unchanged: the admin has no admin power until a second factor is enrolled, and the FIRST factor still needs the one-time enrolment token + an e-mailed code. The token is issued by `--issue-enrolment-token`, which refuses unless the password is already set and no factor exists, and refuses unless stdin AND stdout are an interactive terminal, so only the owner, in his own terminal, ever sees it (an agent's captured shell cannot). (3) Invariant: Accounts RPC `superAdminSummary()` returns counts `{ active, ready }` (ready = verified + TOTP or passkey); the api's daily `0 3 * * *` cron job `super-admin-invariant` (`apps/api/src/lib/super-admin-invariant.ts`) sends a P1 through `sendAlert` when active = 0, when ready = 0, or when the RPC cannot be reached (unmeasured is never healthy). Evidence: `apps/accounts/test/bootstrap-super-admin.test.ts` (create/idempotency/second-admin refusal/merchant refusal/full mail -> password -> token -> TOTP -> `pa` path/summary counts), `tests/unit/super-admin-invariant.test.ts`. The Store profile row needs no step: `reconcileShadowUser` runs at every sign-in, and on the Worker (no Postgres, NZ-D23) the identity is the whole account. Residuals: (a) the ready = 0 P1 fires daily from deploy until the first admin enrols a factor, which is intended; (b) "sent = 1" proves the service queued the mail, not that the mailbox received it (mail errors are logged by the service only); (c) `admin_audit` has no UI: it is read with `--show-audit` (operator-only security trail, two event types). Cost if wrong: if the reset code is lost the owner re-runs with `--resend-email` (3 per address per window); a mailbox compromise before the password is set lets the attacker set the password, but not reach admin power, because the enrolment token never leaves the owner's terminal.

Ruling S3-O7 (2026-11-12, Ahmad: yes) - a courier COD settlement statement marks the order paid. In `importCodRemittances` (StoreDO, the same section that books the lines, Ruling CF-R7-2) a line booked NOW whose shipment is `delivered`, whose order is `delivered` and `unpaid`, with a `cod_pending` payment, completes that payment and sets `payment_status = paid` when the cash the statement carries for the shipment (this line plus earlier lines) equals both the payment's COD due and the shipment's `cod_amount`; it writes a `payment_events` row (`reason: cod_collected_per_courier_statement`) and an `order_events` row `cod_paid_by_statement`, both carrying the statement reference, carrier, tracking number and batch. Any other amount books the line in full (an external money fact is never refused) and leaves a `cod_statement_mismatch` order event for the merchant; the order stays unpaid. Cancelled, refunded, already-paid, non-COD and other-store orders are untouched (every read and write is `store_id`-scoped; matching is carrier + tracking inside the store). Idempotent: only a newly inserted line can settle, so a re-imported statement is all duplicates and writes nothing. The Worker fires the same `order/created` post-payment fan-out (journal posting) as a COD order paid on delivery. The Postgres path (`CodReconciliationService` without a StoreDO) is not changed: Postgres is removed in production. Tests: packages/repo/test/do-stock-books.test.ts "COD statement marks the order paid (S3-O7)". Cost if wrong: a statement line carrying the right amount for a parcel the merchant later finds undelivered would mark it paid; the delivered-status and amount guards bound this, and the payment event names the statement line to reverse.

Amendment (review of #735): a line whose carrier + tracking + collected + fee equal an already-booked line, whatever its date or reference (a statement with no date column is stamped with the upload day, which changes the line id), is still booked in full but gets `source = <source>:suspected_duplicate`, is excluded from the collected sum, and leaves a `cod_statement_duplicate` order event. So re-uploading a partial file the next day cannot pay the order with cash never collected. The `order/created` fan-out is sent through `deferAfterTenantCommit` and awaited (tests/unit/cod-statement-fanout.test.ts). Cost if wrong: two genuine, identical partial remittances (same amount and fee for one parcel) are flagged for the merchant to confirm instead of paying automatically.

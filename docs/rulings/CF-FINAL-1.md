# CF-FINAL-1

Ruling CF-FINAL-1 (2026-10-29, INFRA-CF-1 PR D2b-4a, Ahmad via the controller) - the first slice of the last code pieces of the DO move; it closes CF-ORDERS-CART-1 and the quote, status, delivery-slot and personalisation refusals, and turns "what is still not on the DO" into a build-failing inventory. (1) STATUS: `orderStatus` is a money op (`do/order-status.ts`) for pending/confirmed/processing/shipped/delivered: the state machine (`ORDER_STATUS_TRANSITIONS`, `INVALID_STATUS_TRANSITION` 400), `INSTAPAY_CONFIRM_REQUIRED` 409, the fanout arming (`status_fanout_*`, so the stuck-fanout sweep finds an undelivered transition - the gap listed in orders-on-do.md), `delivered_at` stamped once, the COD settlement on delivery (MONEYB-7: payment `completed`, order `paid`, a `status_change` payment event) and the order event are ONE section; a same-status write is allowed and writes again, as Postgres does. `OrderService.updateStatus` ends with `advanceOnDo` (the Postgres tail: customers cache, `order/created` for a settled COD, `order/delivered`, `order/status-changed` with the inline fallback, socket push). `ORDER_STATUS_NOT_ON_DO` is gone. (2) QUOTE: `quoteOrder` runs `placeOrder` with `dryRun` (no stock, no wallet, no hold slot, no cart claim, no key) and abandons the section through a signal, so it writes nothing and is not refused for stock the way an order is (Postgres quotes first, refuses at the order); it answers totals and per-line prices, the Worker maps lines back to cart item ids. `QUOTE_NOT_ON_DO` is gone. (3) CART CLAIM: the cart rows are still on Postgres (see the list below), so the engine's row-comparison claim cannot run; instead `createOrder` takes `cartClaim {id, fingerprint}` and claims it in the SAME section in `_cart_claims` (fingerprint = hash of the cart's row ids and quantities, so a cart cleared and refilled is a new state and a re-purchase is never blocked): a second submit of one cart state (no key, another key, a request that read the cart before the first one cleared it) is `CART_CHANGED` 409, a refused order releases its claim with the section, an idempotency-key replay returns before the claim. 40 concurrent submits on real workerd create one order; three concurrent `OrderService.create` on one cart create one order on Postgres and on the DO. This removes the CF-ORDERS-CART-1 residual (the double order); it does NOT move the cart rows. (4) DELIVERY SLOT AND PERSONALISATION: `DELIVERY_SLOT_NOT_ON_DO` and `PERSONALISATION_NOT_ON_DO` are gone: the Worker validates the date with the same `resolveOrderDeliveryNote` against the live Store row and the DO's own product lead times and passes the note as the order notes (first line, then the shopper's note); each cart line's personalisation text is written to `order_items.personalisation` by the engine. (5) FLIP-GATE INVENTORY: `docs/cf/not-on-do.json` lists every remaining refusal (`refusals`) and every flow a DO store still runs on Postgres (`postgresOnly`); `tests/unit/do-not-on-do-guard.test.ts` finds every 501 / `*_NOT_ON_DO` with the TypeScript AST over `apps/api/src` and `packages/repo/src` and fails when the code and the list differ in EITHER direction (a new refusal must be listed, a closed one removed); `node scripts/cf/not-on-do.mjs` exits 1 until both lists are empty. NOT DONE in this slice, each listed in that file: partial-return journal, gold `setProductPricing`/`asRepricer`/`bulkSwitchMode`, InstaPay receipts (refusals); cart rows, fiscal documents and counters, the Return row lifecycle, order reads, the wallet-movement journal (WALLET-GL-1 / PR #325, unmerged), the CSV import orchestrator, the `handleWebhook`/`refund` end-to-end contract test (Postgres-only or untested). Evidence: `packages/repo/test/do-order-status.test.ts` (8), `do-quote.test.ts` (4), `do-cart-claim.test.ts` (5), `tests/integration/repo-factory-orders-contract.test.ts` (17 scenarios: status chain with COD settlement, status refusals, quote, concurrent submits, personalisation and delivery date; Postgres 17 vs the DO schema, equal traces), `apps/api/workers-do/orders.test.ts` (+2 on real workerd: 40 submits of one cart = 1 order, 30 deliveries settle the COD payment once), the guard test (5).

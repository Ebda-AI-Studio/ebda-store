# CF-R7-3

Ruling CF-R7-3 (2026-10-30, INFRA-CF-1 R7, Ahmad via the controller) - the `search-index-kill-switch` "flake" was a test pinned to the handler's exact step list, not a timing race. The test asserted `steps` equal `['plan-0']`; the D1 backend-flag read was then added to `handleSearchProductIndex` as its own memoized step (`is-do-store`, CF-R6B-1), so the same test failed until the list was edited to `['is-do-store', 'plan-0']`, and it passed on the re-run only because the edit had landed in between. It was NOT reproducible as a race: 25 isolated runs, 40 runs under ten-way CPU contention and runs under `JOBS_ON_DO=1`, `NODE_ENV=production`, `JOBS_CF_ALARMS=all` and `SEARCH_SEMANTIC_ENABLED=true` all passed (measured). The property the test exists for (Ruling SEARCH-T11-8) is "ONE plan step and no embed or write step, no provider call", so it now asserts exactly that and no longer breaks when an unrelated memoized step is added. Evidence: 20 consecutive runs of `tests/unit/search-index-kill-switch.test.ts`, 0 failures. Cost if wrong: a handler that gained a real extra plan step would be caught by the `plan-` filter; one that gained an embed step by the second assertion; a regression that adds an unrelated step is (correctly) no longer a test failure.

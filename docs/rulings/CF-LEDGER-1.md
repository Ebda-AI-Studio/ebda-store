# CF-LEDGER-1

Ruling CF-LEDGER-1 (2026-10-29, INFRA-CF-1 PR D2b-3) - the general ledger of a DO store is posted on the DO (`do/ledger.ts`): `journalSale` (= `postOrderPaymentJournal`: the sale entry and the COGS entry), `journalRefund` (= `postRefundJournal`: reverses the sale, the COGS and any partial adjustment entry) as `moneyOp`s, with the Postgres twin's identity - `(store_id, source, source_id)` is the entry, `<sourceId>:reversal` the mirror, a reversed entry is never reversed again, DR = CR is checked before anything is written, the number is claimed by one upsert on `sequences`. The Worker functions branch on `storeMoney()` (`order-posting.ts`, `refund-posting.ts`); a DO store's Inngest posting jobs therefore need no Postgres rows. TRIAL BALANCE PARITY is a test: `tests/integration/repo-factory-payments-contract.test.ts` posts a paid order twice and refunds it twice on real Postgres 17 and on the DO schema and compares the per-account debit / credit totals, the entry list and statuses (equal, balanced, netting to zero per account); `apps/api/workers-do/payments.test.ts` fires 20 concurrent sale posts (two entries) and 20 refund posts (two reversals, four distinct numbers, book balanced). Differences kept on purpose: (a) a missing system account is `ACCOUNT_NOT_FOUND` 409, not self-healed from `COA_TEMPLATE` (the template lives in the API package; the import carries the store's accounts); (b) WALLET-GL-1 (open PR, not in this branch's base): the wallet tender is journaled as that ruling decides - DR 2150 for `wallet_amount`, DR cash for the rest, no zero cash line - so a whole-order refund puts the liability back through the mirror lines; until WALLET-GL-1 merges, Postgres still skips a wallet-paid order (W-3), so wallet-order parity is asserted by expectation in `do-payment-ops.test.ts`, not by the contract test; (c) the pro-rata journal of a partial return (`postPartialReturnJournal`), the store-credit movement journal (`postWalletMovementJournal`, WALLET-GL-1) and expense / PO / stock-adjustment postings are NOT ported: the first is refused 501 `PARTIAL_RETURN_JOURNAL_NOT_ON_DO`, the others have no DO caller yet. The 2150 liability for refunds onto the wallet is booked by the sale mirror (whole order) and, for `refund_credit`, by the not-yet-ported partial-return journal. Cost if wrong: a DO store whose chart of accounts was not imported cannot post (a loud 409, no half entry); a mapping of cash accounts that differs from what Ahmad wants is a re-mapping of `PROVIDER_TO_CASH_CODE`, which the DO copy shares by value with the API one (a unit test pins them equal), not a data loss.

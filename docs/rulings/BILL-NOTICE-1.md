# BILL-NOTICE-1

> Section: S2-13 — grace-period notices (branch `fix/grace-end-notices`; foundation criterion 18: billing notices idempotent per stage)

Ruling BILL-NOTICE-1 — An InstaPay merchant is told at three grace stages: `grace_start` (the payment went overdue; the store is paused at due + 3 days), `grace_d1` (one day or less before the pause) and `suspended` (the store was paused). Each is email + bell; the in-admin banner shows the overdue notice and, on the last day, the louder `graceEnding` wording (derived from `billing.overdue` + `billing.suspendAt`). Each stage is owned by whoever wins the INSERT of its `billing_reminders` row (UNIQUE subscription + period end + kind, kinds `grace_start | grace_d1 | suspended`) BEFORE anything is sent: `grace_start` and `suspended` are claimed in the same transaction as the compare-and-set that takes the decision, `grace_d1` in its own transaction from the daily job. No money moves, two migrations widen the `billing_reminders_kind_check` CHECK: Postgres (`20261111000100`) and D1 platform `0013_billing_reminders_grace_kinds.sql` (a leaf-table rebuild, because SQLite cannot ALTER a CHECK; D1 is the runtime, and a stage the CHECK rejected would roll the past_due decision back). Cost if wrong: a crash between the claim and the send loses that one notice (at-most-once, by design: the banner and the bell page still show the state), never a duplicate email.

Ruling BILL-NOTICE-2 - the unpaid-store suspension is ordered so a crash is self-healing, not made atomic. D1 has no interactive transaction (`prisma-lite/d1.ts`), so `manualPayDue` now suspends the store (idempotent), claims the `suspended` stage, and clears `nextRetryAt` LAST; a failure after any step leaves the row due and the next cycle finishes it (`tests/unit/billing-grace-suspension-d1.test.ts`, failure injected at the suspend call and at the claim write). Previously the retry was cleared first, so a failure left the store active and out of the due scan forever. A payment landing mid-way restores the store (`restoreFromBilling`). Cost if wrong: a notice can be lost (claimed, then the run dies before sending) but the suspension itself can no longer be lost.

Ruling BILL-NOTICE-3 - the grace notice is an outbox, not a fire-and-forget after the claim. The claim row in `billing_reminders` carries `notice_sent_at` (D1-only column, platform migration 0011, expand-only, NULL = claimed but not confirmed sent). `deliverGraceStage` sends the stage's effect (`deliverBillingEffect` reports success; `runBillingEffects` swallows failures) and only a delivered effect stamps `notice_sent_at`. `resendUnsentGraceNotices`, called by every full `runBillingCycle`, re-sends grace stages unstamped for 5 minutes and younger than 2 days (a lease bumping `created_at` from the value read gives one winner); a stage whose subscription is no longer `past_due` (the store paid) is stamped without sending. Delivery is at-least-once with the stamp as the dedupe; there is no provider-side idempotency key because `EmailService` and the bell take none. Rows older than 2 days (including any `suspended` rows from before this column) are never re-sent. `tests/unit/billing-grace-suspension-d1.test.ts` kills the run after the claim and before the send (grace_start and suspended) and shows the next cycle sends exactly once. Cost if wrong: a notice can be delivered twice if a worker dies between a successful send and the stamp.

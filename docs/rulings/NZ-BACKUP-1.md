# NZ-BACKUP-1

> Section: NEON-ZERO backups (2026-11-05)

**Ruling NZ-BACKUP-1 - production data (D1 `ebda-platform` + every StoreDO store) is copied every night OFF the Cloudflare data plane by `.github/workflows/cf-backup.yml`: `wrangler d1 export --remote` plus a paged, read-only `__export` of each DO, gzip -9, then age to `EBDA_BACKUP_AGE_PUBLIC_KEY`, into R2 bucket `ebda-db-backups` under `cf/daily/`, `cf/weekly/` (Sunday) and `cf/monthly/` (the 1st); an artifact whose content digest equals the last daily is referenced from the manifest, not re-uploaded; every object is read back and sha256-compared; a size guard fails the run when one run uploads more than 2x the median of the last 7 or the estimated `cf/` total passes `EBDA_BACKUP_CF_CAP_BYTES` (default 1 GiB). A backup counts only when `scripts/ops/restore-drill.mjs` restores it into a local D1 and a local StoreDO through the production `__import` path and every table's row count AND content digest equal the manifest (weekly fixture drill in CI, `cf-backup-drill.yml`; the drill against the real R2 backups is run by the controller).** The export is authorised by `BACKUP_EXPORT_SECRET`, a Worker secret that opens only `__export`, `__tables`, `__fks` and `__status` (never `__import`, `__seal`, `__unseal`, `__auth`), so the nightly job never holds the cutover secret, which is deleted when the cutover closes. Retention is by prefix lifecycle rules (7 / 28 / 93 days, `scripts/ops/r2-lifecycle-cf.sh`); weekly and monthly objects are their own uploads (a reference into `daily/` would expire with it) and a daily reference is used only while the target has at least 3 days of life left. The Neon final dump under `final/` has no expiry and is untouched. The size ledger `cf/ledger.json` is an estimate (R2 cannot be listed from wrangler), not an invoice.
Evidence: `tests/unit/ops/cf-backup.test.ts` (tiers, skip-if-unchanged, reuse window, read-back, guard, drill negative controls, secret scoping); a local fixture round trip on workerd (real StoreDO schema, 132 tables, 32 of them populated; real API Worker as the import target) reproduced every table digest.
Known limits (not hidden): (1) the drill's admin read is SKIPPED locally, merchant tokens are ES256 checked through the `ACCOUNTS` binding which a local worker lacks, orders are covered by the table digest; (2) `__export` refuses a BLOB (HTTP 422) rather than lose it silently, the nightly job then fails loudly; (3) a nightly export is not a point-in-time snapshot of a store taking writes (pages are read one after another), so DO PITR stays the precise tool and the R2 copy the provider-loss tool; (4) `cf-backup.yml` follows the `EBDA_RUNS_ON` switch as instructed, so with the variable set it runs on the Mac-hosted runner, the exact dependency OFFMACHINE-1 avoided for the Postgres dump; unset the variable (or dispatch from a hosted run) if that matters on the night.
Cost if wrong: if the age key is lost or the secret is not set, the job fails every night and there is no off-Cloudflare copy; if the cap or growth guard is mis-tuned it raises a false alarm (a failed run still stored the data) or lets R2 spend grow at $0.015 per GB-month beyond the first 10 GB.

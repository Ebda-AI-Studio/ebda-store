# CF-R4-1

Ruling CF-R4-1 (2026-10-30, INFRA-CF-1 PR R4, Ahmad via the controller) - the admin order-list search on a DO store is answered from the StoreDO's own derived search index, and `ORDER_SEARCH_NOT_ON_DO` is deleted from `docs/cf/not-on-do.json`. (1) WHAT IS INDEXED: nothing new is stored; the index CF-SEARCH-T14 already keeps in the DO is the one used: `customer_search_fts` holds one row per registered customer and one per GUEST order (the contact snapshot in `shipping_address`: first and last name Arabic-folded by the shared `normalizeArabicSearch`, the phone as digits by `digitsOnly` / `phoneSearchDigits`, the e-mail), and order numbers are matched on `orders.order_number` itself. (2) SAME-SECTION FRESHNESS: the index is DERIVED STATE kept by triggers (`search_orders_ai/au/ad`, `search_customers_*`): they mark the row in `search_dirty` INSIDE the section that writes the order (a `createOrder`, `createAdminOrder`, cancel or any prisma-lite write), so the mark commits or rolls back with the order and cannot be lost; the TypeScript fold (SQLite cannot fold Arabic) runs when the next search starts (`flushSearchIndex`), in the section of the new money op `searchOrders` (`do/order-search.ts`). A search therefore never sees an order that is not committed and never misses one that is. (3) SHAPE: `searchOrders` returns three id sets (order-number matches, registered customers, guest orders) and a `truncated` flag; `orderSearchWhere` builds the same three OR arms as the indexed Postgres path (`id IN`, `customer_id IN`, `id IN`), including the scanned-barcode arm, the digits-alone arm ("#1234" finds "EB-1234") and `indexed: false` for a customer's own orders. There is no relation fallback on a DO (no join to the platform `User`), so a term that matches more than 20,000 customers or orders is refused `ORDER_SEARCH_TOO_BROAD` 422, never answered with a short list. (4) EVIDENCE: `tests/integration/repo-factory-orders-contract.test.ts` "admin order search": 22 terms (whole order number, its random part, `ORD-`, Arabic folded and unfolded, alef/teh-marbuta variants, two-token names in either order, a phone in national, `+20 101 234 5678` and Arabic-Indic forms, a spaced guest phone, an e-mail part, case, `%`, `_`, no match, a 2-character term) plus the customer's-own-orders filter and the status filter return the SAME order names and totals on real Postgres 17 (the `ebda_*_search_ids` definers) and on the DO schema; the existing `packages/repo/test/do-search-customers.test.ts` keeps the index fresh under every writer. No workerd concurrency test: a search takes no lock on Postgres. Residual, accepted: the admin command palette route (`/admin-search`) still reads Postgres for its order and customer arms; it is not the order list and is not listed in the inventory, so it is named here. Cost if wrong: a wrong DO search shows a merchant the wrong orders but moves no money; the flag stays `pg` and a flip is one D1 UPDATE back.

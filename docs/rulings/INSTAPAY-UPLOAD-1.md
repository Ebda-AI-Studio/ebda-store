# INSTAPAY-UPLOAD-1

> Section: Backfill audit 2026-11-12 follow-up (branch `fix/web-webhook-realtime-hardening`, review of PR #866)

Ruling INSTAPAY-UPLOAD-1 - the InstaPay receipt upload and submit accept EITHER the order's signed view token (TEN-5, the tab that placed the order) OR the signed-in customer who owns the order, not the token alone. A shopper who returns on a new tab or device has no sessionStorage token and could not pay; the owning customer session is an equally strong credential. Both paths fail closed: a customer is accepted only when `order.customerId` equals their user id on the order's own store (another customer's order, a guest order, a missing order, any lookup error all answer 403 `ORDER_VIEW_TOKEN_REQUIRED`), and the guard still runs before multer buffers a file. Impersonated sessions are refused like `/payments/create`. Evidence: `requireOrderAccess` in `apps/api/src/lib/order-view-token.ts`, `customerOwnsOrder` in `apps/api/src/routes/payment.routes.ts`, tests in `tests/unit/guest-order-view-token.test.ts`. NOT done: the controller asked for a third path, the signed order-status link token under `ORDER_STATUS_LINK_SECRET`; no such secret or token exists in this repo (searched `apps/` and `packages/` on this branch and origin/main), so there is no existing signing to reuse and inventing one is a separate decision. Cost if wrong: if the customer lookup wrongly accepts an order, a signed-in customer could upload a receipt to someone else's order hold (money-adjacent, noticed via the owner's receipt review); if it wrongly refuses, a returning shopper is told to sign in and cannot pay from that device until they do.

## Part b - the signed order-status link (register G54, 2026-11-17)

Done once the order-status link existed (Ruling WA-COD-V2-2). The InstaPay instructions, the receipt upload, the receipt poll and the submit ALSO accept the signed order-status link in `X-Order-Status-Link`. It is accepted only when the token is valid and unexpired, names exactly this order, AND names the store the order belongs to (`getOrderStoreId`). A token for another order, for another store, or tampered gets the same 403 `ORDER_VIEW_TOKEN_REQUIRED`. The guard opts in per route (`requireOrderAccess(customerOwnsOrder, getOrderStoreId)`), so no other order route accepts the link. With the link the shopper sees their own receipt fields unmasked, the same as with the view token, because the link holder is the person the WhatsApp message went to.

- Storefront `/o/<token>`: the summary returns `instapayPayable`, true only when the order status is `awaiting_payment_confirmation` AND it has an InstaPay payment. In that case the page renders the checkout's `InstapayCard` (instructions + upload). The link is kept in memory for the page and sent only on that order's `/payments/instapay/` calls, never when the tab holds the view token.
- Evidence: `tests/unit/guest-order-view-token.test.ts` (G54 block), `tests/unit/order-status-link.test.ts` (instapayPayable), `apps/web/src/lib/order-status-link-header.test.ts`.

Cost if wrong (part b): anyone who holds the WhatsApp message within its 14 days could upload a receipt to that order's hold. A receipt sent with the link goes through exactly the same checks (duplicate reference refused, amount and payee read, owner review) as one sent with the view token; the link adds no way to confirm a payment that did not happen.

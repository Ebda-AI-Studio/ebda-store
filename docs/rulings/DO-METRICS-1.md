# DO-METRICS-1

Ruling DO-METRICS-1 - Operators measure per-store Durable Object data through ONE read-only, count-only, allow-listed path (option A of docs/plans/2026-11-17-do-readonly-metrics.md): a fixed `METRICS` table compiled into the StoreDO (each entry a constant single-statement aggregate), one super_admin + MFA route with an audit row per call, a bounded fan-out (the existing 500-store cap, concurrency 8, a 2 s per-store timeout), a 10-calls-per-minute-per-user rate limit with a 60 s cache, a `DO_METRICS_ENABLED` kill switch, per-store NUMBERS only (never a row, never a person), and a CLI wrapper that uses the controller's existing super_admin + MFA session (no new credential or identity is created; the design stays open to add a scoped service credential later, which needs Ahmad's OK). First five metrics: `journal_unbalanced`, `journal_repaired`, `journal_unrepaired` (track 1), `push_subscriptions_active`, `stores_with_push_enabled` (track 4). Every later metric is its own PR with its own ruling line.

Enforcement, as measured by the spike (apps/api/workers-do/do-readonly-guard.test.ts, local workerd, CI lane `workerd-integration`): the StoreDO SQLite API has NO runtime read-only mode: `PRAGMA query_only` (get, on or off), `PRAGMA writable_schema` and `ATTACH` are all refused with SQLITE_AUTH, and `sql.exec` RUNS EVERY statement of a multi-statement string (a `SELECT 1; DELETE ...` deleted the rows). So read-only is enforced by what the code can reach, in this order: (1) the constant allow-list: only a metric NAME crosses the RPC, never SQL text; (2) a static test over the table: one statement, a single `SELECT` aggregate, no `;`, no write keyword, no `ATTACH`/`PRAGMA`/DDL; (3) an `EXPLAIN QUERY PLAN` test per metric (works on workerd) that must use an index, no full scan of a large table; (4) the numbers-only return type, tested, so no row can leave; and, as defence in depth for DML, (5) a rollback guard: the statement runs inside `transactionSync`, and `cursor.rowsWritten > 0` throws, which the spike proved undoes an `INSERT` and a multi-statement `DELETE`. DDL under the rollback guard is NOT verified (the spike hit SQLITE_LOCKED on `CREATE`/`DROP` inside the harness), so DDL is excluded by (2) alone. Per-store latency on a large store is not measured yet; the 2 s timeout is a starting value to be set from the first measurement.

Cost if wrong: a metric whose query is slow or scans too much slows that store's Durable Object for a few seconds for everyone on it (bounded by the index test, the timeout, concurrency 8, the cache and the kill switch); an allow-list that grows carelessly becomes a data-export path (bounded by numbers-only output, one ruling and one review per metric); using the super_admin + MFA session for the CLI means the controller's own session is the credential, so a stolen session could read counts (it could already read the same stores through the admin UI).

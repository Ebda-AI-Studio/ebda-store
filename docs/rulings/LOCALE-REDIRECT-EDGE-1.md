# LOCALE-REDIRECT-EDGE-1

> Section: 2026-11-09 — production check after #494

Ruling LOCALE-REDIRECT-EDGE-1 (2026-11-09) - the Worker, not the root layout, now redirects an old unprefixed URL of a store with language-in-the-URL on (`apps/web/locale-redirect-edge.ts`, called first in `sentry-worker-entry.ts`). Evidence: `curl https://storedemo-lamma.ebda.app/` returned the 308 with an 82 KB `<html id="__next_error__">` body. A `permanentRedirect()` thrown inside the root layout render comes back as Next's error shell. It costs a whole layout render (store fetch, metadata, viewport) for a response that is only a Location header, and lamma/dahab returned 500 for the same request earlier that day, when something in that render failed before the redirect. Now it is an empty-body 308 (store default language) or 307 (visitor cookie in the other language), `private, no-store`. It uses the same rules as before (`decideLocalePath` + `pendingRedirect`) and gets the default language from the store resolver call the edge cache already makes (`storeVerdict`, which now carries `defaultLanguage`, remembered 60 s per isolate). Anything the Worker cannot decide falls through to Next exactly as before: not GET/HEAD, locale paths off for the store, the admin preview (`?_preview=`), a non-pending path, an unknown or inactive store, or the resolver down. The default language is BOUNDED-stale for <= 60 s per isolate after a merchant changes it, the same window the layout's data-cache read had. Tests: `tests/unit/locale-redirect-edge.test.ts`. Cost if wrong: for up to 60 s after a merchant switches the default language, a first visit lands on the previous language's URL (the switcher is one tap); no browser keeps the redirect.

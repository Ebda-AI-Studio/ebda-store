# ACCOUNTS-PAGE-1

> Section: 2026-11-10 - accounts.ebda.app gets its own Ebda AI Studio sign-in page (branch `feat/accounts-standalone-signin`, launch-map row ACCOUNTS-PAGE)

Ruling ACCOUNTS-PAGE-1 - `GET accounts.ebda.app/login` is a standalone Ebda AI Studio sign-in page served by the `ebda-accounts` Worker (`apps/accounts/src/sign-in-page.ts`), and `GET /` 302s to `/login` on the same host carrying only `product`, `return`, `return_to`, `lang`. It replaces, for these two paths only, the 302 to `store.ebda.app/login` of Ruling ACCOUNTS-ENTRY-1; `/sign-in` and every other route are unchanged, and the Store sign-in page (`apps/admin`) is not touched. The page holds no auth logic: its script (`/sign-in.js`, served by the Worker) calls the same `POST /login {email, password, aud:'store'}` and `POST /login/mfa {challenge, code|backupCode}` as the Store page, so the limiters, the CSRF checks (`originGuard`, JSON-only bodies), the audience rule and the `__Host-ebda_rt` cookie are the service's own. To let its same-origin POST pass those checks, `https://accounts.ebda.app` is added to `ALLOWED_ORIGINS` and to `ORIGIN_PRODUCTS` as `store` (like store/orders); the minted store token is discarded and each product asks `/token` for its own audience from the cookie. `return` (Ebda Chat's existing name, primary) or `return_to` is validated server-side by the Store's own `safeSignInReturn` (Ruling SIGNIN-RETURN-1, imported, not copied; `cf-accounts-deploy.yml` now also triggers on that file), default `https://store.ebda.app/`. `product` is an allowlist (`whatsapp`/`chat` -> "Sign in to Ebda Chat", `store` -> Ebda Store, anything else -> generic studio sign-in), never rendered raw. CSP: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src https://ebda.app; form-action 'none'; base-uri 'none'; frame-ancestors 'none'`, plus noindex, `no-store`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`; with no script nothing is submitted (no credential can reach a URL). Passkeys, forgot-password and sign-up stay on the Store pages and are linked (passkeys on a new origin need `PASSKEY_ORIGINS` and WebAuthn client code: not a launch-day change). A platform admin who must enrol a second factor is sent to `store.ebda.app/account/security`, as on the Store page. Ebda Chat needs no change: `ebda-whatsapp` `web/src/data/auth.ts` already redirects a 401 from `/token` to `accounts.ebda.app/login?product=…&return=<wa url>`. Evidence: `apps/accounts/test/sign-in-page.test.ts` (open-redirect classes incl. `//evil`, `https:evil`, backslash, double-encoded, userinfo, port, lookalike, http, control characters, length; headers; no inline script/style; cookie attributes; CSRF; audience; limiter; logs; the Chat flow end to end; unchanged routes), each guard mutation-checked red; `sign-in-redirect.test.ts`, `sign-in-entry-params.test.ts`. Cost if wrong: an XSS on accounts.ebda.app would now run on the origin that holds the session cookie and can call every cookie-authenticated route, so the page keeps no inline script, renders only allowlisted or escaped values, and a revert of this one PR (code and the two vars travel together) restores the 302 while the Store sign-in keeps working throughout.

# PWA-MANIFEST-2

> Section: Pre-QA sweep 2026-11-10 (branch `fix/preqa-p2-batch`), extra finding: a visitor on `/en` with no language cookie is handed the Arabic app manifest

Ruling PWA-MANIFEST-2 - the language of the web app manifest comes from its URL: a page under `/en` links `/en/manifest.webmanifest`, a page under `/ar` links `/ar/manifest.webmanifest`, and a page with no language in its path keeps `/manifest.webmanifest`; `Accept-Language` is never read. Root cause (measured in production 2026-11-10): every storefront page linked the one URL `/manifest.webmanifest`, a browser fetches a manifest without credentials unless the link says otherwise, so the `force-language` cookie never arrives and `resolveStorefrontLocale` falls through to the store's default language; on the demo store an English visitor's install prompt carried the Arabic name and description. The middleware already knows the language of a prefixed path, so `decideLocalePath` gains one decision, `manifest`, for exactly `/<ar|en>/manifest.webmanifest`: it rewrites to `/manifest.webmanifest` with the `x-locale-path` request header set and sets no cookie (a manifest fetch must not change the visitor's saved language). Any deeper path (`/en/manifest.webmanifest/x`) keeps today's redirect. The root layout's `generateMetadata` picks the href with `manifestHref(urlLocale)` on all three of its return paths. Next's file convention could not carry this: a root `app/manifest.ts` always overrides `metadata.manifest`, so two links or the wrong one would render; the builder moved unchanged to `apps/web/src/lib/pwa/store-manifest.ts` (`buildStoreManifest`) and a hand-written route `apps/web/src/app/manifest.webmanifest/route.ts` serves it with the same `Content-Type: application/manifest+json` and `Cache-Control: public, max-age=0, must-revalidate` the convention sent. Measured on `next dev` against the production API with `Host: storedemo.ebda.app` and language paths on (2026-11-10): `/manifest.webmanifest` and `/ar/manifest.webmanifest` answer 200 and are byte-identical (`cmp`) to the production manifest captured after #505; `/en/manifest.webmanifest` answers 200 with the English name and description; none of the three sets a cookie; `/en` renders exactly one `<link rel="manifest" href="/en/manifest.webmanifest">` and `/ar` exactly one with the `/ar` href. Evidence: `apps/web/src/lib/pwa/store-manifest.test.ts` ("the language in the URL decides"), `apps/web/src/app/manifest.webmanifest/route.test.ts` (body and key order, headers, no file-convention manifest left beside it), `tests/unit/web-locale-paths.test.ts`, `tests/unit/storefront-head-metadata.test.ts`; removing the `manifest` decision turns five tests red, dropping `manifest` from the metadata turns one red. `scripts/ci/next-worker-smoke.mjs` now also asks the built storefront Worker for `/manifest.webmanifest` and requires 200 `application/manifest+json`, because nothing else in CI requests the route from a build.

Residuals, accepted for launch. (1) A store with language paths off (`STOREFRONT_LOCALE_PATHS_STORES` does not name it) has no language in its URLs, so its manifest still follows the store default; production runs `all`. (2) `start_url` stays `/` in both languages, so an installed app opens in the store default and then follows the visitor's cookie; changing it would break the byte-identical Arabic manifest. (3) `/ar` pages now link a new URL with the same bytes; by the manifest specification an installed app is identified by `id`, else `start_url`, not by the manifest's own URL (inferred from the specification, not measured on a device), `start_url` is unchanged, and no store has launched, so no installed app exists to be affected. (4) HTML already held at the edge keeps linking `/manifest.webmanifest` until it expires; that route still answers. (5) Not verified locally on the built Worker (Next production build, OpenNext, workerd): the CI smoke is the first run of it, and production must be re-measured after the deploy.

Cost if wrong: if the built Worker does not serve the hand-written route, every storefront loses its manifest (no install prompt, a console error on each page) until a revert; the CI smoke refuses the PR before that reaches a deploy.

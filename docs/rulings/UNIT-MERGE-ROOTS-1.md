# UNIT-MERGE-ROOTS-1 - the unit merge job re-roots the shard blobs and fails when a shard is dropped

Ruling UNIT-MERGE-ROOTS-1 - the `Unit Tests` merge job (`vitest run --merge-reports --coverage`) first runs `scripts/ci/unit-merge-blobs.mjs reroot .vitest-reports "$GITHUB_WORKSPACE"` (every `<runner root>/_work/<repo>/<repo>` prefix in the blobs becomes this checkout's path), tees the merge output to `$RUNNER_TEMP/unit-merge.log` under `pipefail`, and then runs `unit-merge-blobs.mjs check`, which FAILS the job unless the merged `Test Files (N)` equals the sum of the shards' file counts (`blob[2].length` per blob) or the summary line is missing. Evidence (measured 2026-11-18): (1) #951 group run 44343978493: all 3 shards ran on ebda-mac-1 (root .../actions-runner-ebda/\_work/ebda-store/ebda-store), the merge job on ebda-mac-2 (.../actions-runner-ebda-2/...): vitest keeps only blob entries under the merge checkout's root, matched none, and logged `No test files found, exiting with code 1` with no failure text (CI log line 17202, before the coverage table); reproduced locally from the run's blob artifacts (RC=1) and fixed by rewriting the roots (RC=0, `Test Files 2080 passed | 3 skipped (2083)`). (2) The silent false-green: #955's passing group run 44326426543 (shards on ebda-mac-1, -2, -1; merge on ebda-mac-1) reported `Test Files 1386 passed | 3 skipped (1389)` where a full run has 2083 files (695 + 694 + 694 per shard blob): one whole shard (694 files) was DROPPED from the merged report and from the coverage the 24%% threshold is computed on. (3) Of 10 recent runs with this job, the only failure is the one where the merge runner ran none of the shards. The shard jobs still gate their own test failures, so a failing test was never lost; the merged coverage/threshold and the file counts were computed on partial data. Pinned by tests/unit/unit-merge-blobs.test.ts (mixed-root fixture, drop detection with the 2083 vs 1389 numbers, CLI exit codes, ci.yml order reroot -> merge -> check; mutations: check disabled, root regex disabled and the check step removed from ci.yml each fail). Verified on the real blobs of run 44343978493: reroot rewrites 4641/5189/5009 paths, check reports 2083 == 2083 against the re-rooted merge. Cost if wrong: a blob format change makes reroot refuse (a blob with no runner root fails loudly) or the check fail; both stop the merge job red instead of green on partial data.

Amendment (AI review of #957, two criticals): (1) vitest/tinyrainbow colours the summary even when piped to `tee` on Actions (CI + GITHUB_ACTIONS set), so the `Test Files (N)` parse would have failed on every real run (my local proof ran without colour). `mergedFileTotal` now strips the SGR escapes before parsing, the merge step sets `NO_COLOR=1`, and the tests use the real escape sequence (and are run with CI=true GITHUB_ACTIONS=true FORCE_COLOR=1); mutation (no strip) fails. (2) The root pattern matched only `<root>/_work/<repo>/<repo>`; it is now ANY absolute prefix followed by `/<repo>/<repo>`, with the repo taken from the checkout root's own directory name (so `/home/runner/work/ebda-store/ebda-store` and a custom prefix are rewritten, while an arbitrary doubled directory such as `/x/lib/lib` and a single `/x/ebda-store/` are not); mutation (back to `_work` only) fails. A blob with no workspace root to rewrite still refuses the merge (fail closed) with a message naming the expected `/<repo>/<repo>`.

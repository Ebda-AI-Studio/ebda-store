# GOLD-DISAGREE-MERCHANT-1

> Section: Gold-rate pricing (2026-11-09, branch `feat/gold-disagree-merchant-decides`)

Ruling GOLD-DISAGREE-MERCHANT-1 - when the two gold-rate feeds disagree beyond the 2 % cross-check, the STORE OWNER decides, not the platform operator (Ahmad, 2026-11-09). (1) Every opted-in store keeps getting a PENDING rate (`forcePending`, nothing auto-applies; unchanged) whose `feed_reference.disagree` carries both 24k values, the gap and that store's fallback candidates; `GoldRateService.getState` returns it as `disagreement`, the gold-rates page shows `DisagreementBanner` (apply first source = confirm the pending rows; apply second = the existing manual PUT with `confirm: true` then reject the pending rows; own rate = the existing editor, the page rejects the pending rows after it saves; keep current = reject), the dashboard `GoldRateBanner` says so, and ONE email per store per disagreement episode goes out (sentinel `gold:disagree-mail:<store>`, set after the send, cleared by the first run where the feeds agree, 3-day TTL as the backstop so a disagreement longer than 3 days re-notifies once per 3 days). No second confirm flow was built. (2) The platform alert is `info` (`cron.gold-rate-feed-disagree`), it no longer pages. A platform P1 still fires for both feeds down (`cron.gold-rate-feed`) and for a gap over `DISAGREE_SANITY_BPS` = 2000 (20 %, `cron.gold-rate-feed-broken`): that is a broken feed or conversion, so nothing is stored and no merchant is asked to pick between garbage. (3) A store that does not decide keeps its last CONFIRMED rate; price is NEVER-stale, so the rule is: no auto-apply ever, the rate ages out through the max-age checkout block and the staleness watch (fail closed); pending rows are not read for pricing, so no cache invalidation is owed until a decision applies one, and that path already purges every layer (B5-21). Cost if wrong: an owner who ignores the email and banner sells gold products on a rate that drifts from the market until the max-age block (26 h) stops those orders, and one that picks the wrong source reprices at that source's figure (bounded: the two sources are within 20 %).

Ruling GOLD-FALLBACK-LAG-1 - the fallback is ONE daily file, so against a live primary its age is lag, not disagreement (2026-11-11). Measured: fallback dated the day before (gold 4121 vs live 4058 USD/oz, EGP 53.98 vs 53.35) gave 281 bps against a correct primary and opted-in stores were asked to decide for nothing. When the fallback's own time is older than 6 h the cross-check gate is `STALE_FALLBACK_CROSS_CHECK_BPS` = 600 (200 stays for a current file); the 2000 bps sanity bound is unchanged. Units were checked and are right. A demo store (no owner to decide) takes the primary on a disagreement instead of a pending rate nobody sees. The dashboard banner now shows for any waiting rate even with zero gold products, and the product gold toggle shows an explanation while store gold pricing is off: turning ON is disabled, turning OFF always works. Cost if wrong: a primary that is wrong by 2-6 % while the fallback is a day old is applied without asking the owner (bounded by the max-age block and the 20 % sanity stop).

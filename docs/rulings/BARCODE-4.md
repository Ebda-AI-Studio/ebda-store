# BARCODE-4

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling BARCODE-4 - minimum scannable size, replacing "it decodes at 1600px". (1) The bars carry a COMPACT reversible scan code, not the printed number: `ORD-<6 base36>-<5 base36>` packs into 18 digits (Code 128 C, 134 modules + 20 quiet = 154, vs 211 for the raw 16 chars in B), `EBD-<16 digits>` into its 16 digits; the number is still the printed label and `orderNumberFromScanCode` inverts it (the orders app scans the digits). Legacy 24-char numbers keep B and will fall back to plain/too-narrow; not promised. (2) Floor: a module is never narrower than 2 css px at the surface's display width (`MIN_MODULE_CSS_PX`; 2px at 96 dpi is 0.53 mm in print, over the 0.25 mm floor). Display widths: storefront receipt 344, invoice 360, billing receipt 344, email PNG 360 shown (720px file). (3) A shape that would break the floor at that width renders PLAIN (`resolveBarcodeShape`, rule c): at 344/360 only `pineapple` (1.96 css px at 344) falls back; palm, the billing shape, passes. (4) Gate: `shaped-barcode-decode.test.ts` decodes every shape x 3 real-format numbers at the real CSS width (1x, worst case) and the 2x email size, with the decoration stripped (zone alone must decode); deleting the zone path fails it. Evidence: 156 cases. Cost if wrong: a device whose camera cannot read 2 css px modules prints unscannable receipts; the store can pick `plain`, whose modules are the same width, so the real lever is the display width constants.

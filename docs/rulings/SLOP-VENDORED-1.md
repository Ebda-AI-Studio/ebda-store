# SLOP-VENDORED-1

Ruling SLOP-VENDORED-1 (controller, 2026-11-14) - the slop guard (`.github/pr-quality/slop-guard.mjs`) waives ONLY the `unused-export` rule, ONLY for the vendored `@ebda/foundation` folder (`foundation.lock.json` "dir", `packages/shared/src/foundation`), and ONLY while the lock proves every vendored file byte-matches the tagged release and the parity test (`tests/unit/foundation-parity.test.ts`) exists. It is the single `ruleExemptions` entry in `.pr-quality.json`; there is no whole-folder `skip`. `no-any` and every other rule still run on vendored files. Why: the vendored exports are the shared API of every Ebda product, consumed unevenly by each, so "nothing in this repo imports it" is not slop there; editing vendored files to satisfy it is forbidden (the lock). Evidence: `tests/unit/slop-vendored-exemption.test.ts` (waived only for that folder and only that rule; OFF when the parity test is removed, the path widens, another rule is named, a second entry or a short reason appears, a vendored file is edited or an unlocked file appears, or there is no lock; the real config has exactly one narrow entry). Ids the active waiver covers are ignored on both sides of the baseline compare, so an old baseline entry for a waived vendored export never forces every later PR to rewrite the baseline. Note: CI runs the guard from the BASE branch, so the exemption takes effect on the first PR after this lands on main; the store's copy of the guard is tested on this PR by the unit test above. The guard script is a copy of ebda-foundation `ci/pr-quality/slop-guard.mjs`; the foundation copy should adopt the same `ruleExemptions` handling. Cost if wrong: a genuinely dead export inside the vendored foundation is not flagged in a product (the foundation's own guard still sees it).

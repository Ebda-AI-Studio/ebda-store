# SKIN-DEL-10

Ruling SKIN-DEL-10 - SKIN-DEL-9's rejecting triggers are a CONTRACT step and ship one release after the code stops writing retired templates; until then every shipped migration is expand-only. Audit 2026-11-12 (backfill-data-jobs, P2-2): `platform/0009_store_template_current.sql` and `store/0004_template_current.sql` remapped retired skins lossily and added BEFORE INSERT / BEFORE UPDATE OF template triggers that ABORT on a retired value. `cf-api-deploy.yml` runs `wrangler d1 migrations apply` BEFORE `wrangler deploy`, so (a) the previous release's isolates run against the new schema for the whole deploy window, (b) a code rollback (deploy-guard) leaves the triggers under old code, and (c) a restore that replays rows holding a retired value into a database built from the migrations hits the trigger. A migration must never reject what the running release, or the one a rollback returns to, can write (standard `migrations-backward-compatible`). Fix, applied as forward migrations because 0009 and 0004 are already applied in production (the d1_migrations ledger and each DO's `_migrations` row are keyed by name, so editing their text changes nothing in prod and would only make fresh databases disagree with live ones; they are left untouched): `platform/0010_store_template_original.sql` (generated late column `stores.template_original`, the revert path) and `platform/0011_template_expand_only.sql` (drops the two triggers; sets `template_original = 'modern'` for `qa-walk-store-1010`, the only row 0009 is known to have remapped; no other original survives, 0009 kept none); `store/0006_template_expand_only.sql` (`cf-0006_template_expand_only`, drops the two `store_profile` triggers; DO stores are pre-launch and keep no original). Code needs no change: readers already map any stored value through `normalizeLegacyTemplate` and writers reject a retired value at the API (400 TEMPLATE_RETIRED), so a retired value reaching the column is stored and read as its mapped template. The triggers are parked, unshipped, at `packages/cf-schema/migrations-pending/platform/0012_template_current_contract.sql` and `.../store/0007_template_current_contract.sql` (outside `migrations/`, not in `STORE_MIGRATIONS`; a test pins both facts and that each works on top of the shipped set). GATE to move them into `migrations/`: the release that stopped writing retired templates has been live one full release, the previous release writes none, prod `SELECT count(*) FROM stores WHERE template NOT IN (...)` is 0, and the previous release's backup has been restored in the drill. `packages/cf-schema/test/store-template-current.test.ts` proves: no template trigger after the shipped set (D1 and DO), a prod DB at 0009 upgrades with triggers gone, and a pre-0009 backup's rows (retired skins) load into a database built from the shipped migrations (fails against the old set: 5 tests). Not verified: `restoreD1FromBackup` itself in workerd (apps/api `cf:test`), and `parity.test.ts` / `model-split.test.ts` (need a generated Prisma client, absent here). Cost if wrong: a retired template can again be stored for a window (rendered as its mapped template, so nothing visible); undo = move the two pending files into `migrations/` early, which re-creates the abort-on-write behaviour this ruling removed.

# COD-REFUSE-1

Ruling COD-REFUSE-1 (2026-11-11, Fixes #614) - a customer's WhatsApp "refused" (and the cancel of a chat order whose buyer was erased) may cancel an order ONLY from a pre-ship state (`pending`, `confirmed`), decided atomically inside the store's Durable Object: the DO `cancel` op takes `onlyFrom` and reads the status in the same section as the cancel (the DO runs one op at a time with no await between the read and the write). When the order is already `processing`, `shipped` or `delivered` (a ship that landed between the consumer's read and its cancel, or a refusal that arrives after shipping), nothing changes but a delivery-exception note appended to the order for the merchant (Arabic first, English after): no cancel, no restock, no reversal; the Worker answers 409 `ORDER_STATUS_MOVED` and the consumer records "not acted". Evidence: `apps/api/workers-test/merchant-orders-do.test.ts` ("a COD refused racing the merchant ship"): on the old code the DO cancel of a shipped order restocked it (inventory 48, expected 46) and no shipped order got a note; green now, including five concurrent ship + refuse pairs where stock returns only for the cancelled ones; `packages/repo/test/do-order-ops.test.ts`, `tests/unit/wa-store-events-consumer.test.ts`. Cost if wrong: a refusal for an order that is still being prepared (`processing`) no longer cancels it automatically; the merchant reads the note and cancels by hand.

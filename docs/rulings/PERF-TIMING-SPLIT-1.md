# PERF-TIMING-SPLIT-1

Ruling PERF-TIMING-SPLIT-1 - when a request called AuthState, its `Server-Timing` carries three more entries beside the existing `auth-state;desc=<calls>;dur=<summed ms>`: `auth-state-crit;desc=<calls finished before the response head>;dur=<their summed ms>` (the trips the response actually waited for), `auth-state-open;desc=<calls not finished at that moment>` (in flight, or the rest of a cache write-back that runs in waitUntil after the response) and `auth-state-max;dur=<slowest single call ms>`. Observability only: no call, order, cache or limiter changes; the same credential-path rule applies (sign-in, register, reset, MFA, passkeys and staff-invite responses carry no io entries in production, `showsIoCounts`). Why: the 2026-11-19 live check of #868 showed 5-7 `auth-state` calls on cold paths, but `auth-state` counts background write-back trips too, so call count could not be told apart from per-call latency (a fresh-host resolve is about one critical-path trip taking 1-2 s). Evidence: tests/unit/io-tally.test.ts (crit/open/max, nothing added without AuthState), mutation-checked by removing the finished-call count; the latency-budget parser ignores the new names (it only reads known kinds). Cost if wrong: a few extra bytes on every AuthState-touching response and a `crit` figure that is a lower bound (a call that finished after the head but still delayed it cannot exist, so it is exact for the response; background trips show only as `open`).

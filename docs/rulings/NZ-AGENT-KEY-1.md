# NZ-AGENT-KEY-1

Ruling NZ-AGENT-KEY-1 (2026-11-11, follows NZ-MONEY-AGENT-1) - a store on its Durable Object has an agent (MCP write) key: `StoreCredential` joins `DO_WRITABLE_MODELS` (and `storeCredential` the `WritableModel` list), and `routes/agent-credential.routes.ts` GET / POST / DELETE read the row through `storeDb` and write it through `storeWriter(...).storeCredential.upsert` with the same `encryption.encrypt` ciphertext as before; the plaintext is returned once by POST and never logged or stored. The rotation time of a DO store is the credential row's `updatedAt` (`Store.agentApiKeyRotatedAt` is not a DO column); a Postgres store keeps its relation write byte for byte. Nothing is weakened: the key is still checked per request by `agent-auth.ts` (decrypt + constant-time compare), a rotation or revoke takes effect on the next call, the generic write path only ever sees ciphertext, and the POST/DELETE chain (MFA, store access, feature gate, `rejectImpersonated`) is untouched. Proof: `workers-test/merchant-mcp-do.test.ts` mints a key, sees `hasKey` true, places a COD order with it, rotates (the old key is refused at the write gate, the new one works), revokes (writes refused), `pgReaches` empty; on the previous code the mint fails with STORE_RECORD_REFUSED. Cost if wrong: if the DO row were readable by a path that returns columns unfiltered, the ciphertext (not the plaintext) could leak, and a DO store's `rotatedAt` would show the last row touch rather than a rotation-only time.

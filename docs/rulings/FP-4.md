# FP-4

> Section: Admin fix pass 2026-11-04, track T1 API core (branch `feat/admin-fix-t1-api-core`)

Ruling FP-4 - staleness class NEVER-stale (account suspension, role change, deletion). The account-state half of the live identity check (`getAccountState`) is cached per ACCOUNT for 30 s and shared by concurrent requests (`accountStateCached`, `apps/api/src/lib/identity-live-cache.ts`; one in-flight lookup per account); only a POSITIVE answer (the account exists and is `active`) is stored, a suspended, inactive, unknown or failed answer never is. `setAccountStatus`, `setAccountRole` and `revokeIdentityUser` invalidate the entry on this isolate in `finally`. Session REVOCATION (`isRevoked`, the logout path) is NOT cached: it is asked on every live request. Both RPCs have a 3 s budget (`withIdentityTimeout`, 503 `IDENTITY_UNAVAILABLE` on expiry, never an allow). The two answers a request already fetched in `tenantContext`'s pre-check (LAZY-TX-3) are handed to `authenticate` through a per-request memo, so nothing is asked twice. Residual: a suspension, role change or deletion made through another Worker isolate, or directly at the identity service, is seen after at most 30 s. Evidence: `tests/unit/identity-timeout.test.ts`, `tests/unit/accounts-token-auth.test.ts`. Cost if wrong: a just-suspended merchant keeps acting for up to 30 s on an isolate that cached them as active.

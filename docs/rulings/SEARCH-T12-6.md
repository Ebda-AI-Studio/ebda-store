# SEARCH-T12-6

> Section: 2026-10-16 — Search program, PR 4 (P1c, hybrid ranking): SEARCH-T12-\*

Ruling SEARCH-T12-6 (coordinator security review, 3 findings on the SEARCH-T12-3 commit) — ONE charge point for every query-time Workers AI call: `takeQueryEmbed(storeId, searcher)` (`apps/api/src/lib/search/embed-budget.ts`), called exactly once per real provider call, immediately before it, inside `queryVector` (`product-search.service.ts`), and never on a query-vector cache hit. (1) Parser differential, CONFIRMED in a different shape than reported: the route middleware decided "embed-eligible" from its own reading of `sort`, so `?search=x&sort=foo`, `sort=RELEVANCE` or `sort[]=x` was NOT counted by the limiter while the route treated the unknown sort as no sort and ranked it (embedding uncounted). Fixed by deleting the predicate: the middleware is gone and the per-searcher counter is charged at the provider call, so no URL shape, parameter name, repetition or encoding can reach the provider without being charged. The limiter key stays the SEARCHER (normalised IP, `searcherFromIp`), deliberately NOT the normalised query the review suggested: a key per query value gives every unique query a fresh bucket, which is exactly the attack. (2) Wrong accumulator, CONFIRMED in a different form: the counters were already charged per real call and never on a cache hit, but a refused attempt still INCRemented the store and platform daily counters, so one rate-limited client could burn the whole store's day. Now the searcher's per-minute counter is checked first and alone, and a refusal by any daily cap refunds all three daily counters (`DECR`), so each daily counter equals the provider calls actually made (a crash between the steps can over-count by one, never under-count). (3) MCP sibling path, CONFIRMED: `search_products` (`apps/api/src/mcp/tools/catalog.tools.ts`) reaches `listPublic`'s ranked path; it was already under the flag and the daily budgets (both live in the service) but bypassed the per-searcher limit. It now passes the caller's `searcherFromIp(req.ip)` (`mcp.routes.ts` → `buildStoreMcpServer` → `registerCatalogTools`) under the MCP route's existing `runInStoreScope(store.id)`. Default deny: a caller without a searcher never embeds, so a future caller that forgets the identity costs nothing. Caller sweep (`grep` of `rankedSearch|semanticProductIds|queryVector|takeQueryEmbed|listPublic(`): embed-capable = `/public/products` (searcher = IP) and MCP `search_products` (searcher = IP); `listPublic` without a search = the AI product feed (never ranked); lexical-only, never embed = admin product list + exports (`product.service` list, `admin.routes`), `wa-bridge.routes` (WhatsApp, flagged off), `bulk.routes` + `bulk.service`, `bundle.routes`, `promotion.service`, `warehouse.service`, typeahead `/search/suggest`; the indexer's own provider calls go through `takeEmbedCalls`. Evidence: `hybrid-search-abuse.test.ts` "no URL shape escapes the limit" (400 requests over 10 shapes from one IP: ≤ 20 calls per minute window) and "MCP search_products goes through the same gate" (1000 unique queries from one agent IP: ≤ 20 per window, the semantic hit appears exactly when an embed was granted; built without a searcher: 0 calls); `hybrid-search.test.ts` "a cache hit charges nothing; every miss charges once" (store counter == 1 == provider calls), "no searcher identity → never embeds", "one searcher, 1000 unique queries"; `search-embed-budget.test.ts` (refusals refunded, the 980 refused attempts of one client never reach the store's day, IPv6 /64). Each guard deleted in turn turned its test red (no-searcher deny, per-searcher check, refund, MCP searcher, charge-on-hit). Residual: the per-minute window is fixed, so a client can make up to 2× the limit across a minute boundary; and a search degraded to keyword-only (budget or limit) is cached for 120 s like any other result, so a client that spent its own limit can make a popular term keyword-ranked for others for one cache lifetime (quality only, never an error). Cost if wrong: one client gets at most 40 embeds in a 2-minute span, and a popular term can lose semantic ranking for 120 s. **Amended (Task 12 review M4):** `searcherFromIp` groups IPv6 by /64 explicitly (`ipKeyGenerator(ip, 64)`; the library default is /56, which the docs mis-stated), and a request with no IP returns `undefined`, so it gets no embed (keyword-only) instead of sharing one `ip:noip` bucket with every other IP-less request (`search-embed-budget.test.ts`: two /64s inside one /56 differ; no IP → `undefined`; red before).

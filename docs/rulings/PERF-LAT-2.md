# PERF-LAT-2

> Section: 2026-11-09 — follow-up of PERF-LAT-1 (latency audit, PR #485), launch map PERF-LATENCY

Ruling PERF-LAT-2 (2026-11-09) - the product-cache bust (`clearProductsRedis`, behind both `invalidateStoreProductCachesAfterOrder` on every order and `invalidateStoreProductCaches` on every content write) runs its eight invalidations TOGETHER (`allInvalidations`, `Promise.allSettled`), not one after another. Nothing is dropped: every key and prefix (public product list, product detail, suggest, recommendations, admin product list, public + admin categories, bundle list) is still cleared in every layer, each still bumps its generation BEFORE its own delete (the keys are disjoint, so no invalidation waits on another), and the storefront purge is unchanged. Failure semantics: every invalidation now runs to its end even if one throws (the serial chain stopped at the first throw and left the rest stale), and the first error is re-thrown afterwards, so `OrderService.bustProductCaches` logs the same warning as before and the order never fails on it. Evidence (local workerd, PR #485's `latency-budget.test.ts` run on this branch merged with #485): guest COD order create 37 -> 19 serial round trips, remote calls unchanged at 30 (the same calls, made in parallel); `tests/unit/order-cache-bust-concurrent.test.ts` counts the bust alone at 16 -> <= 2 waves with the io-tally wave rule, checks every delete, the bump-before-delete order and the failure behaviour. Cost if wrong: concurrent generation bumps for one store land on the AuthState DO in one burst (eight INCRs instead of eight spaced ones); the DO serialises them, so the only cost is a few ms of DO time per order.

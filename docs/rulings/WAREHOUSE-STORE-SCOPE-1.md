# WAREHOUSE-STORE-SCOPE-1

> Section: 2026-10-15 — Phase B1 Qamar (B1-\*)

Ruling WAREHOUSE-STORE-SCOPE-1 (search Task 11 review M9, pre-existing since 2f0e2541a / fc70b0dea) — `WarehouseService.syncAggregateInventory(storeId, productId, variantId, tx)` now takes the store id from its callers (`setStock`, `adjustStock`, which already had it) and every raw statement carries it: `products` lock + UPDATE `AND "store_id" = storeId`, the `warehouse_stock` SUM `"store_id" = storeId`, and the `product_variants` lock + UPDATE through their product (`product_id = productId AND EXISTS (products … store_id = storeId)`; variants have no `store_id`). Before, a wrong product id from another store relied on RLS alone (0 rows silently under `ebda_app`, a real cross-store write on any BYPASSRLS role) — a breach of the Global Constraint "every raw query that names a tenant table carries store_id". Evidence: `tests/integration/warehouse/sync-aggregate-store-scope.test.ts` on the owner (BYPASSRLS) fixture client: another store's id leaves product and variant inventory unchanged, the right store recomputes (red before: old signature); the warehouse suite's other 5 files pass (`reconcile-endpoint.test.ts` needs the HTTP API on :4000 and fails identically on the base commit locally). Not changed, noted for the inventory owner: the variant path writes `products.inventory = SUM(all variants)`, while CLAUDE.md's inventory model says a variant product's `products.inventory` stays 0 and stock counts ACTIVE variants only. Cost if wrong: none; a store-mismatched call now updates 0 rows exactly as RLS already made it on `ebda_app`.

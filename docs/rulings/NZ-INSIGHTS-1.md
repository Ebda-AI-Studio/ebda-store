# NZ-INSIGHTS-1

Ruling NZ-INSIGHTS-1 (2026-11-11, Postgres removed from the Worker; row 1 of `docs/cf/neon-zero-final-classification.md`) - every `/stores/:storeId/insights/*` route reads a store on its Durable Object from the DO: the sixteen `runInTenantContext` wrappers become `readInStoreContext` (bare store scope on a DO store, the same tenant transaction on a Postgres store), the `order.aggregate` / `orderItem.groupBy` reads go through `storeDb(storeId)` (prisma-lite: aggregate, groupBy and the to-one `order` relation filter), and the dashboard's repeat-purchase rate is the new DO read op `analyticsRepeatBuyers` (`packages/repo/src/do/analytics-reads.ts`), the SQLite twin of `repeatPurchaseInDb`: same buyer key (customer id, else lowercased email, else verbatim phone, each only a non-empty JSON string; NO `'guest:' || id` fallback, unlike `CUSTOMER_KEY`), two counts, never the rows. Found with it and fixed at the source: prisma-lite answered `_count: true` as `{ _all: n }` while Prisma answers a number, so the dashboard's `orderCount30d` (and `return.service` / `review.service` / `analytics.service` counts that read `_count` as a number) rendered an object on every DO store; `_count: true` is now a number in `aggregate` and per group (`packages/repo/test/prisma-lite-review.test.ts`, Prisma parity case in `prisma-lite-writes.diff.test.ts`). Proof: `apps/api/workers-test/merchant-orders-do.test.ts` (a DO store with a registered customer and guests, five real COD orders marked paid) answers every insights page and the other dashboard cards with zero Postgres reaches; on the old code `/insights/dashboard` was a 500 (`POSTGRES_REMOVED ... $transaction`). Cost if wrong: a merchant's dashboard shows a wrong repeat-purchase rate if the SQLite key drifts from `customerKeyOf` (the unit case pins the three key kinds and the unpaid/out-of-window exclusions).

# FP-2

> Section: FP-2 (2026-11-04, admin fix pass T2, L-1)

Ruling FP-2 - loyalty on DO stores: the DO is the source of truth; the Postgres loyalty rows of a DO-backed store are migrated once. Evidence: `loyalty.service.ts` read and wrote `loyalty_points` / `loyalty_transactions` on Postgres for `awardBonusPoints`, `initializeCustomerPoints`, `awardReviewBonus`, `getCustomerPoints`, `getTransactionHistory`, `listMembers`, `getStats` and the admin transaction log, while earn, redeem and both reversals already ran on the StoreDO (CF-MONEY-1, CF-ORDERS-1), so on a `storage_backend = 'do'` store the admin pages showed nothing earned and a manual award was never seen by the DO redeem. Every one of those now branches on `storeMoney(storeId)` to new money ops (`loyaltyAward`, `loyaltyInit`, `loyaltyReviewBonus`, `loyaltyCustomerPoints`, `loyaltyHistory`, `loyaltyMembers`, `loyaltyStats`, `loyaltyStoreTransactions`); earn / redeem / reversal semantics are untouched. The one-off `loyaltyImport` (service `LoyaltyService.migrateLedgerToDo`, dry run by default, `docs/cf/loyalty-do-migration.md`) copies the Postgres-only ledger rows keyed by transaction id (or the same customer / type / points / time) so a re-run and an already-copied row move nothing; Postgres rows are never deleted. A DO store with no `store_config` row has loyalty off. The members list joins the customer's name and email from Postgres `users`, scoped to the store's customer accounts (SEC-CUSTOMER-SCOPE-1). Evidence of behaviour: `packages/repo/test/do-loyalty-admin.test.ts`, `apps/api/workers-do/loyalty-admin.test.ts` (real workerd), `tests/integration/repo-factory-money-contract.test.ts` (Postgres vs DO traces). Cost if wrong: points are double counted or lost for the DO stores; the idempotent key makes a re-run safe and the Postgres rows remain, so a wrong import is reversible from them.

# SEARCH-T12-3

> Section: 2026-10-16 — Search program, PR 4 (P1c, hybrid ranking): SEARCH-T12-\*

Ruling SEARCH-T12-3 (coordinator security review: cost amplification) — anonymous storefront search cannot be used to spend Workers AI. Unique queries defeat the query-vector cache, so the bound is: (1) budgets per Cairo day in Redis, all of which must have room (`takeQueryEmbed`, `apps/api/src/lib/search/embed-budget.ts`): the account-wide `SEARCH_EMBED_GLOBAL_DAILY_CAP` (20 000, now shared by the indexer and queries, so one ceiling bounds daily spend), a query-wide `SEARCH_QUERY_EMBED_GLOBAL_DAILY_CAP` (10 000, below the account-wide cap so shoppers can never use up the indexer's share) and a per-store `SEARCH_QUERY_EMBED_STORE_DAILY_CAP` (1 000); no Redis = no embed (fails closed); (2) a per-searcher limit (20 query embeds per normalised IP per minute) that DEGRADES instead of refusing: over it the search is keyword-only — first built as a route middleware, then moved into the budget gate itself by SEARCH-T12-6; (3) no embed when the keyword leg is strong (≥ `KEYWORD_STRONG_AT` matches; amended from 20 to 50 = `HYBRID_LEG`, see below), for queries under 3 characters, SKU/model-code-shaped single tokens, and personal-data-shaped terms (`isPersonalDataTerm`); the embedded text is capped at 100 characters; (4) the query-vector cache is keyed per store (no cross-store timing signal about what was searched). Worst case per day is 10 000 query embeds (≈ 0.1 M input tokens at ~10 tokens a query, far under a cent at bge-m3's $0.0118/M). Evidence: `tests/integration/hybrid-search-abuse.test.ts` (1000 unique queries from one IP through the real public router: ≤ 20 provider calls per minute window, every response 200 or the existing `publicLimiter` 429, never 500; a second IP is still served the semantic hit); `hybrid-search.test.ts` "1000 unique queries in one store make at most the per-store budget" (cap 25 → exactly 25 calls, every search answered); `tests/unit/search-embed-budget.test.ts` `takeQueryEmbed` (per-store, query-wide across 1000 stores, shared account cap, cap 0, no Redis). Each guard was deleted in turn and its test went red. **Amended 2026-10-16 (Task 12 review M2, coordinator ruling):** `KEYWORD_STRONG_AT` = `HYBRID_LEG` = 50, one constant in `product-search.service.ts`. At 20 the fused head never saw a keyword list longer than 19, so E10's appended tail never ran and a query with 20-49 keyword hits was never re-ranked; at 50 every list the fused head can hold is re-ranked and the tail is live. Spend stays bounded by the budgets, not by this constant. Task 13's eval measures lift at 20, 50 and no threshold and may change it. The strong count is taken store-wide BEFORE the category, price and option filters (a filtered search with few in-filter hits but ≥ 50 store-wide stays keyword-only; documented, not changed). Evidence: `hybrid-search.test.ts` "30 keyword matches (under the fused head) still embed and fuse" (red at 20) and the 60-match "strong keyword leg" case. Cost if wrong: an attacker with many IPs can spend the day's query budget early and turn semantic search into keyword-only for every store until the next Cairo day (never an outage), and a broad term that matches ≥ 20 products by keyword gets no semantic re-ranking.

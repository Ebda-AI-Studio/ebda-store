# PROVIDERS-ACTIVATION

> Section: PROVIDERS-ACTIVATION (2026-10-08)

Ruling PROVIDERS-ACTIVATION — every payment gateway and shipping carrier the catalog (and the marketing site) lists is a real integration, and an unverified one is switched on PER STORE on request instead of being "coming soon" for everyone. Ahmad's decision; merchants are told activation takes about 5 hours (`ACTIVATION_HOURS`, the marketing line, the admin card and the email all say so). What changed of PROVIDERS-2 / PROVIDERS-9: (1) SAVE and TEST are open to every merchant for every catalog provider (`assertMayConfigure` / `assertMayConfigureCarrier` no longer 403 `PROVIDER_NOT_AVAILABLE`); (2) ENABLING still needs the provider usable FOR THAT STORE: catalog-`verified` OR a `provider_activation_requests` row with `status = 'activated'` for that store + provider (`isProviderUsableForStore`, `assertEnableAllowed(row, {storeActivated})`, `assertCarrierEnableAllowed(row, {storeActivated})`, the three payment-settings enable paths, the shipping save path, the payment factory's runtime offer / `getAvailableProviders`, `createShipmentForOrder` and the pickup service at the point of use); the Test-connection-current rule is unchanged and still applies after activation. Flow: merchant saves own keys and tests, `POST /provider-activation/store/:storeId/:provider/request` (needs saved credentials; idempotent while open; 409 for a verified provider; one live row per store + provider by a partial unique index) → audit `provider_activation.requested`, ops email to `BRAND.supportEmail` (ahlan@ebda.app) through the existing email queue and a P1 Telegram alert through `sendAlert`, both AFTER the request transaction committed and both best effort (the row is the record and shows in the queue). Super admin (`/admin/provider-activation`, authenticate → MFA → super_admin): list with the store's last Test connection (ok / code / mode / time / `current` = covers the credentials stored now), "Run test" re-runs the adapter with the STORE's stored credentials (status only, never a key), "Activate for this store" is refused 409 `CONNECTION_NOT_TESTED` unless that store's latest test passed for exactly the stored credentials (check and write in one transaction), "Reject with note" (note required) emails the merchant. Every action is audit-logged (`provider_activation.{requested,test_run,activated,rejected}`); activation and rejection also email the merchant. A merchant has NO route that sets `activated`. Table `provider_activation_requests` (migration `20261008150000`, expand only): store-scoped, one policy = own store OR an active super admin (`ebda_is_super_admin()`), no contextless allowance; the cross-store list runs through `acrossStores`, one short tenant transaction per store. Evidence: `tests/unit/provider-activation-routes-d1-do.test.ts` (8, ported off Postgres 2026-11-23: real routers + platform D1 requests + one StoreDO schema per store + Kashier and Bosta stubs: save/test but not enable; request + email once, idempotent; refusals; merchant cannot activate; never-tested / stale / failing test blocks activation; after activation the store enables it and checkout offers it while another store cannot; rejection keeps it off and emails; the carrier flow), `tests/unit/provider-connect.test.ts`, the PROVIDERS-2 cases in `provider-connect-routes` and `shipping-carrier-connect-routes` updated to the new rule. Mutations (defence-mutation runner, `--only`, both KILLED): `money-provider-activation-needs-passing-test`, `money-provider-activation-store-scoped` (removing the `storeId` from the activation lookup turned 5 of 8 red). Cost if wrong: a store whose provider was activated on a test that no longer reflects reality keeps it enabled until someone rejects/disables it (there is no revoke action yet; disable from the store's own settings); the activation list reads every store (one transaction each), which is fine at today's store count and should become a definer when it is not.

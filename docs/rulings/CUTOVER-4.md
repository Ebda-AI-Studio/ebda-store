Ruling CUTOVER-4 (2026-10-26) - rollback never discards live writes (Audit DB-1). `__seal` records a per-row sha256 baseline of every StoreDO table and the flip records the same for D1; `flip-backend.mjs --to pg` diffs against it and either replays the added/changed/deleted rows into Postgres in one transaction, committing only when Postgres and the live side then have equal counts and checksums, or refuses (no replay URL, replay or verify failure, live-side data with no Postgres column, a store created or deleted live). `--accept-data-loss` is the only named override. The replay is fenced per store (the row's store key, an ownership predicate on every write, exactly one affected row, read-back; any violation aborts the transaction) and a committed replay rebases the baselines. `__unseal` (exact confirmation string) wipes a DO so a cutover can be retried. Cost if wrong: the replay uses a writable owner connection to Neon; a replay bug that passes the in-transaction digest check could write wrong data into the fallback, so the replay is rehearsed on every rehearsal run and Postgres is never the only copy (the DO keeps its data, sealed).

# NEVER-OVERWRITE-1

Ruling NEVER-OVERWRITE-1 (2026-11-11) - no automated job overwrites a stored product value. The one AI write layer (`writeAiFieldsGuarded`: the Postgres writer and the DO procedure `guardedAiWrite`) is FILL-ONLY by default: a field is written only when its stored value is empty (or is the `name === nameAr` placeholder of an Arabic-only product, NAME-PAIR-1), whatever its `aiFieldSources` stamp. An 'ai' stamp no longer licenses a refresh: the autopilot (`product.upserted`) and the daily sweep (incl. stale refresh) only fill gaps. This covers name, nameAr, description(Ar), meta titles/descriptions, searchTerms and every other AI-writable field. Only a merchant-initiated run may replace a non-empty AI value: hand-back "Switch to AI" (`onlyFields`) and the language-balance button/bulk (revert backup kept); they pass `overwrite`. `generateFill` also stops spending Gemini on such fields. Evidence: QA store 1bb14d0e product Signal Signet, nameAr «خاتم الإشارة» (ai-stamped) replaced by «سيجنال سيجنيت» at 01:04:42Z ~3 min after the last merchant save (the `name` edit put `name` in changedFields, which refreshed the ai-owned nameAr); no repair-product-names request in the 00:50-01:10Z Logpush window; `tests/unit/ai-fill-only.test.ts` (red on the old code). Cost if wrong: an AI translation is never refreshed after the merchant changes the English name; the merchant retypes it or uses Switch to AI.

Addendum (issue #620): the bulk-ai-_ jobs (seo, translate, excerpt, aeo meta, geo citation copy) no longer call `product.update` after the AI wait; they call `writeBulkProductFields` -> `writeAiFieldsGuarded` (compare-and-set against the row they read, 'human' stamps respected, fill-only unless the merchant's own `force`, 'ai' stamped). `tests/unit/ai-writers-use-guarded-write.test.ts` fails if any `bulk-ai-_`/`ai-autofill-\*`job writes`product.update/updateMany/upsert`directly. Extended to every other AI-written entity: category rows and product-image alt go through `writeBulkRowFields`(one atomic conditional`updateMany`per field: matches only while the column still holds what the job read, blank unless the merchant's`force`; 0 rows = skipped), and the Store row (meta, AEO, llmsTxt, aboutJson, translate) through `writeBulkStoreFields`->`storeCompareAndSet`: on a Durable-Object store ONE StoreDO transaction (`casStoreFields`, packages/repo/src/rpc/settings.ts) writes each field only while it still holds the value the job read (null, '', whitespace and `{}`are all blank), then only the WRITTEN fields that live in D1 are mirrored; on Postgres it is one conditional`updateMany`per field. The guard test is an AST scan (line breaks,`db["product"]`, `["update"]`, comments cannot hide a write; bad fixtures for each evasion) over every `bulk-ai-_`/`ai-autofill-_`job AND the services / generators they import, failing on a direct`product`/`category`/`productImage`/`store` `update|updateMany|upsert`or`storeUpdate(prisma, ...)`. Tests: `packages/repo/test/rpc-store-cas.test.ts`, and `apps/api/workers-test/store-settings-do.test.ts` (a merchant edit made mid-run wins on a real StoreDO). No residual: the StoreFaq / StoreHowto / ProductFaq / recommendation sweeps replace only AI-owned (non-manual) rows by design and are unchanged. Cost if wrong: a forced bulk run no longer replaces a merchant-edited field.

# WAREHOUSE-ROUTE-1

Ruling WAREHOUSE-ROUTE-1 (2026-11-12, Ahmad: "get it in") - order creation routes each stock line to one warehouse, in the same StoreDO section as the order write. Supersedes the "checkout does not know which warehouse ships" rejection in STOCK-SYMMETRY-1 part (1).

Rule. `products.inventory` / `product_variants.inventory` stay the authoritative, oversell-guarded numbers; the warehouse rows are the per-location shadow whose SUM equals them. For a store with 2 or more ACTIVE warehouses, `placeOrder` (storefront checkout) and `placeAdminOrder` (phone / manual order, #713) do per line, inside the order's section (`packages/repo/src/do/warehouse-route.ts`): (1) reconcile the SKU's shadow to the aggregate (no-op when equal); (2) choose the first warehouse by `priority desc, code asc` that holds the WHOLE line (the `WarehouseService.routeOrder` priority rule; amended by WAREHOUSE-ROUTE-3: when none does, the line is split across warehouses); (3) decrement the aggregate exactly as before, then decrement that warehouse row by the same quantity, so SUM == aggregate still holds; (4) AMENDED by WAREHOUSE-ROUTE-3: when no single warehouse holds the line but the aggregate does, the line is split greedily across warehouses (it is no longer refused 409 `NO_SINGLE_WAREHOUSE`, a code that no longer exists); (5) store the allocation as an order event `warehouse_allocated`. A cancel, refund or partial return reads it and gives the units back to the SAME warehouse (`restoreLine` -> `releaseToWarehouses`), tracking what was already given back in `warehouse_released` events, so a second return or a replayed cancel never returns more than was taken. The admin order page shows "Fulfilled from" (warehouse code and quantity per line, `WarehouseCard`), fed by `OrderService.getById` -> `warehouseAllocations`.

Unchanged by design. A store with 0 or 1 active warehouse is not routed: `planRoute` returns null and every statement, total and history row is what it was (proved by a test that runs the same order and cancel on a no-warehouse and a one-warehouse store and compares results, with no event written). Backorder units (an aggregate shortfall taken under the backorder feature) are not routed; the existing reconcile sweep attributes them. The proximity rule is not used on order creation (no coordinates at checkout); priority only. The legacy Postgres path (`OrderService` Prisma transaction) is NOT wired: Postgres was removed from production in NEON-ZERO (the Worker throws `POSTGRES_REMOVED`), every store runs on the StoreDO, and the Postgres path stays a test twin. Idempotency: a keyed checkout retry returns the stored order before any stock step, so it reserves nothing twice (tested).

Evidence: `packages/repo/test/do-warehouse-route.test.ts` (6 of 8 cases are red on the old code: routed warehouse, priority fallback, NO_SINGLE_WAREHOUSE, retry, cancel release, phone order; the other 2, oversell and single-warehouse parity, must stay green). Cost if wrong: a multi-warehouse merchant whose priority order is not the one they want ships from the wrong warehouse until they edit priorities, and (until ROUTE-3) an order whose line is split across warehouses was refused instead of split.

Admin how-to: Stock > Warehouses defines warehouses and their priority (higher number ships first); each order of a store with two or more active warehouses shows a "Fulfilled from" card on `/stores/<id>/orders/<orderId>`; a line that no single warehouse can cover is split across branches automatically (WAREHOUSE-ROUTE-3), and the card lists each branch with its quantity; no stock transfer is needed first.

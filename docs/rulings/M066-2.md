Ruling M066-2 (Issue 618, amends M066-1) - M066-1 removed the per-account cap and keyed address counters on the exact address, which an attacker with one IPv6 /64 defeats (2^64 addresses, each a fresh budget), leaving only a sleep as the account-wide control; and `verifyOtp` compared the code before claiming the attempt, so parallel guesses all got a comparison. Now: (a) the password and emailed-code budgets key address counters on the /24 or /64 prefix; (b) every brake budget has an account-wide HARD ceiling (ACCOUNT_CAP = 50 per 15 min, all addresses) admitted atomically in the same D1 batch BEFORE the guarded work, plus the progressive delay; (c) `verifyOtp` claims an attempt with one guarded `UPDATE ... RETURNING` before comparing, so K parallel guesses get at most 5 comparisons per code and the 5th claim burns it. This covers /login, the signup/verify code, /password/reset and the two_factor email code (all go through `hit` + `verifyOtp`). Residual: an attacker can again lock an account for the window, but only by spending 50 admitted attempts (not 5), and the per-address lock still keeps the owner's own address unaffected until the account ceiling is hit; a CAPTCHA/Turnstile past BRAKE_FREE would remove it and is not built. Evidence: apps/accounts/test/account-guess-cap.test.ts (90 parallel guesses from 90 networks -> at most 50 evaluated; 30 addresses in one /64 -> at most 5; 25 parallel code guesses -> attempts exactly 5, code burned). Cost if wrong: a sustained attacker can deny one account's sign-in for up to 15 minutes at a cost of 50 requests per window; before #557 it cost 5.

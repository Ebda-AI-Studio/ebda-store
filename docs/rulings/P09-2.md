Ruling P09-2 - Opus review of P09-1. (a) `receivePurchaseOrder` also locks the PRODUCT rows it receives (sorted by id, after the PO lock) before it reads open backorders, on-hand or cost: two receives of DIFFERENT purchase orders for the same product used to read the same open backorder line and both write `qtyFulfilled`, healing the stock debt and posting the variance journal twice, and to write absolute weighted-average costs from the same unlocked read. Lock order is PO, then products by id. (b) `cancelPurchaseOrder` is one conditional update (`status <> received`), so a cancel racing a receive can never overwrite a received PO (stock and accounts payable already posted) with `cancelled`. NOT DONE (listed for the controller): the audit `toStatus` read-back in POST /payments/refund can reflect a second refund that committed in between (cosmetic); the new integration tests run as the CI superuser, not `ebda_app`, so row-level security is not exercised.

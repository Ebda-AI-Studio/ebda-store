Ruling WA-BRIDGE-BIND-1 (2026-11-12, audit 2026-11-12 backfill-auth-security WA-1..WA-4; foundation PR #28, live-state-beats-token-claims) - the Chat bridge never trusts a claim the caller sends when the Store can recompute it.

- WA-2: `createCheckoutLink` and `createOrderFromChat` (the two methods that take both `buyerKey` and `phoneE164`) recompute `buyerKeyFor(SUITE_BUYER_KEY_SECRET, phoneE164)` and refuse a mismatch with `invalid` (constant-time compare, no link minted, no order placed). The secret is a REQUIRED dep of `createBridge` (`buyerKeySecret`); a missing or short secret throws, so the call fails closed. Methods that take only a `buyerKey` (addresses, order status, order list) cannot be bound without a phone; they stay gated by the key being an unguessable HMAC.
- WA-1: `attachPaymentProof` stores `mediaRef` = origin + path of the proof URL (query, fragment and credentials dropped), never the signed URL (`bridge/proof-ref.ts`). The logger also redacts `*.mediaUrl`, `*.checkoutUrl`, `*.paymentUrl`. Consequence for WA-RPC-5: the merchant's audit history shows the media reference, not an openable link, until WA-RPC-F2.
- WA-3 (Store side): the `/cart/from-wa?t=` token carries `bk` = HMAC(derived key, storeId + suite buyerKey), 32 hex chars, not the suite-wide key, so links cannot be joined across stores. Tokens minted before this change (30 min TTL) still verify and redeem (redeem never reads the buyer field). NOT done here: a caller allow-list or per-call HMAC on the service binding needs Ebda Chat to send a signature; Chat-side follow-up: sign each bridge call (storeId + method + args hash + timestamp) with a shared secret, Store verifies in `WhatsAppBridge`.
- WA-4: `buyerKeyForErasure` throws when `SUITE_BUYER_KEY_SECRET` is set but shorter than 32 chars (the erasure fails and is retried; it no longer silently skips Chat); unset stays a logged no-op (WhatsApp never configured). `assertWhatsAppLinkConfig` also refuses a set-but-short secret at boot even with no queue bound.
  Cost if wrong: a Chat caller that sends a buyerKey computed with a different secret or normaliser now gets `invalid` instead of an order (the /health `buyerKeyVector` proves both Workers agree); an erasure fails while the secret is misconfigured instead of leaving Chat un-notified.

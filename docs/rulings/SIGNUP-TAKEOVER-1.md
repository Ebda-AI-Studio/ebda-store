Ruling SIGNUP-TAKEOVER-1 (2026-10-27) - merchant signup identity binding. (2, FIXED) `MerchantSignupService.signup` generates the id up front (or reuses the existing profile's), sends it to `createIdentity`, and writes the profile row and the legal acceptances only when the identity answers with exactly that id; a mismatch writes nothing, logs an error and answers the same generic `{ emailVerificationSent: true }`. Test: tests/unit/merchant-signup-legal.test.ts. (1, NOT CHANGED, awaiting the controller's confirmation) The reported overwrite of an unverified credential is not an account takeover under Ruling ID-10: the password of a signup is bound to the verification CODE it produced, never written to the user row, and `/otp/verify` needs the code AND the password of that same signup, so a second signup (attacker or victim) only decides whose password the NEWEST mailed code can activate; the code goes to the mailbox owner, so an attacker without the mailbox cannot activate anything, and a victim who does not know the attacker's password cannot activate the attacker's credential either. This exact path is pinned by apps/accounts/test/hardening.test.ts ("the takeover path from the review: victim signs up, attacker signs up, victim resends and verifies with their own password -> never the attacker's" and the two order tests). Refusing to replace an existing pending credential would re-open the pre-hijack lockout fixed in stage 1 (an attacker signs up first with the victim's address and the victim can never register). Cost if wrong: if a path exists where a mailed code activates a credential the mailbox owner did not choose, an unverified address could be claimed; the hardening tests are the evidence that none exists today.

Ruling SIGNUP-TAKEOVER-1 (2026-10-27) - merchant signup identity binding. (2, FIXED) `MerchantSignupService.signup` generates the id up front (or reuses the existing profile's), sends it to `createIdentity`, and writes the profile row and the legal acceptances only when the identity answers with exactly that id; a mismatch writes nothing, logs an error and answers the same generic `{ emailVerificationSent: true }`. Test: tests/unit/merchant-signup-legal.test.ts. (1, NOT CHANGED, confirmed by the controller 2026-10-27) The reported overwrite of an unverified credential is not an account takeover under Ruling ID-10: the password of a signup is bound to the verification CODE it produced, never written to the user row, and `/otp/verify` needs the code AND the password of that same signup, so a second signup (attacker or victim) only decides whose password the NEWEST mailed code can activate; the code goes to the mailbox owner, so an attacker without the mailbox cannot activate anything, and a victim who does not know the attacker's password cannot activate the attacker's credential either. This exact path is pinned by apps/accounts/test/hardening.test.ts ("the takeover path from the review: victim signs up, attacker signs up, victim resends and verifies with their own password -> never the attacker's" and the two order tests). Refusing to replace an existing pending credential would re-open the pre-hijack lockout fixed in stage 1 (an attacker signs up first with the victim's address and the victim can never register). Cost if wrong: if a path exists where a mailed code activates a credential the mailbox owner did not choose, an unverified address could be claimed; the hardening tests are the evidence that none exists today.

Addendum (2026-10-27, controller): the orphan residual is closed. When the identity answers with another id and there is no Store profile for the address, signup ADOPTS that id only if the identity service reports the SAME address, still unverified, and no profile row exists under that id (`isAdoptableOrphan`); otherwise nothing is written. Tests: merchant-signup-legal.test.ts (adopt, refuse other address, refuse verified, refuse existing profile) and apps/accounts/test/hardening.test.ts (victim signs up, attacker re-signs: no code verifies with the other's password). Cost if wrong: an identity that is not really the caller's orphan gets a Store profile bound to it; the same-address, unverified and no-profile checks bound that to an address whose mailbox the signer must still control to verify.

# NZ-AN-1

Ruling NZ-AN-1 (2026-11-04, controller; NEON-ZERO-1 items N-11 remainder and N-13) - the per-store analytics tables `SearchQueryDaily`, `ProductDailyView`, `QrScanDaily`, `NotificationLog` and `GscDailyMetric` move into each store's own StoreDO (new DO tables `search_query_daily`, `product_daily_views`, `qr_scan_daily`, `notification_logs`, `gsc_daily_metrics`; `model-split.json` target `store-do`, generated into `0001_init` and into `cf-0003_analytics` for a StoreDO that already ran 0001; the five join `DO_WRITABLE_MODELS`, so reads and writes go through `storeDb` / `storeWriter` for a DO store). `AiUsage` moves to the platform D1 (`d1:ai_usage`, migration `0005_ai_usage.sql`) because the AI quota counts usage ACROSS stores (`lib/ai-quota.ts countAiUsage`): it is the new model-router family `ai-usage` (`services/platform/cutover.ts`, marker `platform_cutover.ai-usage`, same freeze / new-connection-verify / claim rules as the `billing` family, ruling NZ-10-3), rows are append-only with a client-side id (`recordUsage` passes `randomUUID()`, so a retried insert is one row), every `prisma.aiUsage.*` call is answered by the router, the raw `ai_usage` SQL of the usage summary, the super-admin AI dashboard and the monthly usage snapshot is replaced by router-compatible `count` / `aggregate` / `groupBy` (`services/usage-aggregates.service.ts`), and `countAiUsage` reads D1 once the marker exists. Per-store AND platform-wide counts stay correct because every writer goes through one table after the marker and the copy carries the history; before the marker nothing changes.

How a DO store switches: `lib/analytics-backend.ts analyticsOnDo(storeId, mode)` is true only for a store whose backend is `do` AND after the D1 marker `platform_cutover.analytics` (family `analytics`, no routed model). Before the marker every store, DO or not, keeps these tables in Postgres, so no row is ever split between the two. The writers are `recordSearch` / `purgeSearchLog*` / `getSearchInsights` (`search-log.service`), `recordProductView` (`view-ingest.service`), `recordQrScan` / `qrStats` (`qr.service`), the GSC ingest and dashboard, the analytics rollup's product-view total, the push and SMS notification log and the notification routes; the raw upserts are DO ops (`packages/repo/src/do/analytics-ops.ts`: `searchLogRecord`, `searchLogPurge`, `searchInsights`, `qrScanRecord`, `viewRecord`, one section each, SQLite spelling of the same statements, the 2147483646 counter cap kept). `search-log-purge-daily` and `gsc-ingest-cron` / `-on-demand` are now PORTED jobs (the two crons are `ALL_STORES_JOBS`: one cron run lists every store, DO stores included, and reaches each through `runInStoreCtx`).

During the `ai-usage` freeze a routed write answers 503 `PLATFORM_FAMILY_FROZEN`; `recordUsage` then writes the row (the AI call already ran) to Postgres with an idempotent raw statement and `cutover-platform-family.mjs` copies those rows into D1 after the thaw and refuses to finish while one is missing (`tests/unit/ai-usage-freeze.test.ts`), so a freeze never loses usage or undercounts a quota. The platform-wide `countAiUsage` is BOUNDED-stale (30 s in-isolate memo, documented at `lib/definer.ts`; the per-store cap is uncached). The `ai_usage` D1 migration is `0005_ai_usage.sql` (0003/0004 belong to the late-columns PR).

The analytics freeze is #407's (a `system_settings` row with `expiresAt`, ignored and paged after the TTL, `--freeze-ttl-ms`, lifted on every exit including SIGINT/SIGTERM; reads are never cached "off" while it exists). The copy always converges: a store already `done` is kept only if it still equals FRESH Postgres totals, otherwise (and for any partial copy or rows a store flip copied) the DO is reset (`analyticsImportReset`, refused by the `__analytics` route once the D1 marker exists) and re-copied; batch ids are keyed by the first row id, not a position; the verifier compares row counts, SUMs of small counters and MIN/MAX of the epoch columns (no float SUM of epoch-ms).

The data move is `scripts/cf/copy-analytics-to-do.mjs` (the CONTROLLER runs it; dry run by default; `docs/runbooks/analytics-cutover.md`): `--commit` FREEZES the family (a DO store's analytics WRITE answers a retryable 503, which the fail-open counters swallow), drains, opens the Postgres snapshot only then, copies each DO store's rows in fixed-size batches whose ids make a re-run a no-op (DO ledger `_analytics_import`), asks each DO to FINISH (the DO compares its own row counts and the SUM of every counter column with what Postgres held and writes its done-marker only on an exact match, after which every batch is refused), sets the D1 marker only if every store finished, waits, thaws and re-counts Postgres on a NEW connection (exit 2 on drift). It refuses after the marker, and refuses a DO that already holds analytics rows it did not import. The ingress is `POST /cutover/stores/<id>/__analytics` with the cutover bearer, three named ops only. AiUsage moves with the existing `scripts/cf/cutover-platform-family.mjs --family ai-usage`.

Residuals, each with what would settle it: (1) none for the recipient hash: it used to be an unsalted SHA-256 of the phone (reversible over the ~4e8 Egyptian mobile space, so personal data); it is now the suite buyer key HMAC (`lib/notification-recipient.ts`), the log is `customer-pii` / `delete` matched by `buyerKey`, a shopper erasure deletes the rows by it (`tests/unit/notification-log-erasure.test.ts`), and the copy does NOT carry the historic unsalted hashes (they arrive as NULL); (2) `ProductEmbedding` is still `analytics` in `model-split.json` (Vectorize track, CF-JOBS-4C residual 1), not touched here; (3) cross-store reports over the five tables fan out per store (`acrossStores`-style) and the platform-wide AI numbers need no fan-out; (4) a StoreDO flipped from Postgres AFTER the analytics marker gets its rows from `migrate-store-to-do` (the five tables are in its plan now); before the marker the copy script covers it, and the copy refuses a DO that already holds rows. Evidence: `tests/unit/analytics-on-do.test.ts`, `tests/unit/ai-usage-on-d1.test.ts`, `packages/repo/test/do-analytics-ops.test.ts`, `packages/repo/test/analytics-copy-parity.test.ts`, `tests/unit/jobs-blocked-gsc-on-do.test.ts`, `tests/unit/jobs-blocked-retention-on-do.test.ts`, `tests/unit/jobs-blocked-usage-snapshot-on-do.test.ts`, `tests/unit/do-writable-direct-readers.test.ts`, `packages/cf-schema/test`. Cost if wrong: analytics history is split per store, which complicates cross-store reports (acceptable; super-admin reports fan out); a copy run in the wrong order only costs a retry because the marker is set last.

# WA-RPC-8

Ruling WA-RPC-8 - `createOrderFromChat` completes on replay and classifies refusals (issues #616, #617). (1) Replay: the buyer-key stamp (fill-only-NULL), the payment row (an open COD row is reused, an awaiting InstaPay order returns the same instructions) and the `order/created` send (its fanout claims `order_created_notified_at` atomically) are idempotent, so they run on EVERY call including a replay; only the address save stays first-call-only. The stamp runs before the payment step so the buyer sees the order even if a later step throws, and a failed `order/created` send now THROWS instead of being logged, so the caller retries the same key and the replay completes it (the stuck-sweep only re-sends paid orders, so an unpaid COD/InstaPay order had no other recovery). (2) Refusals: `refusalOf` (`lib/wa/bridge/do-port.ts`) maps engine refusals to a typed `PortError`: PRODUCT_UNAVAILABLE / VARIANT_UNAVAILABLE / VARIANT_INACTIVE / OUT_OF_STOCK become `out_of_stock` with the variant ids; MIN_ORDER_NOT_MET, TOO_MANY_OPEN_ORDERS, IDEMPOTENCY_CONFLICT, coupon, wallet, gold and the other listed codes, and any unlisted 4xx engine error, become `invalid`; every refusal carries `code` (new optional field on the failure result) and the engine's message for Chat to show the buyer. Only 5xx, timeouts and unknown errors propagate and are retried. Evidence: `workers-do/wa-bridge.test.ts` (payment failure then retry, send failure then retry, archived product, key conflict, open-order cap, code table). Cost if wrong: an unlisted 4xx engine code is shown as `invalid` with its raw message; a 4xx that was actually transient would not be retried.

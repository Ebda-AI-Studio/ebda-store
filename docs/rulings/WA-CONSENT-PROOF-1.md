Ruling WA-CONSENT-PROOF-1 (Controller, 2026-10-27; automated security review, 3 MEDIUM) - a profile phone is SELF-DECLARED, so it can never authorise an action on someone else's WhatsApp consent or data. An attacker who types a victim's number into their own profile must not be able to switch the victim's consent off, delete it, or make WhatsApp erase the victim's contact. Three rules, one proof (a delivered order of THIS customer with that number, `phoneOnOwnOrder`, or an existing row the account already OWNS via `user_id`): (1) the `account/erased` event carries `buyerKey` ONLY when the erased account's phone is proven (`eraseProvenBuyerKey`, computed inside the erasure transaction before the order scrub); otherwise it is undefined and WhatsApp keeps the contact; (2) a phone change revokes the old number's rows only when the account owns them or the old number is proven (`revokeForPhoneChangeInTx(storeId, userId, oldPhone)`, same rule as `revokeForAccount`); (3) a REVOKE through the checkout endpoint needs the same proof as a grant, or a row the account owns; otherwise `phone_unproven` and nothing is written (it also no longer creates a revoked row for a number nobody consented for). The merchant admin revoke and a STOP from WhatsApp are unaffected: they are not driven by the profile phone. Cost if wrong: a legitimate customer whose proving order is gone and who never owned a row cannot withdraw through the checkout box; the merchant revoke and WhatsApp STOP still work.

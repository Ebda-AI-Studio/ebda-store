# ITEST-14

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling ITEST-14 - egypt-gateway-webhooks (paymob) was a real routing ambiguity, not only a test race. `ebda_webhook_resolve_store` matched `payments.transaction_id`/`invoice_id` with no provider filter and `LIMIT 1` without ORDER BY, so two payments sharing a reference string (another provider's, another merchant's own gateway account, or the small ids the stubs mint) made the owning store arbitrary; the delivery to the RIGHT store's URL was then answered 200 "ignored" and the paid order stayed pending. 3 of 3 runs of 29 payment-related files at 6 workers reproduced it; the failing body was `{"status":"ignored"}`. Fixed by the additive `ebda_webhook_resolve_store_scoped(txn, invoice, provider, prefer_store)` (provider filter; the URL's store first; then newest payment), used by the gateway webhook handler. Same exposure as before (store id only, exact reference). Opus review: ACCEPT. The rest of the class is closed in the same change: the payment status route (`?provider=`), the refund route (optional `provider`, validated as paymob / kashier / fawry) and the payment-callback redirect (provider taken from the query parameter the gateway used) resolve through the scoped function, and the callback now resolves the store ONCE and reads both the payment status and the storefront from it (it used two separate definer lookups that a shared reference could answer with different stores). Migration number `20261103000260` (registry: `0300` is #216 staff_invites; renumber to `0310` if #216 merges first). Cost if wrong: one extra definer function.

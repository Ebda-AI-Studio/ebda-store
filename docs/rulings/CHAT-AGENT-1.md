Ruling CHAT-AGENT-1 (2026-11-14, Ebda Chat agent audit D2/D4) - three read RPCs on `WhatsAppBridge` give the Chat agent the Store's own knowledge: `searchProducts`, `getStorePolicies`, `getCustomerProfile`.

- `searchProducts(storeId, query, { maxPriceMinor?, limit })` runs the SAME `rankedSearch` the storefront uses (Arabic light stemming pr 740, AI Franco/dialect `search_terms`, the meaning leg behind `SEARCH_SEMANTIC_ENABLED`), so Chat and the website cannot disagree. Active, public, non-deleted products of the resolved store only; rank order is kept; rows are the same `CatalogRow` as `listCatalog` (`retailerId` = variant id or simple product id, whatever `listCatalog` returns; this file does not define it). `maxPriceMinor` is PIASTERS (never major units) and is applied per sellable row. `limit` 1..20, query 1..200 chars. An empty list is a real negative (`ok: true, items: []`). It replaces the 500-variant client-side scan that gave a false "we don't have it" on large stores (audit D2).
- `getStorePolicies(storeId)` returns only what the merchant declared: shipping zones and per-governorate fees (cheapest/dearest area fee, lowest free-shipping threshold), return window and who pays, COD availability and fee, payment methods (InstaPay as a boolean, the handle is not exposed), hours, address/map link. Anything not declared is `null` or an empty list, never a default: a `0` COD fee is `null`, blank text is `null`, a store with COD off reports no COD fee. There is no store-wide free-shipping threshold in the schema, so there is none in the answer. A return window of `0` ("no returns") stays `0`.
- `getCustomerProfile(storeId, phoneE164)` returns first name (the placeholder `WhatsApp` CRM name is no name), sticky locale, the default (else newest) saved address with governorate/building/notes, and the last 3 orders with item names. The phone IS the buyer proof: the bridge rebuilds `buyerKey = HMAC(secret, phone)` and there is no key-only form, so it is strict regardless of `WA_BRIDGE_REQUIRE_BUYER_PROOF`. An unknown phone answers `ok: true, value: null` (nothing), never an error that confirms or denies a customer. The phone is not logged by the bridge.
- `WA_BRIDGE_REQUIRE_BUYER_PROOF` is NOT flipped by this change. The order is unchanged (see WA-BRIDGE-BIND-2 and ebda-whatsapp pr 67): Store proof-optional -> buyer-key backfill -> Chat sends proofs -> set the var -> live check. The new profile method does not depend on the var; the seven older methods still do.
- Contract: nine cases in a NEW byte-pinned fixture `tests/vectors/ebda-wa/bridge-chat-context-v2.json` (sha in SHA256SUMS). `bridge-v1.json` is untouched so ebda-whatsapp pr 67 and its re-vendor are not disturbed. ebda-whatsapp vendors the new file and replays it through its adapter.
  Cost if wrong: the agent quotes a policy or a profile the merchant never declared (mitigated: undeclared = null and the agent is told to refuse) or a profile read for the wrong shopper (mitigated: key rebuilt from the verified sender phone); a new method name drifting between repos fails the shared fixture on one side.

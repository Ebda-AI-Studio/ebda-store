Ruling CF-ERASE-2 (2026-10-26, OFFBOARD-1) - a column shaped like a user id (`*_by`, `*_by_id`, `actor*`, `*_user_id`, `user_id`, `owner_id`) is personal data and MUST be listed in `piiColumns` of `erasure-classification.json`; the completeness test no longer accepts `reviewedNotPii` for one, and its only exemptions are two named non-user columns (`journal_entries.reversed_by_id` is an entry id, `store_config.return_fees_paid_by` is an enum). The old pattern did not match `created_by`, so ~30 tables with an acting staff id were classed no-pii. Each such column is now accounted for exactly once as `actorScrub` (nulled, or tombstoned when NOT NULL, on user erasure or offboarding; the row survives), `subjectColumns` (the row belongs to the user; the erasure engine deletes it) or `retainedUserIds` (`stores.owner_id`, `store_profile.owner_id`: removed by owner closure M-024, not a column scrub). `*_name` columns were reviewed one by one: personal ones joined `piiColumns` (`wholesale_applications.business_name`, `store_tax_profiles.legal_name`, `instapay_receipts.receiver_name`), catalog/label/carrier/file names went to `reviewedNotPii`. `packages/repo/src/platform-erasure.ts` reads `actorScrub` straight from the classification, so a new classified column is handled without code and a test fails if the two disagree. Builder column `store_page_revisions.published_by` joins `actorScrub` when 20261105000200 lands (`published_by_name` was dropped: the name is read at view time; `created_by` is already covered). Cost if wrong: a staff id left on a business record after offboarding.

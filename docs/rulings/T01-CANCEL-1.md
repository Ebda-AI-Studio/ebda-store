# T01-CANCEL-1

> Section: 2026-11-11 - open recount track T01, order money edges (S3-O10)

Ruling T01-CANCEL-1 - a signed-in shopper may cancel their OWN order (`POST /public/orders/:id/cancel`, button on the account order page) only while it is `pending`, unpaid, and every payment row is cash on delivery. Anything else is a 409 that writes nothing: paid (`ORDER_ALREADY_PAID`, the shopper asks the store for a return or refund), online or InstaPay (a provider payment could still land after the cancel), or moved past `pending` (`ORDER_NOT_CANCELLABLE`, the merchant already acted). The cancel is the merchant's cancel (`OrderService.updateStatus`, so stock, coupon, loyalty and wallet are reversed in the same section) called with `unpaidOnly` + `onlyFrom: ['pending']`, so "still pending and still unpaid" is decided atomically on the store's Durable Object; Postgres stores check unpaid in `updateStatus` (their row lock belongs to the caller, so a same-instant payment is a residual there, and COD has no payment to race). A repeat on a cancelled order is a 200 with `changed: false`. Guests cannot cancel (no account to prove ownership); another customer's order is a 404. Evidence: `tests/unit/customer-cancel-order.test.ts`, `tests/unit/order.test.ts` (unpaidOnly case). Cost if wrong: a shopper with a paid online order sees no cancel button and must message the store, which is slower than self-service but never lets an unreviewed refund obligation be created.

# PREPUSH-5

> Section: 2026-11-11 CI fast, parallel, never flaky

Ruling PREPUSH-5 - the pre-push SCANNER run (PREPUSH-3, still always run, CI still runs it too) no longer takes `heavy-test.lock`. It runs `--maxWorkers=2` inside a 4-slot host-wide semaphore (`scripts/ci/prepush-slot.sh`, slot files `~/.claude/locks/prepush-slot-N.lock`, wait up to 900 s then fail 75, never skip) and is skipped on a pass-cache hit keyed by `git rev-parse HEAD^{tree}` plus the scanner list (`~/.cache/ebda-prepush/scanners-<key>.ok`, 7-day expiry), read or written ONLY when `git status --porcelain` is empty because scanners read the working directory (`scripts/ci/prepush-scanner-cache.sh`); the key also folds in a size+mtime fingerprint of every present GITIGNORED file except node*modules and `.husky/*`, because scanners DO read ignored inputs (measured: they import built `packages/\*/dist`, read `packages/cf-schema/generated`, and walk dirs that may hold `.next`/`.open-next`), so a guard test asserting "no scanner reads ignored paths" would be false. Evidence (measured 2026-11-11, load average 27 on 10 cores): 204 scanner files, 2186 tests, 128 s wall under that load with `--maxWorkers=2`, 96 s user CPU, 0.5 GB max RSS for the parent, so a scanner run is light and does not need the exclusive heavy lock that queued pushes 20+ min behind unrelated vitest runs. On a clean tree the same tree plus list gives the same result, so a re-push of it costs 0 s; a dirty tree always runs. Cost if wrong: a scanner whose result depends on something outside the working tree (env, network, a node_modules change without a lockfile change) could be cached as a pass for a tree that fails in CI, and the failure then shows on the PR instead of before the push.

# CF-STOCK-1

Ruling CF-STOCK-1 (2026-10-29, INFRA-CF-1 PR D2a) - stock and inventory writes move to the StoreDO as named operations, one per admin write, replacing the Postgres row locks with the Durable Object's single thread (plan section 4 rows 1, 2). (1) Shape: `packages/repo/src/do/stock-ops.ts` exports `runStockOp(db, storeId, op, args, key?)`; each operation is ONE `transactionSync` section (read, check, write, history row, aggregate sum, warehouse shadow re-sync) with no `await` inside, so no `FOR UPDATE` is needed. It is reached through its own RPC `StoreDO.stockOp(storeId, op, argsJson, key?)` (`rpc/stock.ts` `answerStockOp`: a refusal is an ANSWER `{ ok:false, code, status }`, never a throw), NOT through `mutate`, which keeps refusing every stock column (`STOCK_WRITE_REFUSED`, CF-WRITES-1) - stock cannot move through a generic write on either path. The Worker side is `storeStock(storeId)` (`lib/repo-factory.ts`): `null` on Postgres, a typed `StockClient` on `do`; a service does `const stock = await storeStock(id); if (stock) { ...DO path... }` and the Postgres code below it is UNCHANGED, so with every flag at `pg` nothing runs differently. The StoreDO is bound to one store: another store id is `STORE_MISMATCH`. (2) Operations (six): `adjustProduct`, `setProduct`, `bulkAdjustProducts` (InventoryService adjust, count and bulk; a bad row fails alone, planned from the state at the start exactly as Postgres does), `setVariantInventory` (VariantService.bulkUpdateInventory), `setWarehouseStock` and `adjustWarehouseStock` (WarehouseService setStock/adjustStock: warehouse row upsert on the right unique index, aggregate = SUM of the warehouse rows, floor at 0 for a delta, audit row `[Warehouse: CODE] ...`). Error codes and statuses are the Postgres ones (`NOT_FOUND` 404, `VARIANT_PRODUCT` 400, `INSUFFICIENT_STOCK` 400, `WAREHOUSE_NOT_FOUND` 404, `PRODUCT_NOT_FOUND` 404, `INVALID_QUANTITY` 400). (3) Idempotency: an operation may carry a key (8-128 chars); the first run stores its result under the key INSIDE the same section in `_stock_ops` (marker row), a replay returns it without touching a row, the same key for other arguments is `IDEMPOTENCY_KEY_REUSED` 409, a refused or failed operation stores nothing so the retry runs, keys live 24 h and are pruned on the next keyed write. The services pass no key yet (an admin RPC is not retried by the platform); the order/refund callers of D2b are the ones that will key by order id plus line. (4) Deliberate differences from Postgres, each measured by the contract test and kept: (a) the warehouse shadow re-sync that `adjustInventory`/`setInventory` run best-effort AFTER commit runs inside the same section on the DO (atomic instead of log-and-swallow); (b) FOUND, replicated, since FIXED by WAREHOUSE-NEG-1: `reconcileWarehouseStockToAggregate` shifts the default warehouse row by `quantity + diff` with no floor, so a product-level count below the shadow drives that row NEGATIVE on Postgres (scenario "a product-level count re-syncs", Postgres `-1`); the DO replicates it (`mode: 'shift'`) so the traces stay equal - fixing it changes Postgres behaviour and is a separate decision for Ahmad (Cost if wrong: a negative shadow row only skews per-warehouse routing, never the aggregate the storefront sells from); (c) FOUND: `bulkAdjustInventory` never re-syncs the shadow on Postgres, so the DO bulk does not either (parity, pre-existing gap); (d) the DO refuses a negative or non-integer variant stock count as a failed item, Postgres would store it (the route's schema stops it earlier). (5) Side effects stay in the service: cache bust, back-in-stock notifications, `notifyCatalogChanged` (raw SQL bypassed the write observer on Postgres; the DO path calls it explicitly). Evidence: `packages/repo/test/do-stock-ops.test.ts` (11, every operation, refusal, store scoping, replay, failed-op-leaves-no-marker); `tests/integration/repo-factory-stock-contract.test.ts` (7 scenarios through the real services, each on real Postgres 17 and on the DO schema on SQLite via the real wire codec; traces = return values or error code+status AND the resulting products, variants, warehouse_stock and inventory_history rows; it found (4b) and (4c) on its first run); `apps/api/workers-do/stock.test.ts` on real workerd (100 concurrent removals against 40 in stock: exactly 40 succeed, 60 get `INSUFFICIENT_STOCK`, stock ends at 0, 40 history rows; 20 concurrent calls with one key apply once). Bundle: see the PR (budget 8.3 MB). NOT moved, with reason: the CSV import's stock part (its row write is one `withMoneyTx` that also writes non-stock fields, slug redirects into a D1 model and gold specs; needs the import orchestrator, own PR); variant create/update opening stock and `inventoryHistory` rows written inside `ProductService`/`VariantService` create paths (still refused on the DO by CF-WRITES-2, which keeps those two flows on Postgres until the orchestrator lands); warehouse CRUD (`create/update/deactivate`, default-warehouse invariants; plain rows, next slice); barcode sequences (advisory lock, D2b with `sequence.next`); stock reservations: there is NO reservation table - an open hold is an unpaid order counted by `stock-hold-cap.ts` (advisory lock + `orders` count), so it moves with orders in D2b. Cost if wrong: with every flag at `pg` the stock services run their Postgres code unchanged; a wrong DO stock write is reachable only for a store the operator flipped, one D1 UPDATE back, and the cutover gate (runbook rows 1-3) still forbids a flip until D2b (orders/payments/refunds/ledger/coupons/wallet) lands.

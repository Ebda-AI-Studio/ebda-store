Ruling ID-15 (2026-10-25) - platform administrators: (1) created or promoted only by `apps/accounts/scripts/upsert-super-admin.mjs`, run by Ahmad himself (dry run default, `--apply`, hidden password prompt, never an argument, hash-only temp file); (2) `pa: super_admin` is minted only for a session created with a second factor (TOTP or passkey), so an admin without one signs in to a token with no admin power and the client is told to enrol (`mfaEnrollmentRequired`) - this is a deliberate refinement of "login refused until enrolled": the password step succeeds but grants nothing, which avoids a second, enrolment-only token type; (3) `auth_time` is added to the access token, the identity service refuses to mint for a platform-admin session older than 12 h (REAUTH_REQUIRED) and the Store refuses a `pa` token with no or stale `auth_time` (aud=store only, already pinned). Evidence: apps/accounts/test/super-admin.test.ts and tests/unit/accounts-token-auth.test.ts. Review follow-up (same day): the FIRST factor of a super_admin additionally requires the operator's one-time enrolment token (printed by the script, 30 min, single use, sha256 at rest, table `enrolment_tokens`) AND a code e-mailed to the account; the script clears a promoted account's old TOTP/passkeys and re-running keeps existing factors unless `--reset-factors`. Fourth round (P1): a platform admin who has a passkey cannot be signed in by the password alone at all (`/login` returns `secondFactorRequired`, creating no session, so a phished password cannot hold a half session that could remove the passkey), and removing a super admin's passkey needs a fresh second-factor session. Residual: for merchants, removing a passkey still needs only the password (+TOTP code if on); cost if wrong: a phished merchant password can strip a merchant's passkeys (a nuisance, the password still signs in). Third round (E1): every account's FIRST factor needs a code e-mailed to the account (mode `password` -> `EMAIL_CODE_REQUIRED`/`EMAIL_CODE_INVALID`), and each bound factor mails a "new sign-in method added" notice; the upsert script runs the factor clears and the token insert BEFORE the role promotion. Second review round: the policy is decided at begin and stored on a session-bound ticket (so a factor appearing between options and verify cannot skip the bootstrap proof), completion re-checks the current state, adding a factor to an account that already has one requires a fresh (10 min) second-factor session or a current TOTP code, and a successful bootstrap deletes all pending enrolments and revokes the other sessions. Cost if wrong: an admin whose session is 12 h old must sign in again with their second factor, an unenrolled admin sees an ordinary merchant view until they enrol, and losing the printed token means re-running the script. Amended by Ruling ID-20 (2026-11-11): a platform admin may also be CREATED password-less by `apps/accounts/scripts/bootstrap-super-admin.mjs` (password set by the owner through the mailed reset code); the one-time enrolment token for such an account is issued by that script's `--issue-enrolment-token`, on the owner's interactive terminal only.

# B5-13

> Section: 2026-10-22 — Phase B5 Dahab (B5-\*)

Ruling B5-13 — the price is MATERIALISED into the existing `price` columns; the pricing spec lives in new integer columns, never in facts or `weight Float` (Task 9). New columns. `products.pricing_mode` (`fixed` | `gold_rate`, default `fixed`), `products.gold_karat` (SMALLINT, CHECK in 24/21/18), `products.gold_weight_mg` (INT, CHECK 1..1 000 000), `products.making_charge_type` (`fixed` | `per_gram`), `products.making_charge_value` (INT piastres, ≥ 0), `products.gold_margin_bps` (INT, −5 000..10 000, default 0), `products.gold_rate_id` (the rate row the current price was computed from). The same nullable set on `product_variants`, where null means "inherit the product", plus `product_variants.pricing_mode` (null = inherit). The repricer is the only writer. In the same transaction as the rate write, it recomputes every gold-priced row with `computeGoldUnitPrice` and writes `price`. For a variant product, `products.price` is set to the minimum active variant price, so SQL sort/filter, feeds, search results, JSON-LD and every card path stay correct without a single reader change. A BEFORE INSERT/UPDATE trigger enforces it. `ebda_gold_price_guard` on both tables refuses a `price` / `compare_at_price` change on a gold-priced row unless the transaction set `app.gold_reprice = 'on'` via `set_config(…, true)`. That covers every writer that exists (`ProductService.create/update/bulkUpdate`, `VariantService.createVariant/updateVariant`, CSV/XLSX import in `bulk.service.ts`, the MCP admin-write tools, the admin mass edit) and every future one. Why not the alternatives. `facts` are free text ("عيار 21") and cannot drive money. `Product.weight Float` has no defined unit and is a shipping field (B5-5). Compute-on-read would need every reader changed: `cartLineUnitPrice`, `createAdminOrder`'s own loop, the payment-link `unitPrice`, `getProductPricing`, PLP SQL sort/filter on `p.price`, the feed, `llms.txt`, recommendations, wishlist and the 4 hand-built card mappers. Missing one is a mispriced order. Cost if wrong: a rate write holds row locks on the store's gold rows for the repricer's duration. It is bounded at 5 000 gold rows per store (refused above that with `GOLD_CATALOGUE_TOO_LARGE`) and measured in Task 10 (2 000 rows < 2 s on the capped local DB, or the task reports the real number and the cap drops).

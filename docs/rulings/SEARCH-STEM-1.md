# SEARCH-STEM-1

> Section: 2026-11-12 - Arabic light stemming on the StoreDO keyword search

Ruling SEARCH-STEM-1 - the StoreDO FTS5 index gets two ADDITIONAL columns, `stem_doc` and `stem_name_doc` (the stem of every word of `doc` / `name_doc`), built by the pure-TS light stemmer `packages/shared/src/search/arabic-stem.ts` (prefixes وال بال كال فال لل ال; one suffix of ات ون ين ان ها تين ه; broken plurals افعال and فعال; a 4-letter مفعل loses its م). The query matches each word of 3+ letters as `(literal OR stem)`; the folded `doc` and its tokens are untouched, and a row that contains every word literally ranks before a stem-only row. Default ON for the storefront scope, OFF for admin (admin search also selects the rows of bulk edits, which must stay literal; `stem: true` opts in). Not ISRI root extraction: on `tests/search-eval` (EVAL_STEM, 22 cases over the 345-query catalogue) light stemming passes 22/22 (literal: 2/22), no existing query loses a hit, so a root extractor (which over-merges names) is not justified. Existing indexes: `ensureSearchIndex` (StoreDO bootstrap) drops a `product_search_fts` that lacks `stem_doc` and marks every product dirty; `flushSearchIndex` rebuilds it in batches of 2000 on the next search; re-running is a no-op. The index is derived state (restored from rows), so nothing is lost. Cost if wrong: a stem merges two unrelated words (مكتب desk with كتب books), so a storefront search returns an extra, lower-ranked product; recall only, never a missing result, and `stem: false` switches it off per call.

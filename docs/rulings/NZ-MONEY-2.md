# NZ-MONEY-2

> Section: NEON-ZERO money path (2026-11-05)

**Ruling NZ-MONEY-2 - a PAYMENT reference is handed out only when D1 can route it. `StoreDO.moneyOp`, for every op that answers a payment (`paymentCreate`, `instapayInitiate` and its replay, and `paymentIndexCheck`, which `POST /payments/create` calls before it hands an EXISTING payment out again: the COD replay, the InstaPay replay, a live invoice / Fawry code), writes that payment's still-queued index rows NOW (backoff ignored) and reads every id back from D1 (`awaitEntityIndexed`, 3 s bound); when they are not there it answers 503 `ENTITY_INDEX_UNAVAILABLE`. The check reads D1, not "did this call write rows", so a retry during an outage is refused too (review NEW-1). Every retry returns the same committed payment. Any other op keeps its answer, a checkout order included (its retry is a replay that would not re-run the post-commit fan-out, review NEW-2); its rows are written by the op when D1 is up and otherwise wait for the alarm, and `POST /payments/create` by that order id answers 404 until they land. A forced write (the reference-handing paths) never counts toward the outbox dead-letter limit and revives a dead-lettered row, so shopper retries during an outage cannot strand a payment (review NEW-3); the alarm keeps retrying dead-lettered rows on their capped hourly backoff and logs a `[P1]` once when a row crosses the limit (about two hours of failed paced attempts). Rows still queued arm a short alarm (`max(next attempt, now + 30 s)`, env `STORE_DO_INDEX_RETRY_MS`); the alarm backs the store up only when the nightly backup is due (`_identity.backup_due_at`). Evidence: `drainEntityIndexOutbox` had no caller in the Worker, so D1 `entity_index` never learnt a DO store's new orders, payments or gateway references. Reviews I-2 and NEW-1 of PR 455 found the earlier fixes answered success on a failed write and on a replay. Tests: `money-path.test.ts` (D1 refuses the payment row: first and retry 503, back up: 200 with the row in D1 before the answer; D1 refuses the order row: the checkout still answers 2xx and a keyed retry replays it), `workers-do/index-retry-alarm.test.ts`. Cost if wrong: during a D1 write outage payment creation answers 503 (retryable) instead of handing out a reference nobody can route, and a checkout placed in the outage waits up to the next alarm before it can be paid online.**

# CF-ORDERS-CART-1

Ruling CF-ORDERS-CART-1 (2026-10-29, INFRA-CF-1 PR D2b-2, Ahmad via the controller) - carts have not moved to the StoreDO, so `OrderService.createOnDo` reads the cart (lines and bundles) from Postgres, passes them to `createOrder` WITHOUT the engine's `cart` claim, and clears the Postgres cart rows after the order committed (`deleteMany`, idempotent: a replay of a keyed order clears nothing twice and creates no second order). Accepted residual: the cart claim is not atomic with the order, so two concurrent submits of one cart with no idempotency key can both create an order from the same full cart (the Postgres path serialises them with `FOR UPDATE` on the cart row); a keyed retry is safe because the key is hashed with the cart id. Delivery slots, personalisation notes, order-time affiliate attribution and the fiscal sale document are likewise not written on the DO (Ruling DO-MONEY-2). The cutover gate stays closed: no store is flipped to `do` until carts (with abandoned carts) and fiscal documents move to the DO in the follow-up PR, which uses the engine's existing `cart` claim and removes this ruling's residual. Evidence: `docs/cf/orders-on-do.md` residuals, the engine claim is covered by `packages/repo/test/money-stock.test.ts` (cart claim). Cost if wrong: a double-tapped cart on a flipped store could create two orders (stock and coupon taken twice, cancelled by the customer or merchant), reachable only for a store the operator flipped, which the gate forbids until this closes.

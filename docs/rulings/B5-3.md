# B5-3

> Section: 2026-10-22 — Phase B5 Dahab (B5-\*)

Ruling B5-3 — legacy Dahab stores are safe by construction and migrated by script, never by SQL. `TEMPLATE_THEMES.dahab` and the layout baseline are a neutral base (B5-3a), so a `template = 'dahab', look = null` row renders without the night theme. `tileShape: 'arch'` stays in the section Zod enum (saved documents keep validating) but is dropped from the editor's option list, the registry preset defaults to `'rectangle'`, and `DahabTile` maps a stored `'arch'` to the rectangle (`dahab-tile-arch.test.tsx`: byte-identical markup). `scripts/dahab-demo/migrate-legacy-dahab.mjs` moves a store with `StoreService.applyLook(id, look, { design: 'keep' })`: dry run by default, loopback-only without `--yes-production`, idempotent by selection (`look IS NULL`). Evidence: production has 0 such rows (read-only count 0 / 0 / 1 on 2026-10-21), and `tests/integration/dahab-apply-look.test.ts` rehearses a legacy store on a real database through all three looks and back with content identical at every step. Not done: the plan's fixture was to be the old `seed-dahab.mjs` run (22 pieces, variants, 3D model row); the rehearsal uses a compact fixture (2 products, one with required personalisation, a category photo, a logo, an arch tile list, the night theme) because the content oracle does not depend on catalogue size. Cost if wrong: a Dahab store appears that nobody counted; it renders the neutral base until the script runs.

# B5-13b

> Section: 2026-10-22 — Phase B5 Dahab (B5-\*)

Ruling B5-13b (Task 10) — implementation facts the plan left open. (1) Every rate write takes a per-store advisory lock (`pg_advisory_xact_lock(hashtext('gold-rate:<store>'))`) before the `FOR UPDATE` on `gold_rates_current`, because the FIRST write of a karat has no row to lock and two such writes would otherwise race on the primary key. (2) `withMoneyTx` opens its own connection even inside a request transaction (`nested-transaction-registry.test.ts`), so a rate write is atomic among its own statements; the audit row goes through the definer on the request connection and commits with the request. (3) The repricer is also run for a variant added to a gold product (`GoldRateService.asRepricer`, used by `VariantService.createVariant` / `generateVariants`); a caller-supplied price on such a variant is refused. (4) `ProductService.bulkUpdate` skips gold products for a price write (counted in `skippedVariantProducts`), a CSV row for a gold product may repeat its current price but not change it (the row fails, the others import), and the MCP admin tools and the mass edit are covered by the database trigger (409 GOLD_PRICE_MANAGED). (5) Cost measured on the capped local DB: 2 000 gold rows re-price in 128 ms inside one transaction. Cost if wrong: none known.

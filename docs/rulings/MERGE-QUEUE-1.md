# MERGE-QUEUE-1

Ruling MERGE-QUEUE-1 (DRAFT, inert) - ebda-store is prepared for a GitHub merge queue but NOTHING is enabled: no ruleset change, no queue. This PR only adds (a) a `merge_group: checks_requested` trigger to ci.yml, which fires only once a queue exists, with a per-group concurrency group `mq-<sha>` that is never cancelled, and `notify-failure` skips merge_group (a failed group drops one PR; it is not "main is red"); (b) `scripts/ci/merge-queue-enqueue.sh`, the drain's final step when a queue is on, used as `MERGE_GATE_MERGE_CMD`: it re-reads the PR, refuses unless it is still open at the head the gate verified, then calls `enqueuePullRequest` with `expectedHeadOid` = that sha (GitHub refuses a moved head), so the money stamp, AI review and creator checks the gate ran on that head stay the control plane and the queue only batches CI and merges. Evidence: `tests/unit/merge-queue-enqueue.test.ts` (enqueue pins the sha, a moved head is refused with no GraphQL call, GitHub refusing exits non-zero, ci.yml wiring), `node scripts/ci/merge-gate-required.mjs` output unchanged (the required list does not gain or lose a check). NOT done and NOT verified: enabling the queue ruleset (waits on Ahmad keeping Enterprise past about 2026-12-05); whether the plan allows a merge queue on a private repo; "the queue run counts as main's green" (needs its own reviewed change to the drain's main gate: skip the push full lane when the tree equals a tested merge_group tree, or point `--main-workflow` at merge_group); the ruleset's required-check list must match merge-gate-required.mjs and jobs skipped by `changes` must still report on merge_group.

Cost if wrong: while no queue exists the new trigger and script are dead code and nothing changes; once a queue is enabled, a missing required check on merge_group removes every queued PR (the queue is switched off with one ruleset change and the drain falls back to `gh pr merge`).

Amendment (aggregator, 2026-11-17, design approved by the main controller): the queue ruleset requires exactly three checks, `Repo guards`, `API Worker boots on workerd` and `Merge queue gate`, because GitHub matches required checks BY NAME on the pull request and on the merge group while each CI lane reports only on its own event (the pull-request lane `Unit Tests (affected)`, `App builds (affected)` and the deploy-change check never run on a merge group; the full lane `Build`, `Unit Tests`, `Integration Tests`, `E2E Tests`, `Security Audit` never run on a pull request). `Merge queue gate` (ci.yml `merge-queue-gate`, verdict in `scripts/ci/merge-queue-gate.mjs`) is an instant success on a pull request and, on a merge group, succeeds only when every full-lane job it needs succeeded: a failure, a cancelled run or a SKIPPED job fails it, and an empty needs object is never green. `tests/unit/merge-queue-gate.test.ts` fails when a job that runs on a merge group is missing from its `needs` (unit shards count through `test-unit`). The drain's own required list (`scripts/ci/merge-gate-required.mjs`) is unchanged: the gate is not a pull-request check it waits on. Not yet verified: a real merge group run (the ruleset is created `disabled`, id 27480470); the first live queue entry is the proof, with the ruleset switched on only after the drain change "a merge_group run counts as main's green" is merged. Cost if wrong: a full-lane job missing from `needs` would let a merge group go green without it (the structural test prevents that); a wrongly required name would make the queue wait forever, switched off by setting the ruleset back to `disabled`.

Amendment (part B, tested-tree skip, 2026-11-17, requested by the main controller): every queue merge fires a push run that would repeat the full lane (about 75 job-minutes) on a tree the merge group already proved, and that run is where the throughput goes. A new always-on job `tested-tree` (`Tested tree check`, `scripts/ci/tested-tree.mjs`) runs on every event; on a PUSH it compares the git TREE id of the pushed commit (not commit shas: a queue squash makes a new sha with the same tree) with the tree of each completed `merge_group` run of ci.yml and answers `skip=true` only when every matching run has conclusion success AND a succeeded `Merge queue gate` job. It FAILS CLOSED: any API error, an unreadable tree, no matching run, any completed non-success run of the same tree (ambiguity) or any other event answers `skip=false` (full lane). The full-lane ROOT jobs (build, unit shards and their aggregate, security, workerd integration, worker dry-run) carry `needs: [tested-tree]` and `needs.tested-tree.outputs.skip != 'true'`; everything else in the full lane hangs off them (build-dependent jobs skip when build skips). `API Worker boots on workerd` is a REQUIRED pull request check, so it keeps NO job-level `if` (a skipped required job reads as a pass; `tests/unit/ci-api-smoke-scope.test.ts` enforces it): it only `needs: [tested-tree]` and its existing `scope` step turns a tested-tree skip into `run=false` (the job always runs and reports, every heavy step is already gated on that output). The derived required list is the previous one plus the always-reporting `Tested tree check`; `scripts/ci/merge-gate-required.mjs` is unchanged. Until a merge queue exists there is no merge_group run, so `skip` is always false and the lane is unchanged. The drain side is foundation #111 (`merge_group_green`). Not verified: a live skipped push run (needs the queue); the first queue merge is the proof. Cost if wrong: a main commit whose tree equals a green group but would have failed its own full lane (an environment-dependent flake) is not re-tested on main; the nightly full lane (`schedule`, always `skip=false`) still runs the whole lane against main every night.

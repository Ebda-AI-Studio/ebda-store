# NZ-INTEG-SCOPE-1

> Section: NEON-ZERO integration (2026-11-05)

**Ruling NZ-INTEG-SCOPE-1 - a Postgres store's `storeDb(id)` / `storeWriter(id)` client scopes its own calls; with no cutover marker the behaviour equals main's.** The NEON-ZERO PRs replaced `withStore(id, tx => tx.model...)` with `(await storeDb(id)).model...` in 40+ services, MCP handlers, jobs and webhooks. For a Postgres store `storeDb` was the bare `prisma` proxy, so a call made with no request transaction (MCP, webhook, job, hub) reached the tenant guard unscoped and failed (`TenantScopeViolation: no tenant context`, 500). PR #443's Integration Tests showed it: 98 failures in 15 files (egypt gateway webhooks 42, MCP agent checkout 35, provider activation 4, key admin 6, and others) that pass on main. Deploying #443 before any marker is set must change nothing, so the repository client now does what the old wrapper did: for a Postgres store, a model call made with DEFINITELY no ambient store scope (`currentStoreId()` says so) runs in a short `withStore(storeId, ...)` (BEGIN + `set_config`, the guard satisfied); with an ambient scope the call is made as-is, so a request keeps its one atomic transaction, `$transaction([ ...ops ])` arrays keep working (an unscoped call is a deferred `ScopedCall`; an array containing one runs and commits inside one `withStore`), and a service handed a FOREIGN store id from inside store B's scope is still refused by the guard (the page-builder isolation test pins it). A store id that is not a UUID is never scoped (`withStore` refuses it) and the call goes as-is. A Durable Object store never comes through this client. Companion fixes found by the same run: the integration identity stand-in (`lib/test-identity.ts`) answered `mfaEnabled: false` / `emailVerified: true` for every account, so an enrolled super admin looked un-enrolled the moment the live identity check fed `require-mfa`; it now answers from the `users` row, which is the identity store in that tier (the Postgres path of main). `provider-activation.runTestForStore` reads its payment config inside `withStore`. The contract tests that hand-build a DO repo gain the split-aware `store` delegate the real DO repo has (`tests/helpers/do-store-delegate.ts`).

Evidence: PR #443 job 127183024032 (98 of 2598 failing), then locally against Postgres 17 + pgvector 0.8 (Apple `container`) exactly as the CI job runs: `tests/integration` + `apps/api/src` 305 files / 2597 passed / 0 failed, the serial planner lane 6 files / 80 passed, `tests/unit` 0 failed. Cost if wrong: a model call that is made outside any scope for a store id the caller did not authorise would run in that store's scope instead of failing; every such call already names its store explicitly through `storeDb(id)`, and the guard still checks each `where` against the scope it runs in.

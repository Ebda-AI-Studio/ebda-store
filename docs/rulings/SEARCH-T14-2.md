# SEARCH-T14-2

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling SEARCH-T14-2 (Task 14 load test) — `product_embeddings` is stored with `toast_tuple_target = 8160` (migration `20261024000400_product_embeddings_inline_vectors`). Evidence: two `halfvec(1024)` per row put a row (~4.2 KB) over the 2 KB TOAST threshold, so both vectors lived in a 115 MB TOAST relation behind a 6 MB heap, and the exact per-store KNN read each through the TOAST index: 120,782 buffer hits (~1 GB of memory traffic) and 74 ms for ONE query at 20,000 products, 1,184 ms mean under 30 searches/s, storefront p95 3,994 ms. With the vectors inline: 16,830 buffers, 30 ms alone, 26 ms mean under the same load, p95 310 ms. Column `STORAGE MAIN` was tried first and does NOT work for writes (a MAIN value is still moved out once the row passes the 2 KB target; 24,576 bytes of TOAST for 150 rows, measured); the table option does. Applies to rows written from now on; production has 0 embeddings, so nothing is rewritten (an existing table needs an offline `VACUUM FULL product_embeddings`). Tested: `product-embeddings-schema.test.ts` (the option, and 150 rows of incompressible vectors grow the heap and leave TOAST at 0 bytes; red first). Exact KNN is linear in the store: ~30 ms per 20,000 products, so SEARCH-8's "no ANN below ~20k per store" holds, and the question moves to ~100k per store (pgvector 0.8 iterative scans are the candidate). Cost if wrong: none functionally; the heap is ~1.5x larger than the TOASTed layout (4.2 KB inline vs 2 x 2 KB TOAST chunks plus index).

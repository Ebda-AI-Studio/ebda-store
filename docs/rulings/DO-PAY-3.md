# DO-PAY-3

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling DO-PAY-3 (2026-10-26) - audit DB-2 (High): the entity index is no longer eventually consistent on the payment path. (1) The checkout queues the `order` entity-index row in the SAME `transactionSync` that creates the order; `createPayment` already queued `payment` + `webhook:<provider>:<ref>`. (2) `createPaymentIndexed` / `awaitEntityIndexed` write those rows to D1 NOW (drain, then verify the specific ids) BEFORE the provider reference or payment url is handed out; if D1 cannot take them the call fails 503 `ENTITY_INDEX_UNAVAILABLE` and the reference is never returned (the rows stay queued for the alarm). (3) `routePaymentWebhook` answers `{retry}` for an unresolved reference and `webhookHttpResponse` turns it into 503 + `Retry-After: 30` + a `webhook_unresolved_reference` alert, never a 2xx "ignored" (no store existence is revealed). Test: a callback before the alarm is non-2xx and routes after the drain; the indexed create is routable with no alarm; D1 down fails the create. NOT done here (Worker glue, other PR): the webhook route itself (`webhook.routes.ts`) must call these two; a reconciliation job that re-queries gateways for pending payments older than N minutes (audit option 2). (4) SECURITY: `awaitEntityIndexed(db, d1, storeId, ids)` fails CLOSED: it throws on any drain `conflict` for a requested id (`ENTITY_INDEX_CONFLICT`, 409: the id is owned by another store) and then re-reads EVERY id from D1 and requires it to resolve to this store (an unqueued/unknown id is `ENTITY_INDEX_UNAVAILABLE`), so "not pending" never counts as indexed and a reference can never route a payment to the wrong tenant. Cost if wrong: a payment create fails 503 while D1 is down (checkout cannot take that payment method) instead of silently losing a callback later.

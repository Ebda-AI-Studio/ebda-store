# NZ-MCP-1

Ruling NZ-MCP-1 (2026-11-11, postgres-removed final sweep) - the merchant-admin MCP surface and the merchant API-key routes run on a store's Durable Object with no Postgres: every `runInTenantContext` around the admin read tools and the key routes becomes `readInStoreContext`, every one around the admin write tools (`ctx.inStore` in `mcp/merchant-write.ts`), the agent order tools and the denied-write audit in `mcp/agent-auth.ts` becomes `runInStoreTenantContext`, `admin_get_order`'s `orderEvent` read goes through `storeDb`, and the key list reads the owners' display facts from the identity service (`getAccountsBrief`, one call) because `MerchantApiKey.user` cannot be joined across databases after the `access` cutover; the admin MCP transport answers in JSON mode (`enableJsonResponse`) because on workerd the SSE stream of a stateless POST closed empty for every tool that awaits a DO call. Proof: `workers-test/merchant-mcp-do.test.ts` mints, lists and revokes a key, drives admin read tools (orders, customers, marketing), a write tool and an agent order tool against a store with orders and customers, every call under 500 and `/__dev/pg-reaches` empty; on the old code it fails 4 of 6. NOT ported (money): the COD `payment.create` and `recordPaymentEvent` of the agent `place_order` still use Postgres (`order.tools.ts` `withTenantContext`), they need the DO `paymentCreate` op. Cost if wrong: if the JSON-mode transport is not what production clients negotiate, an MCP client expecting an SSE frame gets one JSON body instead, and the agent place_order COD path keeps failing (and rolling back its order) until its payment leg moves to the DO.

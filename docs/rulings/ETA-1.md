Ruling ETA-1 (2026-10-26, eta agent of PLANS-ALL-1) - the ETA e-receipt connector is per merchant and per store, behind the hidden super-admin feature `eta_ereceipt` (OFF by default, in no plan baseline), and VAT-0 stands (Ebda itself charges no VAT; this is for merchants' own receipts). Merchants connect their OWN ETA credentials (client id/secret, POS serial, optional pre-shared key) stored AES-256-GCM encrypted and shown masked. Receipts are built once, stored, and re-sent unchanged; a 202 is only "received", acceptance is the submission-details verdict; a total that cannot be reproduced exactly is refused (`failed`, never submitted). Receipts ship UNSIGNED (the SDK says signature validation is not deployed) with a merchant-side signing-bridge seam; B2B e-invoices need the merchant's eSeal on a USB token/HSM, which a Worker cannot use, so P4 is design-only until a merchant with B2B sales and an eSeal commits. Partial returns are built from the order/refunded line items and the stored sale line map (a price-only refund with no goods lines stays `manual`). Evidence: docs/plans/done/2026-10-07-egypt-vat-and-eta.md section 11 (every API fact cited to sdk.invoicing.eta.gov.eg), `tests/unit/eta-*.test.ts`. Cost if wrong: a PreProd run may show a serialization or field detail we read differently (the UNVERIFIED list), which rejects receipts until the mapper is corrected; nothing is sent while the flag is off.

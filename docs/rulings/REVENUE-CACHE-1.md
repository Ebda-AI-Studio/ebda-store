# REVENUE-CACHE-1

Ruling REVENUE-CACHE-1 (2026-11-20, STORE-QA-74 live on Amelia: after the first full refund the ledger tiles moved at once but finance "Net sales" and the analytics revenue stayed at 10000 / 3 orders until a later refund) - the order-based revenue figures are a NEVER-stale class for the merchant and are invalidated by EVENT on every write path, every layer.

- Root cause: `AnalyticsService.getDashboardStats` (`analytics.service.ts`) cached the whole dashboard payload (`totalRevenue`, `totalOrders`, customers, profit) for 120 s in Redis then isolate memory, keyed by store and date range, and NO order / payment / refund / return write invalidated it. The finance dashboard's "Net sales" panel and the analytics hub read that same payload. The ledger tiles are not cached, so they moved first.
- Fix: the payload now rides the generation-guarded cache (`getCached`, public-cache FIX-001: a fill that read the pre-write numbers cannot republish them) under `analytics:dashboard:<storeId>:`, and `invalidateStoreRevenueCaches(storeId)` (`lib/revenue-cache.ts`) bumps that prefix and the customers-spend snapshot. It is called from the ONE transport every money write of a Durable Object store passes through (`repo-factory.ts` `callMoney`, after the op committed and before the caller answers) for every money op except the reads (`analytics*`, `search*`, `trialBalance`, `stockValue`, ...) and the one documented exception below; a new write op is covered by default. `importCodRemittances` (a statement import can mark COD paid) invalidates too.
- Exception, bounded-stale on purpose: `createOrder`, the guest checkout hot path. Invalidating costs 2 remote calls and a serial wave per order and breaks the latency budget (`workers-test/latency-budget.test.ts`). A NEW order only adds to the totals; residual: a just-placed order is missing from the dashboard for up to the 120 s TTL. Everything that can remove or change a counted sale (confirm, pay, cancel, status, refund, return) invalidates at once.
- Redis down: invalidation is best-effort (logged) and the TTL bounds the stale window; it never fails the write that committed.
- Evidence: `apps/api/workers-test/merchant-orders-do.test.ts` "STORE-QA-74" (real Worker + real Durable Object store: read fills the cache, a second read is the cached one, an InstaPay full refund, the NEXT read is lower by the order total and one order fewer), `tests/unit/revenue-cache.test.ts` (classification over the real `MONEY_OP_NAMES`).
- Cost if wrong: an over-invalidating op only costs one recompute of the dashboard; an op wrongly left out shows the old revenue for up to 120 s. Postgres stores (removed from production) keep their older per-route invalidation.

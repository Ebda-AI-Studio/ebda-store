# CART-EMAIL-3

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling CART-EMAIL-3 (2026-10-21) - once per cart is a database claim, not a timer. The sweep flips `email_status` NULL -> `queued` with one conditional UPDATE and only the sweep that wins emits the event (event id `cart-recovery-email/<cart>`); the job mails only a `queued` row, uses Resend's idempotency key `cart-recovery-email/<cart>`, and then marks `sent`. An enqueue failure marks the row `failed` (`ENQUEUE_FAILED`); `onFailure` marks a still-queued row `failed` (`SEND_JOB_FAILED`). Conversion stops it: the order transaction already marks the cart `recovered` (issue 2356) and the job re-reads that status, the cart's items and the claim in one SELECT pass AFTER the platform send-slot wait (up to 30 s under contention) and immediately before the Resend call (review item 2; the first read at load time alone left a window of that length). Residual (accepted, narrowed): an order committed in the few milliseconds between that final read and Resend accepting the message still gets one email. Unit evidence uses a sequential fake, so the claim's concurrency guard (`emailStatus: null` in the UPDATE) is not proven by a test; an integration test against Postgres is the follow-up once the DB slot is free. Cost if wrong: a duplicate email to one subscriber in a double-sweep race.

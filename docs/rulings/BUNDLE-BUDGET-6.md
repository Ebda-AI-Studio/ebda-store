# BUNDLE-BUDGET-6

Ruling BUNDLE-BUDGET-6 (2026-10-30, INFRA-CF-1 final integration) - the API Worker bundle (`worker.js`) is cut 7,819,641 -> 7,430,377 B (-389,264 B, -5.0%) by building exceljs from its own source instead of embedding the browserify copy, with no change to what the Worker does; the budget (`scripts/ci/worker-startup-budget.json`, 7,800,000 B raw, 2,200,000 B gzip) is unchanged and now has 370 KB of room instead of being 20 KB over. Measured on the integration stack (#349 + #351 + #352 + #353 + #354 + #327 + the final-integration ports): before 7,819,641 B (gzip 2,125,853), after 7,430,377 B (gzip 2,009,290); startup CPU 88.7 ms (limit 140, `worker-startup-budget.mjs` exit 0).

Why: source-map attribution of the minified bundle showed `exceljs/dist/exceljs.bare.min.js` (862 KB) carries its own browserified crypto and stream stack - bn.js 132 KB, elliptic 70 KB, asn1.js 50 KB, hash.js 17 KB, browserify-aes, a `buffer` polyfill 21 KB, readable-stream copies - because exceljs' browser build must supply `crypto`, `events`, `buffer`, `util` and `stream` itself. The Worker already runs with `nodejs_compat`, which provides all five. `scripts/ci/gen-exceljs-workers.mjs` bundles `exceljs/lib/exceljs.bare.js` (the same entry the bare dist is built from) with esbuild, leaves those five built-ins external, and maps `fs`, `tmp`, `unzipper` and `archiver` (the file and stream readers the Worker never calls) to an empty module, as exceljs' own browser build treats `fs`. The output is committed as `apps/api/src/cf/stubs/exceljs-workers.cjs` (474 KB, header `exceljs@<version>`) and `wrangler.jsonc` aliases `exceljs` to it. Only `crypto` is used at runtime by exceljs (`utils/encryptor.js`, sheet protection).

Evidence nothing changed behaviourally: `tests/unit/ops/exceljs-workers-build.test.ts` (4): built from the installed exceljs version; the exported surface equals the one the Worker used before (`dist/exceljs.bare.min.js`); a workbook with RTL text, rich text, a formula, a date, a number format and a merge written by the new build is read back equal by the stock library and the reverse; a protected sheet writes a salted SHA-512 hash that the stock library reads. `apps/api/workers-test/exceljs-workers.test.ts` (real workerd, `npm run -w apps/api cf:test`): write, read back, protect on the new build. The startup-CPU gate passes.

Tried and dropped: `RECEIPT_BARCODE_SHAPES` from a hand-listed id array instead of `Object.keys` of the 70 KB drawings: no saving, because `renderBarcodeSvg` (invoices, packing slips) reads the SVG paths; the DO migration SQL minified in `migrations.generated.ts`: a test pins it verbatim to the `.sql` files; `prisma-meta.json` without `list:false`/`optional:false`: ~38 KB but touches every prisma-lite consumer.

Cost if wrong: `npm run -w apps/api cf:dry-run` plus the pre-deploy smoke fail loudly if a built-in is missing; revert = point the `exceljs` alias in `apps/api/wrangler.jsonc` back at `../../node_modules/exceljs/dist/exceljs.bare.min.js` (+389 KB). Regenerate after an exceljs upgrade with `node scripts/ci/gen-exceljs-workers.mjs` (`--check` fails when the committed build is from another version).

Ruling SHARIA-BNPL-1 (Ahmad, 2026-11-03) — no installment provider is on by default. Read from code on this branch (NOT a production query): a Paymob method exists only when the merchant types its integration id (`paymobSettingsBaseSchema.integrationIds` defaults to `{}`), Kashier methods default to `['card','wallet']`, and no migration, seed or catalog field pre-fills valU, Kiosk or `bnpl`, so the default was already OFF and this change alters no stored row and no live store: a store that already saved a valU or `bnpl` setting keeps it. What is new is the disclosure under the valU and Kiosk fields and the Kashier `bnpl` option in the payment settings (`BNPL_DISCLOSURE`, ar + en, `paymentSettings.connect.bnplDisclosure`), pinned by `tests/unit/bnpl-default-off.test.ts`. What would settle which live stores already use one: `SELECT store_id, provider FROM payment_configs WHERE settings::text ~ '"(valu|kiosk)"|bnpl'` (read-only, not run). Evidence: research section 1 (valU/Kashier fee terms not found, many BNPL contracts carry late fees, which scholars treat as riba). Cost if wrong: a merchant who wants installments sees a notice they must read, and a live store that relied on a default we assumed is OFF would already have been OFF.

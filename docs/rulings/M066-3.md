Ruling M066-3 (Issue 664, amends M066-2) - the account-wide guess slot is claimed only after this request's own address counters admitted it. In M066-2 the account row was inserted in the same batch even when the (account, address) pair or the address budget refused, and removed afterwards, so one locked-out address firing parallel requests could fill the 50-slot account cap and lock the owner out. Now each request's rows carry a per-request time fraction, and the account statement inserts only if THIS request's pair row and address row exist (and the cap has room), all inside the one D1 batch; a refused address claims nothing, not even briefly. Evidence: apps/accounts/test/account-guess-cap.test.ts (the batch-spy test fails on the old code; 100 parallel requests from one refused address leave the account tally unchanged and a second network is still admitted); review2.test.ts now asserts the /24 prefix key instead of an exact address that never existed. Cost if wrong: if D1 ever stored the fractional time differently from the bound value the account row would never insert and every login would be refused; the full accounts suite (76 tests across the throttle files) passes locally.

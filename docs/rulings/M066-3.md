Ruling M066-3 (Issue 664, amends M066-2) - the account-wide guess slot is claimed only after this request's own address counters admitted it. In M066-2 the account row was inserted in the same batch even when the (account, address) pair or the address budget refused, and removed afterwards, so one locked-out address firing parallel requests could fill the 50-slot account cap and lock the owner out. Now each request's rows carry a random nonce (crypto.randomUUID, new nullable TEXT column `login_attempts.nonce`, expand-only migration 0005), and the account statement inserts only if THIS request's pair row and address row exist by nonce (and the cap has room), all inside the one D1 batch; a refused address claims nothing, not even briefly. No time or float comparison remains in the admit logic (the first version matched a fractional timestamp: if that comparison ever missed, every login would be refused). Evidence: apps/accounts/test/account-guess-cap.test.ts (the batch-spy test fails on the old code; 100 parallel requests from one refused address leave the account tally unchanged and a second network is still admitted; every admitted request, serial or in a burst of 10, produces exactly one account row); review2.test.ts now asserts the /24 prefix key instead of an exact address that never existed. Deploy order: migration 0005 must be applied before the new Worker code runs (the new code writes the column). Cost if wrong: if migration 0005 were missing at deploy the insert would error and logins would fail loudly (500), not silently; the throttle test files pass locally (77 tests).

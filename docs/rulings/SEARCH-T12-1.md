# SEARCH-T12-1

> Section: 2026-10-16 — Search program, PR 4 (P1c, hybrid ranking): SEARCH-T12-\*

Ruling SEARCH-T12-1 (plan amendment E11) — the storefront query embed is the ONE synchronous third-party call allowed in a storefront GET. It races `QUERY_EMBED_BUDGET_MS` = 400 ms (`apps/api/src/services/product-search.service.ts`); on losing, the call is aborted through the provider's `AbortSignal` (cancelled, not abandoned) and the list is keyword-only. Any provider error, a vector-SQL error (inside `withSavepoint`, so the request transaction survives) or no provider gives the same keyword-only answer with HTTP 200. It runs inside the request transaction, so a slow provider holds one pooled connection for at most ~400 ms plus the budget `INCR`s. Evidence: `tests/integration/hybrid-search.test.ts` "a slow provider loses the ~400 ms race" (a provider that never answers and ignores its signal: keyword result, `signal.aborted === true`; red with the race removed) and "falls back to keyword results when the provider throws". Cost if wrong: during a Workers AI slowdown every embed-eligible search pays up to 400 ms extra and holds a connection that long (Task 14 measures p95). **Amended (Task 12 review M3):** the 400 ms timer now starts BEFORE the budget step, so it bounds the budget round trips (AuthState DO) and the provider call together; a budget answer that arrives after the race was lost never reaches the provider (`tests/unit/query-embed-race-budget.test.ts`: a 1.5 s budget step returns in < 700 ms, provider not called; red before at 3 s). The vector SQL that follows stays outside the race (one short indexed statement, 5.7 ms measured at 2 000 products).

# DO-PAY-2

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling DO-PAY-2 (2026-10-25) - settlement shape after the Opus money review (Postgres `refund-settle.ts` + StoreDO `payments.ts`). ONE function settles a refund (webhook, manual refresh, claim release; the in-band executed write now also takes the lock and reads the LOCKED row): `FOR NO KEY UPDATE` on the payment, decide from the locked row and its refund events, patch built only from the locked copy, outcome event in the same transaction; `inSettlementTx` joins the ambient tenant transaction only when it is scoped to this store, else opens one. Rules: absorb only a COMPLETED event, oldest young unconsumed claim of the same amount, consumed by an `refund_webhook_absorbed` event (unique partial index per claim with `refund_failed`), the absorbed id is FILED as accounted by `commit()`; a claim released after absorb is reviewed, not decremented; an executed answer whose id differs from the id a webhook was absorbed under is marked for review (`refund_reconcile_review`) + P1; a pending/failed notice never accounts or consumes; Fawry amount-less notice is attributed only on positive evidence (parsed reference + same fawryRef + kind + an executed unconsumed claim, 30 min) else held + alerted, and the Fawry refund ref now carries the notice's own signed reference (`~<ref>`) so repeated partial notices are not dropped as redeliveries; Kashier: an unknown id while ANY executed claim is unconsumed is HELD whatever its age (P1, never auto-booked), a claim closes on its own id's webhook (`via: id_match`) or an audited operator match (`/refund-match-claim`, needs a held webhook for that exact id, refuses an accounted id); the DO applies the GATEWAY's refund status after confirmation and refuses a relabelled kind (nothing applied). NOT done, ruled: alerts and `applyRefundEffects` still run while the row lock is held in the webhook branch (long-lived lock; an alert can precede a rollback) - deferral after commit is a follow-up; the unique index is built without CONCURRENTLY: run `SELECT details->>'claimId', count(*) FROM payment_events WHERE event_type IN ('refund_webhook_absorbed','refund_failed') GROUP BY 1 HAVING count(*) > 1` read-only on prod before deploy (new event types, expected 0). Cost if wrong: a held webhook needs an operator within a day or the refund stays understated (never overpaid); a late Kashier delivery for a genuinely separate refund is held while an own claim is unconsumed.

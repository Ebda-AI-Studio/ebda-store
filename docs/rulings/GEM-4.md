# GEM-4

> Section: 2026-10-29 — issue 49, Gemini 429 behaviour after the multi-key failover

Ruling GEM-4 - the answer-engine Gemini provider keeps two distinct 429 outcomes, both now pinned by tests. (1) A GROUNDED call that 429s on every key still falls back to ONE ungrounded call and records `groundingUnavailableReason: http_429` (grounding has its own quota, B0-51). (2) If the UNGROUNDED call also 429s on every key, the scan fails with `502 GEMINI_API_ERROR` ("all Gemini keys rate limited") and records no usage: there is no third degrade, and a silent empty answer would be scored as a real "not mentioned" result. Issue 49's two failing tests were already fixed on main by B0-51 (the mock `headers`, the grounding-scoped bench); the gap was no test for the multi-key exhausted case, added in `gemini.provider.test.ts` (2 tests: grounded exhaustion tries each key then answers plain; plain exhaustion = 4 fetches, 502, no `recordUsage`). Evidence: 14/14 in that file; production code unchanged. Cost if wrong: if product prefers a soft "unavailable" result over a 502 when every key is exhausted, the scan caller needs a catch that records a skipped check instead of an error.

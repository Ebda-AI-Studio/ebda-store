# NZ-ACCT-1

Ruling NZ-ACCT-1 (2026-11-11, `docs/plans/2026-11-11-nz-money-auth.md` items M5, M6, A1, A2) - the accounts and books paths answer on a store whose data lives on its Durable Object without the removed Postgres client, and no money or auth check is weakened to do it: billing grants (`grants.service` `inOwnTx`) run their function directly once billing is served from D1, because every atomic piece is already one D1 statement or batch (`insertCappedGrant` lock-then-count with `ON CONFLICT (idempotency_key) DO NOTHING`, `applyGrantsBatchD1`, `revokeGrantsD1`, `claimRestoreD1`), while a Postgres store keeps its own transaction; `recordReferral` reads the two owners from D1 `stores.owner_id` (same-owner self-referral still refused); the tax report reads the new DO read op `taxReportLines` (SQLite twin of the raw Postgres query: 2100 tax / 4000 base per posted or reversed `order` entry, order id from the `source_id` prefix, `HAVING tax <> 0`, customer name from the store's `customers` row else the `json_type`-guarded shipping-address snapshot, every table filtered by `store_id`); the four customer MFA endpoints answer the existing NZ-N9-1 `MFA_UNAVAILABLE` 409 BEFORE any `withUser` for a customer of a DO-auth store (and `/verify` on a Postgres-less Worker once the challenge token has verified), so nothing enrols, verifies or disables a second factor; merchant resend-verification and forgot-password with no store on a Postgres-less Worker answer the enumeration-safe generic result, the reset delegating to `forgotIdentityPassword`. Evidence: `apps/api/workers-test/account-books-do.test.ts` (red on the old code: tax report 500, every MFA endpoint 500), `packages/repo/test/do-tax-report-lines.test.ts`, `tests/unit/tax-report.test.ts`, `tests/unit/mfa-do-store-refusal.test.ts`, `tests/unit/grants-no-pg-transaction.test.ts`, `tests/unit/merchant-email-flows-no-postgres.test.ts`. The manual-payment route now records a fresh payment (201, `duplicate: false`) on workerd with zero Postgres reaches, so the award path runs past the D1 commit (the earlier `duplicate` answer was fixed on main); the referral record is unit-tested (`recordReferral`). Not proven red: the merchant e-mail flows (the route swallows every error into the generic 200, so the old code was not red there). Cost if wrong: a D1 grant write that lost its Postgres lock could award a founding slot past the 20 cap (the cap is inside the single INSERT, so the exposure is a regression in that statement, not in this change), and a DO store customer who enrolled MFA on Postgres before the cutover stays refused until the store clears it, the documented NZ-N9-1 behaviour.

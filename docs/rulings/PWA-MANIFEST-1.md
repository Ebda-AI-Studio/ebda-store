# PWA-MANIFEST-1

> Section: Launch follow-up 2026-11-10 (branch `fix/public-normal-browsing-404s`): the per-store PWA manifest never applied

Ruling PWA-MANIFEST-1 - the storefront reads the per-store PWA manifest from the route that exists (`GET /stores/public/<storeId>/manifest.json`), accepts it only when it passes `storePwaManifestSchema` (`@ebda/shared`) and answers within 3 seconds, and otherwise serves its own generic manifest; the API emits ONLY the members the merchant saved (no icon when none was uploaded, no default name, description, colour, display, orientation, start URL or scope), and the storefront lays them over its generic manifest. Measured in production 2026-11-10 before the fix: the storefront asked `GET /public/<storeId>/manifest.json`, which is no route (404 `Cannot GET`, one store-miss per render), so every store has been served the generic manifest since the feature shipped; the real route answered 200 for all five demo stores (Qamar, Dahab, Jasmine, Lamma, Souq) with `start_url` and `scope` `/`, hex colours, a non-empty `name` and `short_name`, and two icons `/icons/icon-192x192.png` and `/icons/icon-512x512.png` that no app ships (404 on the storefront; `/icon-192.png` and `/icon-512.png` answer 200 `image/png`). Not cached at the edge: the API route sends no `Cache-Control` and the storefront manifest is `public, max-age=0, must-revalidate`; the storefront's own fetch is held in the Next data cache for 300 seconds under the tag `pwa:<storeId>`, which a PWA settings write clears. Either deploy order is safe: the new storefront against the old API refuses the relative icons and serves the generic manifest (today's behaviour), and the old storefront against the new API still asks the wrong path. Evidence: `apps/web/src/app/manifest.test.ts` (generic manifest on a rejected fetch, a hung fetch, a non-JSON body and 14 invalid manifests), `tests/unit/pwa-manifest-generation.test.ts` (no icon named when none is set).

The alternative was taken (controller review of #505, 2026-11-10), so the visible change this ruling first accepted is gone. `PWAService.generateManifest` answers `{}` for a store with no saved PWA settings and one member for each saved value; `apps/web/src/app/manifest.ts` builds the generic manifest once (`genericManifest`) and lays the saved members over it (`withSavedSettings`), so a member that was never saved keeps exactly the generic value, including the description from `pickMetaDescription(store, locale)` that the per-store branch used to skip in favour of "Shop at <name>". Under `ar` the two names resolve in this order: the saved Arabic member, the store's own Arabic name, and only for a store with no Arabic name the saved English member; a description never crosses languages. `PWAService.updateSettings` stores only what was sent, merged over what is already stored: it used to write every default into the row on the first toggle or icon upload, which would have turned defaults into "saved" values. The admin settings read (`PWAService.getSettings`) is a separate code path and still shows the defaults in the form; the public `pwa/config` route is untouched. For Qamar (measured in production 2026-11-10: `pwaSettings` is `{}`, live manifest `theme_color` `#141414`, the store's own description) nothing changes. The only reader of the public manifest route is `apps/web/src/app/manifest.ts` (grep over every app, package, script and workflow). Evidence: `apps/web/src/app/manifest.test.ts` ("saved PWA settings are laid over the generic manifest": `{}` deep-equal to the generic manifest in `ar` and `en`, a Qamar-shaped store, each single saved member, the schema with members absent), `tests/unit/pwa-manifest-generation.test.ts` ("only what the merchant saved", "stores only what was sent"); six hand mutations of the two files each fail those tests.

Residual: a store whose row already holds defaults written by the old `updateSettings` (any PWA toggle or icon upload before this change) cannot be told apart from a merchant who chose those values, so it is served them. Not verified for Dahab, Jasmine, Lamma and Souq before the deploy (no read-only route by id for the saved settings); after the deploy their API manifest shows it directly (`{}` means none).

Cost if wrong: a store that toggled PWA or uploaded an icon before this change shows the near-black `#0A0B0C` browser bar and "Shop at <name>" in its installed app instead of its theme colour and its own description, until the merchant saves the PWA form once.

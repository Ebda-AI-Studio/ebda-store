# EDGE-BUILD-1

> Section: 2026-11-10 — edge-cached HTML outlived the build that rendered it (pre-QA sweep P1)

Ruling EDGE-BUILD-1 (2026-11-10) - both Worker HTML edge caches (`apps/web/demo-edge-cache.ts`, `apps/web/store-edge-cache.ts`) put the Worker version id in their cache key (`…__build=<CF_VERSION_METADATA.id>`, `apps/web/edge-build-id.ts`), so a page rendered by one build is never served by another; with no id the two layers do not read or write the cache at all (fail closed: slow, never broken). Staleness class of "which build rendered this HTML": NEVER-stale. Evidence (measured): the storefront deploy of `076472a29` finished at 2026-11-09 20:58:01Z (run 42697312524); at ~21:33Z and ~21:37Z `https://storedemo.ebda.app/en` answered `x-demo-edge: STALE` with HTML naming 5 JS chunks and 1 CSS file under `/_next/static/` that returned 404 (Workers Static Assets belong to one Worker version: a deploy replaces them, the old ones are gone; the same URLs were still 404 at 21:56Z); `/ar` was clean only because the deploy workflow's warm step requests `/ar` and nothing else; `/en` healed when a stale refresh stored a new copy at 21:37:03Z. Inferred, not measured: the bad copy was written before 20:58Z (the sweep did not record `x-edge-cached-at`). Same class, by code: the demo layer keyed on host + path + look and served stale for 24 h with nothing invalidating it on deploy; the store layer (every merchant store) keyed on host + path and served for up to 600 s, purged only by a store write (per-store epoch in R2), never by a deploy, so each deploy could hand merchants' visitors unstyled, dead pages for up to 10 minutes (not observed live across a deploy). Not in the class: the OpenNext R2 incremental cache (its key already holds the Next build id), the API's public JSON edge cache (no asset URLs), the service workers (no HTML cache). Rejected: purging on deploy (the Cache API deletes per data centre, and a request racing the deploy re-stores the old page); keeping the previous build's assets alive (Workers Static Assets has no such mode); a shorter stale window (shrinks the outage, keeps it). Enforcement: `scripts/assert-cf-cache-bindings.sh` fails the web deploy and the PR dry run when the generated `wrangler.jsonc` has no `version_metadata` binding named `CF_VERSION_METADATA`; the Worker logs one error per isolate when the id is missing at runtime. Tests (vitest on Node with a Map-backed fake of the Cache API, not workerd): `tests/unit/demo-edge-cache.test.ts`, `tests/unit/store-edge-cache.test.ts`, `tests/unit/edge-build-id.test.ts`, `tests/unit/cf-cache-bindings-assert.test.ts`. Accepted residuals: every deploy (and any other new Worker version, e.g. a secret change) starts with a cold HTML edge cache in every data centre, so the first visitor per page pays a full render (the warm step covers only `/ar` of the demo hosts); a rollback reads its own old entries (rendered by that same version, so their assets exist); old entries are not deleted, they expire on their own `max-age`; a binding that is present but returns no id at runtime raises no page, only the log line. Cost if wrong: if the version id were not unique per deployed asset set, a visitor could again get HTML whose scripts and styles 404 (a page that renders unstyled and cannot be used) until the stale window ends.

Update 2026-11-10: the warm step now requests `/ar` and `/en` of every demo host (WEB-COLD-1, amended), and `scripts/ci-affected.mjs` selects the web Worker checks for a change to either edge cache, `edge-build-id.ts` or any other local module the Worker entry bundles.

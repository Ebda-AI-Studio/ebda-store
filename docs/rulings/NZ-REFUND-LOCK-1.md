# NZ-REFUND-LOCK-1

Ruling NZ-REFUND-LOCK-1 (2026-11-23, NEON-ZERO, money) - the Postgres lock paths of the refund flow are removed: `lockPayment` (`SELECT ... FOR NO KEY UPDATE`) and `inSettlementTx` (the joined / opened tenant transaction that held it) in `apps/api/src/services/payment-providers/refund-settle.ts` (`lockPayment` becomes the plain re-read `readPayment`), their callers in `routes/order.routes.ts` (refund-match-claim, refund-status refresh) and `payment-providers/payment.factory.ts` (refund webhook branch, executed-refund write), and `lockOrderReturns` / `lockOrderReturnsBounded` (`pg_advisory_xact_lock` / `pg_try_advisory_xact_lock`) in `services/return.service.ts` (`complete()`, `create()`). Evidence, per site: (a) every one sits after a DO branch that returns first (`storeMoney(storeId)` -> `refundMatchClaim`, `applyPolledRefundOnDo`, `handleWebhookOnDo`, `refundOnDo`, `createOnDo`, `completeOnDo`), and on the Worker `storeMoney` is never null: `backendFromRow` (lib/store-backend.ts) answers 410 `STORE_STORAGE_REMOVED` for a `pg` row, 404 for no row, 503 for an unreadable flag; (b) the DO serialises the same critical section in ONE `transactionSync` on a single-threaded object (packages/repo/src/do/payments.ts `beginRefund` remaining-balance + CAS on `refunded_amount`, `completeRefund`, `releaseRefund`, `matchRefundToClaim`, `applyPaymentEventSync` -> `applyRefundWebhook`; packages/repo/src/do/returns.ts `createReturn` over-claim check + insert, `returnClaim` -> `assertOrderNotBusy` RETURN_ORDER_BUSY); (c) the Worker has no Postgres binding (apps/api/wrangler.jsonc) and its `prisma` throws POSTGRES_REMOVED on any call (apps/api/src/worker.ts), and every removed lock sits behind a Prisma read, so even a missed branch fails before any write. Proof: `apps/api/workers-do/payments.test.ts` 'concurrent partial refunds that together exceed the payment' (2 and 20 concurrent 2000 claims on a 3000 payment: one ok, refunded_amount 2000) is red when the remaining-balance guard is removed (`expected { ok: 2 } to deeply equal { ok: 1, REFUND_EXCEEDS_REMAINING: 1 }`); `workers-do/returns.test.ts` 'two different returns of one order completing together' is red when `assertOrderNotBusy` is disabled. `tests/integration/return-order-lock.test.ts` (it proved the Postgres advisory lock) and the defence-mutation entry `money-return-order-lock` are retired with the lock. Found on the way: the admin completion error map listed RETURN_ORDER_BUSY as create-only, but the DO's `returnClaim` raises it on completion; it now has its own EN + AR message. NOT changed: `payment-state-claims.ts` `lockPaymentRow` (payment confirm paths, not refund-only), `instapay.service.ts` `lockOrder` / payment `FOR UPDATE` (shared with confirm/expiry, covered by `tests/integration/instapay-refund-lock.test.ts`), `commitOnOwnTransaction` in `PaymentService.refund`. The Postgres branches that remain run only under Node (unit tests, local dev) and are no longer serialised; they go with the N-16 dead-code removal. Cost if wrong: if a Postgres-backed API were ever deployed again before N-16, two concurrent refund settlements or two returns on one order could interleave there; on the Worker nothing changes.

# SEARCH-P2-8

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling SEARCH-P2-8 (Search P2 review I3) — customer and guest-order search are STORE-FIRST. Evidence (measured, pg17 + pgvector, role `ebda_app`, 20 stores: 18 x 1,000 customers and guest orders, one store with 12,000 guest orders, one tiny store with 10; every name starts with "محمد"): searching the tiny store for "محمد" took about 200 ms and sequentially read 19,011 users with the global trigram indexes; with the fix it takes about 24 ms and reads none (users and orders each < 3,000 sequential tuples, asserted). Mechanism: the user arm is joined to the store's own customer set (live order here, or registered here) BEFORE the name/phone/email match; the three guest-order indexes are `btree_gin` composites that lead with `store_id` (`orders_guest_phone_digits / name_norm / email_store`), so the store restricts the index scan itself. Residual: a store with very many customers still pays for its own matches (bounded by the 1,000 / 20,000 caps, 50 / 200 in the palette). Post-launch plan: if one store's own customer set makes the user arm slow, add a store-leading composite on a denormalised `store_customers` table. Cost if wrong: a very large single store's common-name search stays tens of ms, not milliseconds.

# CF-SCHEMA-8

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling CF-SCHEMA-8 (2026-10-25, cutover dry run found two blockers in #205) - (1) workerd refuses a LIKE/GLOB pattern over 50 bytes when the statement runs, so the 67-byte hex GLOB in `product_option_values_swatch_hex_format` failed EVERY non-null `swatch_hex` insert on a real Durable Object while node:sqlite accepted it. Both hex-colour templates in `pg-raw.mjs` are now `length = 7 AND substr(c,1,1) = '#' AND substr(c,2) NOT GLOB '*[^0-9A-Fa-f]*'` (15-byte pattern, same accepted set); `generate.mjs` throws if ANY emitted or shipped SQL holds a LIKE/GLOB literal over 50 bytes (none else did), and `like-glob-limits.test.ts` repeats the scan and pins the swatch accept/refuse set. (2) `stores.storage_backend TEXT NOT NULL DEFAULT 'pg' CHECK (storage_backend IN ('pg','do'))` is added to the D1 `stores` table through `cf-additions.mjs` (it is not a Postgres column: the Postgres side keeps the same value in the flag table task 2.4 reads until cutover) for the backend selector and `flip-backend.mjs`. Counts, stated once: the generator emits 118 StoreDO tables (113 models + store_profile, store_config, commerce_outcomes, d1_outbox, do_flags) and 23 D1 tables (21 models + entity_index, platform_audit_log). The plan's 114 / 25 differ by exactly two known things: WhatsAppTemplate left the StoreDO with #223 (114 -> 113), and the four identity models counted in the plan's 25 live in ebda-identity (CF-SCHEMA-2; 25 -> 21), plus the two D1 infrastructure tables the plan did not count. 145 models total (was 146). Cost if wrong: a longer pattern reintroduced only fails on a real DO; the generator and test now fail first.

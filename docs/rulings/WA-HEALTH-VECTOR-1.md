Ruling WA-HEALTH-VECTOR-1 (Controller, 2026-10-27) - GET /health on the API adds `buyerKeyVector`: the first 16 lowercase hex chars of HMAC-SHA256(key = SUITE_BUYER_KEY_SECRET as UTF-8, message = "suite-buyer-key-probe:v1" as UTF-8). It lets Ebda Chat (and an operator) prove both Workers hold the same secret without the secret ever travelling; a mismatch is visible at once, instead of showing up as one customer with two buyer keys. The probe message is a constant, so the value is not derived from any phone, order or customer, and 64 bits of an HMAC output reveal nothing usable about the key. The field is OMITTED, never a placeholder, when the secret is unset. A test pins the value for a fixed key and asserts /health carries only status, timestamp, commit, deploymentId and buyerKeyVector, with no buyer key, E.164 or long digit run. Cost if wrong: 64 bits of a keyed HMAC of a public constant leak; rotating the secret changes the value and every buyer key.

Addendum (Controller, 2026-10-27; security review): `buyerKeyVector` is public, so for a WEAK secret it would be an offline guessing oracle (brute-force candidates against the 64 published bits). It stays public because the real secret is 256-bit random, but `buyerKeyVector()` returns null (the field is omitted) unless the secret is at least 64 characters (`MIN_PROBE_SECRET_LENGTH`). A short secret therefore never exposes the probe; the buyer keys themselves still accept a 32-char minimum (`suiteBuyerKeySecret`), so a 32-63 char secret works for keys but cannot be cross-checked through /health. The shared test vector is `tests/vectors/ebda-wa/buyer-key-probe.json` ({secret, message, vector}, sha256 in SHA256SUMS), which Ebda Chat vendors and runs too. Cost if wrong: a deployment with a 32-63 char secret has no /health cross-check and must compare out of band.

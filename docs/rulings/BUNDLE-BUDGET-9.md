# BUNDLE-BUDGET-9

> Section: API Worker budget failures on every PR off main (2026-11-09)

**Ruling BUNDLE-BUDGET-9 - the "Worker dry-run (api)" failures of 2026-11-09 were the gzip ceiling, not a startup-CPU regression; the fix sheds the 64 zod locales from `worker.js` (-272 KB raw, -42 KB gzip) and no ceiling moves.**

What failed. Every PR whose head included today's main (#469 808288d35, #476 59786e952, #483 5c4bbfe08, and 24f48683e) failed on `gzipped bundle size ... is over the budget of 2200000 B` (2,200,038 / 2,200,351 / 2,201,701 / 2,208,514 B). Their startup CPU (~365-405 ms) is NOT the failure: PRs run the RELATIVE CPU gate (base measured beside the PR in the same job), and base and PR were equal every time (367.4 vs 366.0 on #469). The passing runs on the older base read the same: #475 (4b64dff52, job 129088519275) 368.2 ms PR / 369.8 ms base, gzip 2,198,266 B; 20aa342b2 393.3 / 405.4 ms, 2,197,956 B. So ~370 ms is what GitHub's hosted `ubuntu-24.04` runner (2 vCPU) measures for this Worker; the 140 ms absolute ceiling was calibrated on a local machine, where the same bundles measure ~115 ms. The absolute ceiling is applied only on non-PR events, which skip this job today. No change to the CPU gate is needed: the relative mode already handles the slower runner.

Why gzip tipped. Today's six merges added ~1.5 KB gzip in total (bisected locally: 2a1a6d763 2,193,096 B -> 12d13f788 2,193,896 -> eb3153799 2,194,048 -> 2bd5f1243 2,194,337 -> d9db82f6c 2,194,629 -> 8b587c579 / 6cf43b65c 2,194,570 B; startup CPU main vs 2a1a6d763 interleaved: 164.8 vs 162.4 ms, equal). No single commit regressed; the headroom was already ~2 KB, so any PR adding a few hundred bytes of gzip failed.

The dead weight. The esbuild metafile showed `zod/v4/locales/*` at 260 KB raw in `worker.js` (64 files; only `en` is used). Cause: `apps/api/src/contracts/wa-v1.ts` does `import { z } from 'zod'`; zod 4's root re-exports `z` as a namespace that carries `locales` and `core` (which carries `locales` again), and esbuild cannot tree-shake members of a re-exported namespace (measured in isolation: `import { z } from 'zod'` -> 454 KB with 261 KB of locales; `import * as z from 'zod/v4'` -> 85 KB, none). `wa-v1.ts` is byte-pinned to the WhatsApp repo (`tests/unit/wa-contract-pin.test.ts`), so the import is not rewritten there.

Fix. `apps/api/wrangler.jsonc` aliases exactly `zod` (wrangler's alias matches the whole specifier; `zod/v3`, `zod/v4` are untouched) to `apps/api/src/cf/stubs/zod-root.ts`: named exports re-exported from the real `zod/v4` (same class instances, e.g. the MCP SDK's `ZodOptional`), and a `z` namespace equal to zod's minus `locales` and `core` (undefined; nothing in `apps/api/src` reads them). English error messages are unchanged (zod's classic schemas set the `en` map). Result: `worker.js` 8,081,116 -> 7,808,831 B raw, 2,189,277 -> 2,146,807 B gzip; startup CPU unchanged (12 interleaved runs, quiet tail: PR 114.0-121.0 ms, main 114.8-119.7 ms; min 114.0 vs 114.8 ms).

Guards. `scripts/ci/worker-startup-budget.mjs` now writes the dry-run's esbuild metafile and fails on any `BANNED_BUNDLE_INPUTS` (first entry: non-English zod locales), naming the cause on the PR that brings it back whatever imports it (mutation: alias removed -> "62 banned bundle input(s): zod non-English locales"). `tests/unit/ops/zod-root-alias.test.ts` pins the alias, the stub's equivalence to zod and the English messages.

Cost if wrong: if some future code in the Worker reads `z.locales` or `z.core` from the `zod` root it gets undefined at runtime (the unit test scans `apps/api/src` for exactly that); if zod or esbuild ever fixes the namespace shaking, the alias becomes a harmless no-op that should be removed with a Ruling.

# CF-FIX-1

Ruling CF-FIX-1 (2026-10-30, INFRA-CF-1 final fix-ups) - on a DO store, `orders.customer_id` is a platform `users.id` (the Postgres foreign key is `orders_customer_id_fkey -> users(id)`: migrated orders and every signed-in shopper's order carry it) OR a `customers.id` (an order a merchant opened for a CRM row, `createAdminOrder`), and a CRM row reaches its user only through `customers.user_id`, which equals `customers.id` just by chance. So `matchingCustomers` returns, for every matched CRM row, the row id AND its linked `user_id` (`userIds`; the order-list `customer_id IN` arm and the palette both read that list), the palette lists a linked CRM row under the user id Postgres lists (`key = user_id ?? id`) and resolves an order's customer name by either id. The DO migration seal and diff skip the derived FTS search tables (their `*_data` shadow table holds a BLOB the canonical form refuses, so `__seal` answered 500 on every store, and a DELETE on a shadow table corrupts the index); `cutover.test.ts` names the real `store_profile` table (it used the retired `stores`). Evidence: `packages/repo/test/do-search-customers.test.ts` (a migrated order whose `customer_id` is a `users.id`, a merchant-opened one, another store), `tests/integration/repo-factory-admin-search-contract.test.ts` (real Postgres 17 vs the DO schema: a migrated customer by name and phone, byte-equal bodies, red without the fix), `apps/api/workers-do/cutover.test.ts` (real workerd: import, seal, diff, unseal, verify). Closes the CF-R6A-1 residual. See CF-FIX-2 for the write side. Cost if wrong: a registered customer's orders missing from the order search or palette, or one extra user id in the match list; both are read-only and the order list keeps its `ORDER_SEARCH_TOO_BROAD` refusal.

Evidence: as `ebda_app` with 20,000 orders none of the nine trigram indexes (`orders.order_number`, the four guest shipping-contact JSON expressions, `users` first/last/email/phone) was scanned (idx_scan 0 for every one, red first in `order-customer-search-rls-index.test.ts`), because `ILIKE` and `->>` are not LEAKPROOF; the `users` policy additionally runs per-row subqueries. After: the order-number and four guest indexes are scanned as `ebda_app`; the customer lookup runs the definer's `users`/`orders` semijoin (the planner may probe the store's customers by key instead of scanning a users GIN, which is bounded by the store; evidence there is the exact result against a SQL oracle and the time). Admin list + typeahead mix at 20,000 orders, 8 parallel workers, as `ebda_app`: p95 141 → 52 ms (list) and 119 → 51 ms (customers), 75 → 209 requests/s. Each half still degrades on its own above `ORDER_SEARCH_CUSTOMER_ID_CAP` (the order-number half is new and does the same), nothing matching yields an explicit match-nothing arm, and the guest typeahead escapes LIKE metacharacters (it did not before). Terms under 3 characters keep the relation fallback (no normalising function is involved, so it is a cheap scan, ~20 ms at 20,000 orders). Not routed, by volume and caller: the super-admin platform user/customer lists in `admin.routes.ts` (platform users are a few hundred rows; the customer list reads store by store). Cost if wrong: a bug in the definer's caller check would let an `ebda_app` session list the order or customer ids of another store (ids only); the same GUC the RLS policy reads gates it, and `order-customer-search-rls-index.test.ts` plus the products definer test pin it.

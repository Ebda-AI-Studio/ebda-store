# SEARCH-T12-9

> Section: 2026-10-16 — Search program, PR 4 (P1c, hybrid ranking): SEARCH-T12-\*

Ruling SEARCH-T12-9 (Task 12 review I2; corrects SEARCH-T12-5's cache note) — the query-vector cache key is the EXACT embedded text: `queryEmbedText(raw)` = the Arabic-normalised query cut to `QUERY_EMBED_MAX_CHARS` (100), and that same text is what is sent to Workers AI. Before, the key was the whole normalised query while the provider got the raw first 100 characters, so two spellings that fold alike shared whichever vector came first, and a query arriving through MCP (`z.string().min(1)` under a 10 MB JSON body limit) kept a key of up to ~20 MB per entry (500 entries → past the 128 MB isolate limit). Now: (1) folding-equal queries share a vector by design (the model sees the folded text, as the keyword leg does); (2) MCP `search_products` `query` is `.max(100)`, the same cap as `/public/products` `search` (route slice) and the typeahead `q` (route slice), so no edge passes more; (3) staleness class is BOUNDED-stale by model version, 10 minutes: nothing a merchant writes changes a query vector, but the provider's model behind the same id can, and the TTL bounds that; a model-id change changes the key. `data-map.md`'s "at most 100 characters" is now true of the key too. Evidence: `hybrid-search.test.ts` "caches the query vector per store and normalised query" (the provider receives the folded text) and "a 10 000-character query embeds (and caches) only its first 100 normalised characters" (red before: 2 calls, raw text); `tests/unit/mcp-search-products-query-cap.test.ts` (100 accepted, 101 refused; red before). Cost if wrong: if bge-m3 ranks the folded spelling (ا for أ, ه for ة) worse than the raw one, query vectors lose a little precision; Task 13's eval measures it.

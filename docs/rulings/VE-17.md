# VE-17

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling VE-17 (Task 12, 2026-10-22) - classic-only theme toggles ported into the theme pane before retirement. The parity gate was green with zero `classic-only` rows, but it tracked only `updateSection` layout writes, `siteSettings` keys and API paths; the classic page also staged five theme booleans through `setPendingThemeUpdates` to `PUT /theme` (`showBrandBadge`, `showNewBadge`, `showQuickAdd`, `normalizeProductImages`, `saleBadgeLegacyCorner`), and `grep` found no editor control and no other admin UI for any of them (only type declarations). They are now checkboxes in a `cards` group of `THEME_SETTINGS_SCHEMA` (so the draft whitelist, publish merge and rollback snapshot carry them), strict booleans at `PUT /theme` (`THEME_BOOLEAN_KEYS`), searchable (`builder.card-*`), excluded from Smart Palette. Design reset: none is look-owned (`lookTheme` never sets them), so a look switch with keep or reset leaves them; no `shownFor` because the shared and per-skin cards read them. The parity manifest now records `pendingThemeUpdates` keys (`theme-key` entries from `classic-facts.json`) and parity item 6 fails if a form-staged theme key lacks an editor setting. ThemeTab's ceiling of 7 belongs to the classic branding ThemeTab and is unaffected. Evidence: `tests/unit/theme-card-switches.test.ts`, `visual-editor-parity.test.ts` item 6, `new-badge-setting.test.ts`. Cost if wrong: a merchant who relied on a switch finds it in the editor's Theme pane (Product cards) instead of the old Page Builder card, and `saleBadgeLegacyCorner` stays visible on templates whose card ignores it.

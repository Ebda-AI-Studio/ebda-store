# CF-R6A-4

Ruling CF-R6A-4 (2026-10-30, INFRA-CF-1 PR R6a) - `instapay_order_receipts` is copied at cutover, with count and checksum, so a store with orders awaiting payment confirmation can be flipped: `PG_SOURCED_DO_TABLES` (cf-migrate coverage) maps the DO runtime table to the `kind = 'order'` rows of the platform `instapay_receipts` (same column names; `kind`, `claim_id`, `updated_at` deliberately not carried, and any other column the Postgres table gains stops the run), `migrate-store-to-do.mjs` exports and imports it after the plan tables, `verify-store.mjs` digests both sides (rows plus the semantic sums of its dates and flags) in the same `__verify` call, and the harness StoreDO creates the table like the real one (`ensureMoneyOpsSchema` already does). Residuals, stated: a receipt submitted on the DO AFTER the flip is not replayed to Postgres by a rollback (the platform table keeps the imported rows); the D1 `instapay_ref` claim of a receipt submitted on Postgres before CF-R6A-4 was deployed is still not seeded (INSTAPAY-DO-1 residual). Evidence: `packages/cf-migrate/test/pg-sourced.test.ts` (columns equal the DO DDL, every Prisma column carried or ignored, the source query is store-scoped and order-only, import then replay then verify with equal count and digest), `scripts/cf/rehearse-cutover.sh`. Cost if wrong: an order awaiting confirmation loses its receipt at the flip and the payer must upload it again.

The id is classified for pseudonymisation on offboarding (OFFBOARD-1). Staleness class of page content after publish is NEVER-stale: event invalidation on every publish path clearing every layer `bustStoreCaches` owns, the purge retried 3 times and error-logged if it still fails; the 60 s storefront revalidate is a backstop, not the mechanism. Measured residual (2026-10-27, local `next start`, one instance, phone 390 px and desktop 1440 px, fresh browser context per read): after publish #1, publish #2 and a restore the served HTML carried the new content within 1.5-1.8 s, and the first read right after the toast was still the old page for phone in two of three cases, because the purge is deferred until the response is released and then travels to the storefront. Cost if wrong: a purge that fails all three attempts leaves a page stale for at most the 60 s backstop and raises an error log; a visitor can see the previous page for ~2 s after Publish.

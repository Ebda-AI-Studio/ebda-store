# CF-FIX-2

Ruling CF-FIX-2 (2026-10-30, INFRA-CF-1 final fix-ups, Opus review C4) - on a DO store the `customerId` of a checkout, a wallet entry (refund/return credit, cancel) and an admin order is the shopper's PLATFORM `users.id`, never a CRM `customers.id`: the identity lives on the platform (the Worker authenticated or validated it, `createAdminOrder` checks the user against the store before the call) and the DO has no users table, so the three lookups `SELECT id FROM customers WHERE id = ?` (`checkout.ts`, `refund.ts` `applyWalletEntry`, `admin-order.ts`) are removed: a wallet and an order are keyed by the users.id and need no CRM row (the Postgres twin checks `users`). The CRM row is only the GROUP link, reached through `customers.user_id`: a checkout without an explicit buyer is a `session` buyer, an admin order a `merchant-selected` buyer with `shopperUserId` (the DO `Buyer` now carries the field the Worker already sends), and the first-order count of a session buyer counts `orders.customer_id = users.id` directly. Evidence: every DO fixture now seeds the CRM row with its OWN id (`crm-<user>`, `user_id = <user>`) so the old lookup fails them (`do-refund`, `do-returns`, `do-order-ops`, `money-stock`, `do-payment-ops`, `do-promotions`, the wallet/returns/orders workerd suites, the wallet, returns and orders Postgres-vs-DO contracts), plus `workers-do/returns.test.ts` (a return credit with NO CRM row) and `money-stock.test.ts` (a checkout for a user with no CRM row). Cost if wrong: a wallet or order for an id the platform never issued, which the Worker has already refused before the DO is reached.

# CF-WRITES-2

Ruling CF-WRITES-2 (2026-10-29, INFRA-CF-1 PR D1b) - collections and the settings copy: (1) there is NO `Collection` model in the schema; the storefront's "collection" surfaces are `Category` (+ `ProductCategory`) and the `StorePageRevision` page-builder document with `pageKey` collection, both StoreDO models (model split table, plan s1), so they live in the store's Durable Object and need nothing new; both are on `storeWriter` as of D1/D1b. (2) `Store` stays split as plan s1 / Task 1.4 / `store-split.mjs` already decide: the D1 (Postgres until cutover) `Store` row is AUTHORITATIVE for the directory (domain verification, email domain, billing suspension, deletedAt) AND for the mirror columns (id, name, slug, domain, pixels, llmsTxt, aboutJson); the StoreDO carries the READ copy the storefront uses, `store_profile` (branding, content, SEO, theme, mirror) and `store_config` (commerce, flags, integrations, AI and accounting switches). Direction of the write-through: every admin settings write enters through the API, so it writes the authoritative `Store` row FIRST and then the changed fields to the DO (`StoreDO.applySettings`, fields as Prisma names, mapped to columns by the generated model metadata, `store_profile` UPDATE-only and `store_config` upsert, D1-only fields reported not stored, unknown fields refused, another store refused). Implemented once in `updateStoreThrough` (store.service.ts), which replaces `withStore(... tx.store.update ...)` at the 12 settings writers and captures the patch from the update call itself; on Postgres `copyStoreSettings` is a no-op, so behaviour is unchanged. The plan's DO-to-D1 outbox (`d1_outbox`, retried by alarm) is NOT used for admin settings: it is only needed if the DO becomes authoritative for a mirror column, which no admin path does. Staleness class of the copy: NEVER-stale (theme, currency and flags decide what the storefront renders and what checkout charges); invalidation is the synchronous write-through in the same request on EVERY settings write path that goes through `StoreService`; there is no cache layer (the DO is read directly), so the residual window is the gap between the two writes inside one request, and a failed copy fails the request with 502 `SETTINGS_COPY_FAILED` (the update is idempotent, the retry converges). Residual, listed in the doc: 38 `store.update`/`updateMany`/`upsert` sites outside `StoreService` (measured: agent credential, typography, store-layout, tax-profile, admin, AI jobs' store-level SEO) and 2 inside it written as `async tx => ...` still write only the authoritative row; each must route through `updateStoreThrough` before a store may be flipped, which is a cutover gate item (a CI grep for `store.update(` outside the helper must reach 0). (3) D1b mechanics: the writer gets named in-DO procedures (`$proc`, allow-listed in `DO_PROCS`, typed args, never SQL text) for the one write Prisma cannot express, the `ai_field_sources` jsonb delta merge (`mergeAiFieldSources` = SQLite `json_patch` + `json_remove` in the batch transaction, the twin of the raw `UPDATE ... jsonb ||` that stays the Postgres path); `ProductService.update` has two paths that share one hoisted `updateArgs` (Postgres: the unchanged interactive transaction; DO: one atomic batch with the saved category positions read first). A product or variant carrying a non-zero `inventory` is refused on the DO (create no longer sends the zero default), so opening stock and every stock edit stay D2; the D1 `store` relation of `ProductService.getById` is fetched separately on the DO and attached. Moved: product create/update/soft delete/bulk update (status, flags, category link, price) and bulk delete/status, variant options, option values, create/update/delete/generate/reorder and option delete, page-builder revisions, price tiers, product relations (replace-all now atomic), product FAQ, the AI writers' product/category/image/tag/FAQ/category-link writes, store-category suggestions (one batch with generated ids). Evidence: `tests/integration/repo-factory-writes-d1b-contract.test.ts` (12 scenarios, each run on Postgres and on the DO schema with equal traces, mutation-checked), `packages/repo/test/rpc-writes.test.ts` (+3 procedure tests), `apps/api/workers-do/mutate.test.ts` (+2 on real workerd: `json_patch` and `applySettings`); the guards `nested-transaction-registry` and `reindex-write-paths` and `store-reads-are-scoped` fired on the move and were updated with reasons. Not moved (D2 or later, with reason): bulk CSV import transactions (write `inventory` per row), `bulkUpdateInventory`, variant `inventoryHistory` rows, barcode sequences (advisory lock), provisioning seeds (the store does not exist in a DO yet), `ai-autofill-cleanup` (mixes D2 models in one transaction), job READS (PR E). Cost if wrong: with every flag at `pg` the moved methods run the same Prisma calls as before (one deliberate exception: variant option delete, option reorder, relation replace-all and store-category suggestions are now one `$transaction([...])` batch on both backends, the same atomicity with fewer round trips); a wrong `do` write is reachable only for a store the operator flipped, one D1 UPDATE back; the unrouted `prisma.store.update` sites are the real risk and are a hard cutover gate.

# B2B-20

> Section: B2B wholesale pricing (feat/b2b-wholesale, 2026-10-21)

Ruling B2B-20 (controller, 2026-10-21; the open question the final-review fix wave left; amends B2B-14) - When an early partial return hits the zero-refund floor, the part of the tier adjustment it could not collect is CARRIED FORWARD on the order, per product (the scope the adjustment is computed on, B2B-17), in `return_items.tier_carry` (migration `20261028000700`; a signed delta on the product's first item of each completed return: + carried, - consumed or waived; the sum over completed returns is the outstanding carry). The product's later refunds on the same order (later partial returns and the final-return release alike) add the carry to their raw adjustment FIRST, before the floor and the release clamp: a charge collects it from that return's refund, never below 0 per refund (what still does not fit is carried again); a release cancels it before handing anything back. It is consumed exactly once: without overrides `retained + carry == clawback(kept now)` after every return, and the B2B-14 release clamp (never release more than was retained) still holds. A merchant override (`orders:refund`, B2B-15) on any item of the product replaces the computed refund, carry included: the carry is WAIVED (persisted as consumed, never re-claimed) and the waived amount is audit-logged with the override (`tierCarryWaived`). The provider refund, store credit and the GL all read the one adjustment that includes the carry (`allocatePartialReturn` `thisAdjustment` / the persisted `tier_adjustment`), and the shopper's estimate at creation runs the same computation. Scoped to the PRODUCT, not the whole order: collecting product A's carry from product B's refund would let A's final release hand the same money back. Evidence: buy 100 @ 80 (tier 100+, list 100), return 10 (refund 0, 1000 carried) then 80 -> 7000 (was 7200: the merchant lost 200, now 0); three steps 10 / 5 / 75 -> 0 / 0 / 7000; GL cash credits == refunds == 8800 (`packages/shared/src/__tests__/return-adjustment.test.ts`, `tests/integration/b2b-return-adjustment.test.ts`, `tests/integration/accounting/accounting-partial-return.test.ts`). The integration test that pinned 7200 as intended was rewritten. Cost if wrong: a merchant who preferred the old behaviour (an early floor forgiven forever) sees a later refund of the same product reduced by up to the forgiven amount; the per-item override refunds it, audited.

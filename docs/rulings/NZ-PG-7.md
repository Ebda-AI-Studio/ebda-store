# NZ-PG-7

> Section: NEON-ZERO Postgres remnants (2026-11-05)

**Ruling NZ-PG-7 - the three Postgres callers a dead-Postgres cron/route sweep still found are ported to the store's DO.** (1) Loyalty point expiry: `loyaltyExpire` (`packages/repo/src/do/loyalty.ts expirePoints`) deducts the lapsed earn points per member (floored at the balance), writes one `expire` row and clears `expires_at` in one section, a page of 500 earn rows at a time with an id cursor (a member with no balance row is skipped like Postgres). (2) The birthday bonus: `loyaltyBirthdays` awards `birthdayBonus` to members whose date of birth in the store's customer directory is today and who have no `earn_birthday` row this year, one section, no tier recalculation (as in Postgres). (3) Search-insights index line: `vectorStatus` counts indexable / ready / stale / failed from `product_vector_state` (same staleness rules as `planVectorWork`); the route no longer opens a Postgres scope or savepoint for a DO store (that was the `$transaction` first hit). Siblings checked: `product-index.service` functions are job-only and already behind the `onDo` branch of `search-product-index`; `loyalty.service` already uses the DO ops. One store failing no longer stops the expiry sweep over the others. Evidence: `packages/repo/test/do-loyalty-admin.test.ts`, `do-job-ops-b.test.ts`, `tests/unit/loyalty-automation-do.test.ts`. Cost if wrong: a member's expiry or birthday bonus is booked on the DO ledger with a wrong amount, fixed by an `adjust` row (the earn rows keep their history).

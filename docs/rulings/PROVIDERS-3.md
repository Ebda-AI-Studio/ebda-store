# PROVIDERS-3

> Section: 2026-10-07 — Provider catalog, Batch 0 + payments Batch 1 (PROVIDERS-\*)

Ruling PROVIDERS-3 — enabling a gateway requires a passing Test connection of EXACTLY the credentials stored for the active mode: `connection_test.fingerprint` is a keyed HMAC (`encryption.hash`, ENCRYPTION_KEY-derived) of provider + mode + fields, compared at enable time after decrypting; any edit of the active mode, or a mode switch (also through the generic PUT), invalidates it, and an edit of an ENABLED gateway's active keys disables it. Read paths compare against a fingerprint stored in `credential_hints` at save time, so GETs never decrypt (#2010). Evidence: unit cases "edited secret / switched to live / forged fingerprint / no credentials"; integration "rotating the active secret disables the gateway", "switching an enabled gateway to the other mode is refused". Cost if wrong: a merchant who rotates a key must press Test connection again before payments resume.

Ruling PROVIDERS-3 (Ahmad 2026-10-24; implemented 2026-10-25, branch feat/providers-unverified-connect) - there are NO provider test accounts: the first merchant's own credentials are the verification, and the marketing site keeps all providers listed (no "coming soon"). Product: (1) every catalog provider connects and enables whatever its `verified` flag (supersedes PROVIDERS-2 as a gate and makes PROVIDERS-ACTIVATION dormant: the request/activate workflow and its tests stay in the code but nothing requires them; `PAYMENT_PROVIDERS_ALLOW_UNVERIFIED` is no longer read); (2) saving credentials runs a SANDBOX-FIRST automatic check of the SAVED mode (the adapter's one read-only/auth call, never a charge or shipment) and returns `check = {status: connected|credentials_wrong|unreachable|unrecognized|unverified, messageEn, messageAr}` from `describeConnectionCheck` (`@ebda/shared`, never echoes a provider message); the enable gate is unchanged (a passing test of exactly the stored credentials), and a provider with no safe check call stores `no_check` (usable, warned, unverified); (3) the first real use of an unverified provider by a store, and every failure while it is unverified, raises a P1 store-scope alert (store, provider, op, outcome/error code); an unrecognised check answer also pages; (4) when `PROVIDER_AUTO_VERIFY_AFTER` (default 3) DISTINCT stores have each settled a LIVE operation (payment paid-confirmed, shipment booked; sandbox and invoice-only operations never count) `provider_verifications.ready_at` is set and an info alert is sent; ONLY a super admin confirm (`POST /admin/provider-verification/:provider/confirm`, audited) sets `verified_at`, and until then the first-use and failure P1s keep firing; evidence is the append-only `provider_verification_events` (store, mode, op, counted, outcome, reference, error code; no credential or body) on /provider-activation (`GET /admin/provider-verification`); bookkeeping runs through `deferAfterTenantCommit`, never on a request transaction; (5) docs and the help articles (payment-providers, shipping-providers, shipping, create-your-store, ar+en) updated. Ruling PROVIDERS-3b (controller review) - only LIVE, SETTLED operations count (paid confirmation through the central confirm path; webhook-driven paid paths outside it are not counted yet; a booked shipment), from >=3 distinct stores, and a human confirms. Cost if wrong: a provider whose refund or webhook variant is still broken can be confirmed on happy-path evidence, which silences its alerts; and until the webhook paid path is wired into the evidence, payments reach ready more slowly. Ruling PROVIDERS-3c - the runtime offer needs only catalog membership; the enable gate plus "a credential edit disables the row" is the single guard. Cost if wrong: an enabled row that bypassed the settings routes is offered without a passing test (none exist pre-launch). Evidence: `tests/unit/provider-verification.test.ts`, `packages/shared/src/providers/connection-check.test.ts`, `tests/unit/provider-connect.test.ts`; integration (CI only, needs Postgres): `tests/integration/provider-connect-routes.test.ts`, `shipping-carrier-connect-routes.test.ts`, `shipping-sp7.test.ts`; provider activation moved to `tests/unit/provider-activation-routes-d1-do.test.ts`.

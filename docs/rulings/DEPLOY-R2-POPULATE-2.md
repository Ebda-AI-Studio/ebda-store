# DEPLOY-R2-POPULATE-2

Ruling DEPLOY-R2-POPULATE-2 - the storefront deploy populates the R2 incremental cache with `scripts/ci/populate-r2-cache.mjs` (`wrangler r2 object put --remote`, the Cloudflare REST API), then runs `OPEN_NEXT_DEPLOY=true npx wrangler deploy`; it no longer calls `opennextjs-cloudflare deploy`. Supersedes DEPLOY-R2-POPULATE-1.

**Evidence:** since `EBDA_RUNS_ON` moved to Umbra (2026-11-02 18:08Z) every storefront deploy failed (runs 41654873558, 41735165065 x2). OpenNext 1.20.9 populates R2 by starting a local worker with `unstable_startWorker({ dev: { remote: true } })` and POSTing entries to it; on the VM all 3 (tiny) entries time out from attempt 1, so the remote-proxy tunnel itself never answers (plain HTTPS to api.cloudflare.com works, clock synced, no IPv6). `--cacheChunkSize 4` (POPULATE-1) cannot help: concurrency is irrelevant when nothing answers. `--rclone` needs the unmaintained `rclone.js` (last release 2022, postinstall binary download), rejected by the dependency rule. The script loads OpenNext's own `getCacheAssets`, `computeCacheKey`, the R2 binding and prefix env by file URL from the pinned package, so assets and keys are identical to OpenNext's; each entry is retried (4 attempts, 2 at a time) and a final failure names the key. The config enables neither skew protection nor a D1 tag cache (tag cache is the sharded Durable Object, which has nothing to populate), so OpenNext's deploy added no other `--var` or step. DEPLOY-TIMEOUT-1 and the verify/rollback step are unchanged.

**Cost if wrong:** an OpenNext upgrade that moves its CLI modules or key format fails the deploy step loudly (import error) or writes keys the Worker does not read (cold ISR cache until fixed), so the script's imports are re-checked on every `@opennextjs/cloudflare` bump.

# NZ-PG-4

> Section: NEON-ZERO Postgres remnants (2026-11-05)

**Ruling NZ-PG-4 - there is no RLS and no tenant guard on D1 for the `access`, `platform` (merchant API keys, store features, legal acceptances, slug redirects, provider activation), `payments` (InstaPay receipts, manual-payment claims) and `ops` (usage snapshots, OneSignal devices) families; isolation is the `storeId` / owner / user filter in the query, exactly as NZ-10-4 ruled for `billing`.** `tests/unit/d1-tenant-filter-guard.test.ts` scans `apps/api/src`: every SQL literal on a tenant table must name store_id / owner_id / user_id (or the account keys sent_by / invited_by / accepted_by / email), and every model call on a tenant model must name `storeId` / `ownerId` / `userId` / `claimId` or sit in the exemption list with its reason (a stale exemption fails the test, and the scan fails when it stops finding statements). Platform-wide tables have no tenant column by design and are not scanned: `legal_notice_sends`, `legal_notice_deliveries`, `provider_verifications`, `provider_verification_events`, `ci_insights`, `answer_engine_provider_configs`, `system_settings`; they are reachable only from super_admin routes and crons. Cost if wrong: a new query that forgets its store filter fails CI instead of reading across stores; a filter that names the tenant but is built wrongly is not caught by a static scan, which is why the route tests keep asserting the filter.

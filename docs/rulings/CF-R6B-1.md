# CF-R6B-1

Ruling CF-R6B-1 (2026-10-30, INFRA-CF-1 R6b, Ahmad via the controller) - ONE source of truth for "this store is on the Durable Object", and every direct Postgres reader of a DO-writable model is routed, annotated or listed dead. (1) FLAG: the D1 column `stores.storage_backend` is read live by EVERY consumer: `backendFor` (per store) and the new `doStoreIdList` / `doStoreIdSet` (every DO store) in `lib/store-backend.ts`. The jobs guard (`doStoreIds`, now async), alarm arming and the alarm dispatch, the DO webhook resolver (`resolveDoStoreFromWebhookRef`) and its unresolved-webhook 503 lane, the nightly backup sweep, the InstaPay retention sweep, the search index job and the Phase 0 spike gate use them; `STORE_DO_ENABLED_IDS` is read in ONE place (the selector's local / test fallback where D1 is unbound; production with a listed store and no D1 is a 503) and is no longer defined in `wrangler.jsonc`. A store flipped only in D1 is therefore seen by all of them, and the flip (runbook 8.3) writes D1 only. Guard: `tests/unit/backend-flag-single-source.test.ts` fails on any production read of the variable outside the selector. Closes Opus C3 and M3. (2) READERS: the baselined direct readers (250 at #355, 206 after #363) of DO-writable models were reviewed one by one: 133 routed through `storeDb` (catalogue, categories, tags, carts, abandoned carts, consent, shipments, dead-stock flags, reviews, counts on the admin / provisioning pages; the product low-stock threshold write now follows the read through `storeWriter`), 5 already routed through a `tx` that IS the repo client (marked `repo-tx`), 2 dead (`InventoryService.reduceOnSale`, `returnToStock`: no caller, listed in the baseline `dead` section and verified by the test), and the rest annotated in `tests/unit/fixtures/do-writable-direct-readers.json` with a kind and a reason the test checks: `pg-branch` (the file has the storeMoney / storeStock / storeRepo early return that serves a DO store), `pg-only-flow` (named in `docs/cf/not-on-do.json` `postgresOnly`, so the flip gate STAYS CLOSED: accounting flows, barcode scan stock flows, the product bulk-update inventory field) and `platform` (super_admin cross-store product list, the pre-cutover Postgres half of account erasure). Storefront reads on a DO store cannot join the D1 `store` or a reviewer's `customer` (a User): `readPublicDetail`, `listingFor` and the shipment detail route drop them from the DO select and put them back from their own source, so the row has the same shape on either backend. The COD report resolves "has a remittance" from Postgres for a DO store (CodRemittance is not a DO-written model). The scan test now compares the baseline EXACTLY (a stale entry fails too). Evidence: `tests/integration/repo-factory-r6b-contract.test.ts` (5 scenarios, Postgres 17 vs the DO schema: product by slug incl. hidden / archived / wholesale, filter options, listing with the store ref, COD report, a threshold written on the DO and honoured on read), `tests/unit/backend-flag-single-source.test.ts` (8), `tests/unit/do-writable-direct-readers.test.ts`, `tests/unit/webhook-do-resolver.test.ts` (D1-only flip resolves; env-only is not routed once D1 is bound). RESIDUALS, found and not hidden: accounting purchase orders / stock adjustments / opening balance, barcode scan-to-adjust, the bulk-update inventory field and `CodRemittance.shipmentId` (a Postgres FK to `shipments`, so importing a settlement line that matches a DO store's shipment cannot reference it) still write Postgres for a DO store; the first three are in `postgresOnly`, the fourth must be fixed or listed before a flip. Cost if wrong: with every flag at `pg` nothing here changes behaviour (storeDb IS prisma); for a flipped store a wrong route is one D1 UPDATE back, and the gate refuses the flip while `postgresOnly` is non-empty.

# GUEST-RET-1

Ruling GUEST-RET-1 (2026-11-11, audit S2-7, ebda-foundation criterion 19, ebda-foundation PR #24) - a guest shopper can request a return with `POST /public/returns/guest`. Identity is the order number plus a second factor already on the order: the phone (compared after `normalizePhoneForStorage`, so `01001234567` equals `+201001234567`) or the email (trimmed, lower-cased); a factor that is given must match and at least one must be given. Only a guest order (`orders.customer_id` null) qualifies: a signed-in customer's order answers like a missing one and the shopper signs in. Every identity miss (no such order, a customer's order, wrong phone, wrong email, no factor) is ONE response, `404 GUEST_RETURN_NOT_FOUND` with one fixed message, echoing no phone, email, address or name; the compare is a SHA-256 plus `timingSafeEqual` and runs whether or not the order exists. The route is rate-limited per IP (10 per 15 min) and per (store, order number) (5 per 15 min), both keyed on a hash, fail-open on a store error like the other limiters, both answering the same `429 RATE_LIMITED` body. Once identity holds, the row is made by `ReturnService.create` (Postgres) or `returnCreate` (StoreDO) unchanged: delivered-only, the merchant's return window, the over-claim check. With no lines named the request is the whole order (a guest cannot see line ids). A request moves no money: the refund method is chosen by the merchant at completion, and a guest return cannot be completed to store credit (`GUEST_RETURN_NO_WALLET`, no wallet to credit). `returns.customer_id` is nullable everywhere (Postgres migration `20261111100000_guest_return_customer_nullable`; StoreDO migration `cf-0006_returns_customer_nullable`, which renames the column aside, adds the nullable one, copies with `''` turned into NULL and drops the old one, so no parent row is dropped and no ON DELETE action of `return_items` or `wallet_transactions` fires). A guest return stores NULL on both backends; nothing writes `''`. Status mails of a guest return go to the email on the order. Evidence: `tests/unit/guest-return-request.test.ts`, `apps/api/src/middleware/__tests__/guest-return-limiter.test.ts`, `packages/repo/test/do-returns.test.ts` (guest block), `apps/api/workers-do/returns.test.ts` (real workerd: a real guest return row, and a DO at the old schema upgraded with its `''` rows turned NULL and its children intact). Cost if wrong: a shopper who mistypes one field cannot tell which one was wrong (deliberate), and a guest who knows an order number and its phone can file a return request for it (the merchant still approves, and no money moves until the merchant completes it).

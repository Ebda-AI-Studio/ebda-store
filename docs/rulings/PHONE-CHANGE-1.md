# PHONE-CHANGE-1

> Section: 2026-11-02 - QA sweep batch 1 (branch `fix/qa-sweep-batch-1`)

Ruling PHONE-CHANGE-1 - the account phone is changeable: `POST /phone` on the identity service (accounts.ebda.app) and a Phone panel on Admin > Account > Security. Because the phone is the WhatsApp password-reset destination (ID-WA-OTP-1), changing it is a recovery-channel change, so it takes the same step-up as `/mfa/disable`: the current password, plus a TOTP code when the account has a second factor, under a per-account throttle (5 per 15 minutes) and the existing password-guess throttle. The number is normalised (separators stripped, `+` kept) and `/me` now returns `phone`. INTERIM: the new number is NOT proven by a code sent to it, because the WhatsApp channel is flag-off and the OTP table's CHECK constraint has no phone type; the re-authentication is the proof. When the channel is on, send a code to the new number and confirm before writing. Evidence: `apps/accounts/test/phone-change.test.ts` (change with password, normalisation, wrong password refused and unchanged, malformed refused, unauthenticated 401, throttled). Cost if wrong: a stolen access token plus the password could redirect reset codes to an attacker's number (the same exposure as /mfa/disable); an email confirmation to the OLD address would close it and needs a new mail kind.

Ruling RECEIVER-CHECK-1 (Ahmad, option a; closes the open High of M003-2) - the wrong-account check is back, without reading people. (a) `runExtraction` loads the receipt's EXPECTED receivers (an order receipt: the InstaPay handle and mobile frozen on its payment; a subscription receipt: Ebda's `EBDA_INSTAPAY_HANDLE`), normalises them (lower-case address, last 10 digits of a mobile, Western digits) and gives them to Workers AI inside the prompt. The model is asked ONE extra question, `receiverMatches`, answered `true` / `false` / `null` only, and told never to return the receiver; the schema carries the key only when there is something to compare against. Only a strict boolean is kept (`extracted.receiverMatch`); any text the model volunteers is dropped, nothing about the receiver is stored or logged, and a model yes / no with no expected receiver is discarded. (b) `computeReceiptFlags`: `false` -> RECEIVER_MISMATCH for the merchant approver whatever the payer typed (ar / en copy already exists); `true` -> verified on the image, so a payer who left the receiver blank is no longer RECEIVER_MISSING; `null` / AI failed -> the payer-typed comparison exactly as before (RECEIVER_MISSING / RECEIVER_MISMATCH from what was typed) plus AI_UNAVAILABLE. (c) No expected receiver configured -> no AI receiver flag and a `[P2]` warn log (no receiver text); the read still completes. (d) A model error is `failed` = the manual review that exists today; nothing auto-approves anywhere (flags never block, approval stays a human act). (e) Data map and the in-product notice (en / ar, Western digits kept) now say "amount, reference and time, plus a yes or no on whether it went to the store's InstaPay account"; DOC-2's legal text must say the same. Evidence: tests/unit/instapay-receipt-reader-workers-ai.test.ts (prompt content, match, mismatch, missing expected, text-not-boolean, error), tests/unit/instapay-receipt.test.ts (flags), tests/unit/instapay-receipt-extraction-receiver.test.ts (wiring, P2 log, no receiver text stored, error -> failed); red first, then three mutations each fail a test. NOT VERIFIED: the real model's yes / no accuracy on genuine receipts (Arabic masked mobiles especially); queue: run the 5 staging receipts with a deliberately WRONG expected account too. Cost if wrong: a wrong "false" shows the approver a RECEIVER_MISMATCH flag on a good payment (they look at the screenshot); a wrong "true" is today's situation (the approver checks by eye).

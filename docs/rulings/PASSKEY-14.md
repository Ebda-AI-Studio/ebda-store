# PASSKEY-14

> Section: 2026-10-15 — Phase B1 Qamar (B1-\*)

Ruling PASSKEY-14 (review M4) — admin-namespace identities (store_admin, staff, super_admin) are served account endpoints only to PLATFORM origins (`rejectAdminOnMerchantOrigin`, mounted after `authenticate` on the authenticated `/auth/*`, `/auth/mfa/*` and `/auth/passkeys/*` routes); only `customer` tokens ride storefront origins. PRE-EXISTING FINDING: `/auth/me` (name, email, role, MFA state), `/auth/me/export` and the other `/auth` account endpoints answered an admin's cookie to any CORS-allowed merchant domain (`credentials: true`, `SameSite=None`; `restrictPlatformOnlyOrigins` is a path list that never covered `/auth/*`), so a merchant-controlled page could read them for a lured admin. The passkey endpoints are additionally bound to the account's own surface (`assertPasskeyOrigin`: admin namespace <-> admin app, a shopper <-> their own store host). Evidence: `tests/unit/admin-credentials-merchant-origin.test.ts` (behaviour per role and origin; the guard is mounted after `authenticate` on 16 routes) and the origin-binding cases in `passkey.routes.test.ts`. Cost if wrong: an admin session used from a non-platform origin (e.g. a workers.dev preview without `CF_WORKERS_DEV_SUBDOMAIN`) gets 403 on `/auth` endpoints.

Ruling WA-OTP-SENDER-1 (2026-10-29) - sign-in codes for platform accounts go ONLY through a platform-controlled sender, the Ebda AI Studio platform number, never through a store's number. The security review found that the accounts caller sent the owner's reset code through each owned store's WhatsApp number (`WhatsAppOtp.sendOtp(storeId, ...)`): that message is a row in the store's inbox history, so any staff member of the store could read the owner's code (an account-takeover path). Now: `apps/accounts/src/whatsapp-otp.ts` calls `WHATSAPP_OTP.sendCode(phone, code)` (ebda-wa `PlatformOtp`, no store id); the per-owned-store loop and every `STORE_DIRECTORY` use in that file are removed, and `test/whatsapp-otp.test.ts` fails if the caller mentions a store again or consults the directory. The channel is OFF: `WHATSAPP_OTP_ENABLED` is "false" in `apps/accounts/wrangler.jsonc` and only "true" switches it on, because the platform number does not exist yet (a Meta, third-party step); until then codes go by email only. The WhatsApp side is ebda-whatsapp Ruling WA-OTP-SENDER-1 (`PlatformOtp` touches no workspace; its test proves the code and phone are in no store table, no platform D1 table and no log). Sweep of the class in this repo: the only auth code or link that reached a WhatsApp number was this caller; `apps/api` and `apps/web` have no caller of `WhatsAppOtp.sendOtp` and no magic-link sender (grep of `sendOtp|WhatsAppOtp|WHATSAPP_OTP|otpViaWhatsApp|magic`), and the Store-link customer OTP (`WhatsAppOtp`, a store's own customers from that store's number, code masked in the inbox) is a different surface that must never be used for accounts. Cost if wrong: while the flag is off an owner who prefers WhatsApp gets email only; switching it on before the platform number is configured on the ebda-wa side is harmless (`PlatformOtp` answers `disabled`, the email still goes).

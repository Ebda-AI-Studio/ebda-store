# WALLET-GL-1

> Section: 2026-10-29 — wallet in the general ledger (branch `feat/wallet-gl-1`)

**Ruling WALLET-GL-1 — every store-credit movement is journaled on 2150 "Customer Wallet Liability", and wallet checkout works with accounting on. AMENDS W-3 (the refusal is removed) and closes the residuals of OMD-5 and OMD-6.** Ahmad decided 2026-10-29 where each movement lands in the P&L:

- goodwill / admin credit issued (`admin_adjust` +, generic `credit`): DR **5950 Customer Goodwill** (new expense account), CR 2150;
- reversal of a credit (`admin_adjust` -, generic `debit`): the mirror, DR 2150, CR 5950;
- redemption at checkout: the wallet part of an order is a tender like the others in `postOrderPaymentJournal`: DR 2150 for `walletAmount`, DR cash for `total - walletAmount` (the cash part is journaled exactly as before; no zero-value cash line for a wallet-only order), CR revenue/tax/shipping for the whole order;
- forfeit, expiry or erasure write-off (`expire`): DR 2150, CR **4100 Unused Store Credit** (new revenue-type "other income" account, not Sales).
  Other movements are journaled by the posting that already owns them, never twice: `refund_credit` by `postPartialReturnJournal` (OMD-5), `order_payment_reversal` by `postRefundJournal`, which reverses the whole sale entry (its mirror lines include 2150) so a whole-order refund puts the liability back as the wallet gets the credit back.
  Mechanics: `posting/wallet-posting.ts` is called by `WalletService.applyEntry` after the ledger row is written, on the same transaction, for non-replayed writes only (so the GL row and the wallet row commit or roll back together; source `manual`, sourceId `wallet:<wallet_transactions.id>`, idempotent). It does nothing when the store has accounting off. `WalletService.getCheckoutAvailability` no longer returns `accounting_enabled`; `postOrderPaymentJournal` no longer skips wallet-paid orders, which also fixes the case where the WHOLE order (cash collected included) went unjournaled when accounting was switched on between checkout and payment. Both new accounts are in `COA_TEMPLATE`, so existing stores get them on first use through the template self-heal.
  Evidence: `tests/unit/wallet-gl.test.ts` (one test per movement, plus a trial-balance scenario), `tests/unit/wallet-service.test.ts` (journal called once per new write, never on a replay or refused debit), `tests/integration/accounting/wallet-gl.test.ts` (real Postgres: 2150 equals the sum of `customer_wallets.balance` after issue, admin reversal, redemption, whole-order refund and an erasure forfeit; a replay journals once; a wallet-only order is fully journaled), and `tests/integration/accounting/owner-money-decisions.test.ts` (the split sale is DR 2150 2000 + cash 3553).
  Residuals: (1) the redemption entry is posted when the order is PAID, while the wallet is debited when the order is CREATED, so 2150 exceeds the wallet total by the unpaid wallet-held amount of orders still awaiting payment, and catches up on payment; an order cancelled before payment never touches the GL. (2) A merchant who already created their own account with code 5950 or 4100 would have the self-heal reuse it (the upsert does not overwrite), so the postings land on their account. (3) Orders created before this ruling with `walletAmount > 0` and accounting on were never journaled; no live store has the wallet on (W-1), so there are none to backfill.
  Cost if wrong: a store would see 2150 or the goodwill / unused-credit lines differ from what Ahmad wants in the P&L, which is a re-mapping of two account codes and a one-off reclass entry, not a data loss.

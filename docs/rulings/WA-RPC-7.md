# WA-RPC-7

Ruling WA-RPC-7 - COD answers and erasure-race cancels run on the store's Durable Object. The existing `whatsapp.cod_outcome` / `whatsapp.order_after_erasure` consumer (`lib/wa/store-events-consumer.ts`) read the order with `prisma.$queryRaw ... FOR UPDATE` inside `runInTenantContext`, which is POSTGRES_REMOVED on the Worker (NEON-ZERO): on a DO store every COD answer would have thrown and retried into the DLQ. It now uses `applyCodOutcomeOnDo` (`lib/wa/cod-outcome.ts`), shared with the `recordCodOutcome` RPC: only an OPEN COD order (unpaid + pending COD payment) moves; confirmed moves pending to confirmed, refused cancels pending or confirmed with `unpaidOnly` (the DO refuses if a payment landed first), no_reply is audited only; an answer older than the order is ignored; replays are no-ops by state, and the DO section re-checks the live status so racing answers cannot both act. Found by running the RPC against a real StoreDO: `OrderService.applyRefundEffects` also called `prisma.order.updateMany` / `prisma.return.updateMany` for a DO store after its cancel had committed (the DO section already writes both stamps), so any cancel of a DO order threw POSTGRES_REMOVED after the stock was restored; those two calls are now skipped for DO stores. The unit test `wa-store-events-consumer.test.ts` was moved from the Prisma lock to the repo read; the row-lock test is gone because the DO is single-threaded. Cost if wrong: a Postgres store (none in production since N-17) would lose its row lock on this path.

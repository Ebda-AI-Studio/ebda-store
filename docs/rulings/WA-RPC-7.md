# WA-RPC-7

Ruling WA-RPC-7 - ONE COD-outcome implementation. PR #562 (NZ-MONEY-6) moved the `whatsapp.cod_outcome` / `whatsapp.order_after_erasure` consumer (`lib/wa/store-events-consumer.ts`) onto the store's Durable Object (plain read, `OrderService.updateStatus` re-validates the FROM status inside its own DO section, a 400/409 refusal means "no longer eligible") and fixed the POSTGRES_REMOVED arming stamps in `applyRefundEffects`; this PR first built a parallel copy of the same logic, found the same two defects by running the RPC against a real StoreDO, and then dropped its copy. `recordCodOutcome` now calls the consumer's exported `applyCodOutcome` with a synthetic envelope whose id is a uuid derived from the idempotency key (audited as `eventId`), so the queue path and the RPC cannot diverge. Only an open COD order (unpaid + pending COD payment) moves; an answer older than the order, or any non-open order, is ignored; replays are no-ops by state. Evidence: `workers-do/wa-bridge.test.ts` (confirm, replay, refuse cancels and restocks once, a later confirm does not resurrect) and #562's `wa-store-events-consumer.test.ts`. Cost if wrong: a race between a ship and a refusal is settled by the DO status writer, not a row lock; the refused cancel is then reported `ignored` rather than forced.

# WA-RPC-4

Ruling WA-RPC-4 - Customer matching is by buyer key, never by phone lookup. Orders from chat are announced with `order/created`, whose CI planner stamps the buyer key on the order (same normaliser and suite secret as Ebda Chat); status and history reads match `orders.buyer_key`. `getOrderStatus` needs order number AND buyer key, so a number alone never reveals another buyer's order. Addresses hang off the CRM row keyed by `customers.buyer_key`: `saveCustomerAddress` calls the DO proc `waSaveAddress` (`packages/repo/src/rpc/writes.ts`), one tenant-scoped section that finds or creates that row (deterministic id `wa-<buyerKey>` + `INSERT OR IGNORE`, so a race or replay yields one row; no name, phone or email is invented) and adds the address unless an identical one exists (idempotent). An address typed inline in `createOrderFromChat` is saved the same way. Controller ruling 2026-11-11 replaced the earlier `not_found` answer for a buyer with no prior order. Cost if wrong: a placeholder CRM row named "WhatsApp customer" shows in the merchant's customer list until a real order or profile enriches it.

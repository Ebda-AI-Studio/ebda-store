Ruling ID-WA-OTP-1 (2026-10-29) - the accounts service sends a password-reset code over WhatsApp as well as by email, through a service binding to the ebda-wa Worker, and fails closed. `apps/accounts/wrangler.jsonc` binds `WHATSAPP_OTP` to service `ebda-wa`, entrypoint `WhatsAppOtp` (the RPC `sendOtp(storeId, phone, code)`, ebda-whatsapp `src/index.ts`, contract in its `docs/store-link.md` section OTP-1). `issueAndMail` (`apps/accounts/src/app.ts`) calls `sendCodeOverWhatsApp` (`apps/accounts/src/whatsapp-otp.ts`) with the SAME code it mails, only for `password_reset` and only when ALL hold: the binding exists, the account is active, `email_verified = 1`, `users.phone` is set, the role is not `super_admin`, and the user OWNS a store (first three owned stores tried; a store without a usable sender - `disabled | not_found | no_number | template_unavailable` - hands over to the next, any other refusal stops). The email is always sent and never waits on, or fails with, the WhatsApp call (4 s timeout, every throw and refusal swallowed, one log line with the reason only, never the code or the phone). ebda-wa itself stays off until the store switches `otpViaWhatsApp` on, allows Egypt (+20) only, rate-limits per phone and per workspace, and refuses the shared platform number. NOT sent over WhatsApp: signup verification and staff invitations (the phone is not yet proven to belong to the mailbox owner; a pre-registered address could name an attacker's phone), first-factor enrolment (Ruling ID-15 makes the e-mailed code the proof of mailbox control) and platform-admin recovery. Evidence: `apps/accounts/test/whatsapp-otp.test.ts` (10 tests: same code on both channels and it resets the password; absent binding = no attempt; no phone / unverified / no store / staff role skipped; fallback across stores; throw and directory-down never block the email and never log the code or phone; cap parity; enrolment, super-admin and signup stay email-only). Deploy order: ebda-wa is live with `WhatsAppOtp` (a binding to a missing Worker or entrypoint fails the accounts deploy, the old version keeps serving). Cost if wrong: a reset code reaches the phone of whoever last set `users.phone` on a verified account (set only through the email-verified signup path today), so a SIM-swapped phone can reset that account's password without the mailbox; mitigated by the existing reset throttles (3 per email per window, 5 guesses per code) and by being off until a store enables `otpViaWhatsApp`; remove the binding line to switch the channel off everywhere.

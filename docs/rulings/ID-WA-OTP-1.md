Ruling ID-WA-OTP-1 (2026-10-29, amended same day by WA-OTP-SENDER-1: the sender is the PLATFORM number, see docs/rulings/WA-OTP-SENDER-1.md; the per-owned-store loop described in the first draft is removed) - the accounts service sends a password-reset code over WhatsApp as well as by email, through a service binding to the ebda-wa Worker's `PlatformOtp.sendCode(phone, code)` (no store id), OFF by default (`WHATSAPP_OTP_ENABLED`) and failing closed. `issueAndMail` (`apps/accounts/src/app.ts`) calls `sendCodeOverWhatsApp` (`apps/accounts/src/whatsapp-otp.ts`) with the SAME code it mails, only for `password_reset` and only when ALL hold: the flag is "true", the binding exists, the account is active, `email_verified = 1`, `users.phone` is set, the role is not `super_admin`. The email is always sent and never waits on, or fails with, the WhatsApp call (4 s timeout, every throw and refusal swallowed, one log line with the reason only, never the code or the phone). ebda-wa's `PlatformOtp` allows Egypt (+20) only and answers `disabled` until the platform number is configured there. NOT sent over WhatsApp: signup verification and staff invitations (the phone is not yet proven to belong to the mailbox owner; a pre-registered address could name an attacker's phone), first-factor enrolment (Ruling ID-15 makes the e-mailed code the proof of mailbox control) and platform-admin recovery. Evidence: `apps/accounts/test/whatsapp-otp.test.ts` (9 tests: same code on both channels with exactly (phone, code) and no store id; the Store directory is never consulted; flag off or binding absent = no attempt; no phone / unverified skipped; refusal and throw never block the email and never log the code or phone; enrolment, super-admin and signup stay email-only). Deploy order: ebda-wa must be live with `PlatformOtp` (ebda-whatsapp PR #44) (a binding to a missing Worker or entrypoint fails the accounts deploy, the old version keeps serving). Cost if wrong: a reset code reaches the phone of whoever last set `users.phone` on a verified account (set only through the email-verified signup path today), so a SIM-swapped phone can reset that account's password without the mailbox; mitigated by the existing reset throttles (3 per email per window, 5 guesses per code) and by the channel being OFF until the flag is set; set `WHATSAPP_OTP_ENABLED` back to "false" to switch it off.

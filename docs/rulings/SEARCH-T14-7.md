# SEARCH-T14-7

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling SEARCH-T14-7 (automated security review of SEARCH-T14-1/T14-5: "SECURITY DEFINER id lookup as a search oracle") — `ebda_product_search_ids` (`20261024000300`) and `ebda_order_search_ids` (`20261024000500`) run as the table owner, so they ignore RLS and had to be made unable to answer a question the caller's RLS would not. Findings verified against the code first: (1) the store was an ARGUMENT checked against the session scope, with an exemption for owner/BYPASSRLS sessions, so an owner-role caller with no scope could ask any store; (2) with no scope set the function returned an empty set, indistinguishable from "no match"; (3) the `customers` kind returned any user who had an order here, including accounts the `users` RLS policy hides from a store scope (registered on another store, or `store_id` NULL), i.e. a probe for "does this phone/email have an account"; (4) soft-deleted orders still counted toward a customer; (5) a customer searching their OWN orders still triggered the store-wide lookups; (6) no route checked `orders:read` itself. Honest scope of the fix: today every role that passes `authorize` (store_admin, super_admin, staff) already holds `orders:read` in `rbac.ts`, and per-staff permissions do not exist, so the checks added to `customers/search`, `export.xlsx` and the order list can NOT fail today; they are defence in depth that keeps the store-wide lookups behind the permission once granular staff permissions exist (the test pins the source text, it does not prove a closed hole). The closed holes are (1) to (5). Now: the store comes ONLY from `app.current_store_id` (no scope or no store = `RAISE 42501`; an argument naming another store = empty, identical to "no match"; no exemption for owner sessions); both return ids only and the app re-reads them through RLS (`orders` / `products` selects as `ebda_app`) before any row or count reaches a user; the `customers` kind applies the `users` policy's own predicate (same store, the caller, the store's owner/staff, or a super admin) and ignores soft-deleted orders; soft-deleted orders and (unless the caller asks, own store only) deleted products are excluded; EXECUTE for `ebda_app` only, `search_path = pg_catalog, public, pg_temp` (both are covered by the `rls-ebda-app` definer hygiene test and by `search-definer-authz.test.ts`); `orderSearchWhere(..., { indexed: false })` makes a customer's search skip the store-wide lookup; `customers/search` and `export.xlsx` chain `requirePermission('orders:read')` and the order list checks `hasPermission(role, 'orders:read')` for store viewers (`order-search-route-permissions.test.ts`, red against the previous routes). Behaviour change, deliberate: a customer the `users` policy hides is no longer found by the order search (the old tests asserted the owner-role reading). Tests, each red first (`_t14c_red.log`, `_t14c_red2.log`): cross-store probe returns nothing and looks exactly like a nonexistent term (both definers); no scope is refused (also for an owner session); a soft-deleted order/product and a hidden customer are not returned; the count cannot be inferred (a term that exists only in another store gives the same answer as a term that exists nowhere). Open measurement (review M-5): the `customers` kind searches `users`, which spans all tenants. For a very common term (`gmail`, `+20`, a common first name) its cost can grow with platform-wide matches instead of store size, unless the planner probes the store's customers first (it did at 1,000 customers per store). Its `LIMIT` has no `ORDER BY`, so which 50/1,001 rows come back is arbitrary (correct, not stable). Plan: when the platform holds more than ~50 stores or ~200k users, run `EXPLAIN (ANALYZE, BUFFERS)` of the definer's `customers` statement as `ebda_app` for the three most common terms on a copy of production-shaped data and add an `ORDER BY u.id` if the cap is ever hit; until then INCONCLUSIVE. Not changed, and why: the argument `p_store_id` stays in the signature (a mismatch is the probe the test exercises); `include_deleted` / `only_active` remain caller-chosen flags because they only widen to the scoped store's own rows. Residual: a caller that can run arbitrary SQL as `ebda_app` could `SET app.current_store_id`; that is the same trust boundary the RLS policies themselves rest on. Cost if wrong: a missed visibility rule returns ids of rows in the caller's OWN store that the policy would hide (never another store's), and every row is re-read through RLS before use.

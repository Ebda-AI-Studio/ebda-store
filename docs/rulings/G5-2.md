Ruling G5-2 (2026-10-25) - per-store schedules are Durable Object alarms (`StoreSchedule`, one SQLite DO per store, `JOBS_CF_ALARMS` per job), not a global cron that lists every store. Evidence: `src/cf/store-schedule.ts` (alarm logic, tested with `runDurableObjectAlarm` on workerd), `src/lib/jobs/next-run.ts` (DST-safe next occurrence for Africa/Cairo crons: 400 chained days, exactly one 23 h and one 25 h gap). The alarm starts the same function scoped to its store (`event.data = { alarm, storeId }`); the Workflow instance id is the event id (a re-fire is a no-op), the concurrency gate becomes `<job>|<store>`, a start failure retries 30 s..15 min and after 5 tries the occurrence is skipped and `inngest/function.failed` feeds the alert channel, a late alarm beyond 24 h is skipped, not replayed. A job is alarm-ready only if its handler honours the store scope: `audit-log-archive-weekly` (one cross-tenant system table) and `ai-autofill-sweep` (platform-wide leader lock and shared Gemini quota) stay crons on purpose. New stores are armed by the hourly sync (`0 * * * *`), not at creation (creation runs inside a transaction). Cost if wrong: a store whose schedule is not armed misses a night; the hourly sync arms it and the cron path is one var away (`JOBS_CF_ALARMS` empty).

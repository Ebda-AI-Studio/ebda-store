# CF-MONEY-1

Ruling CF-MONEY-1 (2026-10-29, INFRA-CF-1 PR D2b, first slice) - money operations move to the StoreDO as named operations behind their own RPC, and the read RPC gains `aggregate`/`groupBy`. (1) Shape: `StoreDO.moneyOp(storeId, op, argsJson, key?)` -> `answerMoneyOp` -> `runMoneyOp` (`packages/repo/src/do/money-ops.ts`), the twin of `stockOp` (CF-STOCK-1): ONE named operation = ONE `transactionSync` section (the single thread replaces the Postgres `FOR UPDATE`), an optional idempotency key stored as a marker row INSIDE that section (`_money_ops`, shared discipline in `do/keyed-op.ts`: replay returns the first result, same key for other arguments is `IDEMPOTENCY_KEY_REUSED` 409, a refused or failed operation stores nothing, 24 h), a refusal is an ANSWER `{ ok:false, code, status }`. Money cannot move through the generic `mutate` (it still refuses those models). The Worker side is `storeMoney(storeId)` (`lib/repo-factory.ts`): `null` on Postgres, a typed `MoneyClient` on `do`; a service does `const money = await storeMoney(id); if (money) {...DO path...}` and its Postgres code below is UNCHANGED, so with every flag at `pg` nothing runs differently. (2) Moved in this slice: `LoyaltyService.earnPointsFromPurchase`, `reverseEarnedPointsFromOrder`, `reverseRedeemedPointsFromOrder` (`loyaltyEarn`, `loyaltyReverseEarned`, `loyaltyReverseRedeemed`), over the engine already in `do/loyalty.ts`. The platform feature flag `loyalty` is resolved by the service and passed as `featureEnabled`; the settings come from the DO's own `store_config` (the CF-WRITES-3 write-through copy). Two deliberate differences, each measured and kept: (a) the DO reads the order total from its own order row (Postgres is handed `orderTotalFils`; both are the order's total in every caller) and refuses an earn for an order it does not hold (`ORDER_NOT_FOUND` 404) or one that belongs to another customer; (b) a REVERSAL for an order the DO does not hold answers `null`, as Postgres does when there is no ledger row. EXTERNAL MONEY FACTS ARE RECORDED, NEVER REJECTED (feedback-never-reject-an-external-money-fact): a reversal after the customer spent the points reverses what the balance holds (floor at the balance), still writes the full tagged `adjust` row and drops `total_earned` by the full amount, exactly as Postgres. (3) `aggregate` and `groupBy` are `READ_OPS`; prisma-lite's engine now also answers groupBy `having` (aggregate filters and group-key filters, AND/OR/NOT), `orderBy` on an aggregate (`_count/_sum/_avg/_min/_max`), `take` and `skip`, and refuses everything else loudly (unsupported operator, negative take, `cursor`). (4) FOUND by the contract test and fixed in the engine for every `orderBy`, not only groupBy: Postgres sorts an enum by `pg_enum.enumsortorder`, SQLite sorts the text, so `ORDER BY status` came out in a different order on the DO. The engine now orders an enum column by a CASE over the declared order (`prisma-lite/enum-order.ts`); `OrderStatus` and `PaymentStatus` were extended with `ALTER TYPE ADD VALUE` out of schema-file order, so their Postgres order is pinned there and the contract test compares the engine's order with `pg_enum` for ALL enums of the schema. A cursor whose sort key is an enum now throws instead of paging by text. (5) PR E residual closed: an event that carries no `storeId` names its store through a resolver (`EVENT_STORE_RESOLVERS` in `lib/jobs/do-guard.ts`; today only `payment-webhook-process`, whose inbox row holds the store the route resolved from the provider reference, WEBHOOK-SCOPE-1), so the queue and Workflow runners (`decideRunForStore`, the lookup is its own Workflow step because code outside a step has no database) refuse it for a DO store with a P0 alert like any unported money job. A run for which NO store can be named (platform-only inbox row, unreadable row) still runs against Postgres as before: a DO store's payment reference does not resolve there until the D1 entity index (plan task 3.5) exists; a unit test fails when a new typed event has neither a required `storeId` nor a resolver. (6) NOT moved in this slice, with reason: orders create/status/holds (`OrderService.create` is one 3.7 k-line service whose stock reservation, hold cap, coupon limit, loyalty redeem, wallet debit and gold price check share ONE interactive transaction; the engine `do/checkout.ts` exists but the service-to-engine mapping needs its own PR), payments/webhooks/refunds/returns (`payment.factory.ts`, `return.service.ts`: same shape, plus the entity index for webhook routing), ledger/accounting posting, coupons, wallet, gold repricing, the hold cap, interactive-transaction and security-definer lookups (72 files). The flag stays `pg` for every store and the cutover gate (rows 1-3) still forbids a flip. Evidence: `tests/integration/repo-factory-money-contract.test.ts` (5 scenarios through the real `LoyaltyService`, each on real Postgres 17 and on the DO schema on SQLite via the real wire codec, equal traces = return values AND the resulting `loyalty_points` / `loyalty_transactions` rows), `packages/repo/test/do-money-ops.test.ts` (5), `apps/api/workers-do/money.test.ts` on real workerd (50 concurrent earns for one order credit it once; 20 concurrent calls with one key apply once; a refusal is an answer; a second store id is `STORE_MISMATCH`), `tests/integration/repo-factory-aggregate-contract.test.ts` (aggregate, groupBy with having/orderBy-aggregate/skip/take, enum order against `pg_enum` for every enum), `tests/unit/jobs-do-guard.test.ts` (resolver, both runners, the typed-event list). Cost if wrong: with every flag at `pg` the loyalty services run their Postgres code unchanged; a wrong DO loyalty write is reachable only for a store the operator flipped (one D1 UPDATE back) and the cutover gate still forbids a flip until orders, payments, refunds and the ledger move.

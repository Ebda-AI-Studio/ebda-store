# WALLET-DO-TX-2

Ruling WALLET-DO-TX-2 (2026-10-30, INFRA-CF-1 final integration; supersedes the refusal of WALLET-DO-TX-1) - `WalletService.applyEntry` for a Durable Object store takes the `walletEntry` money op whether or not a Postgres transaction is open around it, and `WALLET_IN_TRANSACTION_NOT_ON_DO` is deleted from `docs/cf/not-on-do.json`. WALLET-DO-TX-1 refused it because the return completion credited the wallet inside the request's Postgres transaction with a key that a retry could mint afresh, so a rollback after the DO write plus a retry credited twice. That caller is gone for a DO store: the Return lifecycle is one DO section per step and `returnFinish` writes the store credit and the wallet share of a gateway refund in the same section as the completion row, the tier items and the restock, keyed on the return id (Ruling CF-RETURNS-1), so `return.service` never reaches `WalletService` for a DO store. Every remaining caller keys the movement on the entity it belongs to (`admin-adjust:<request key>`, `order-payment:<order>` / `order-payment-reversal:<order>`, `erasure-forfeit:<wallet>:<ledger position>`), and the DO ledger row is unique on that key, so a request that rolls back after the DO write and is retried REPLAYS the entry (credited once). The merchant's manual adjustment, which runs inside the request's tenant transaction, now works on a DO store (it was refused 501). Order create, cancel, refund and payment-failure rollback are already DO sections (Rulings CF-ORDERS-1, CF-PAY-1). Evidence: `tests/integration/repo-factory-wallet-contract.test.ts` (the Postgres transaction fails after the wallet write: three attempts leave one credit; a caller client replays; an in-transaction admin adjustment applies once and replays), `tests/integration/repo-factory-returns-contract.test.ts` (store credit on both backends). Not verified: `forfeitOnErasure` of the shopper's own account reads the wallet from Postgres, so for a DO store it finds nothing and forfeits nothing; the account erasure of a DO store is a separate port (listed in `docs/cf/not-on-do.json`). Cost if wrong: a future caller that mints a fresh idempotency key per retry inside a Postgres transaction would double a DO credit on rollback plus retry; `assertValidInput` demands a key and every present caller derives it from an entity id.

# RULINGS-INDEX-1

Ruling RULINGS-INDEX-1 (2026-11-10, controller) - the rulings index is the `docs/rulings/` folder itself; `docs/rulings/README.md` is a static page with no table and no count, and adding a ruling means adding ONE new file, nothing else. Evidence: almost every PR appended a row to the shared README table AND rewrote its hand-typed "NNNN rulings." line (and prettier re-padded every row when an ID or decision was wider than the column), so any two open PRs conflicted - #516 and #527 re-merged main 2-3 times on 2026-11-10. `merge=union` in `.gitattributes` was rejected: GitHub's mergeability check and merge button do not run custom merge drivers, so it only helps local merges, and it cannot fix the count line or prettier re-padding. A generated, committed table was rejected for the same reason (every PR would regenerate the same shared file). `tests/unit/rulings-index.test.ts` now reads the files directly and keeps the guarantees that still mean something: real data scanned (>1000 files), every file non-empty with a safe `<ID>.md` name, IDs unique case-insensitively (macOS/Windows checkouts), legacy `docs/RULINGS.md` stays a pointer, and the README stays table-free and count-free so the shared edit cannot come back. "Every file listed" and "no dangling row" are now true by construction. Proven in a scratch repo: two branches each adding a ruling file on a common base merge with no conflict. Cost if wrong: no one-page ID/decision/date table on GitHub; the folder listing and `grep` replace it.

# LAZY-TX-1

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling LAZY-TX-1 (2026-10-22) — a cached public catalogue read opens no per-request tenant transaction. Measured with the per-hop log: every public GET opened an interactive transaction (a lookup plus BEGIN and the GUC `set_config`, two database round trips, about 90-190 ms) before the handler could answer a KV hit that needs no database. `publicStoreContext` (`middleware/tenant-context.ts`) now skips `tenantContext` for exactly an anonymous GET/HEAD of `/categories` or `/tags` with no query, no Authorization, no Cookie, whose store came from the host/id lookup (`skipsRequestTransaction`, `middleware/public-read-limit.ts`). Their handlers read only inside `getCached(..., () => readInStoreContext(storeId, ...))`, so a cache miss reads in its own short store-scoped transaction under RLS and a hit touches no database. FAIL CLOSED: with no ambient scope the tenant guard throws `TenantScopeViolation` on any tenant-model query and on raw SQL naming a tenant table, and RLS returns nothing, so an unscoped read on this path cannot succeed. Everything else (other routes, queries, authenticated or cookie-bearing requests, writes) keeps the request transaction unchanged. Evidence: `tests/integration/lazy-request-tx.test.ts` on a real `ebda_app` login (arrives with no scope; miss returns the store's own data; hit issues zero tenant queries; a forced unscoped model query and raw query on the path throw; another store sees only its own categories; auth/cookie/query/other routes still get the store scope), the existing `rls-ebda-app` and `tenant-guard-ebda-app` suites unchanged and green, and two defence-mutation entries (killed). Cost if wrong: a handler added to `/categories` or `/tags` that reads the database outside `readInStoreContext` gets a `TenantScopeViolation` 500 instead of data (loud, never a leak).

# CF-ERASE-3

Ruling CF-ERASE-3 (2026-10-29, INFRA-CF-1 PR D1) - the StoreDO erasure registry is GENERATED, not typed: `scripts/cf/gen-erasure-registry.mjs` turns `packages/cf-schema/erasure-classification.json` plus the store migrations into `apps/api/src/cf/erasure/registry.generated.ts` (122 schema tables + the two the DO creates itself, `payment_event_log` and `vector_usage`, both reviewed as holding no personal data). `no-pii` stays `no-pii`; `merchant-pii` and `legal-retention` become `store-owned` (they leave with the store, never with a customer); `customer-pii` gets a `match` (email / phone / user id / buyer key columns by name, `customerId` resolved through the customers rows the subject resolves to, `via` the parent order for shipments) and, for scrub tables, a value per column (NULL when nullable, `{}` for NOT NULL address/JSON columns, `[erased]` for other NOT NULL text; any other NOT NULL type or a match column that is not scrubbed stops the generator). CI: `tests/unit/cf-erasure-registry.test.ts` fails when the committed file is not byte-identical to the generated one (it runs in every PR unit lane), and `cf-schema-current.yml` runs `--check` on main. The generator refuses a classification that disagrees with the schema (unclassified or unknown table) and a customer-pii table that no subject key can reach and no cascading parent removes (only `affiliate_referrals`, an anonymous session id with no subject key, is named as unkeyed; it goes with its affiliate by `ON DELETE CASCADE`, residual accepted). Engine rules (`store-do-sql.ts`): `via` tables are handled before their parent and `customers` last, so every child can still resolve the subject; `do_flags.erasure` is raised for the erase and lowered after it because the append-only trigger on `commerce_outcomes` allows `buyer_key -> NULL` only then (found by the real-schema test: the first run aborted with `commerce_outcomes is append-only`). Evidence: the same test inserts, for every one of the customer-pii tables, a subject row per matchable key and a bystander row into the REAL DO schema (CHECKs and triggers on), then exports (every key finds its row, no bystander), erases (delete tables lose the subject, scrub tables keep the row with the identifiers gone and the bystander byte-identical), re-counts to 0, repeats the erase to 0, and shows an identifier-less subject matches nothing; mutation-checked (running `customers` first fails it). `apps/api/workers-do/erasure.test.ts` (real workerd): a customer subject is now SERVED on the full schema and still REFUSED (`ERASURE_REGISTRY_INCOMPLETE`) once the DO holds a table the registry lacks, and the registry covers every table `storeTables` reports. Not covered by this registry (unchanged): the D1 platform erasure (`packages/repo/src/platform-erasure.ts`), identity, CI and media surfaces. Cost if wrong: a customer erase on a DO store leaves a personal column behind (the classification, not this code, decides which columns are personal; the generator and the real-schema test make a missing or mis-keyed column fail the build); no store is on the DO yet and the Postgres erasure path still runs.

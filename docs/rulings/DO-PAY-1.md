# DO-PAY-1

> Section: Lifecycle emails and referral attribution (2026-10-22, branch `feat/lifecycle-emails`)

Ruling DO-PAY-1 (2026-10-25; the Fawry window/prefix and relabelled-delivery parts are SUPERSEDED by DO-PAY-2) - payments, refund claims and webhooks on the StoreDO (`packages/repo/src/do/payments.ts`, `src/platform/entity-index.ts`). (1) `applyPaymentEvent` is idempotent by (provider, signed event id): the `payment_event_log` row is written in the same `transactionSync` as the effects, and re-checked inside it, so a delivery replayed 3x in parallel (even across a slow gateway confirm) has one effect. (2) PROVIDERS-17: Kashier (set `CONFIRM_BEFORE_APPLY`) is applied ONLY from the gateway's own record; no `confirm` dependency or no answer = 503 `WEBHOOK_UNCONFIRMED` and nothing written; a relabelled delivery is corrected and recorded (`webhook_corrected`); an authorization moves no money. (3) Refund protocol: `beginRefund` commits the claim (amount + `refund_initiated` event, atomic CAS on `refunded_amount`, cap = remaining balance, outstanding `refundKey` refused) BEFORE the provider call; `completeRefund` writes the provider id, `refundEventIds`, the order flip and `refund_completed` in one section and books a non-return partial keyed on the provider id; `releaseRefund` only when the provider refused; `markRefundIndeterminate` keeps the claim. (4) A settle webhook is reconciled with the OLDEST YOUNG (5 min) UNCONSUMED claim of the same amount, and CONSUMES it in its own section (`refund_webhook_absorbed {claimId, refundId}`), so a second genuine same-amount refund is added, never swallowed; a stale claim never absorbs; a claim released after being absorbed is NOT decremented, it is marked `refund_reconcile_review`. An amount-less Fawry notice is correlated to our refund by payment + 6 h window + the `fawry-refund-<ref>-` prefix (no alert), otherwise held + alerted. (5) Deviation from Postgres, stricter: a failed/expired/pending notice never downgrades a payment already completed/refunded/disputed (recorded, state kept, alert). (6) Entity index: `d1_outbox` rows are written with the entity and drained to D1 `entity_index` (write-once per (kind, id); a re-point attempt is reported as a conflict); webhooks route by `webhook:<provider>:<ref>`; an unknown reference is a 200 no-op with a breadcrumb, never a default store. (7) `rowsWritten` (the DO `changes`) counts index writes, so guards use `< 1`, never `!== 1`. InstaPay receipt approval stays in D1 (the Worker passes `proofSubmitted`). NOT VERIFIED: real provider payload parsing and signature checks (they stay in the Worker adapters; this module takes the verified event), the Worker glue that calls `routePaymentWebhook` then the DO, the GL/notification fan-outs (returned as `postCommit` and `alerts`). The refund-settlement rule now lives in `@ebda/shared` (one implementation for the Postgres path and the DO). Cost if wrong: a refund webhook that matches no claim and no ledger is held with an alert (money understated, never overpaid); the 5-minute window can be widened if provider answers ever take longer.

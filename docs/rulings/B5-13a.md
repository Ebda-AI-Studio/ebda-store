# B5-13a

> Section: 2026-10-22 — Phase B5 Dahab (B5-\*)

Ruling B5-13a (Task 9, implementation detail of B5-13) — the price guard's two trigger functions are `gold_price_guard_products()` and `gold_price_guard_variants()`, SECURITY INVOKER, and deliberately NOT named `ebda_*`. The `ebda_*` functions are SECURITY DEFINER by rule (hygiene test in `rls-ebda-app.test.ts`), but a definer runs as the table owner, which under FORCE ROW LEVEL SECURITY has no policy of its own and reads NO product row: the variants guard would see every variant as `fixed` and let the write through. A variant resolves its product's mode under the caller's own RLS view (a variant the caller cannot see cannot be written anyway). Ids are TEXT like every other table (the plan said uuid); history timestamps are `timestamptz`. `gold_rates_current.rate_id` cascades from `gold_rates`, so no NO ACTION child exists (verified from `information_schema.referential_constraints` in `gold-rate-rls.test.ts`). Cost if wrong: a gold-aware writer that runs as the table owner with FORCE and no tenant GUC would be refused (correct) rather than allowed.

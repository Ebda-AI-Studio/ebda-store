# NZ-PG-1

> Section: NEON-ZERO Postgres remnants (2026-11-05)

**Ruling NZ-PG-1 - `storeDirectory()` is answered from D1 `stores` wherever the platform D1 is bound; the Postgres `ebda_store_directory()` definer is only the answer where no D1 is bound (Node, tests, local dev).** The hourly `syncStoreSchedules` and about twenty jobs and services (loyalty, abandoned carts, accounting and stock sweeps, domain claims, R2 cleanup, grants, search log) listed stores through the definer, so each dead-ended on POSTGRES_REMOVED once Postgres was gone. The resolver (`ScopeResolver.directory`, registered in `lib/store-scope-resolver.ts`, implemented in `services/platform/directory-entries.ts`) reads D1 in keyset pages of 1000 (`listDirectoryStores`), so the list is complete at any fleet size; status, soft-delete and the hidden-store scope are applied exactly as for the definer. The three per-store switches (`accountingEnabled`, `aiFeaturesEnabled`, `loyaltyEnabled`) live in the StoreDO `store_config`, not in D1: a caller's `filter` is probed with every switch on and every switch off, and only a filter that reads a switch makes the resolver read that store's DO (8 at a time); an unreadable DO keeps the store in the list (the job's own per-store gate decides) with a warning. Evidence: `packages/database/src/__tests__/scope-resolver.test.ts`, `tests/unit/store-directory-d1.test.ts`. Cost if wrong: a store whose DO switch read fails is swept once although its merchant turned the feature off (the per-store gate inside the job still refuses the work).

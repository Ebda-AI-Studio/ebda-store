Ruling ID-13 (2026-10-24) - one rule for inviting an address that already has an account. An invitation binds only to an identity row it created (`inviteUser` returns `created:false` with the REAL id, role and verified flag for any existing row, mails nothing, changes nothing; only a retry with the same id and role re-mails). The Store creates its profile row only with the id it generated and asserts the identity answered with it. An existing account (unverified, mid-signup, no Store profile, or a merchant) is never added silently: it gets an e-mail with a signed 72-hour token and accepts it signed in as that address (`POST /staff-invites/accept`; verified e-mail, same address, active). A merchant that owns a store is refused (OWNS_STORE); a merchant with no store becomes a staff account (identity role switch ends its sessions, so it signs in again). An already-verified staff account is added at once. The invitation is STATEFUL: the link's jti is the id of a pending `staff_invites` row (store-scoped, RLS), honoured only while pending and unexpired; accepting flips the row in the same transaction that creates the membership (a link works once), and removing the member, re-inviting the address or the owner revoking it (`DELETE /stores/:id/staff/invites/:id`, listed at `GET .../staff/invites`, admin UI en/ar) ends it. The accept route also refuses impersonation tokens. `staff_invites` is a store table and moves into the StoreDO schema with the others (docs/plans/done/2026-10-28-store-on-cloudflare.md, phase 1). Evidence: Opus review (cross-tenant takeover through an unverified row; replay of a stateless link by a removed member) and the controller's rulings on L2/L3 and non-revocable replay. Seats: the check is atomic with the insert for both the owner's add and the accept (`assertWithinLimit(..., { tx })` locks the store row FOR NO KEY UPDATE (not FOR UPDATE, which would block every FK insert such as checkout) and counts inside the transaction); accept re-checks the plan's maxStaff and the `staff_accounts` feature at accept time; a plan downgrade (`assignPlan`, or `updatePlan` lowering maxStaff) expires the pending invites beyond the free seats (oldest kept). Accept validates read-only first, switches the identity role BEFORE consuming the invite, re-checks ownership, and undoes the switch (409 OWNS_STORE) if a store appeared in the window or any later step fails, so an account is never left staff while owning a store. Accepts are serialised per account (`staff-accept:<userId>` lock, 409 ACCEPT_IN_PROGRESS; best effort when Redis is down) and the rollback is a compare-and-set (`setRole(..., ifCurrentRole)` changes the role only if it is still staff, ends no sessions when nothing matched) that is skipped while the account holds any staff membership, so overlapping accepts leave the final role and memberships consistent. Verified on a real Postgres 17 as the strict-RLS role (tests/integration/staff-invite-seats.test.ts: 8 simultaneous accepts for the last seat -> exactly one member; mutation check: with the lock removed the same test fails 3 of 3 runs). Cost if wrong: if the lock were missing, N simultaneous accepts could exceed maxStaff by N-1.

# STORE-ROW-TOMBSTONE-1

Ruling STORE-ROW-TOMBSTONE-1 (controller, 2026-11-24, class check of the #1109 review) - an existing store's D1 `stores` row is never DELETEd; it is tombstoned (`lib/store-tombstone.ts`: identifying columns cleared, slug `purged-<id>`, domain released, soft-deleted). Reason: billing_events (Ebda's own invoices), instapay_receipts, manual_payment_claims, billing_reminders, store_subscriptions, trust_requests, ai_usage and others reference `stores(id)` ON DELETE CASCADE, so deleting the row destroys them silently. Class check, every path that removed a `stores` row: (1) `retireStoreDirectoryRow(soft:false)` called by `finishStoreDeletion` with `soft = wasOnDo`: hard for a NON-DO store, soft for every DO store; (2) `syncStoreDirectoryFromPg` "gone from Postgres" DELETE (never reached for a `do` row); (3) `store-directory-reconcile` "in D1, gone from Postgres" DELETE (never for a `do` row, which is alert-only); (4) `store-create-do.rollbackDoStore` (a store created seconds earlier, no billing yet: kept as a hard delete on purpose); (5) the closed-store purge (NZ-D15B) already tombstones. Production measurement (D1 `ebda-platform`, SELECT only, 2026-11-24): 7 `do` stores (0 deleted), 1 `pg` store (deleted, soft) - so no hard delete has ever run in production and the cascade has not destroyed anything; the hard paths were latent for any non-DO store. Fix: paths 1-3 now tombstone. Evidence: `tests/unit/store-directory-no-hard-delete.test.ts` (real schema, foreign keys on). Cost if wrong: a tombstone keeps a few non-personal columns and the owner id (opaque) forever; deleting instead loses Ebda's billing records.

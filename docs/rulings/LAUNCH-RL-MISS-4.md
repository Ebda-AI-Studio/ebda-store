# LAUNCH-RL-MISS-4

> Section: Launch follow-up 2026-11-10 (branch `fix/public-normal-browsing-404s`): an unknown store id in a public path went past every public limiter

Ruling LAUNCH-RL-MISS-4 - a store id in a public path (`/public/<uuid>/...`) that is in no directory is still answered 404 `STORE_NOT_FOUND`, but BEHIND the public router's limiters instead of in front of them: `publicStoreContext` holds that one refusal back and `refuseUnknownPublicStore`, mounted right after `storeMissLimiter`, raises it. The 404 now passes the per-IP and per-tenant public limiters, carries the store-miss budget, is counted as a miss and is refused 429 at 20, the same as an unknown slug or host. Nothing changes for a store that exists, for a write (`storeScopeContext` does no directory lookup), or for any other error of the lookup (a 503 `STORE_BACKEND_UNAVAILABLE` is still answered straight away). The limit, the window, the key, the 429 body and fail-open are unchanged. Measured in production 2026-11-10 before the fix: two `GET /api/v1/public/<random uuid>/pages/privacy` answered 404 `STORE_NOT_FOUND` with no `RateLimit-*` header, and the next `GET /api/v1/public/health` from the same IP still showed `ratelimit-remaining: 20`. Cause: `routes/index.ts` mounts `publicStoreContext` in front of the public router, and for a path store id it runs `tenantContext`, whose directory lookup (`backendFor`) throws the 404 before any limiter ran. Found by the workerd test this branch adds (`apps/api/workers-test/failure-only-limiters.test.ts`, "an unknown store still is": expected the counter at 1, got 0). Evidence after the fix: that workerd test passes (404 counted, the next 200 shows 19 left); `tests/unit/public-unknown-store-limited.test.ts` (counted on every miss, 429 at the limit, no handler ran, a real store writes nothing, a 503 is not held back, the mount order in `public.routes.ts` and the single mount in `routes/index.ts`); defence mutations `public-unknown-store-reaches-the-limiters` and `public-unknown-store-refused-after-the-limiters` are both KILLED.

Accepted residual: the directory lookup itself still runs before the limiters, so an IP that is already refused (429) still costs one directory read per request for a path store id, exactly as a store named by host or header does today. Moving the lookup behind the limiters changes where the store scope opens for every legitimate request with a path store id, which is not a change for the day before launch.

Cost if wrong: an IP probing random store ids is cut off at 20 answers a minute but still costs one D1 directory read for each request it sends past that, bounded only by the platform's own per-IP limits.

# ADMIN-STARTUP-BUDGET-1 - the merchant admin Worker has a startup and bundle budget

Ruling ADMIN-STARTUP-BUDGET-1 - the admin Worker (OpenNext, bundle `health-worker-entry.js`) is gated by `scripts/ci/worker-startup-budget.mjs --app admin` against `scripts/ci/worker-startup-budget-admin.json` (startup CPU 60 ms, 21.7 MB raw, 3.9 MB gzip; PRs compare against main built in the same job, ratio 0.25 + 15 ms), in the Worker dry-run (admin) job. It had none (only API and web did). First real measurement, 2026-11-18, local workerd with the CPU profiler, 7 runs: startup CPU 20.7 ms (min; samples 34.6, 20.7, 22.0, 21.1, 20.8, 21.4, 21.2), bundle 19,704,284 bytes raw / 3,551,285 gzip. For scale: web 38.6 ms / 16.07 MB, API 88 ms / 7.09 MB. Local-workerd CPU is not Cloudflare's number. QA-PERF-LOGIN-1 read: this does NOT confirm the cold-start hypothesis. The admin's startup CPU is small (20.7 ms, lower than the storefront's 38.6), so the intermittent ~1 s /login server spikes are not explained by startup CPU of the global scope. What it cannot see: the time Cloudflare takes to fetch and compile a 19.7 MB script into a new isolate (wall time, not CPU), isolate placement, and any upstream call; the spikes remain unproven. Cost if wrong: the ceilings (3x CPU, ~10% size) are generous; a real regression beyond them fails the PR, a regression below them passes unnoticed.

# INSTAPAY-AUTO-1

Ruling INSTAPAY-AUTO-1 (Ahmad 2026-11-14, plan `docs/superpowers/plans/2026-11-14-instapay-auto-confirm.md`, foundation rulings INSTAPAY-1..7 and INSTAPAY-CLEAN-1, vendored `@ebda/foundation` v0.3.0) - a merchant's InstaPay subscription payment whose receipt FULLY matches activates the plan in minutes with no human, through the SAME `recordManualPayment` the human path uses. The model only EXTRACTS a typed object (`readReceiptForAutoConfirm`, foundation `parseReceiptExtraction`); plain code decides (`decideInstapay` + the Store's own checks in `instapay-auto-confirm.service.ts`); text inside the image is never an instruction. Everything off waits for Ahmad and the existing human review is unchanged. Evidence: `tests/unit/instapay-auto-confirm.test.ts` (activate, replay, shadow, off, store off, no dedupe binding, yearly-first-over-cap, claim not the quoted charge, failed activation compensation, ledger recorded but activation failed keeps the dedupe claim), `tests/unit/instapay-auto-confirm-fraud.test.ts` (`fraud: <case>` matrix + mutation controls), `tests/unit/instapay-auto-revert.test.ts`, `tests/unit/instapay-auto-digest.test.ts`, `tests/unit/instapay-auto-confirm-job.test.ts`, `tests/unit/internal-instapay-routes.test.ts`, `tests/unit/instapay-dedupe-wiring.test.ts` (the foundation dedupe contract on the production SQL).

Decisions, each with its cost if wrong:

- Ruling INSTAPAY-AUTO-1a - ONE shared D1 `ebda-instapay-dedupe` (binding `INSTAPAY_DEDUPE_DB`, foundation `D1DuplicateIndex`) is the platform-global duplicate index across every merchant AND both products; a claim holds the reference and the image hash together or neither. A missing binding forces `needs_human` (fail closed). Cost if wrong: one outage of that D1 turns every InstaPay payment into a manual review, never an automatic activation.
- Ruling INSTAPAY-AUTO-1b - rollout state: global mode `off` (default) | `shadow` (decide and record the would-be verdict, activate nothing) | `live`, plus a per-store switch; both live in `system_settings` (keys `instapay.auto_confirm.mode`, `instapay.auto_confirm.store.<id>`), are read from the database on EVERY decision (NEVER-stale class, no cache so nothing to invalidate) and re-read immediately before money moves. A switch-only outcome (off / shadow / store off) sends no "waiting on you" notice. Cost if wrong: a flip takes effect on the next decision, not on one already past its re-read.
- Ruling INSTAPAY-AUTO-1c - strict equality: the receipt amount must equal the quoted charge (plan + interval + Ebda VAT through `chargeFor`) to the piastre, and so must the claim's own amount; an overpayment or a VAT-less payment waits for a human. Cost if wrong: a generous overpayer waits for a person.
- Ruling INSTAPAY-AUTO-1d - the first automatic confirmation of a store is capped at ONE month of the CHOSEN plan (VAT included); a bigger first payment waits. "Clean" is INSTAPAY-CLEAN-1: human-confirmed at once, auto-confirmed only after it appeared in a digest actually SENT to Ahmad (`digestSentAt`, stamped only when the brain answers `sent:true`), never reverted, no waiting window; a second payment above the cap before that digest waits. The Store counts only manual-payment ledger rows (not card charges) toward "clean": the conservative reading. Cost if wrong: a card-first merchant's first InstaPay payment above one month waits for a person.
- Ruling INSTAPAY-AUTO-1e - what the merchant typed must be what the image shows: a typed reference different from the read one adds `EXTRACT_INCOMPLETE` (the foundation has no code for "typed and read disagree"). Cost if wrong: an honest typo waits for a person.
- Ruling INSTAPAY-AUTO-1f - "not received" (one tap from the digest, signed `revert` over HMAC, brain -> `/internal/instapay/auto-confirm/not-received`): only an `auto_confirmed` row reverts. The state change is ONE guarded `UPDATE ... WHERE state = 'auto_confirmed'` whose `changes` decides the winner (the D1 router's `updateMany` selects keys then updates by key, so it is NOT a compare-and-set; the revert therefore does not use it). Effects: the existing void path (`recordManualRefund` with `graceUntil`, `keepReference`) takes back the period only when this payment owns the current one (a later legitimate payment is never touched) and sends the store to `past_due` with `nextRetryAt` = revert + 48 h exactly (the existing instapay cycle suspends it then if unpaid, proven with `renewSubscription` at 47 h 59 m and 48 h + 1 s); free months it earned are revoked; the reference and image are BURNED in the global index; auto-confirm is switched off for the store until Ahmad re-enables it; the merchant is told once (email + in-app banner with a live countdown). Idempotent: a replay or double tap is `already_reverted`, nothing is written twice. A failed void puts the row back to `auto_confirmed` so the tap can be retried. Cost if wrong: a merchant who really paid is put in a 48 h grace and must re-upload.
- Ruling INSTAPAY-AUTO-1g - compensation: a failed activation releases ONLY the dedupe claim this call made, and only when NO ledger row exists for the payment key (a recorded payment keeps its claim); the row becomes `failed`, the claim stays `pending` for a human, a P1 is raised. A human REJECT of a waiting claim releases its dedupe entries; an auto-confirmed or reverted payment never does. Cost if wrong: a reference could stay blocked until released by hand.
- Ruling INSTAPAY-AUTO-1h - digest and taps go through the OS brain (never a Telegram token in this Worker); one digest a day (07:00 UTC) listing every unlisted `auto_confirmed` payment, cursor-free (stamped rows leave the filter), 200 per page; the brain allows one digest per product per UTC day, so a second page the same day waits for the next run and nothing is lost; P1 when the oldest undelivered row is older than 26 h. Cost if wrong: more than 200 payments in one day are listed a day late.
- Ruling INSTAPAY-AUTO-1i - storage: the decision rows are a platform D1 table (`instapay_auto_confirmations`, migration 0013, in the `payments` family, born on D1); the Prisma/Postgres twin exists only for Node and tests. The per-store switch is a `system_settings` row, not a column on `store_subscriptions`: the cf-schema generator cannot add a Prisma-declared column to a live D1 after 0001. Cost if wrong: the disabled-store list is a prefix scan of `system_settings`.
- Ruling INSTAPAY-AUTO-1j - not built (v1): bank-statement reconciliation (the spec allowed the digest + one tap instead); the Chat product has its own PR; the live rollout (shadow first, then Ahmad's own store, then global) is Ahmad's call per plan task R1 and is NOT done by this PR. Cost if wrong: the mode stays `off` until someone turns it on.

Residuals (documented, not hidden): the typed read is one extra Workers AI call per subscription receipt while the mode is not `off`; the cap and the clean test read ledger rows only; D1 has no cross-table transaction, so the ledger row is committed before the claim is confirmed (the existing manual-payment ordering, healed by an idempotent retry).

## Money-review follow-up (2026-11-14, findings from the Chat review checked on the Store)

- Ruling INSTAPAY-CAP-1 - the first-payment cap is CUMULATIVE over auto-confirmed amounts that are not clean yet (not in a sent digest, not reverted): the cap left = one month of the chosen plan minus those amounts. Evidence: `instapay-auto-review-fixes.test.ts` finding 5. Cost if wrong: a merchant paying two months back to back waits for a person on the second until the digest goes out.
- Ruling INSTAPAY-AUTO-1k - a payment a PERSON confirms also claims its receipt in the global index (P1 if it was already used elsewhere, never a refusal of the human decision); `POST /admin/billing/auto-confirm/backfill` burns every approved receipt, idempotent, dry run by default. A system decision whose ledger row exists is `auto_confirmed` even when the rest of the activation failed (so it is digested and revertable); a `pending_decision` row older than 10 minutes is settled by the hourly sweep; a lost race keeps the claim when the claim ended confirmed; a revert that crashed after its state claim is finished by a replay (every effect idempotent, the notice only with a newly created void). Evidence: findings 1, 2, 3, 9 in the same file (7 of 8 failed before the fix). Cost if wrong: a stuck row is settled up to an hour late.
- Not applicable to the Store: INSTAPAY-REVERT-1 credit removal (Store sells no credits; the void path takes back the period instead). Finding 4 (expected amount = the claim's amount, needs_human when the live price differs) was already in place (`AMOUNT_MISMATCH` when the claim is not the live quoted charge). Finding 7 (release on reject) was already in place and is now tested; Store claims have no expiry path.
- Finding 8: `INSTAPAY_DEDUPE_DB` is bound in `apps/api/wrangler.jsonc` with its own placeholder and migrations (`packages/cf-schema/migrations/instapay-dedupe`); `scripts/ebda-cf-api-config.mjs` substitutes `EBDA_INSTAPAY_DEDUPE_D1_ID` (never the platform D1 id) or drops the binding while it is unset; cf-api-deploy applies its migrations only when the variable is set. Evidence: `instapay-dedupe-binding.test.ts`.
- Ruling INSTAPAY-CAP-1 (atomicity, re-review N2) - decisions of one store are serialised: ONE conditional insert of a lock row (`system_settings` id `instapay.auto_confirm.lock.<store>`, primary key) on the platform D1 decides who runs; the loser gets a retryable `AUTO_BUSY` (job retries, hourly sweep); a lock older than 2 minutes is a crashed run and is taken over; the job's per-store concurrency is 1. Evidence: `instapay-auto-review-fixes.test.ts` N2 (5 concurrent first payments: at most one month auto-confirmed, before the fix 2 were). Cost if wrong: a burst of receipts from one store is decided one at a time, a few seconds apart.
- Re-review N1 (consumption-only spend) does not apply: the Store sells no credits. Expiry: Store claims have no expiry path (reject release is in place and tested). A failed human confirm claims nothing (the claim runs only after the payment committed). The backfill is paged by id, 500 per page (test: 501 receipts).

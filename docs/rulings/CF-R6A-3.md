# CF-R6A-3

Ruling CF-R6A-3 (2026-10-30, INFRA-CF-1 PR R6a) - a shopper's account erasure for a DO store runs its store-owned half in the DO as ONE section, the money op `eraseShopper` (`packages/repo/src/do/erase-shopper.ts`), and `AuthService.eraseAccount` calls it BEFORE its unchanged Postgres transaction (which still erases the platform rows and the pre-cutover copy of the same data); both halves are idempotent so a failure in either converges on retry. The op follows the Postgres function table by table and keeps its legal-record rules: orders survive pseudonymised (customer link, both address snapshots, notes, buyer key, area key go; totals, lines, number stay, Egypt MOF >= 5y), reviews lose only the author link, the wallet ledger is a financial record (notes nulled, remaining balance written off with an `expire` entry keyed to the ledger position, never deleted), the merchant CRM row is scrubbed not deleted and ONLY on a single-row match per identifier (an ambiguous match scrubs nothing and is reported), a campaign mail SENT inside the send-cap window is ANONYMISED (tombstone address, subscriber, customer, provider id and error cleared) and every other row of the address deleted so erasure can never hand a store its send cap back, SMS consent deleted, WhatsApp consent deleted except an unlinked STOP opt-out, Customer Intelligence capture rows lose the buyer key under the erasure flag, webhook payloads lose `data.customer`, receipts are scrubbed and their screenshot ids returned so the Worker deletes the R2 objects after the commits (a miss is retried by the retention sweep). THE SCOPE IS SAVED FIRST: the op's first act, inside its section, is a row in the DO table `erasure_ledger` keyed by the user id (order ids, their buyer keys, the proven number's key, the receipt ids), because those are read from rows the same section unlinks; the Postgres half commits AFTER the DO section, so a failure there would leave a retry that derives an empty scope and loses the Customer Intelligence erase and the screenshot deletes. A replay MERGES the saved scope with a fresh read (the union of saved orders and orders still linked; saved receipts and any receipt of those orders whose screenshot still exists), so an order placed or a receipt filed between the attempts is erased too, and saves the merged scope again (`replayed: true`). The ledger keeps only what a resume needs, ids and hashes (order ids, their buyer-key hashes, the earliest order time, receipt ids, the proven key hash), is a DO runtime table classified customer-pii (deleted by a subject erasure), is left out of backups, and does not outlive the erasure: `eraseAccount` calls the op `finalizeErasure` once the Postgres half committed AND the downstream `account/erased` event was queued (inside the same after-commit step, so a rolled-back request deletes nothing), and the nightly DO alarm purges any row older than 30 days (`purgeErasureLedger`), so a stuck row is bounded by the alarm, not by the next erasure. Evidence: the contract test fails the Postgres half once after the DO step, retries, and asserts the `account/erased` event carries both orders, both buyer keys and the proven key, and the receipt screenshot delete runs; `apps/api/workers-do/erase-shopper.test.ts` (a replay returns the saved scope plus an order and a receipt added between the attempts; finalize deletes the row, twice is a no-op; the alarm purges a stale row), and the contract test also asserts the late order and receipt are erased and no ledger row remains after the finished erasure. The role gate is the guard for admin accounts: anything but `customer` is refused 403 by the service before the DO is reached and again by the op, so a super_admin (and therefore the last one) can never be erased here; the platform `DELETE /admin/users/:id` keeps its own LAST_SUPER_ADMIN rule. Driven by the registry: `tests/unit/erase-shopper-parity.test.ts` fails when a customer-pii table of the generated registry has no verdict (handled / kept like Postgres, with the reason / not a shopper's data), when a handled table is not touched by the engine, when a kept table is deleted from, or when the in-window anonymise does not run before the delete. Kept like Postgres (the registry is stricter, the PDPL job covers them): `customer_wallets` rows (balance 0), `returns`, `shipments`, `audit_logs`, `customer_rfm_snapshots`. Evidence: `tests/integration/repo-factory-erase-shopper-contract.test.ts` (the REAL `AuthService.eraseAccount` on Postgres vs the DO: 14 store tables compared row for row, the user row, the returned outcome, and the send-cap count before and after both 1; the ambiguous CRM case; an admin and a store_admin refused; mutation-proven: disabling the in-window anonymise turns it red), `apps/api/workers-do/erase-shopper.test.ts` (real workerd: 20 concurrent erasures write the wallet off once and keep the cap). Cost if wrong: a shopper row left behind, or a send cap reset; the registry-driven PDPL job is the backstop for the first and the parity test plus the contract test guard the second.

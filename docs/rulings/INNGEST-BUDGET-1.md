# INNGEST-BUDGET-1

> Section: Inngest execution budget (2026-10-22, branch `fix/inngest-execution-budget`)

- Ruling INNGEST-BUDGET-1 (Ahmad 2026-10-22: "make sure not to exceed execution limits") - pre-launch, every polling cron runs HOURLY, an idle tick costs ONE execution, and all crons together are capped at 12,000 executions per 30-day month by `tests/unit/inngest-cron-budget.test.ts`. Evidence: the Hobby plan caps at 50,000 executions a month; 27,313 were used by Oct 22 (about 38k for the month) with 9 functions every 15 minutes (25,920 runs a month), one every 30 and two hourly, and 0 real orders. Inngest bills "a single durable function run or step execution" and states Executions = runs x (steps + 1) (https://www.inngest.com/pricing, plan table and calculator), so an idle sweep that opened `find-*` steps cost 2 to 4 executions a tick. Result by the test's own pricing: 29,638 runs (58,556 priced with steps) down to 10,198 runs, 11,036 priced. The 12,000 budget is that total plus a little slack and leaves ~38,000 for events and retry storms; it is deliberately too tight for a new every-5 or every-15-minute cron or even a new hourly one, so a PR that adds one must edit the number and this ruling together. Cost if wrong: if 12,000 is too low a legitimate new cron is blocked until the number is raised in the same PR (a review step, not an outage); if the hourly cadence is too slow see the per-change costs below.
  - (a) Cadence. Hourly (`7 * * * *`): agent-write-denied-watch, domain-claim-sweep, gmail-alert-poller, instapay-expiry, order-created-stuck-sweep, order-status-fanout-stuck-sweep, payment-abandonment-sweep (was 30 min), queue-depth-watch, refund-reversal-stuck-sweep. Unchanged hourly: heartbeat, payment-reconcile-sweep. Every 30 minutes: payment-webhook-stuck-sweep (`7,37 * * * *`), the one exception: a captured payment whose webhook never reaches the consumer leaves a shopper who HAS PAID on a pending order, and the provider retry is the only other recovery. No document promises any of these intervals (grep of docs/, the admin and web copy found only ENVIRONMENT.md describing them, now updated). Cost if wrong: order-created, order-status-fanout and refund-reversal recovery of a lost enqueue is 10-70 minutes, not 10-25 (a delayed confirmation email or restock, still recovered); instapay-expiry cancels an unconfirmed hold up to an hour late on a 24-48h hold (stock freed an hour later); domain-claim-sweep serves a verified custom domain up to an hour late and the 72h claim TTL is unaffected; payment-abandonment-sweep nudges the merchant up to an hour later than its 30-minute threshold (Enterprise feature, 0 stores); queue-depth-watch and gmail-alert-poller (not served on Workers) alert up to an hour later; payment-webhook-stuck-sweep detects in 10-40 minutes.
  - (b) agent-write-denied-watch window. `DENIAL_WINDOW_MINUTES` is 61 (cadence plus the one minute of overlap it always had), because the watcher must read back as far as the last tick. The per-window thresholds are unchanged, so an hour of denials reaches them sooner than 16 minutes did. Cost if wrong: a slightly noisier watcher (an alert on 3 platform faults or 50 anonymous denials in an hour, not in 16 minutes); it can never alert later than before.
  - (c) Empty-run exit. New `lib/inngest/empty-exit.ts` `stepRunUnlessEmpty(step, id, read)`: the read runs un-stepped first and the tick returns when it is empty; otherwise the same read goes through `step.run` so later steps see a stable memoised snapshot. Applied to every first `find-*` step of payment-webhook-stuck-sweep, order-created-stuck-sweep, order-status-fanout-stuck-sweep (both finds), refund-reversal-stuck-sweep (whole-order, partial-return and refund-claim finds), instapay-expiry, payment-abandonment-sweep and payment-reconcile-sweep; domain-claim-sweep loses its single `step.run` wrapper (the sweep is one idempotent unit; a failure retries the run, `retries: 1`). Idle cost per tick: 1 execution, was 2 to 4. Cost if wrong: Inngest re-enters a handler once per step, so on a later pass the un-stepped read can come back empty because the work just landed, which ends the run early and skips only a very-stale alert or resend about rows that have since cleared; and every pass of a run that HAS work pays the read twice (bounded by each sweep's take cap of 200 to 500 rows, on a path that runs only when something is stuck).
  - (d) Merging the hourly sweeps into one cron function was evaluated and rejected. Steps are billed, so one function with N sweep steps costs N + 1 per tick, against N with empty-exit (one per function), and it would collapse per-function retries, concurrency limits and the function-id keyed dead-letter alerts (`alerts-failure-watch`). Cost if wrong: none today, it is not built; revisit only if Inngest changes how steps are billed.
  - (e) The gate. `tests/helpers/inngest-cron-budget.ts` reads every `createFunction({ id, triggers: [{ cron }] })` out of `lib/inngest/functions/*.ts` with the TypeScript AST (no module loading), prices fires per 30-day month times (1 + empty-path steps), requires the file to be imported by `functions/index.ts`, and fails above 12,000 or on any cron firing more than every 30 minutes. `EMPTY_PATH_STEPS` in the test declares 0 for the twelve high-frequency crons and defaults every other cron to 1 step (conservative). Mutation-checked 2026-10-22: a daily cron turned `*/15` (16,736), heartbeat turned `*/5` (18,956), instapay-expiry reverted to `*/15` (13,196), budget lowered to 11,000, the AST matcher blinded, three declarations dropped (13,196) and `stepRunUnlessEmpty` made to always open a step each fail the suite. Cost if wrong: a declaration of 0 for a function that does open a step on an idle tick under-prices it; the empty-tick cases added to the order-created, order-status-fanout and refund-reversal suites and `tests/unit/inngest-empty-exit.test.ts` pin three of the twelve, the rest rest on the declaration and review.
  - (f) Revisit all intervals at launch, when real orders exist (register line in `docs/architecture/inngest-execution-budget.md`; Ebda program register, section 6). Cost if wrong: the launch goes out on pre-launch cadences and a first lost-webhook or late-confirmation incident is found by a shopper before the dashboard.

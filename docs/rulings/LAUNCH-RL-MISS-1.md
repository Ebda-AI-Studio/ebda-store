# LAUNCH-RL-MISS-1

> Section: Launch blocker 2026-11-09 (branch `fix/public-limiter-counts-success`): successful storefront calls spent the store-miss budget

Ruling LAUNCH-RL-MISS-1 - the store-miss limiter (`rl:store-miss`, 20 unknown-store 404s per minute per IP, every public route) READS its counter before the handler and counts a miss only AFTER a 404 response was sent; a response that is not a 404 never writes the counter. The limit, the window, the key, the 429 body, fail-open on a counter outage and the no-client-IP skip are unchanged. Measured in production 2026-11-09 before the fix: seven sequential 200s on `GET /public/<store>/products/<id>/recommendations` returned `ratelimit-policy: 20;w=60` with `ratelimit-remaining` 19, 18, 17, 16, 15, 15, 14, and the pre-QA sweep saw add-to-cart answered 429 and an empty product listing; Egyptian carriers put many shoppers behind one IP. Cause: the limiter was express-rate-limit's `skipSuccessfulRequests`, which counts EVERY request up front and gives the hit back after the response. Measured on local workerd (the built Worker, the real AuthState Durable Object): every 200 carried `ratelimit-remaining: 19` (its own hit), and 30 parallel 200s from one IP were answered 20 x 200 + 10 x 429, so requests in flight spent the miss budget even when every give-back landed. Inferred, not reproduced: in production the give-back (`unhit`, a Durable Object call started after the response and not handed to `waitUntil`) was dropped when the request ended, five times out of six; local workerd lets such a call finish (25 of 25 landed), so no workerd test can fail on the drop itself. After: `apps/api/workers-test/failure-only-limiters.test.ts` (workerd, in the CI workerd job): 25 sequential and 30 parallel successes from one IP are all served with the counter at 0 and `ratelimit-remaining` 20; 20 misses are answered 404 with the header falling 20..1, miss 21 is 429 `RATE_LIMITED` with `Retry-After`, the counter stops at 20, another IP is unaffected. The read rides the PERF-RL-DO-1 batch as `get` + `pttl` (existing Durable Object ops, so a Worker and a Durable Object of different versions agree during a deploy): a store resolve is still ONE AuthState call. The `RateLimit-*` headers of this limiter now carry the misses left BEFORE the response (flat across hits, falling across misses).

Accepted residual: reading then counting is not atomic. Misses already in flight when the budget runs out are still answered 404, so one IP can pass 20 misses in a minute by the number of misses it has in flight, and a miss sent before the previous miss's count landed is not seen. The atomic per-IP public limiter in front of it (`rl:public`, 300 per minute per IP, or the native per-IP limiter on the fast path) bounds that, and each extra miss costs one store lookup. The alternative, keeping the atomic count-then-give-back, is what made honest shoppers pay for it.

Unchanged and worth knowing: the limiter counts ANY 404 of the public router (an unknown product or page of a real store too), and an IP at 20 misses is refused on the whole public router until the minute ends.

Cost if wrong: an attacker rotating unknown slugs gets as many extra free store lookups per minute as it has requests in flight, capped at 300 per minute per IP by the public limiter, instead of exactly 20.

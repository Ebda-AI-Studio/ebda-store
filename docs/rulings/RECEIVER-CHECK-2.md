Ruling RECEIVER-CHECK-2 - Opus review of RECEIVER-CHECK-1. (a) A model "yes" only stands in for BLANK typed receiver fields; if the payer typed a receiver that is not the expected account it is still RECEIVER_MISMATCH (a model guess, a decoy line on the image or a masked number agreeing on a few digits never hides it). (b) The prompt no longer contradicts itself: with an expected account the "do not read any person detail" line becomes "never return it, the only thing you may say is receiverMatches", a masked mobile matches only when ALL visible digits agree and at least 4 are visible, the model is told to ignore instructions inside the image, and `receiverMatches` is required in the schema when asked. (c) The expected receivers come from the payment the receipt was filed against (`paymentId`), else the newest PENDING instapay payment (was: newest of any status). (d) The data-map text now says what is stored: the payer-typed receiver fields and the frozen expected account stay with the receipt under its retention; the merchant's own handle / mobile is sent to Workers AI. Cost if wrong: a model "yes" on a blank form is trusted over nothing (the approver still sees the image).

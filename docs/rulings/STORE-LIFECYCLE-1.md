Ruling STORE-LIFECYCLE-1 (SELF-SERVICE gap A11, 2026-11-14) - a store OWNER deletes their own store and exports its data without a super admin. (a) Delete: `POST /stores/:storeId/deletion/preview` returns the named guard reasons (money in flight, billed store subscription, billing parent with sibling stores) or a single-use HMAC confirm token bound to (store, owner, slug); `POST /stores/:storeId/deletion` needs that token AND the typed slug (a wrong slug does not spend the token), re-checks the guards, writes `settings.deletionRequest` (a SERVER-OWNED settings key, so no generic settings write can plant or revert it) as `pending` with `executeAfter` = now + 14 days, audits `STORE_DELETION_SCHEDULED`, emits `store/deletion.scheduled` and emails the owner when the session carries an address; `DELETE /stores/:storeId/deletion` cancels (owner, while pending); the Inngest job `store-deletion-execute` sleeps until `executeAfter`, re-reads the request (cancelled / replaced / not due stops it), re-checks the guards (blocked: stays pending with `lastBlock`, re-checked daily for 30 days, then a P1 alert) and calls `StoreService.delete`, which keeps its own money-in-flight refusal, fiscal archive and anonymisation (MONEYB-4, FOLD-ERASURE-2). (b) Owner = `store.ownerId === userId`; staff, non-owner store admins and impersonated sessions are refused; the store id is the path param, never the body. (c) Export: `GET /stores/:storeId/export`, owner only, one zip of NDJSON per table (product, category, order+items, customer, coupon, review, return, expense) plus `manifest.json`, synchronous, 20000 rows in total, 1 per store per hour; above the cap a plain 413 `EXPORT_TOO_LARGE` (an async job is NOT built); credential tables are not listed. (d) Super-admin override unchanged: `DELETE /stores/:id` stays `authorize('super_admin')` and immediate (support and test stores). (e) Evidence: tests/unit/self-service-store-lifecycle{,-routes,-export}.test.ts, apps/admin settings `OwnerStoreLifecycle.test.tsx`. NOT verified: a live Inngest 14-day sleep, a live Durable-Object store (its money check runs at execution inside `StoreService.delete`, the preview cannot read it without a close-and-reopen probe), the email send, a real browser run. `requireMfaEnrolled` binds only super_admin and there is no fresh-password helper, so the merchant step-up is the typed slug + single-use token. Cost if wrong: a lost scheduling event means a requested deletion never runs (fails safe, the request stays visible and cancellable); a guard that flips to allowed wrongly would delete a store the owner confirmed 14 days earlier, which is why the checks run again at execution.

Amendment (Opus review of #772, same day). (f) A money-in-flight / billing-parent 409 thrown by `StoreService.delete` at execution (the only place a Durable-Object store's money can be read) is mapped to BLOCKED: `lastBlock` on the request, an audit row `STORE_DELETION_BLOCKED` per attempt, back to `pending`, re-checked daily for 30 days, then the P1 alert; it is never a silent job retry. (g) At execution the requester must still be `store.ownerId`; a transfer during the window cancels the request (`voidedReason: owner_changed`, cancelledBy `system`, audit `STORE_DELETION_VOIDED_OWNER_CHANGED`); no address is stored on the request, so the owner notice is the audit row only. (h) Execution is `pending -> executing` by compare-and-set (one conditional UPDATE on Postgres; read-after-write on a Durable-Object store, whose settings patch has no condition, so a two-call window remains there); a cancel that loses the race, or arrives during `executing`, is refused 409 `DELETION_IN_PROGRESS`; an `executing` request left by a crash is resumed by the job's retry. (i) `super_admin` can read and cancel any store's pending deletion (audited with `byRole: super_admin`; preview, schedule and export stay owner-only). (j) The store's VAT-registration change records (#774: `system_settings` rows `tax.change.<storeId>` and `tax.change-result.<storeId>` plus the private evidence object named in the first) are purged after the delete on every store (`lib/tax-change-purge.ts`, a retried, alerted `anonymiseDeletedStore` step; object first, then rows); the keys are mirrored here, not imported, so the PR does not depend on #774 (a store without such rows is a no-op). Cost if wrong: a DO store whose block never clears keeps its request pending until the 30-day alert; a DO compare-and-set lost in the two-call window could still delete a store whose cancel landed in that window.

Amendment 2 (re-review of #772). (k) C1: the owner's deletion no longer runs `StoreService.delete` as a would-be super_admin (which threw "not an active super_admin" for the owner and rolled everything back): `StoreService.delete(storeId, ownerId, { ownerRequest: { requestId } })` skips the platform-operator step, so the owner's account is NOT removed with the store (closing the account is the separate closure flow). (l) C2: `store-deletion-execute` has an `onFailure` that compare-and-sets `executing` -> `pending` (`lastBlock.code = EXECUTION_FAILED` + reason, audit `STORE_DELETION_EXECUTION_FAILED`) and raises a P1 alert; `FISCAL_ARCHIVE_FAILED` (503, #821) is a BLOCKING code like money in flight. (m) M1: on a Durable Object store the compare-and-set is a precondition (`expect`) on the StoreDO `patchSettings`, checked inside its synchronous transaction; the two-call window of amendment (h) is gone. (n) M2: the export needs the same single-use step-up token (`POST /export/preview` then `POST /export`; the old `GET` is removed) and the owner is emailed on every export at the identity-service address of the OWNER account, never one the request supplies. (o) M3: the Postgres money check counts `customer_wallets balance > 0` and unsettled `affiliate_payouts`, as the DO check does. (p) M4: scheduling EMITS the event first and saves the request second, so a failed send leaves nothing pending (no 409 on retry); a save that fails after a send leaves an event whose job finds no such request id and ends. (q) m1: the owner is emailed on execution and when a request is voided. m3: at most 200 lines per order in the export.

Ruling DEL-FLAG-1 - owner self-delete respects `PDPL_CF_ERASURE_ENABLED`. The post-delete anonymisation of a Durable Object store (`anonymiseDeletedStore` eraseDo / D1 / payments) is the erasure step this flag gates (`cf/erasure/job.ts`). Decision: while the flag is not "true", the owner deletion of a DO store is REFUSED, never run without erasure: guard code `ERASURE_NOT_ENABLED` at preview, schedule and again at execution (request back to `pending` with `lastBlock`, re-checked daily, P1 alert after 30 days), the same honest "nothing erased, not enabled" semantics as the merchant account closure (503 `ERASURE_NOT_ENABLED`, S3). A Postgres store is not gated: its people are removed by the delete's own cascade and only the VAT-record purge runs. The super_admin `DELETE /stores/:id` is unchanged. Evidence: tests/unit/self-service-store-lifecycle.test.ts (M5). Cost if wrong: while the flag is unset (today, everywhere) no owner can delete a Durable Object store themselves; support still can via the super_admin route.

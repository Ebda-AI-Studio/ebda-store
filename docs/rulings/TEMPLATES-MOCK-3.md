# TEMPLATES-MOCK-3

Ruling TEMPLATES-MOCK-3 - how a mock trait ships without changing a merchant's saved choice (the "new visual features default OFF" rule, `CLAUDE.md` UI/UX rule 2, read for what it is FOR: never surprise a merchant who chose something). Each trait is an OPTIONAL `StoreTheme` key that is ABSENT until the merchant picks a value in the editor; the look (`MOCK_TOKENS` / `traitDefault`) supplies the mock-faithful default. Precedence merchant > look > skin. So: (a) a store that has SAVED the setting keeps it byte-for-byte; (b) a store that never touched it picks up the mock default, which is the intended change and the only one; (c) a store with NO look (`stores.look` null, legacy) is untouched, except the lockup, which TEMPLATES-MOCK-1 already makes a built-in for a logo-less store; (d) a merchant logo always beats the lockup; (e) every trait has a value that restores the previous behaviour (`plain`, `landscape`, `always`, `regular`, `on`), a `reset` that deletes the key, and a design reset clears it with the look's other keys. Rule 2's "utility fills empty space may default ON" is the category used: these defaults replace a worse use of the same space (a 41 px notice strip, a 76 px permanent tab bar), they add no new element. Evidence: `traitDefault` / `resolveLockup` unit tests and the editor-matrix rows. Cost if wrong: a store that never customised sees the mock look instead of the old one until it picks the old value; no stored data changes.

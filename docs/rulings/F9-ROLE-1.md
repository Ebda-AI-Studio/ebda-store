Ruling F9-ROLE-1 - the Workers database role guard (`apps/api/src/cf/database-role-guard.ts`, run by `checkRole()` in `worker.ts` on every request's first lease per isolate) now also refuses a role that OWNS a `public` table with RLS enabled but not FORCEd (`pg_class.relowner = role AND relrowsecurity AND NOT relforcerowsecurity`), alongside the existing BYPASSRLS / superuser / unverifiable refusals. Why: a table owner is exempt from its own RLS unless FORCE ROW LEVEL SECURITY is set, so Hyperdrive pointed at the migration role (`neondb_owner` without BYPASSRLS, or any `NOBYPASSRLS` owner) passed the old guard while serving every store's rows. The unknown case fails closed too (`ownsUnforcedRls` must be exactly `false`). The refusal throws per request, so a deploy pointed at an owner role fails the post-deploy `/health` + unknown-store probes and auto-rolls back (DEPLOY-SAFETY-2); it cannot serve.

Evidence. (1) Prod today, measured 2026-10-29 read-only: `wrangler hyperdrive get 27ddf4cdf7c84a7abc65f4b12043c20a` (the id in repo variable `EBDA_HYPERDRIVE_ID`, account 69188202...) returns `name: ebda-neon`, `origin.user: "ebda_app"`, `caching.disabled: true`, host `ep-plain-mode-b2omn7jh-pooler...neon.tech`; no credential was read or changed. `api.ebda.app/health` is 200 on `beef621ce` and every request goes through the old guard, which rejects any role with `rolbypassrls OR rolsuper`, so prod is serving as a non-bypass, non-super role. (3) `tests/unit/cf-database-role-guard.test.ts` gained the owner and unknown-ownership cases (red before the guard change, 8/8 after).

# PROVIDERS-ACTIVATION-2

> Section: self-service gap A7 / task 12 (2026-11-14, branch `feat/self-service-providers`)

Ruling PROVIDERS-ACTIVATION-2 - turning a provider on needs NO super admin, and the merchant's own "Test and turn on" is the activation. Premise check: the audit row "merchant tests, then a super admin re-tests and activates" was already false in code since PROVIDERS-3 (2026-10-25): `provider-gate.ts` `isProviderUsableForStore` accepts every catalog provider, the enable gate is only `assertEnableAllowed` / `assertCarrierEnableAllowed` (a passing test of exactly the stored credentials), and nothing reads an `activated` request row any more; the request panel was never mounted. The real gaps closed here: (1) no confirm step on a checkout-visible switch and no ledger, (2) failures had only the fixed code-mapped sentence, (3) no P1 at the moment a store turns on an unverified provider, (4) stale "we activate within about 5 hours / request activation first" copy (admin i18n en+ar, the ops email, docs), (5) the super admin could not turn a provider off for one store. Built: `POST /provider-activation/store/:storeId/:provider/activate/preview` (the SERVER runs the connection test, the body is ignored, so a result can never be forged; a pass returns a confirm token, a failure returns `{check, triage}` and no token) and `.../activate/confirm` (confirm token from `mcp/merchant-confirm-token.ts`: HMAC bound to tool + store + user + a hash of {provider, mode, that exact test run}, 2 minute TTL, single use via atomic claim, fail closed; `Idempotency-Key` required via `withIdempotencyKey`; the CURRENT stored test must still be ok + current; then the provider is enabled through the existing gates, the request row becomes `activated`, one append-only ledger row `activation.activated_self` is written and `provider_activation.self_activated` audited; a failed write after the enable switches it off again and frees the key). Tenant comes from the path + `requireStoreAccess` + owner check, role from auth (`store_admin` / `super_admin`, `store:settings`, MFA, not impersonated); a per-store+provider limiter (10 per 10 min, super_admin exempt) guards the provider call and the AI call. Ledger = the `activation.*` ops of `provider_verification_events` (migration `20261114000100`: a trigger refuses UPDATE and DELETE of those rows; ref = the request id, the actor is on the audit row) so no new platform-family table was needed; `recordProviderOperation` ignores those rows when deciding "first REAL use". P1 (decision PROVIDERS-3): turning on a provider nobody has verified raises a store-scope P1 `provider.activation.first_connection` (titled "First connection" when no store ever activated it). AI triage: `AIService.triageProviderCheck` gets provider + mode + the machine code + our fixed English reason (never keys, never a provider body), returns {en, ar} validated by zod and a no-URL / no-token-run filter; any AI problem (disabled, quota, bad shape) falls back to the fixed `describeConnectionCheck` sentence, and `unreachable` never spends an AI call; AI never decides pass or fail. Super admin overrides kept: `activate` (still needs the store's own passing test; no force past the money gate, annotated in the route) and the new `POST /admin/provider-activation/:storeId/:provider/deactivate {note}` (switches it off, closes the activated row, emails the merchant, ledger `activation.deactivated`). Evidence: `tests/unit/self-service-provider-activation.test.ts`. Cost if wrong: a merchant can turn on a provider whose test passes but whose payment flow is broken (the same exposure PROVIDERS-3 already accepted; the P1 and the first-order watch are the control); the old `POST /payment-settings/store/:storeId/:provider/toggle` and the carrier PUT still enable with only the test gate (no confirm token) for API callers, so the confirm step is enforced in the admin UI path, not yet at those two routes; AI triage uses the existing Gemini service, not Workers AI (project 2 moves it).

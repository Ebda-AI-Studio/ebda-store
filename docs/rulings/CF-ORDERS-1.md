# CF-ORDERS-1

Ruling CF-ORDERS-1 (2026-10-29, INFRA-CF-1 PR D2b-2) - order creation and the money-moving status changes are four named StoreDO operations behind `moneyOp`: `createOrder` (stock reservation, hold cap, coupon usage limit, loyalty redeem, wallet debit and the order rows in ONE `transactionSync` section), `confirmPayment` (InstaPay), `cancel` (status plus the whole reversal) and `expireHold`, each with an optional marker-row idempotency key (`_money_ops`, CF-MONEY-1); the engines (`do/checkout.ts`, `refund.ts`, `payments.ts`) already existed and are now reachable only through the registry, which never takes `storeId` or `now` from the caller. The Worker side is `OrderService.createOnDo`, `OrderService.cancelOnDo`, `InstapayService.confirm`/`expireOne` behind `storeMoney()`; with every flag at `pg` the Postgres code runs unchanged. The state machine is the existing one (`assertValidTransition` on the DO-read status, `INVALID_TRANSITION` in the engine); external payment facts are recorded in full, never rejected (feedback-never-reject-an-external-money-fact). FOUND by the contract test and fixed in the engine to equal Postgres: sale ledger rows carried a positive quantity, `loyalty_points_redeemed` was 0 instead of NULL, no sale reason; refusals are translated to the Postgres codes and statuses. Evidence: `docs/cf/orders-on-do.md` (map of every read and write of the Postgres transactions), `packages/repo/test/do-order-ops.test.ts` (9), `tests/integration/repo-factory-orders-contract.test.ts` (5 scenarios through the real `OrderService`, Postgres 17 vs the DO schema, equal traces and tables), `apps/api/workers-do/orders.test.ts` on real workerd (60 concurrent orders for 25 items sell exactly 25; a coupon with 7 uses under 40 orders is used 7 times; a wallet of 5000 under 30 orders pays 5 and ends at 0; hold cap 2 under 20 orders holds 2; one key x20 creates one order; 20 concurrent cancels restore stock once; confirm racing expiry has one winner). Bundle 8,157,961 bytes (budget 8,300,000), gzip 2,240,482 (budget 2,400,000), startup CPU 102.7 ms vs 100.8 ms on the base. Cost if wrong: with every flag at `pg` the order services run their Postgres code unchanged; a wrong DO order write is reachable only for a store the operator flipped (one D1 UPDATE back) and the cutover gate still forbids a flip until carts, fiscal documents, the order reads and payments/refunds/ledger move.

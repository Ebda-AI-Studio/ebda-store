# CF-LAST-2

Ruling CF-LAST-2 (2026-10-29, INFRA-CF-1 PR D2b-5, found by the controller's sweep) - the FOUNDING-1 `billing_grants` append-only guard is ported to the D1 platform database, closing the "NOT YET PORTED" of CF-SCHEMA-GRANTS-1. `migrations/platform/0002_invariants.sql` gets `billing_grants_guard_delete` (every delete refused, no cascade exemption: grants have no parent FK, like Postgres) and `billing_grants_guard_update` (immutable identity/source/money columns; revoked needs `revoked_at` + `revoke_reason`; `revoked_at`/`restored_at` only on a revoked grant; applied needs its period bookkeeping; pending -> applied | revoked, applied -> revoked only with bookkeeping untouched, a revoked grant is final except `restored_at` set once), one `RAISE(ABORT)` per Postgres `RAISE EXCEPTION`, same wording. `docs/cf/fn-map.json` maps the three functions/triggers as ported. Evidence: `packages/cf-schema/test/platform.test.ts` (+4: deletes and every immutable column, pending moves, applied moves, revoked finality); a one-off parity run of 68 transitions (4 start states x 17 updates) on real Postgres 17 (the migration's own function and triggers) vs the D1 triggers agreed on 65, the 3 differences being an artefact of the script (`created_at = now()` compared with a literal on SQLite, while the same-millisecond now() equals the stored value on Postgres) - the committed test pins the SQLite refusal of a changed `created_at`; the parity script is not committed. The Postgres side stays covered by `tests/integration/billing-grants.test.ts`. Not verified: the guard under D1 itself (node:sqlite runs the same triggers; D1 is SQLite). Cost if wrong: after the billing cutover to D1 a grant could be rewritten at the DB level where this guard has a gap; the application code (`grants.service.ts`) still enforces the moves.

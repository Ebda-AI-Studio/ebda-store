# CF-R7-4

Ruling CF-R7-4 (2026-10-30, INFRA-CF-1 R7 security sweep, Ahmad via the controller) - the StoreDO write RPC guard is enforced by the EXECUTOR, not only by a static scan, after a review of the FWB twin's DO write RPC found three bypass classes; Ebda's `packages/repo/src/rpc/writes.ts` had the first two in a different shape, and not the third. (1) PARSER DIFFERENTIAL: `checkMutation` looked for the op model's own stock column NAMES anywhere in `data` / `create` / `update` (key scan, depth cut-off 6, fail OPEN) and for `DO_WRITABLE_MODELS` on the top-level model only, while prisma-lite's executor walks nested writes by relation. So a writable parent could create or update rows of models the DO write path does not own: `Product.update({ data: { warehouseStock: { create } } })` and `{ inventoryHistory: { create } }` (the stock tables), `CartItem.create({ data: { product: { create: { inventory } } } })` (a stock column on a model whose own list is empty), and a value nested past depth 6. Fix: `WriteEngine` takes a `WriteGuard` (`{ writable, stock }`) and calls `allow(model, data)` at every point it inserts, updates, deletes or links a row (`insert`, `applyUpdate`, `deleteByPk`, owner `connect` and the found branch of `connectOrCreate`), at any depth and through any nested operation, so the guard reads nested args exactly the way they run and an operation the executor does not know (a bare `update` with no `{ where, data }`, an unknown nested key) throws instead of being skipped. `runWrites` binds the guard through `client.$guarded(WRITE_GUARD)`; a client that cannot bind it is refused (`NO_WRITE_GUARD`), never run unguarded. The static depth cut-off now fails CLOSED. (2) CONNECT: `Product.update({ data: { orderItems: { connect } } })` re-parented a money row (an order line) without any check; the executor guard refuses every nested connect, disconnect, set, update and delete whose target model is not writable (`MODEL_NOT_WRITABLE`). (3) PLACEHOLDERS: Ebda's wire has no `$ref` / placeholder resolution (args are decoded once, then run), so there is no guard-before-resolution window; with the guard inside the executor there is none by construction, and `$ref`-shaped values are literals the executor rejects as unknown fields. Evidence: `packages/repo/test/rpc-write-guard-bypass.test.ts` (11 tests; every class has an OLD half that runs the previous static check then an unguarded client and shows the rows landing, and a NEW half through `runWrites` that is refused with nothing written; a control shows a nested connect to a writable model still works). Existing suites unchanged: `packages/repo/test` 541 pass, workerd `cf:test:do` 131 pass. Cost if wrong: a legitimate nested write to a model missing from `DO_WRITABLE_MODELS` is now refused as an answer (add it to the list with a ruling) instead of silently landing; with every flag at `pg` nothing here runs.

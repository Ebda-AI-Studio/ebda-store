# CF-R4-5

Ruling CF-R4-5 (2026-10-30, INFRA-CF-1 PR R4, Ahmad via the controller; job layer per CF-JOBS-1 and CF-JOBS-2) - the abandoned-cart jobs run for a DO store. (1) DETECTION AND REMINDERS (the 15-minute legacy cron `abandoned-cart` -> `abandonedCartService.process`): `detectNewAbandonments`, `processReminders`, `sendStep`, the config and the record writes go through `storeDb` / `storeWriter` / `storeRepo` per store. A DO store cannot join the platform `User`, so its candidate query reads carts by `customerId` or consented guest e-mail, attaches the customers (`withCustomers`, as the admin reads already do) and keeps the carts whose customer has an e-mail or a phone, the same set the Postgres relation filter selects; its `store` relation is attached with `withStore`. The legacy cron is not a guarded job, so its `storeDirectory` lists DO stores too and one pass serves both backends; CF-JOBS-2 is unchanged (the write freeze skips or parks the legacy cron as before). (2) RECOVERY COUPON: the step-3 coupon is a money model, so it is a named op `recoveryCoupon`: create-or-re-activate by the derived code, new expiry, and the link to the cart in ONE section (Postgres did an upsert and an update as two statements). (3) E-MAIL CHANNEL: `sweepCartRecoveryEmails` (the NULL -> queued claim, stale and stuck handling) and `deliverCartRecoveryEmail` (cart state, config, consent, daily cap, the stop-on-convert re-read, the sent / failed finish) use one helper `inStore`: the Postgres tenant scope for a Postgres store (unchanged), none for a DO store. (4) THE JOBS: `cart-recovery-email` (its `onFailure` marks a still-queued row failed through the store's writer) and `abandoned-cart-purge-weekly` (count, find and delete through the store's repo; its alarm run for a DO store is the existing per-store alarm) are added to `PORTED_JOBS`, so the jobs guard no longer refuses them for a DO store and a Postgres store behaves as before. (5) EVIDENCE: `tests/integration/repo-factory-carts-contract.test.ts` "abandoned-cart detection, reminders, recovery coupon and the e-mail claim": a customer cart, a consented guest cart and a cart nobody can reach go through detection (2 records, never 3), three reminder rounds (the dispatches and the status chain), the step-3 coupon (one coupon, linked), and two e-mail sweeps (first claims, second claims nothing, events emitted) with equal rows and equal dispatches on real Postgres 17 and on the DO schema; real workerd (`apps/api/workers-do/newsletter-carts.test.ts`, where Postgres used a conditional UPDATE): 30 concurrent sweeps claim a cart's e-mail exactly once (and the finish once), 25 concurrent step-3 sends for one cart create ONE coupon and link it. Residual, accepted: the PUSH / SMS reminder dispatch (`notificationDispatcher`) still reads the store's notification config from Postgres, as before this ruling; and `campaign-send` stays unported (CF-R4-4). Cost if wrong: a missed or doubled reminder e-mail; the claim is a conditional write on both backends so a double send needs two failed claims, and Resend's idempotency key is the last guard.

# WALLET-DO-TX-1

Ruling WALLET-DO-TX-1 (2026-10-30, INFRA-CF-1 R3, security review) - a wallet movement of a Durable Object store runs on the DO ONLY when no Postgres transaction is open around it. `WalletService.applyEntry` for a DO store (a) takes the `walletEntry` money op (ledger row, balance and the WALLET-GL-1 journal half in ONE DO section, `do/refund.ts` `applyWalletEntry` + `do/ledger.ts` `postWalletMovementJournal`) when it is called with no client and no ambient tenant transaction (`currentTenantGucs()` undefined), and (b) is REFUSED `501 WALLET_IN_TRANSACTION_NOT_ON_DO` when it is called with a client or inside an ambient tenant transaction (return completion with a store-credit refund, erasure forfeit, order create). Reason: a DO write cannot roll back with a Postgres transaction. If the transaction failed after the credit, the credit stayed and the retry (a new request key, a fresh refund key) credited again - a double refund. The refusal is listed in `docs/cf/not-on-do.json`; it closes when each of those callers becomes ONE DO section (return completion is R1's `moneyOp`, branch `feat/cf-r1-returns`). The class was swept: every other `storeMoney` caller (`order.service` create / cancel / refund, `loyalty.service`, `order-posting`, `refund-posting`, `payment.factory`, `instapay.service`) calls an op that is idempotent in the DO's own data (an order-keyed marker, a unique ledger row, a source id), so a replay after a rolled-back Postgres transaction converges instead of doubling; only the wallet took a caller-supplied key. Evidence: `tests/integration/repo-factory-wallet-contract.test.ts` (the Postgres transaction fails after the wallet write: refused twice, no wallet row, no credit; a caller client is refused; outside a transaction the same credit applies once and its retry replays). Not verified: the admin adjustment route, which may run inside the request's tenant transaction, is refused for a DO store by the same rule until it opens no transaction around the call. Cost if wrong: a merchant's manual credit on a DO store is refused (501) instead of applied until that route is moved off the request transaction; no money moves.

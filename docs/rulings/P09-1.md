Ruling P09-1 (audit M-022, M-062, M-063, M-128) - refund and inventory writes are serialised or relative. (a) M-022: `receivePurchaseOrder` takes `FOR UPDATE` on the purchase order BEFORE reading it, so concurrent receives (double click, two staff) see each other's receipt and the qty guard / `qtyReceived` are judged on the locked state; the non-variant product stock write is `{ increment }`, not an absolute `onHandBefore + n` built from an earlier read (the variant branch already incremented), so a customer order that decrements the shelf during a receive is no longer overwritten. (b) M-062: the billing refund idempotency key is numbered by ALL prior attempts (`refund:<charge>:<n>`), not only the pending/succeeded ones, so a rejected or failed refund can be retried; only succeeded rows count toward `remaining`, and a pending one still blocks. (c) M-063: `InstapayService.recordRefund` takes the order row lock (the same one confirm/expiry/cancel use) and the payment row lock, then RE-READS the payment, so the duplicate-reference check, `remaining` and the `refunds` metadata array are judged on the locked row (a double submit records once; two different references cannot over-refund; neither record is lost). (d) M-128: admin `POST /payments/refund` runs `PaymentService.refund` (which commits its own claim and completion), then writes the audit rows on their own transaction; a failure there logs, raises a P1 `payment.refund.audit_failed` alert and still answers 200, and the audit `toStatus` is read back from the payment instead of a pre-refund snapshot. DO side: none of PO receive, the InstaPay refund recorder or platform billing refunds exist in the StoreDO engines yet; when PO receive / the recorder are ported they must be ONE `transactionSync` (the DO is single-writer, so the same guard is then structural) with a workerd test. Evidence: tests/integration/accounting/po-receive-concurrency.test.ts (6 concurrent receives -> 1; 25 sales during a receive keep the shelf exact, 3/3 absolute-write mutations caught), tests/integration/instapay-refund-lock.test.ts (lock mutation fails 2/3), tests/integration/subscription-billing.test.ts (rejected refund retried; key mutation caught), tests/unit/payment-refund-audit-status.test.ts (audit failure -> 200 + alert; mutation caught). Cost if wrong: a PO receive now waits on its own PO row lock (one receive at a time per PO); a lost audit row after a refund is an alert plus a manual entry.

Ruling P07-1 (audit M-012) - one cart, one order. (a) `OrderService.create` takes the cart row lock inside the order transaction and re-reads the cart under it: what is there NOW must equal, line by line (cart item id, product, variant, quantity; box id, bundle, quantity), what was priced, not just the number of lines (a tab that swapped A for B or changed x1 to x5 kept the count and had its cart silently eaten). The cart rows are then deleted with a count check; any mismatch is 409 CART_CHANGED and nothing else was touched (stock, coupon, wallet and loyalty are in the same transaction). (b) `Idempotency-Key` (8-128 chars) is stored as sha256(session | key) in `orders.checkout_idempotency_key` (unique per store) with `checkout_request_hash` = sha256 of what the shopper asked for (address, payment method, coupon, points, wallet, notes, delivery slot; `expectedTotal` is a guard, not intent). The same key + same request returns the first order (also for concurrent requests: the loser of the P2002 race returns the winner); the same key with a CHANGED request is 409 IDEMPOTENCY_CONFLICT (a shopper who switched from COD to a card must not get the COD order back). The storefront sends one key per attempt, keeps it across retries and clears it on success, CART_CHANGED and IDEMPOTENCY_CONFLICT. (c) DO twin (`placeOrder` with `input.cart`): the claim compares the cart rows with the ordered lines and boxes by content and deletes them in the same `transactionSync`; the key is scoped to the cart (`<cartId>:<key>`) so another shopper cannot read an order back with a guessed key. NOT WIRED / NOT VERIFIED: `input.cart` is optional and no production caller passes it yet (`placeOrder` is only reached from tests and workers-test), so the DO claim fails OPEN until the DO checkout route is wired and must pass it; the `do` backend of POST /public/orders (storeDo().createOrder spike) ignores the Idempotency-Key header; the integration tests run as the CI superuser, not `ebda_app`. Evidence: tests/integration/order-checkout-idempotency.test.ts (2 and 8 concurrent POSTs -> 1 order and 1 decrement; same key concurrent -> same order; changed request -> 409; swapped quantity -> CART_CHANGED; hash and tuple mutations each fail a test), packages/repo/test/money-stock.test.ts. Cost if wrong: a shopper who legitimately edits the form after a lost response sees a clear 409 and re-submits (the key is cleared), never a duplicate or a wrong order.

# SWEEP-BOUND-1

> Section: Audit M-149 (2026-11-12)

**Ruling SWEEP-BOUND-1 - every cross-store sweep is bounded by a required `take` and makes progress per item, so one tick never loads a whole platform and a failed tick resumes where it stopped.** Measured on main 2026-11-12: `sweepAcrossStores` (`lib/cross-store.ts`) has a required `take: number` and cuts the merged rows to it; its two callers (`lib/jobs/store-db.ts`, `ShippingCarrierService.runTrackingCron`) both pass it. The tracking cron caps a run at 200, orders by `lastPolledAt` nulls first, and writes `lastPolledAt` per polled shipment (`shipping-carrier.service.ts:1189,1210`), so the next tick starts at the shipments not yet polled; a failing shipment is caught and logged, never stopping the loop. Not covered: the legacy cron jobs that do not use `sweepAcrossStores` (abandoned-cart, loyalty-daily) were not audited for batching here. Guard: `tests/unit/sweep-bounded.test.ts` fails if `take` becomes optional, a caller omits it, or the tracking cron stops stamping `lastPolledAt`. Cost if wrong: a sweep that loads every store's rows in one Worker tick hits the CPU or subrequest limit and silently stops mid-way.

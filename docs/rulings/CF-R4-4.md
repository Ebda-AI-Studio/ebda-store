# CF-R4-4

Ruling CF-R4-4 (2026-10-30, INFRA-CF-1 PR R4, Ahmad via the controller) - DECISION: `newsletter_subscribers` goes to the STORE DURABLE OBJECT, not to D1 `ebda-platform`. Reasons, measured against the plan section 1 rule ("storeId read in one store context = StoreDO; cross-store indexes = D1"): (a) section 1 already classes `NewsletterSubscriber` as `StoreDO` (row 85) and `packages/cf-schema` already emits the table into the store schema and the erasure registry; (b) every reader is store-scoped (signup, the signed per-subscriber unsubscribe token carries the store id, the admin list and exports, the broadcast and campaign audience, the cart-recovery consent gate) and none is cross-store; (c) the consent gate of the abandoned-cart e-mail must be read in the same Worker call as the cart rows it protects, and a D1 hop per cart would add a second database to a path that has one; (d) an erasure or an unsubscribe is then a single-store operation. D1 would be right only for a cross-store suppression list; none exists. WHAT CHANGED: `NewsletterSubscriber` joins `DO_WRITABLE_MODELS` and `WritableModel`; `POST /public/newsletter/subscribe`, the one-click `GET|POST /public/campaigns/unsubscribe` (subscriber token AND the campaign-recipient token: a link sent before the flip still withdraws consent on the store's own list), `recordCartEmailConsent`, the admin subscriber list, count, CSV and XLSX exports, the broadcast recipient read, `buildCampaignAudience` and `audienceCount` (the raw aggregate is Postgres SQL; a DO store counts the very list `buildCampaignAudience` returns, so the two cannot disagree) and `deliverCartRecoveryEmail`'s consent read all go through `storeDb` / `storeWriter`; on Postgres those are the `prisma` proxy, so the same calls run. CONSENT RULES KEPT, each asserted equal on both backends: a `cart_reminders` address (the checkout box) never receives a campaign or a broadcast; the checkout box never re-activates an unsubscribed address (`unsubscribed`), withdrawing it touches only the cart; one-click unsubscribe is idempotent and a forged token is refused; the audience is active, not `cart_reminders`, de-duplicated by normalised address, with a valid `@`; a re-signup re-activates the row. Evidence: `tests/integration/repo-factory-carts-contract.test.ts` "signup, re-signup, one-click unsubscribe, re-subscribe, the cart opt-in box and the campaign audience" (public routes through supertest, real Postgres 17 vs the DO schema, equal traces and rows); real workerd (`apps/api/workers-do/newsletter-carts.test.ts`, where Postgres used the (store, email) unique index): 40 concurrent signups of one address create one row and 39 `P2002`; an unsubscribe racing 30 re-subscribes never leaves a torn row (active iff no unsubscribed timestamp) and a repeated unsubscribe changes nothing. NOT moved, and why: the campaign tables and the campaign SEND job (`campaign-send` stays `unported`, refused for a DO store by the jobs guard, CF-JOBS-1, so no campaign reaches a DO store's list yet); account erasure of a platform user (`AuthService`'s `deleteMany`) keeps its Postgres transaction, because a DO store's rows are erased by the DO erasure registry (`cf/erasure`), which already lists this table. Cost if wrong: a subscriber list that missed a write can send one mail to someone who unsubscribed; the checkout box and the audience both read the SAME rows, the flag stays `pg`, and a flip is one D1 UPDATE back.

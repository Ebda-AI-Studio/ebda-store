# BARCODE-8

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling BARCODE-8 - review 2 outcomes. (I1) BARCODE-4 is now true end to end: `orderSearchWhere` and `OrderService.getByOrderNumber` run the input through `orderNumberFromScan` (the 18 scanned digits -> `ORD-xxxxxx-xxxxx`; typed text, phones and `EBD-` numbers are untouched), so the admin orders search, the orders PWA search (same API) and exact lookups open the scanned order; every query still carries `storeId`, so a code scanned against another store finds nothing (`tests/unit/order-scan-lookup.test.ts`). (I2) the email PNG, plain or shaped, is only attached when `meetsModuleFloor(number, shape, 360)` holds; a legacy 24-char number needs ~273 modules (1.3 css px) so its email carries the number as text only. The on-page SVG for such a number still renders at its surface width and is NOT promised scannable (legacy numbers are not covered by BARCODE-4). (M2) R2 barcode names are keyed by `BARCODE_KEY_SECRET`, else an HKDF key from ENCRYPTION_KEY (`ebda:barcode-key:v1`), never `JWT_SECRET`; rotating JWT moves nothing. (M4) a bulk slip returns the requested ids that printed nothing in `X-Packing-Slips-Skipped` and the viewer shows "N orders skipped". ACCEPTED, not changed: (M3) the 400-day derived-object expiry means a barcode image in an email older than ~13 months stops loading (the number stays as text and the alt names it); (M5) the billing payment number is a 64-bit FNV-1a display number, not collision-proof and not an identifier (look charges up by the ledger id, never by this number). Cost if wrong: M3 - raise `DERIVED_R2_RETENTION_DAYS`; M5 - add a real invoice sequence.

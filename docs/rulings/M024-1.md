Ruling M024-1 (audit M-024) - merchant and staff account closure now has a trigger for the PDPL erasure job, and the production flag stays OFF. (a) `POST /auth/me/close-account` (non-customer roles; shoppers keep `POST /auth/me/erase`; impersonated and admin-origin sessions refused) calls `closeNonCustomerAccount` (services/account-closure.service.ts). (b) Order: an owner with a live billed store is refused first with the OFFBOARD-1 predicate (409, Arabic); then, flag on, `runErasure` runs once per owned store (request id `close:<user>:<store>`, so a replay short-circuits on the job's ledger), whose StoreDO surface refuses while money is in flight BEFORE identity, media or CI data is touched (409 `MONEY_IN_FLIGHT`, Arabic); a staff user (no store) runs the identity surface only. (c) Flag off (today): the request is recorded as an `account.closure.requested` audit row and answered 202 `recorded`, nothing is erased, so the request is never lost and ops can replay it when the flag is on. (d) Wiring (account-closure.wiring.ts): store-do, platform-payments, media, CI and identity surfaces from the Worker bindings; a missing binding is a 503, never a silently skipped surface. Residual: the email-suppression surface has no production port yet (G6), so it is not part of the run. Evidence: tests/unit/account-closure-service.test.ts (5), account-closure-guard.test.ts, auth-delete-me-owner-guard.test.ts. NOT verified against a live StoreDO or the identity binding: that is the first thing to check after the flag is set on a test store. Cost if wrong: with the flag on, a closure the job cannot finish returns 503 and is retried by the user; the suppression table keeps the plain address until its port lands.

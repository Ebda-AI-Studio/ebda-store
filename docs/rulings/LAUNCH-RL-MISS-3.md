# LAUNCH-RL-MISS-3

> Section: Launch follow-up 2026-11-10 (branch `fix/store-miss-counts-unverified-store-only`): a dead product or blog link inside a real store spent the store-probing budget

Ruling LAUNCH-RL-MISS-3 - every 404 on the public router is still a counted miss by default; the store-miss limiter leaves ONE kind of 404 uncounted, and only when all three hold (`apps/api/src/middleware/catalogue-miss.ts`, `isVerifiedCatalogueMiss`): (1) flag: the resolver verified a store for this request (`resolvedStoreId`, set only by `resolvePublicStoreId` after the active-store lookup by `X-Store-ID` or host; a well-formed id read from the path is never proof); (2) list: the route that answered carries `catalogueMissRoute(...)` and its name is on `CATALOGUE_MISS_ROUTES`, which is exactly `GET /public/products/:slugOrId` and `GET /public/:storeId/blog/:slug`; (3) same store: the route's own store id (the path `:storeId` when the route has one, else the header-resolved id) equals the id the resolver verified. The marker is inverted so it fails closed: an unmatched route, `STORE_NOT_FOUND`, a slug-resolve miss, a route nobody classified and any 404 from a request with no verified store stay counted with no marker needed. Counted on any store, explicitly: locations, pages, `/feed/products.json`, order lookup by id, cart, wishlist, wholesale, loyalty, lifecycle-email unsubscribe, builder preview, the blog list, and the blog post when no store was verified or the path id is not the verified one. The limit (20), the window (60 s), the key (client IP), the 429 body, fail-open and the whole-router refusal at 20 are unchanged, and an IP that is already refused stays refused on the two listed routes. Why: a shopper, or the storefront's own server render, opening dead product links on a store that exists spent the 20 per minute budget meant for store probing and at 20 lost the whole public router. The uncounted 404 says nothing that is not public: a draft, another store's product or post and one that never existed answer the same status and a byte-equal body on both routes. Storefront: the blog post server fetch now sends `X-Store-ID` (`apps/web/src/app/blog/[slug]/BlogPostBody.tsx`), the header the product fetch already sends; without it the blog 404 stays counted. Evidence, measured 2026-11-10: `tests/unit/store-miss-catalogue-exempt.test.ts` (one case per condition, the unverified-store count, the marker on exactly two routes, one setter of the flag); `tests/unit/blog-post-miss-body.test.ts` (draft = other store = never existed, byte-equal); on workerd with the built Worker and the real counter, `apps/api/workers-test/failure-only-limiters.test.ts` 12 of 12: 25 dead product links on a real store from one IP are all 404 with the counter at 0 and no 429; 21 unknown-store misses still end in a 429; the product route's draft, other-store and never-existed answers are byte-equal; a blog 404 is uncounted with header store = path store, counted with a different path store, counted with no header; every `/public` row of the generated route table walked on an unknown store (23 answered 404, every one counted) and on a real store (a 404 uncounted only on the two listed routes, a 200 writes nothing), and a public route that is on neither the counted list nor the catalogue list fails the walk. With the exemption widened to every 404, 6 of those 12 fail. Defence mutations `store-miss-exempt-needs-verified-store`, `store-miss-exempt-needs-listed-route`, `store-miss-exempt-needs-same-store` and `store-miss-unverified-store-is-counted` are all KILLED.

Accepted residual: (a) on the blog post route a verified store whose blog is switched off answers 404 `BLOG_DISABLED` from the same route, so that 404 is uncounted too; it says only that the store has no blog, which the storefront shows anyone. (b) Not changed here, measured on workerd: an unknown or missing `X-Store-ID` on a header-resolved route is answered 400 `STORE_NOT_RESOLVED`, not 404, so it was never a counted miss and is held only by the 300 per minute per IP limiter; on the real router the product route can therefore only answer 404 for a verified store, and condition 1 on that route is defence in depth. (c) A 404 from a counted route inside a real store (the blog list with the blog off, locations with the feature off, a wishlist or an order that is not the caller's) still spends the budget, by decision.

Cost if wrong: guessing slugs inside one real store is held by the 300 per minute per IP limiter and the per-store limiter instead of 20 per minute, about 15 times faster, on data that is already public in the sitemap.

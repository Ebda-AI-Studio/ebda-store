Ruling ACT-1 (Store session, 2026-11-14; merchant activation, Ahmad's goal: tell onboarding friction apart from demand and fulfilment) - activation is measured with the CI stream, no new pipeline. (1) Milestones: `merchant.onboarding_step` gains `first_order` and `first_fulfilled_order` (same type, same `ci/onboarding-step` seed `onboarding:<store>:<step>`, so the stream holds one row each per store, ever); `first_order` also carries `channel` (storefront | whatsapp | admin) and both carry the order id in `data.orderId` (an id; the envelope's own `orderId` stays null, so the types stay order-less). They are NOT new emit sites: `planOrderCreated` (paid), `planOrderStatusChanged` (confirmed or later, delivered) and `planShipmentUpdated` (delivered) call `planActivationMilestones` (`lib/ci/planner.ts`), so no order or money write path changed. "Real" order (`lib/ci/activation.ts`): paid, or COD that a confirmation moved forward, not cancelled/refunded; a demo store (`stores.is_demo`, the only test/QA marker in the schema) never counts; an order placed from the admin (the `stock_not_taken` row `createAdminOrder` writes, with its actor) by anyone but the store owner (staff, a super admin) never counts, the owner's own is channel `admin`. First = earliest qualifying instant (tie: lower id) among up to 10 peers read by `activationPeers` (explicit select, served by `orders (store_id, created_at)`), so a second order is not emitted at all and a replay re-derives the same id. (2) Help: new `merchant.onboarding_help` (`ci/onboarding-help`; `step`, `kind`), one row per (store, step, kind). `step` is the first milestone NOT yet reached, read from the store's own state when the event is planned (`onboardingProgress` + `openStep`), `null` (no event) for a store older than 30 days, a demo store, or when every step is done. Kinds with a write path: `assistant_used` (a store_admin's successful POST under `/stores/:id/ai/*`, `routes/ai.routes.ts`) and `super_admin_action` (a super admin WRITE on a store that is not active, `middleware/store-access.ts`, next to the existing STORE_ACCESS audit row). `support_contact` is SKIPPED: the repo has no merchant support-message path (only the public studio enquiry form and mailto links); add the kind to `ONBOARDING_HELP_KINDS` in the same PR that adds the path. (3) View: the daily CI aggregation folds each store's events into `aggregates/v1/store=<id>/activation.json` (`aggregate/activation-file.ts`; +1 R2 get/put per store, no put when unchanged, ids and epoch ms only, trail of at most 10 orders for "where the order stopped"), and `GET /admin/ci/activation` (keyset cursor on store id, one R2 get per store on the page, max 50) + `GET /admin/ci/activation/funnel?from&to` (count, median seconds from signup, help count per step, over stores whose signup is in the range) feed the super-admin page `/activation` (ar/en). (4) Erasure/PII: no buyer key, no phone, no name in any new field. Customer erasure needs nothing (the rows are order-less and key-less; `data.orderId` is a bare uuid that points at nothing once the order is erased). Merchant erasure deletes `aggregates/v1/store=<id>/`, which holds `activation.json`, and the outcome prefix, which holds the events: no registry change needed. The raw events keep the 24-month R2 rule; `docs/privacy/data-map.md` section 4 lists them. Capability registry: the only registries in the repo are the marketing site's customer-facing `capability-registry.ts` (a card per merchant capability, which a platform-operator view must never appear in) and the per-store admin search registry (`settings-registry.ts`, pages under /stores/[id]); the sibling `/ci-insights` is in neither, so no entry was added; the admin-only reason is this ruling plus `docs/admin/activation-view.md`. Residuals: (a) activation files start from the first daily run after deploy and cover the two days that run folds, so history before it is missing until `runCiAggregation` is replayed over the earlier days (idempotent); (b) the funnel reads at most 600 stores per request (`FUNNEL_STORE_CAP`) and says `truncated`; past a few hundred stores move it to a published daily `aggregates/v1/activation/latest.json`; (c) `activationPeers` is one indexed select of 10 rows per paid/confirmed/delivered order event for the life of the store (the existing CI reads per event are 3 to 5). Cost if wrong: a mis-attributed first order shifts one store's time-to-first-order in an internal view (nothing a merchant sees or pays for), and a missing help row under-counts friction at one step until the replay.

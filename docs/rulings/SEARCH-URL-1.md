# SEARCH-URL-1

> Section: Launch blockers 31 and 32 (privacy): the search term and the ad pixels

- Ruling SEARCH-URL-1 (launch blocker 31; closes SEARCH-T5-8 and the storefront half of SEARCH-T5-9) - the storefront search term is in NO URL. Design: (a) API calls carry it in the `X-Search-Query` header, percent-encoded, as the admin does (SEARCH-P2-9): `api.getProducts` moves `search` out of the query (`moveSearchToHeader`), `api.searchSuggest` sends `GET /public/:storeId/search/suggest` with the header and no `?q=`; the API reads the header first (`searchQueryFromHeader`) and still accepts `?search=` / `?q=` for one release for already-deployed storefront bundles (remove them after that, with the admin ones). A header-borne answer is `Cache-Control: private, no-store` plus `Vary: X-Search-Query` and never goes through `setEdgeCache`, because Cloudflare's cache key ignores `Vary` (edge-cache.ts) and a shared copy would serve one term's results to another. (b) The page address is `/search` (plus `category` / `sort`, which are not personal data); the term lives in the history entry's STATE (`apps/web/src/lib/search-term-state.ts`), written with the native History API that Next's app router supports, so back, forward and refresh restore it and nothing sends it. The header search box hands the term over through sessionStorage for one navigation (`openSearch`); a reload whose entry lost its state falls back to the tab's last term (navigation type `reload` / `back_forward` only). (c) An old `/search?q=` link is adopted once and the address bar is rewritten without it, in a layout effect and with the pixels already switched off for that URL (PIXEL-CONSENT-1). (d) `/search` is `robots: noindex, nofollow` (it was not set before). (e) Sentry: `x-search-query` is dropped from the API's captured headers and redacted by `scrubSentryEvent` / `scrubPostHogCapture` wherever an SDK records request headers; pino logs `req.path` only and `redactSensitiveQuery(req.originalUrl)` for the legacy form. Shared links: a link no longer carries the term, so a shared or bookmarked `/search` opens an empty search box (old `?q=` links keep working). Evidence: `apps/web/src/app/search/SearchClient.privacy.test.tsx` (types a phone-bearing term through the page, the typeahead and the real API client: no URL, fetch URL, address bar or console line holds it; the header does), `apps/web/src/lib/search-term-state.test.ts`, `apps/web/src/lib/api.search-header.test.ts`, `tests/unit/storefront-search-api-header.test.ts` (the two routes: header read, no log line, no edge cache), `tests/unit/storefront-search-no-term-in-url.test.ts` (tripwire), `packages/shared/src/__tests__/sentry-url-scrub.test.ts`. Not proven here (needs the deployed Worker): that `api.ebda.app`'s Workers Logs hold no term after deploy; the first request of a legacy `?q=` link is logged by the platform before any code runs. Cost if wrong: (1) a shopper who shares `/search` sends a friend to an empty box, not their results (a share control that copies a link with the term in the `#fragment` would fix it; fragments are not sent to servers but are visible to pixel scripts, so it needs the pixel guard first); (2) a browser that drops history state on reload and blocks sessionStorage shows an empty search after a refresh; (3) a legacy bundle keeps writing terms to the log until the deprecated form is removed.

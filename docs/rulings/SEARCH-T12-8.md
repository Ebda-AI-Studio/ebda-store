# SEARCH-T12-8

> Section: 2026-10-16 — Search program, PR 4 (P1c, hybrid ranking): SEARCH-T12-\*

Ruling SEARCH-T12-8 (Task 12 review M1, pre-existing) — listing and search query params are ONE string at the edge (`assertScalarQuery`, `apps/api/src/lib/query-params.ts`). Express's `qs` turns `?category[startsWith]=secr` into an object, and the `category as string` cast handed it to Prisma as `slug: { startsWith }`: the reviewer's probe listed a product of an INACTIVE category (a per-character slug oracle inside one store), and `?category=a&category=b` was a 500. Now every `/public/products` param (`page limit category search featured sort minPrice maxPrice cursor ids` and every `opt_<name>`), the typeahead `q`, the public review list (`page limit sortBy`) and the admin review list (`page limit status productId`, which also reached a Prisma `where`) return 400 `VALIDATION_ERROR` for an array or object. Swept and left as is because they cannot reach Prisma as an operator: `page`/`limit` through `parseInt` on `/orders`, `/stores`, store and blog lists; the `typeof … === 'string'` reads (`slug`, `locale`, campaign `token`, layout draft); `bundle.routes` (already Zod). A valid request is unchanged byte for byte. Evidence: `tests/integration/hybrid-search-cache.test.ts` "listing params are scalars" (12 shapes, 400 each; red before: `category[startsWith]` was 200) and "typeahead: an array or object q is a 400"; `tests/unit/query-params-scalar.test.ts`. Cost if wrong: a client that sent a repeated param by accident (e.g. two `search=`) now gets a 400 instead of an unfiltered list.

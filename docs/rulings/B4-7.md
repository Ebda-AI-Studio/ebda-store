# B4-7

> Section: 2026-10-22 — Phase B4 Lamma (B4-\*)

Ruling B4-7 — delivery date is chosen from structured fields and written by the server, as built. (1) `daysAhead` is validated at the settings edge only for itself (400 outside 1-14, null clears); the rest of `checkoutDelivery` stays unvalidated as before, so a merchant's saved windows and note cannot start failing. The plan's "unknown key rejected" is NOT done: it would turn every historical or script-written `checkoutDelivery` key into a failed settings save. (2) The estimate input is the store-wide `deliveryDays.min` only; a zone estimate depends on the delivery address, which the chips do not know, and an area-priced store carries no zone days at all. (3) The server requires the date only for `source: web`; WhatsApp and the agent checkout, which have no chips, may omit it (a date they do send is validated). (4) The line shares the prefix and shape of the client-written one so every consumer of `notes` is unchanged; a date store's client sends the customer's note alone. (5) `formatWindowTime` moved to `@ebda/shared` (`formatWindowTime12`) so the storefront and the order note print the same time. Evidence: `tests/unit/delivery-date-resolver.test.ts`, `tests/unit/delivery-date-chips.test.tsx`, `tests/integration/order-delivery-date.test.ts` (frozen clock; stale date, closed window, lead time, off-day edit, other tenant, legacy store, no order and no stock moved on a refusal). Cost if wrong: no structured filter or sort by delivery date in admin until a column is added; an area-priced store whose real lead is a zone's days sees chips that start earlier than the zone promise.

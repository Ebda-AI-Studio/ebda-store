# CART-RESTORE-1

> Section: 2026-10-16 — Search program, PR 4, Task 13 (quality eval): SEARCH-T13-\*

Ruling CART-RESTORE-1 (2026-10-21, review item 1; supersedes the "link is /cart, no restore token" half of CART-EMAIL-4) - the email's button restores the cart through a signed, expiring link. `https://<store>/cart?restore=<token>`, token = `<storeId>.<cartId>.<exp>.<HMAC-SHA256>` (`lib/cart-restore-token.ts`, own HKDF label `ebda:cart-restore-mac:v1`, optional `CART_RESTORE_SECRET`): store-scoped, single cart, 7-day expiry, two UUIDs and a timestamp, no email or session id in the URL. `POST /public/cart/restore` verifies it against the request's store and COPIES the emailed cart's lines (items and bundles) into the visitor's OWN session cart through `CartService.addItems` / `addBundle` (stock and price rules apply; a line that no longer sells is skipped and logged); it never returns the source cart's session id, so the token is a capability for those lines only, not for the cart or the account. Idempotent: lines the visitor's cart already holds are not added again, so reopening the email twice does not double quantities. The storefront hydrator (`CartRestoreHydrator`) runs once the cart context is ready, then strips the param. This closes the old gap that made guests unreachable (an empty `/cart` on another device). Evidence: `tests/unit/cart-restore-token.test.ts` (5), `cart-email-optin.test.ts` restore cases (4), `cart-recovery-email.test.ts` (link verifies to this store and cart). Cost if wrong: anyone who obtains the email within 7 days can copy that cart's lines (not its owner's data) into their own cart; restoring a sold-out line silently adds nothing.

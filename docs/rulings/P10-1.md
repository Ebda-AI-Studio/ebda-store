Ruling P10-1 (audit M-023, M-125, M-032; M-113 left to Ahmad) - billing hardening. (a) M-023: a renewal / upgrade charge whose gateway answer was lost used to stay `pending` for ever (no sweep, no alert; the next day's key was already claimed). Now: the unknown-outcome branch raises a P1; the daily billing cycle runs `sweepStuckCharges` BEFORE reading the due list: every renewal/upgrade pending over 1 h is looked up through the provider's optional `getChargeStatus` (stub implements it; Kashier has no status lookup wired yet, see below) and a definitive answer is settled through the guarded pending -> succeeded|failed transition; one still unknown after 3 days is settled `failed` (`outcome_unknown_timeout`) so the subscription enters dunning (a late success webhook still settles failed -> succeeded: the money moved); whatever is still pending is named in one P1. Idempotent, never re-sends a charge. (b) M-125: `store_subscriptions.billing_anchor_day` (migration 20261106000240) is the day of month the paid cycle started on (set at checkout/upgrade, the first renewal or the first manual payment); every renewal and manual period clamps from it (`addIntervalAnchored`), so Jan 31 -> Feb 28 -> Mar 31, not Mar 28 for ever. Subscriptions that already drifted anchor on their current period end day (no history to recover). (c) M-032: the go-live gate already accepts "card OR InstaPay chosen" (`trial_instapay`, EBDA-FUNNEL-9). `BILLING_PROVIDER=none` is the explicit InstaPay-only value; an UNSET value in production is NOT made a boot failure (that would contradict EBDA-FUNNEL-17 and would take the API down on deploy until the binding exists) but is now a P1 at every boot with the exact fix. Cost if wrong: a stricter boot refusal is a one-line change in `assertBillingConfigAtBoot` once `BILLING_PROVIDER` is set in production (queued for Ahmad). (d) NOT DONE, needs Ahmad: the production trial -> InstaPay -> active end-to-end run (a real transfer and a super-admin confirmation) and the M-113 trial-clock decision (first publish / first order, or a one-time 7-day extension). NOT IMPLEMENTED: a Kashier charge-status lookup (the transactions endpoint used for webhook confirmation, PROVIDERS-17, is the candidate); until then Kashier rows rely on the P1 and the 3-day hand-off to dunning. Evidence: tests/integration/subscription-billing.test.ts (lost success settled once and never re-sent, lost decline -> past_due, blind provider given up only after the window, anchor back to the 31st; poll / give-up / anchor mutations each fail a test), tests/unit/billing-kashier-provider.test.ts (anchor arithmetic incl. leap years, unset-provider warning, none).

# SEC-CUSTOMER-SCOPE-1

> Section: Admin deep audit 2026-11-04, finding S-1 (branch `fix/sec-customer-store-membership`)

**Ruling SEC-CUSTOMER-SCOPE-1 - a customer id taken from a URL or body is a global `users.id`, never a tenancy claim: every admin or store route or service that reads or writes per-store customer data must first prove `users.store_id = :storeId AND role = 'customer'` through `assertStoreCustomer` (`apps/api/src/lib/store-customer.ts`), and answer 404 `CUSTOMER_NOT_FOUND` otherwise.**
Evidence: `POST /stores/:storeId/loyalty/members/:customerId/award` created a `loyalty_points` row for any user uuid and `listMembers` joined that user's email and name, so a store owner could read another tenant's PII. The membership definition is the one wallet, order create, wholesale and the privacy routes already use (customer accounts are store-scoped by `users.store_id`); `users` lives in Postgres for DO-backed stores too, so the one check covers both backends. Fixed in `awardBonusPoints`, `initializeCustomerPoints`, the review-bonus award, `getTransactionHistory` and the two loyalty GETs; the members list and store-level transaction log also filter the joined customer to this store so a stray row can never surface PII. Production check (read-only, Postgres, 2026-11-04): 0 `loyalty_points` rows exist, so none were created by the exploit; DO-held rows of the six DO stores were not queryable read-only. Tests: `tests/unit/loyalty-customer-scope.test.ts`.
Cost if wrong: a legitimate customer whose `users.store_id` is NULL or differs from the store (legacy rows) gets 404 on loyalty actions until the row is repaired, which is the safe direction.

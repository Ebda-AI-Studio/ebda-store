# CF-NOTIFY-1

Ruling CF-NOTIFY-1 (2026-10-30, INFRA-CF-1 final integration) - the notification channel config the push, SMS and WhatsApp dispatchers read (`NotificationConfig`: provider, encrypted credentials, enabled; `NotificationEventConfig`: the per-event channel switches) lives on the StoreDO for a DO store. Both models join `DO_WRITABLE_MODELS` and `WritableModel`; `notification-config.service.ts` reads through `storeRepo` (Postgres keeps its `withStore` read, which sets the RLS GUC for background callers) and writes through `storeWriter`. The merge base of a masked-credential resubmit is read from the store's own row with `findFirst` (the compound unique read is a `findFirst` on the DO), never through the Redis cache, as before. The Redis config cache is keyed on the store id and re-set after every write, unchanged. Evidence: `tests/integration/repo-factory-notification-config-contract.test.ts` (3 scenarios, Postgres vs the DO schema, equal traces and rows: upsert / read / update, a masked credential keeps the stored secret, delete and the event switches), `apps/api/workers-do/notification-config.test.ts` (real workerd: 40 concurrent upserts of one channel leave one internally consistent row, 40 of one event leave one row and another event untouched, a delete racing upserts leaves at most one row). Not ported (stated): `push.service.ts` `PushSubscription` / `NotificationLog` writes still use Postgres, so a DO store's push subscribe and send log are on the push-subscription item, listed in `docs/cf/not-on-do.json` only if the dispatcher is moved; the dispatcher's channel config, which this ruling moves, is what decides whether a reminder goes out. Cost if wrong: a DO store whose config rows were not imported would read as "no channels configured" and send no reminders; the cutover import carries the table (all 122 schema tables), and the config can be saved again from the admin page.

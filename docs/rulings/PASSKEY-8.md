# PASSKEY-8

> Section: 2026-10-15 — Phase B1 Qamar (B1-\*)

Ruling PASSKEY-8 — password login and passkey sign-in share their account gates through `loginGate` (`services/login-gate.ts`): one lockout counter per account (store-scoped key, case-folded), the same suspended/deleted check, the same success reset; failures after the account is identified feed the counter, a locked account refuses a VALID assertion, and the IP bucket is the route's `passkeyFinishLimiter` (IP-only, counts failures). `tests/unit/login-gate-parity.test.ts` fails when `AuthService.login` gains a `loginGate` call or a limiter/guard the passkey path lacks; `tests/unit/login-parity-behaviour.test.ts` (review M6) is the behavioural proof: the same account is signed into by both paths for each gate condition (locked, suspended, inactive, soft-deleted, bad credential, alternating methods, store-scoped key, success reset) and the outcomes and counter effects must agree. Store-access for staff is not a login gate (it is `requireStoreAccess` per request) so it applies identically. Cost if wrong: an attacker who knows a credential id (not secret) can spend an account's lockout budget, exactly as with a known email.

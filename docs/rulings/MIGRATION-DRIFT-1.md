# MIGRATION-DRIFT-1

> Section: 2026-11-02 - QA sweep batch 1 (branch `fix/qa-sweep-batch-1`)

Ruling MIGRATION-DRIFT-1 - `scripts/ci/pg-migration-drift.mjs` compares `packages/database/prisma/migrations/*` with production Postgres's `_prisma_migrations` (two SELECTs, read-only) and exits 1 when any migration is missing while the `stores` table still has rows; `.github/workflows/pg-migration-drift.yml` runs it daily (03:47 UTC) on the self-hosted runner only (a scheduled run on a hosted runner is skipped, CI-HOSTED-1; workflow_dispatch runs anywhere) and alerts through the Telegram notifier. Why: with `EBDA_SKIP_PG_MIGRATE=1` the deploy no longer applies Postgres migrations, so five PG-side migrations were silently missing for days (PG-MIGRATE-CATCHUP-1). Approximation: it counts store rows in Postgres, not stores whose D1 `storage_backend` is `pg`, so it can alert for a store already moved to the Durable Object path; it never stays silent while a PG-side feature lacks its tables. Evidence: `tests/unit/pg-migration-drift.test.ts` (comparison, real directory scan, workflow is read-only and not hosted on schedule); run against prod after the catch-up it printed `ok (235 applied, 7 store rows in Postgres)`. Cost if wrong: a false alert costs a minute of reading; a missed run (runner offline) is the same as no check, so the runner state is part of the on-call picture.

# ADMIN-SESSION-1

> Section: Admin batch pre-push review (2026-11-04, branch `feat/admin-batch-2026-11-03`)

Ruling ADMIN-SESSION-1 (2026-11-04) - the admin treats exactly one answer as "your session is gone": the identity service replying 401 `NO_SESSION`. (a) `refreshAccessToken` throws `RefreshThrottledError` for a 429, any 5xx and any failure that is not an answer from the service (offline, DNS, aborted), so the realtime socket's `getToken` throws (transient: it reconnects without a token) instead of answering `null` (revoked: it signs the merchant out); a flaky reconnect on a phone PWA never ends a session. (b) "Your session ended" is shown only when a session that was signed in on THIS page (`lastGrant`) is revoked mid-use, not on the first-load session check and not on calls that straggle in after a deliberate sign-out (`clearStoredSession` forgets the grant). (c) The proactive refresh delay is computed from the token lifetime (JWT `exp - iat`) relative to the moment it was received, never from `exp - Date.now()`, and never below `PROACTIVE_MIN_DELAY_MS` (30 s): a device clock far ahead of the server, or a token shorter than the 60 s lead, used to give a delay of 0 and each refresh re-armed an immediate refresh. (d) `finishSignIn` checks the staff role BEFORE arming the refresh: a refused customer account has both sessions ended (best effort) and no timer, and the `accessDenied` message still reaches the page. Evidence: pre-push review 2026-11-04 findings 2, 3, 4, 8; tests `apps/admin/src/lib/__tests__/api-refresh-accounts.test.ts`, `apps/admin/src/lib/proactive-refresh.test.ts`, `apps/admin/src/lib/__tests__/auth-admin-second-factor.test.tsx`. Cost if wrong: a 5xx/offline blip leaves a genuinely revoked session on screen until the next call that gets a real 401 NO_SESSION, and a skewed clock refreshes at most every 30 s.

Ruling WEBHOOK-SCOPE-1 (2026-10-28) - a provider reference never decides on its own which store a delivery belongs to. Audit of every webhook/callback reference lookup in `apps/api`: (1) payment webhooks, per-store URL: the payment is resolved by `ebda_webhook_resolve_store_scoped` (provider + URL store first) and must equal the signed store, otherwise the identical 503 as an unknown ref (WEBHOOK-ORDER-1); now ALSO logged server-side (`crossStore` flag), never differently to the caller. (2) The dedupe key was the one remaining cross-store lookup: `orders.idempotency_key` and the inbox key are globally unique, so store B's settled delivery made store A's delivery of the same ref string a "duplicate" and dropped it. The key is now `<storeId>:<provider key>` (`storeScopedIdempotencyKey`) for dedupe, inbox row and `markWebhookProcessed`; pre-existing unprefixed and legacy keys are still honoured, but only when the order they name belongs to the delivering store. (3) Bosta carrier webhook already takes `:storeId` in the URL and checks the token against that store. (4) Billing webhook is platform-level (no store reference). (5) Residuals, unchanged: the generic `/webhooks/payment` and the browser redirect `/payment/callback` carry no store, so they stay provider-scoped, newest-first lookups (the generic URL still authenticates with the resolved store's secret; the redirect only reads status for a redirect URL); `/payments/status` and `/refund` are authenticated and authorise against the resolved store afterwards. No migration or index: `payments` has no `store_id` column (join through `orders`), and `payments.transaction_id`/`invoice_id` are already indexed. Evidence: `tests/unit/inbound-payment-webhook-routes.test.ts` (same ref in two stores resolves only inside the signed store; cross-store ref refused 503 with nothing stored or enqueued; another store's settled key is not a duplicate; store-prefixed key in dedupe and inbox, for paymob/kashier/fawry). Cost if wrong: an in-flight delivery recorded under the old unprefixed key could be processed once more after deploy (the payment status transition is itself idempotent), and a gateway-generic delivery that collides across stores still resolves to the newest one.

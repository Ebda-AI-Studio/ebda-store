# INSTAPAY-DO-1

Ruling INSTAPAY-DO-1 (2026-10-30, INFRA-CF-1 R3) - InstaPay ORDER receipts of a Durable Object store live in the DO (`instapay_order_receipts`, `do/instapay-receipts.ts`), in the same database as the order and its payment; subscription receipts stay platform-owned. Submit (receipt -> `submitted`, hold frozen, payment metadata, payment event), reject (decision, reference freed, hold restarted at max(original, now + 24 h), payment event) and the merchant's confirm (`confirmInstapay` approves the submitted receipts in its own section and returns their ids) are ONE `transactionSync` each, replacing `lockOrder` + a savepoint. Refusals keep the Postgres order (a waiting receipt, then not-a-draft). The AI read, flag computation and object storage stay in the Worker; the Worker passes the `extractionStatus` it saw and a changed row is `RECEIPT_CHANGED` (recomputed once). Reference uniqueness: same store = the DO partial unique index (atomic). Cross store = a synchronous claim in D1 `entity_index` kind `instapay_ref`, BOUND to the receipt id (`claim_ref`), made before the DO section; it is freed only by the receipt that holds it, only after a rolled-back DO answer other than DUPLICATE_REFERENCE, or on reject. A transport error or a duplicate answer never frees it (fail closed: a stuck claim is a refused resubmit, never a double-used reference). Retention (30 / 90 / 180 days) and the shopper erasure run in the DO: the registry classifies the table `customer-pii` via `orders`, and the StoreDO's customer erasure also marks the receipts `personal_scrubbed_at` so the sweep deletes the screenshots. Found on the way: `_cart_claims` was unclassified in the erasure registry, so a customer erasure on any DO store that had run a checkout failed closed; classified `no-pii`. Evidence: `packages/repo/test/do-instapay-receipts.test.ts` (7), `tests/integration/repo-factory-instapay-receipts-contract.test.ts` (7, Postgres vs DO), `apps/api/workers-do/instapay-receipts.test.ts` (20 concurrent submits of one reference from 20 orders: one wins; 20 submits of one receipt: one event; confirm racing reject: one decision), `tests/unit/instapay-ref-claim.test.ts` (8: 20 stores racing, owner-bound release, which failures free a claim), `apps/api/workers-do/erasure.test.ts` (receipts scrubbed and marked). Residual: a reference held by a Postgres-backed receipt (subscription, or a Postgres store's order receipt) is invisible to a DO store's claim (RLS hides other stores' rows from a SELECT; the UNIQUE is only reachable by writing); it closes when the receipts table moves to D1 at the billing cutover. Cost if wrong: during the migration a payer could file one bank reference against a DO store and a Postgres-backed receipt; every receipt still needs a human approval, so the exposure is a duplicate-proof flag the approver does not get, not an automatic payout.

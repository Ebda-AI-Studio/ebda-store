Ruling SF-EXPIRY-1 (2026-11-16, money builder, issue #843) - a StoreFeature override can expire, and an expired override is ignored at READ time (no sweep): `FeatureService.rowsToMap` skips a row whose `expiresAt` is at or before now, so the feature falls back to the plan baseline; `wholesaleEntitledUncached` (the only other reader of override rows for a decision) applies the same rule. Evidence: before this a feature sold through an override (`bundles`, 1 row on prod D1 on 2026-11-15) never ended when the merchant stopped paying (audit S19). New nullable columns `expires_at` (NULL = never, so every existing row and the previous release behave as before: expand-only) and `reason` on `store_features`, in Postgres (`20261116000200_store_feature_expiry`) and D1 (`platform/0014_store_feature_expiry`, generated; the generator learned `latePrismaColumns` for a column that is in schema.prisma but reached production D1 after 0001, which `extraColumns` could only express for D1-only columns). The super-admin single-feature PUT has PATCH semantics per field: an omitted `expiresAt`/`reason` KEEPS the stored value (a plain toggle must never turn a time-boxed grant permanent), an explicit `null` clears it, a past `expiresAt` is a 400 (use DELETE); the bulk PUT leaves both untouched; the admin matrix shows the expiry and edits it. Staleness class: the resolved map is cached 5 min and the public store payload 120 s on top and nothing writes at the expiry instant, so an expiry bites within that BOUNDED-stale window (documented at `rowsToMap`); the uncached wholesale/order path obeys it on the next call. A daily sweep was not added: resolve-time is enough, an expired row is inert and the matrix labels it. NOT in this PR: selling `bundles` through the add-on catalog (part of the unmerged purchase stack, #775 and its dependents), so today `bundles` is still granted by hand and the operator must set `expiresAt` (the field and UI exist; nothing forces it). Existing overrides (including the prod `bundles` row) have no expiry until an operator sets one. Cost if wrong: an expiry takes effect up to about 7 minutes late on cached paths; and an override nobody gave an expiry still lasts forever, exactly as today.

Amendment (2026-11-17, AI review of #859): an omitted `expiresAt` keeps a FUTURE stored expiry but CLEARS one already past, in the single writer `FeatureService.updateStoreFeatures` (single PUT and bulk PUT): otherwise a toggle of an expired (ignored) override returned 200 and changed nothing. The toggle thereby creates a fresh non-expiring override. Readers (`rowsToMap`, `wholesaleEntitledUncached`, admin matrix) share `isOverrideExpired` from @ebda/shared; every other consumer (abandoned-cart, Smart Layer, gates) reads through `featureService`. Cost if wrong: a past expiry is wiped by a toggle, so a lapsed add-on re-granted by a toggle is permanent until an operator sets a new expiry.

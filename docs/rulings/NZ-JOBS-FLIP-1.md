# NZ-JOBS-FLIP-1

> Section: NEON-ZERO production cutover (2026-11-05)

**Ruling NZ-JOBS-FLIP-1 - `JOBS_ON_DO` and `STORE_CREATE_ON_DO` are set to `"1"` in `apps/api/wrangler.jsonc` with the cutover.** Every family marker and the customer-auth markers are set and verified equal in production (the API deployed from #443, D1 0003-0006 applied), so every store is a Durable Object store; the jobs guard (`lib/jobs/do-guard.ts`) must follow each store's backend flag and a new store must be created on D1 + its StoreDO (`lib/store-create-do.ts`), not in a Postgres the Worker no longer binds. The flip gate `node scripts/cf/not-on-do.mjs` prints `{"open":false,"refusals":6,"postgresOnly":0,"jobsRefused":0,"jobsAccepted":0,"sweepSkips":0}` and exits 1 only because of the 6 deliberate fail-loud store-shape refusals (`STORE_FILTER_UNSUPPORTED`, `STORE_READ_UNSUPPORTED`, `STORE_WRITE_UNSUPPORTED`, `STORE_TX_UNSUPPORTED`, `STORE_TX_WRITE_UNSUPPORTED`, Rulings NZ-D8 and NZ-D18). Those are refusals, not Postgres paths: a Store read or write shape the DO path does not serve yet answers a loud error instead of falling back to Postgres. There are no Postgres-only flows (`postgresOnly` 0), no refused job (`jobsRefused` 0) and no unported job; the strict dead-Postgres route sweep, cron group included, hit none of the refusals. With Postgres removed no store is a Postgres store, so the scoped Postgres client of NZ-INTEG-SCOPE-1 is never reached on the Worker (the Worker's Prisma client throws `POSTGRES_REMOVED`, Ruling NZ-D23). Decision: flip both variables with the cutover. Cost if wrong: an unported `Store` read or write shape on a DO store answers an error instead of working (the N-18 / N-19 ports track each one); the variables can be put back to `""` by one deploy, but that would route job guards and new-store creation to a Postgres the Worker cannot reach.

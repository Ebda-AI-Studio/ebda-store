# DEMO-LAYOUT-PURGE-1

> Section: 2026-11-09 — every cache has invalidation on every write path

Ruling DEMO-LAYOUT-PURGE-1 (2026-11-09) - the demo showroom's layout response cache (`GET /public/stores/:id/layout`, demo stores only) is event-invalidated. It used to sit out its 120 s TTL with no invalidation, so the demo seed's home publish showed old hero images for up to 2 minutes. Every layout write path already ends in `bustStoreCaches`: page-builder publish, rollback and look apply through `purgePublishedCaches`, the legacy layout PUT, store updates, and the demo-home seed route (`/internal/demo-home/:slug` -> `publishDraft`). `bustStoreCaches` now clears `demoLayoutCacheKey(storeId)` (generation bump + delete; the key lives in the dependency-free `lib/demo-layout-cache-key.ts`). The route fills it through `getCached` (generation guard, single flight, `cacheIf` demo rows only) instead of a bare `redis.set`, so a read that raced a publish cannot write the old layout back. The key moves to v2 because the value shape changed. Residual: KV deletes reach other data centres within <= 60 s (NZ-D1); 120 s TTL is only the outer bound. Tests: `tests/unit/demo-layout-cache-purge.test.ts`. Cost if wrong: a visitor in another data centre sees the previous demo layout for up to 60 s after a publish.

# AUDIT-SPLIT-1

Ruling AUDIT-SPLIT-1 - GHSA-fc5q-39xc-vjpf (picomatch ReDoS, high) has NO patched version (`npm audit fix --force` would downgrade vite) and reaches the whole tree through vite, tinyglobby, fdir, @rollup/pluginutils and @parcel/watcher (via @sentry/nextjs), so the repo's single `Security Audit` gate turned red on a build-time advisory nobody can fix. The gate is split: (1) BLOCKING: `node .github/scripts/audit-gate.mjs` = `npm audit --omit=dev` on production dependencies, failing on anything not in the allow-list; (2) NON-BLOCKING (`continue-on-error`): the same script with `--all` audits every dependency including development tooling with the same allow-list and shows red for an unlisted advisory without stopping a merge; (3) the allow-list is `.github/audit-allow.json`, one entry per advisory with id, package, reason (at least 20 characters) and an EXPIRY (at most 90 days ahead); an expired or malformed entry fails the gate by itself and an expired entry stops waiving, so a waiver cannot outlive its review. First entry: GHSA-fc5q-39xc-vjpf, picomatch, expires 2026-12-17, "drop when picomatch ships a fix". Measured 2026-11-17: before this change the production-only gate (`audit-gate.mjs`, empty allow-list) reported BLOCKING with exactly this one advisory (8 packages via it; the full audit also lists only this advisory, 31 packages), so the next push-to-main / nightly / queue run of `Security Audit` would have been red (pull requests do not run that job). The file's own policy asks for Ahmad's explicit acceptance of a waiver: risk stated here, picomatch runs only in build-time tooling, never in a running Worker, and the entry self-expires in 30 days; the main controller ruled it. Cost if wrong: a production advisory in the same package that IS reachable at runtime would be waived until the expiry (it is matched by advisory id, so a different advisory still blocks), and the job budget grew from 18 to 20 minutes for the second audit run.

Bundle measurement (2026-11-17, requested by the main controller so that "build tooling only" is measured, not assumed). apps/api Worker bundle (`wrangler deploy --dry-run --outdir`, 42 MB, 3 JS files): ZERO files containing picomatch, tinyglobby, @rollup/pluginutils, @parcel/watcher, node_modules/vite/ or node_modules/fdir. apps/web, apps/admin, apps/orders OpenNext outputs (`scripts/cf-build.sh <app>`, `.open-next`, 1879 / 2482 / 1273 JS files): none contains the npm package picomatch@4.0.7 that the audit flags, nor tinyglobby, @rollup/pluginutils, @parcel/watcher, vite or fdir; each contains exactly THREE files that mention picomatch, all inside Next.js itself: `next/dist/compiled/picomatch/index.js` (Next's own vendored, separately compiled copy, not an npm dependency, invisible to `npm audit`) and `next/dist/shared/lib/match-remote-pattern.js` / `match-local-pattern.js`, which call `makeRe(pattern.hostname)` / `makeRe(pattern.pathname)` to match `images.remotePatterns` / `localPatterns`. So the waiver's claim is exact for the API and is NOT "absent from every bundle" for the three storefront/admin apps: Next's vendored matcher IS deployed there. Why that is not the advisory's attack: the advisory (picomatch <= 4.0.7, no patched version) is a ReDoS when an attacker SUPPLIES THE GLOB PATTERN (for example `+(*)`); here the patterns are static developer config in `apps/*/next.config.js` (`remotePatterns`), the request only supplies the URL string being matched. INFERRED, not measured: the vendored copy's version and whether it carries the same defect (I could not read a version string from the minified file); the audit cannot track it. Residual and follow-up: no user-controlled glob reaches picomatch in any measured bundle; re-check when Next ships a release that updates its compiled picomatch.

Ruling P08-1 (audit M-049, M-050, M-064) - an order's payment state moves through ONE conditional UPDATE, and an unresolved webhook is retried, not dropped. (a) `payment-state-claims.ts`: `claimOrderPaid` (`unpaid|failed -> paid`, only while the order is pending / awaiting confirmation / confirmed) and `claimOrderFailed` (`unpaid -> failed`) are used by the pull-side confirm (guest verify-on-return, admin Refresh) AND by `handleWebhook`; under READ COMMITTED the row lock makes exactly one caller win, and only the winner writes the payment row and runs the fan-out (order/created, socket, "payment received" push, failure push). A paid, refunded or disputed order is never turned `failed`; the payment row's failure write excludes completed/refunded payments. A failure answer no longer asserts an order transition (it never sets the order status). (b) The order/created consumers are idempotent on their own (order-created stamps `order_created_notified_at`, accounting posts by (source, sourceId), CAPI dedupes by event id, lifecycle emails by UNIQUE row), read before #234 removes the Inngest-side dedupe; the claim now also stops the second enqueue. (c) A webhook that names a payment no store owns answers 503 + `Retry-After: 60` + an info alert (was 200 "ignored", which made the gateway drop it for good); a per-store URL naming another store's payment stays 200. Gateways retry on 5xx, so a callback that beat the Payment row's commit is applied on redelivery. Cost if wrong: a stray or other-environment webhook is retried by its gateway until it gives up and raises an info alert each time; the existing payment reconcile sweep remains the backstop for an order that never resolves. Evidence: tests/integration/payment-state-claims.test.ts (8 concurrent verifies -> 1 transition + 1 fan-out; paid vs expired vs failed racing 12 times -> always paid; mutation-checked on both claims), unit tests in payment-confirm / payment-webhook-status-transition / inbound-payment-webhook-routes. NOT VERIFIED: the real provider webhook end to end (needs a gateway), and the 503 against the live Egyptian gateways' retry policy.

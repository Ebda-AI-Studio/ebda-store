# STORE-EDGE-4

> Section: 2026-11-15 - quiet-hour storefront latency (edge stale window) and the status probe's slow state

Ruling STORE-EDGE-4 (2026-11-15) - (1) `STORE_EDGE_STALE_S` in `apps/web/store-edge-cache.ts` goes from 600 s to 21 600 s (6 h); fresh stays 60 s. Evidence (measured, CF analytics, worker `ebda-web`, 2026-11-14/15): busy hours (~1 300 req/h) p50 ~130 ms; quiet hours (100-300 req/h) p50 2-4 s, p99 6-12 s, ~10 subrequests per request, CPU p50 ~150 ms cold vs ~20 ms warm. Cause (inferred from the code path, not measured per page): in a quiet hour the page a shopper asks for was last requested more than 600 s ago, so it was a MISS: a full cold render in front of the shopper. With a 6 h window the same shopper gets the stored copy at once (`x-store-edge: STALE`) and the refresh runs in `waitUntil`. Expected quiet-hour p50: single-digit-to-tens of ms for a page asked for at least once in the last 6 h in that data centre (the cold isolate start of ~150 ms CPU remains); a page never asked for in that data centre in 6 h, and the first request after every deploy (EDGE-BUILD-1 keeps the key space per build), are still cold. Not measured after the change: that needs the deploy and a day of analytics.

Staleness class: price, stock, availability, status, theme, layout = NEVER-stale (event-invalidated; the TTL is only an outer bound). Blog, categories, static pages = BOUNDED-stale under the same purge. The TTL was never what kept price right: the per-store R2 epoch is checked on the fresh AND the stale copy (STORE-EDGE-1/2). A lost purge is not left to the TTL (review, Opus, 2026-11-15): `revalidateStorefrontWithRetry` stays the fast path (3 tries in `waitUntil`); when it ends `failed` or `rejected` (401/503) it enqueues the same purge as event `storefront/purge.retry` -> job `storefront-purge-retry` (jobs queue, 6 retries with backoff, then the job layer's final-failure path: P1 platform alert + Sentry via `reportJobFailure`, message dead-lettered). If even the enqueue throws it logs `purge LOST and could not be queued` at error level. Deviation from "enqueue every purge": a purge that LANDS in the request queues nothing (one extra job run per write would double the cost of every merchant save); the residual is an isolate killed inside its 17 s `waitUntil` budget before the fast path finishes (outside the failure path, so neither queued nor logged). Test: `tests/unit/storefront-purge-durable.test.ts`.

Bundle sale windows (start/expiry, buyability computed per request, `bundle.routes.ts` `withinSaleWindow`) change with no write. Create/update/deactivate call `scheduleBundleBoundary`: it publishes the store's NEXT boundary to the storefront Worker as the purge-channel tag `bundle-boundary:<storeId>:<epochMs>` (stored as `html-epoch/boundary/<id>`; it is NOT an epoch bump) and starts workflow `storefront-bundle-boundary` (id = `<store>:<at>`, so repeats are one instance). The workflow `sleepUntil(at + 2 s)`, purges `products|categories|bundles:<id>` plus the following boundary, then schedules that one. Belt and braces: `entryEpochState` ends a cached copy's life at the boundary (rendered before it, now at or after it), so a lost or late job still cannot extend an expired or not-yet-started bundle past T. Tests (fake timers): `tests/unit/storefront-purge-durable.test.ts`. Timed prices in cached pages, confirmed by code (Opus found the same, then re-verified here): ONLY bundle windows. Coupons and promotions are evaluated in the cart/checkout dry-run (`public.routes.ts` order-preview path), products have no start/end price columns, price tiers are signed-in only (cookie bypass), gold-rate changes are writes (`purgeGoldPrices`). Other residuals unchanged (isolate epoch memo 2 s; KV window <= 60 s on a render right after a purge).

Because the window is now long, every write path that changes what an anonymous page renders was enumerated (map: header of `tests/unit/storefront-edge-write-paths.test.ts`). Gaps found and closed: product carousel reorder (new arrivals / best sellers) cleared Redis only; product FAQ create/update/delete purged nothing; AI autofill / language balance / balance revert and the admin product-name repair wrote product copy and purged nothing; blog create/update/delete purged nothing (and the blog fetches were untagged). All now purge (`invalidateStoreProductCaches`, or `purgeStorefrontBlog` -> `blog:<storeId>`, mapped to the store epoch in `epochKeysForTag`, with the blog fetches tagged). Confirmed not edge-relevant: coupons and promotions (cart and checkout dry-run only), price tiers and customer groups (signed-in buyers carry a cookie and bypass), cart, shipping carrier config, barcodes. Compatible with open PR #777 (tag cache: `apps/web/tag-cache-options.ts` only; the regional tag cache TTL is a different layer from this epoch check).

(2) The status probe (`apps/status`) hard timeout goes from 8 s to 15 s and adds a `slow` state: a correct 200 slower than 8 s is Degraded (never paged); DOWN only on non-200, body mismatch, timeout > 15 s, or 2 consecutive slow probes. Per-probe duration is stored (`last_latency`, `last_slow`) and shown on the page and in `/api/status.json`. Cadence stays 5 min (frugality ruling). No keep-warm pinging: no traffic is added to keep isolates warm (Ahmad's no-traffic-without-users rule). Tests: `tests/unit/storefront-edge-write-paths.test.ts`, `tests/unit/store-edge-cache.test.ts`, `apps/status/test/status.test.ts`.

Cost if wrong: if both the in-request purge and the queued retries fail (all 7 attempts, alert raised), a price or stock change shows on a cached page for up to 6 h instead of 10 min (checkout re-reads price and stock from the store, so it cannot charge the old price or oversell); a slow-but-up service shows amber instead of paging, so a real brown-out is noticed one probe later (2 slow probes = 5-10 min).

Later boundaries rely on the chain: the web cache cutoff only knows the NEXT boundary (one value per store, `html-epoch/boundary/<id>`). Each `storefront-bundle-boundary` run publishes the FOLLOWING boundary in its own purge and schedules the next run, so a copy is capped at every boundary as long as the chain runs; a failed run raises the job layer's P1 alert (and the in-request purge path re-publishes the nearest boundary on every bundle write). Tested after each boundary, including a boundary passing with no job run: `tests/unit/storefront-purge-durable.test.ts`. The lookup for the next boundary is the true earliest start/end (`ORDER BY ... LIMIT 1` per column), tested with 700 bundles where the earliest was inserted last. The one purge loss not queued is STORE-EDGE-5.

# PERF-LAT-1

> Section: Pre-launch latency deep-dive 2026-11-09 (branch `perf/launch-latency`, launch map PERF-LATENCY)

Ruling PERF-LAT-1 - every remote binding call is tallied per request (`lib/io-tally.ts`: D1, StoreDO, AuthState, other DOs, the identity service binding, KV) and reported in `Server-Timing` with the number of serial round trips (`io-waves`); `apps/api/workers-test/latency-budget.test.ts` fails CI when a hot path (store resolve, product list, PDP, cart get / add, guest order create, customer sign-in, `/auth/me`, merchant order list) makes more remote calls or more serial waves than its ceiling. Fixes in the same PR, each a pure reordering of reads or an in-request dedupe, none removing a check: (1) `backendFor` is memoised for ONE request (`lib/request-memo.ts`; a failed load is never kept; the directory lookup that already read the row seeds it), staleness window = one request, no request flips a backend (the flip is the operator cutover outside Express); (2) the HS256 jti denylist read and the token-version read run in parallel, both still refuse; (3) customer sign-in reads the lockout and the credential in parallel (a locked account still gets 429 before any compare), clears the lockout + logs the success alongside the session issue (always awaited), and mints CSRF alongside the audit row. Tried and reverted: starting `getEntitlements`' subscription read together with the store-plan read (it reached the request client on the branch where the store row is absent, which on the Worker is the Postgres-removed client). NOT done here, needs its own review: `authenticate` still asks `Accounts.isRevoked` on every live request (no negative cache: it is already one parallel round trip with the 30 s account-state cache, FP-4), the post-order cache bust runs 7 invalidations serially (handed to the storefront-cache track, `lib/public-cache.ts`), the cart / order services still make 10 StoreDO calls each (NEON-SCALE-1 wants ONE batched call; a money-path change). In production the credential routes omit the per-binding counts (no account-existence signal). Evidence: the budget test is red on `origin/main` (sign-in 11 waves > 8, merchant order list 7 > 4, order create 38 > 37, ...) and green twice on the branch; `tests/unit/io-tally.test.ts`. Cost if wrong: a memoised backend flag could serve one request a backend that changed during it; only the operator cutover changes it and it is not an Express route.

Addendum 2026-11-09 (after merging main with #473, launch rate limits): the ceilings rise by one call and one serial wave on store resolve, product list, PDP, cart add and order create (`rl:store-miss`, an AuthState hit on every public store request) and on customer sign-in (`rl:auth-ip-fail`). Those are deliberate security limiters, measured on workerd with this branch's fixes in place. Running them in parallel with the other rate-limit hits is a follow-up for the rate-limit owner. Cost if wrong: if this were really a regression it would hide one hop per path, but the op trace names both keys.

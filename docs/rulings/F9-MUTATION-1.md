Ruling F9-MUTATION-1 - NOT ADDED: no separate `mutation-testing.yml`. Mutation testing already runs as the `mutation` job in `.github/workflows/ci.yml` (Sunday cron `17 1 * * 0`, or `workflow_dispatch` with `mutation` ticked): `npx stryker run` over `stryker.conf.json` (auth.service, payment.service, recommendation.service, ai-quota) plus `node scripts/defence-mutation-record.mjs --tier=unit`, which deletes each guard registered in `docs/security/defence-mutations.json` and asserts its test goes red. It runs on `vars.EBDA_RUNS_ON` (the self-hosted Umbra runner) so it costs no hosted-runner minutes, and it is in `notify-failure`'s needs. Measured 2026-10-29: the Sunday 2026-10-25 scheduled CI run's "Mutation tests" job concluded `success`. The plan's wording ("add the source file to `mutation-testing.yml` `paths`", p2-backlog plan) assumed a path-filtered PR workflow; a PR-triggered Stryker run on hosted runners would spend minutes the weekly Umbra job does not, and a `paths` filter is exactly the way a new guard silently escapes (the record lists guards by id, not by path). The registered record, not a path list, is the gate. Residual: `stryker.conf.json` mutates 4 files, not every defence module; the defence record is the broader net. Cost if wrong: a defence added to a file outside both lists is not mutation-proven until someone registers it; the weekly job cannot notice.

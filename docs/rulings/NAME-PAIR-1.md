# NAME-PAIR-1

Ruling NAME-PAIR-1 - a product's name is accepted in either language: `name` / `nameEn` (English), `nameAr` (Arabic), optional `sourceLang` for a lone `name`; at least one is required on create. Arabic-script text in the English field with no Arabic name is the Arabic name; Arabic in `name` with English-only `nameAr` is a swapped pair and is put right; an Arabic-only product stores `name` as a PLACEHOLDER copy (the column is NOT NULL) that is not stamped as merchant-typed, so the autofill translates INTO it. The autofill never translates a source written in the other script and never overwrites a merchant-owned name. An update that sends only `nameAr` never changes `name`. The quick-create form sends each name in its own field; onboarding sends `sourceLang` = the admin's language. A super-admin `POST /admin/stores/:id/repair-product-names` reports (default, dry run) or with `{ "apply": true }` repairs swapped / Arabic-in-English / placeholder pairs. Evidence: 2026-11-10 store 1bb14d0e: the quick form stored Arabic in `name` (Arabic on /en), the onboarding product came back `name` = Arabic, `nameAr` = "Sign Ring"; `workers-test/merchant-catalogue.test.ts` and `tests/unit/product-name-pair.test.ts` (autofill cases red on main). Cost if wrong: a product whose English name is deliberately identical to its Arabic name gets that English name replaced by a translation once (the merchant can type it again; it is then theirs).

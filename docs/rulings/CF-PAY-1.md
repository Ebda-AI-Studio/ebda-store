# CF-PAY-1

Ruling CF-PAY-1 (2026-10-29, INFRA-CF-1 PR D2b-3) - payments, webhooks, refunds and gold repricing are named StoreDO `moneyOp`s, each ONE `transactionSync` section with the data itself as the idempotency marker: `paymentCreate`, `paymentWebhook`, `refundBegin`/`refundComplete`/`refundRelease`/`refundIndeterminate`, `refundBook` (full, partial, store credit), `goldApplyRates`/`goldDecidePending`/`goldUpdateSettings`/`goldRepriceProduct`, `fanoutDisarm` (engines already in `payments.ts`, `refund.ts`, `gold-rates.ts`; the registry in `do/money-ops.ts` is the only door). (1) WEBHOOKS: `PaymentService.handleWebhook` for a DO store verifies the signature as before, runs the Kashier confirm-before-apply OUTSIDE the DO (no answer = 503 `WEBHOOK_UNCONFIRMED`, nothing written) and applies the gateway's answer with `paymentWebhook`; the event identity is derived from the verified payload (event, refund id, transaction, status, amount), `payment_event_log (provider, event_id)` is written in the same section as the effects, so a replay applies once whatever the key (20 concurrent deliveries: one `applied`, 19 `replayed`, on real workerd). The WEBHOOK-SCOPE-1 store-scoped key is unchanged on the route; `markWebhookProcessed` stamps nothing for a DO store (there is no Postgres order row). (2) ROUTING: a reference Postgres does not know is resolved through the D1 entity index (`webhook` `<provider>:<ref>`, written in the SAME DO section that creates the payment, drained by the alarm) EXACTLY like the Postgres resolver (`ebda_webhook_resolve_store_scoped`): an empty provider resolves nothing, the unscoped `payment` kind is never read for a gateway ref, the URL's store (`preferStoreId`) must equal the index row or the answer is the same 503 as unknown, and only a store the fleet flag lists is ever routed (`tests/unit/webhook-do-resolver.test.ts`). A reference neither side resolves, while any store is flagged for the DO, is answered 503 + Retry-After (never the constant 401, which the gateway would not retry) with a P0 alert of fixed title (throttled); the answer is identical for a forged delivery, so it reveals nothing. (3) REFUNDS: `PaymentService.refund` for a DO store claims BEFORE the provider call (`refundBegin`: balance CAS + `refund_initiated`; a second attempt with one `refundKey` is `REFUND_ALREADY_ISSUED`, 20 concurrent full claims: one wins) and records the outcome AFTER (`refundComplete`, `refundRelease` on a provider rejection, `refundIndeterminate` on a timeout, the claim stands); a full refund then runs `refundBook` (whole-order reversal in one section: stock, coupon, loyalty, wallet, backorders; 20 concurrent bookings restore stock once) and the `order/refunded` fan-out. `OrderService.updateStatus(...,'refunded')` on a DO store is `refundBook` with `keepPaymentStatus` (FOUND by the contract test: the merchant status path leaves `payment_status` as Postgres does, the provider paths flip it). Any other status of a DO order is refused 501 `ORDER_STATUS_NOT_ON_DO` until the order reads move. (4) EXTERNAL MONEY FACTS ARE RECORDED IN FULL, NEVER REJECTED (feedback-never-reject-an-external-money-fact): FOUND in the engine and fixed - `completeRefund` and the refund-webhook booking called `refundOrder`, whose ceiling (`REFUND_EXCEEDS_ORDER`) and state checks threw AFTER the gateway had moved the money, rolling back the record of a refund that happened. They now pass `external: true`: the full amount is stored on the marker event with `review` set and an alert, and a completed full-refund webhook on an order the machine would not move to `refunded` records the payment and alerts instead of throwing. The same calls from an internal, not-yet-executed refund are still refused. (5) GOLD: `GoldRateService.applyRates`, `decidePending` and `updateSettings` call the DO ops (jump gate, history, current row and the repricer with `do_flags.gold_reprice` on are one section, so an order sees the old rate or the new one); `setProductPricing`, `asRepricer` and `bulkSwitchMode` run caller closures inside the repricer transaction and are refused 501 `GOLD_PRICING_NOT_ON_DO`. (6) SWEEP: `order-status-fanout-stuck-sweep` reads through `storeDb` and disarms a superseded transition through `fanoutDisarm`, so it is a `ported` job (no longer a P0 refusal for a DO store). (7) INSTAPAY RECEIPTS: NOT moved - an ORDER receipt upload/submit for a DO store is refused 501 `INSTAPAY_RECEIPTS_NOT_ON_DO` (the cross-store `reference_key` uniqueness needs its own D1 index kind); confirm and expiry already ran on the DO (CF-ORDERS-1). Evidence: `packages/repo/test/do-payment-ops.test.ts` (14), `apps/api/workers-do/payments.test.ts` on real workerd (6), `tests/integration/repo-factory-payments-contract.test.ts` (ledger, refund by status, gold: Postgres 17 vs the DO schema, equal traces and tables), `tests/unit/webhook-do-resolver.test.ts` (8). Not covered by a Postgres-vs-DO contract: `PaymentService.handleWebhook`/`refund` end to end (a provider adapter and its credentials are needed to drive the real service; the engine behaviour is covered by `do-payments.test.ts` and the workerd tests, the Worker mapping by review). Cost if wrong: with every flag at `pg` the payment services run their Postgres code unchanged; a wrong DO payment write is reachable only for a store the operator flipped (one D1 UPDATE back) and the cutover gate stays closed until carts, fiscal documents, delivery slots, personalisation, quotes and the order reads move.

# NZ-CARRIER-1

Ruling NZ-CARRIER-1 (2026-11-11, Postgres removed from the Worker; row 11 of `docs/cf/neon-zero-final-classification.md`) - a carrier-config save or webhook-secret rotation on a store's Durable Object is a compare-and-swap on `updatedAt`, not a row lock: the Worker reaches the DO in separate calls, so the Postgres `SELECT ... FOR UPDATE` inside one transaction has no DO equivalent (the DO serialises each call, not a read-then-write pair across two calls). The save reads the row fresh (the merge base for a secret), computes the same merge as the Postgres path (one shared `plan()`), then writes `updateMany({ where: { storeId, carrier, updatedAt: <read> } })`; a count of 0 means a concurrent save won and answers 409 `CARRIER_CONFIG_CHANGED` with nothing written (the merchant reloads and saves again), and two concurrent first saves meet the (store, carrier) unique key the same way. Making it the default clears the other carriers' flag only after this row was written (a brief two-defaults window, never a lost secret); `setDefaultCarrier` sets the flag only on a still-enabled row inside one DO batch. The Postgres path is unchanged. Cost if wrong: a merchant saving the same carrier from two tabs within milliseconds sees a 409 and must re-save (never a silently reverted credential).

# PIXEL-CONSENT-1

> Section: Launch blockers 31 and 32 (privacy): the search term and the ad pixels

- Ruling PIXEL-CONSENT-1 (launch blocker 32; closes the SEARCH-T5-9 residual "the pixels' own PageView reads `/search?q=<term>`") - no pixel traffic of any kind before marketing consent, and none on a URL a pixel must not read. Findings: the SSR gate in `layout.tsx` plus the inner `consent.marketing === true` check already kept every provider SCRIPT (Meta, TikTok, Snap, X, Pinterest, GA4, Google Ads, GTM) off the page without consent; the `track*` helpers only worked because a provider global happened to be absent, and every pixel reads the page URL itself, so a `?q=`, `?email=`, `?phone=` or one-time-token URL (`?token=` on reset-password and verify-email, `?restore=` on the cart-recovery link, `?waToken=` on the WhatsApp cart) reached the ad networks for a consenting shopper. Fix, for every provider at once: (a) `MarketingPixelsInner` renders no script and fires no PageView while the URL carries a blocked key (`urlCarriesSensitiveQuery` in `@ebda/shared`, one list with the Sentry, PostHog and API log scrubbers: `SENSITIVE_QUERY_PARAMS` now also holds `token`, `restore`, `waToken`, so PostHog and Sentry stop carrying a reset or verification token too); (b) a module-level `pixelEventsArmed` flag, set during render from the same `allowFire`, gates every `track*` helper (`trackViewContent`, `trackAddToCart`, `trackInitiateCheckout`, `trackSearch`, `trackAddToWishlist`, `trackLead`, `trackPurchase`, which returns `false` so the order stays reportable), so a library that is present for another reason (a merchant's GTM container, a stale tab) receives nothing; (c) the storefront search no longer has a term in its URL (SEARCH-URL-1); (d) Ebda's own acquisition tracker (`packages/shared/src/tracking/browser.ts`, used by `apps/marketing` and `apps/admin`, Meta Pixel + PostHog) was already consent-gated (nothing loads or fires before a yes, `tests/unit/ebda-tracking-browser.test.ts`) but ran PageView / CompleteRegistration on `/verify-email?token=`: it now neither loads Meta nor feeds it an event on a blocked URL; the server-side Conversions API event for the same step (same `event_id`) still goes, so only the browser half of CompleteRegistration is lost on that one page. Evidence: `apps/web/src/components/__tests__/MarketingPixels.consent.test.tsx` (undecided and rejected: no script, no provider call, no fetch or beacon, every helper a no-op with all six globals present; consented on a `?q=` / `?search=` / `?email=` / `?phone=` / `?token=` / `?restore=` / `?waToken=` URL: the same; control: consented on a clean URL, every provider loads and PageView fires), `apps/web/src/lib/pixel-url-guard.test.ts`, `tests/unit/ebda-tracking-browser.test.ts` (the own tracker on a blocked URL). Accepted residuals, named: a library already loaded on the page (single-page navigation from a clean URL to a blocked one) can still read the new URL itself, for example Meta's own history listener; the blocked pages (reset-password, verify-email, cart restore, WhatsApp cart) are reached by a link from an email or a message, which is a full page load, so no pixel is loaded there; the Search event still sends a non-PII-shaped term as an event PARAMETER to a consenting shopper's pixels (SEARCH-T5-9, unchanged). Cost if wrong: a shopper on a blocked URL is invisible to the merchant's ad pixels for that page view (a lost PageView, never a lost purchase: the order confirmation URL carries no blocked key).

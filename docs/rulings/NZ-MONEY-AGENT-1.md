# NZ-MONEY-AGENT-1

Ruling NZ-MONEY-AGENT-1 (2026-11-11, follows NZ-MCP-1) - the agent `place_order` COD payment goes through the storefront COD service (`PaymentService.recordCodPayment`, DO `paymentCreate`: the `cod_pending` payment, its `created` event and the index rows in ONE section, idempotent per order) instead of its own `withTenantContext` + `payment.create` + `recordPaymentEvent`, and audits `payment.created` only when the call was not a replay. Why: the agent path was a second, divergent writer of the same money row, and it was the last Postgres write of the checkout; one service means one amount, one event and one replay rule for human and agent orders, and a failure still runs the existing compensating order rollback. Proof: `workers-test/merchant-mcp-do.test.ts` places a COD order through the buyer MCP endpoint on a store with no Postgres (one `cod_pending` payment, one `created` event, `pgReaches` empty, a repeated call adds no payment or order); on the previous code it fails with POSTGRES_REMOVED ($transaction). Test seam: the agent key cannot exist on a DO store yet (the mint route fails STORE_RECORD_REFUSED and StoreCredential is MODEL_NOT_WRITABLE), so the test uses the store's `agent_checkout_open_writes` grant, which passes the same write gate. Cost if wrong: an agent COD order whose payment write fails after the order committed is rolled back and reported failed, so a COD agent checkout could fail visibly (never silently double-charge) until the service is fixed.

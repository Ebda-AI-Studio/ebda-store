# CF-R7-1

Ruling CF-R7-1 (2026-10-30, INFRA-CF-1 R7, Ahmad via the controller) - the three flows the flip gate listed as `postgresOnly` write the Durable Object for a DO store, so the gate (`node scripts/cf/not-on-do.mjs`) reports `postgresOnly: 0` and exits 0. (1) ACCOUNTING: purchase orders (`createPurchaseOrder`, `receivePurchaseOrder`, `cancelPurchaseOrder`, and the reorder suggestion accepted in the same section), stock adjustments (`createStockAdjustment`, `postStockAdjustment`, including the CSV import with its per-store import key), the chart seed plus the one-time opening-balance journal (`seedCoa`, `openingBalance`) and the ownership check (`assertStoreOwnsInTenantScope` reads the DO client for a DO store). (2) BARCODE SCAN STOCK: scan-to-receive of a variant (`receiveVariant`) and the count-session lines, close and reconcile (`openCountSession`, `submitCountLine`, `closeCountSession`, `reconcileCountSession`: the reconcile creates and posts the cycle_count adjustment and marks the session in ONE section). (3) PRODUCT BULK UPDATE: `fields.inventory` (`bulkSetInventory`, simple products only, floored at 0, no history row, exactly like Postgres). Each is one named operation of `packages/repo/src/do/stock-books.ts`, run as ONE `transactionSync` section through `stockOp` (so it may carry an idempotency key). The DO is single threaded, so the Postgres row locks (the PO row, the products being received, the draft being posted, the sequence upsert) are not needed: the check and the write cannot be separated by another request. The posting of the journals stays with the existing jobs (`stock/po-received`, `stock/adjustment-posted` fire from the service as before and the DO journal ops from CF-JOBS-4 serve them). Deliberate differences, each the safer side: the warehouse shadow re-sync runs INSIDE the section (Postgres runs it best-effort after commit); a refused create of an import key rolls its number claim back (Postgres burns an ADJ number on the failed insert), and the refusal is surfaced as the same P2002-on-import_key shape so the CSV route's replay still fires; the bulk-update op re-derives the simple-product set in the DO. READS follow: list / get of purchase orders and adjustments, the import-key lookup, count-session list / get and the CSV lookup go through `storeDb`. Evidence: `packages/repo/test/do-stock-books.test.ts` (16 on the real DO schema), `tests/integration/repo-factory-r7-books-contract.test.ts` (12 scenarios, Postgres 17 vs the DO, equal answers AND equal rows: adjustments, POs with weighted-average cost, backorder FIFO and stock-debt heal, opening balance, count sessions, variant scan, bulk inventory), and `apps/api/workers-do/books.test.ts` on real workerd with no lock (20 concurrent posts of one draft apply once; 30 concurrent 1-unit receives against a PO of 10 apply exactly 10; 80 concurrent drafts get 80 distinct numbers; one import key creates one adjustment; one opening-balance journal; one reconcile). Cost if wrong: with every flag at `pg` nothing here changes behaviour (`storeStock` is null and the Postgres code runs); for a flipped store a wrong op is one D1 UPDATE back to `pg` and the gate refuses the flip while `postgresOnly` is non-empty.

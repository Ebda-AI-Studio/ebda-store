# CSP-ACCOUNTS-1

> Section: 2026-11-02 - merchant sign-in blocked by connect-src (branch `fix/csp-connect-src-accounts`)

Ruling CSP-ACCOUNTS-1 - the `connect-src` of every Ebda app names exactly the origins its browser code fetches, no wildcards. Admin (store.ebda.app) and Orders (orders.ebda.app) sign in from the browser against the identity service: `apps/admin/src/lib/accounts.ts` and `apps/orders/src/lib/accounts.ts` call `fetch(`${NEXT*PUBLIC_ACCOUNTS_URL || 'https://accounts.ebda.app'}...`)` with credentials, but their CSP builders (`apps/admin/src/lib/csp.ts`, `apps/orders/src/lib/csp.ts`) never listed `https://accounts.ebda.app`, so the browser blocked the call ("Failed to fetch"). It broke when both landed together on 2026-10-28: the accounts clients in #216 (feat(identity), fbe5a11e3) and the builders in the wave-2 integration (8256f72f4); `accounts.ebda.app` was never in either `connect-src`. Fix: each builder takes the accounts origin (`accountsOrigin(process.env.NEXT_PUBLIC_ACCOUNTS_URL)`, https or loopback only) and writes it into `connect-src`; the storefront (apps/web) never calls accounts from the browser and is unchanged; marketing, help, docs, status and accounts itself make no cross-origin browser fetch to an Ebda origin. Guard: `tests/unit/csp-connect-src-covers-browser-clients.test.ts` requires every `NEXT_PUBLIC*_*URL/ORIGIN/HOST`base an app reads to be decided (an origin or null with a reason) and its origin to be present in that app's built`connect-src`. Cost if wrong: an app that fetches an origin through a base not named `NEXT_PUBLIC*_` (a hard-coded URL) is invisible to the guard; review those by hand when adding one.

# B2B Wholesale Pricing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. PLAN ONLY: no product code ships with this file.

**Goal:** A growing Egyptian brand can sell to resellers on Ebda without leaving for Salla/Zid/Shopify: quantity price breaks per product/variant, customer groups with a group price (percent off, or explicit tier prices), wholesale-only products and a minimum order quantity (MOQ), a shopper-applies / merchant-approves wholesale account flow, and wholesale prices that only an authenticated approved buyer ever receives. Every surface that charges, shows or records a price uses the same server-side resolver, and the invoice shows which tier was applied. Business plan and above by default (Ruling B2B-1).

**Architecture:** One pure function `resolveUnitPrice` in `packages/shared/src/pricing/` (inputs: base price, quantity, buyer group, candidate tiers; output: unit price in piastres + provenance) wrapped by one loader `PriceResolver` in `apps/api/src/services/price-resolver.service.ts` (loads tiers + group, decides the buyer from the AUTHENTICATED user id only). It replaces `cartLineUnitPrice` (`apps/api/src/lib/cart-pricing.ts`) as the single place a charged unit price is decided, the same way `lineAllowsBackorder` replaced six scattered stock reads. Group membership already exists (`CustomerGroup`, `Customer.groupId`); this plan adds pricing fields to the group, a `product_price_tiers` table, MOQ/audience columns on products, a `wholesale_applications` table, and order-line snapshots (`list_price`, `price_source`, `price_tier_min_qty`) so invoices, returns and analytics never re-derive a price. Public product payloads carry only PUBLIC tiers (`group_id IS NULL`); group-specific prices come from a separate authenticated, `no-store` endpoint and are painted client-side so the cached/edge-cached storefront pages stay anonymous-safe.

**Tech Stack:** TypeScript, Zod 3, Prisma 6.19 (strict RLS as `ebda_app`, tenant guard), Express on Cloudflare Workers, Inngest, Next.js 16 (web + admin, next-intl), Vitest 4 (supertest + real Postgres for integration).

## Decisions (binding unless Ahmad overrides; each is a Ruling written to docs/RULINGS.md in Task 8)

- **Ruling B2B-1 — Plan gating.** Feature key `b2b.wholesale` ON by default for `business` and `comped`; OFF for `free/basic/growth/pro`; super-admin override per store (existing mechanism). Evidence: Business is the `featureTier: 'enterprise'` plan with 15 staff and unlimited orders; wholesale is a reseller-scale feature. Cost if wrong: a Growth merchant asks to unlock it and a plan seed edit ships.
- **Ruling B2B-2 — Price identity is the authenticated user id, never a typed phone/email (extended by B2B-2c: bound through `customers.user_id`).** `resolveCustomerContext` matches a Customer by shipping phone/email and is correct for promotion targeting (a guest typing a VIP's phone gets, at worst, a promo). A PRICE must never work that way: anyone could type a wholesaler's phone at guest checkout and be charged wholesale. The resolver takes `buyerUserId` from the verified session; guests, WhatsApp-bot sessions and payment-link payers are retail unless the merchant creates the order for a named customer in admin. Cost if wrong: a verified-by-WhatsApp wholesaler orders at retail until a later plan adds the WA path.
- **Ruling B2B-3 — Resolution order (SUPERSEDED by B2B-3b below; kept for history).** Candidates, after stripping tiers with `minQty > qty`: (1) tier for (variant, group) → (2) (product, group) → (3) (variant, all) → (4) (product, all); within a level the tier with the largest `minQty <= qty`. If no tier: group `percent_off` (basis points) on the base price; else base. Result is clamped to `[0, base]` (a tier above retail is rejected at write time AND clamped at read time) and group percent uses integer round-half-up on piastres (`Math.round(base * (10000 - bps) / 10000)`). Variant price = `variant.price ?? product.price` exactly as today; a product's own sale price is the base. Cost if wrong: a merchant expecting "lowest wins" sees a less-specific cheaper tier lose; the order line records `price_source` so it is explainable.
- **Ruling B2B-4 — Quantity for tier lookup = total quantity of that product (or variant for variant-level tiers) across cart lines in the same cart**, summed after merging note-lines. MOQ is per product, summed across its variants. Cost if wrong: a buyer of 6 + 6 across two sizes is priced as 12 when the merchant meant per-variant; mitigated by a per-tier `scope` is NOT added (YAGNI).
- **Ruling B2B-5 — Coupons and automatic promotions do not apply to lines priced by tier or group (`price_source != 'base'`).** Wholesale margin is already thin; stacking a 20% coupon on a tier price can go below cost. Public (all-buyer) quantity breaks are `price_source = 'tier'` too, so they also exclude coupons. Cost if wrong: a merchant wanting stacking asks for a per-promotion toggle (not built now). Mirrors the existing "a coupon never stacks onto an already-discounted box" bundle rule (Ruling B1).
- **Ruling B2B-6 — VAT.** Egyptian VAT is already modelled; the resolved price is the price on the merchant's existing basis (`taxIncludedInPrice`). Wholesale tiers are entered on the same basis as retail prices (the admin form shows the store's basis next to every price field). No per-group VAT, no reverse charge, no buyer TRN in this plan. Cost if wrong: a merchant who prices wholesale ex-VAT while retail is VAT-inclusive undercharges 14%; the form label and a Review Focus test pin the single basis.
- **Ruling B2B-7 — Wholesale-only products are invisible, not just unpurchasable, to anyone not in an approved wholesale group.** `Product.audience = 'wholesale_only'` removes the product from public list, search, sitemap, feeds, semantic index, recommendations and the WA catalogue for non-approved buyers, and cart-add returns 404 (not 403, no existence oracle). Cost if wrong: a merchant wanted "visible, login to buy"; that is a different flag and a follow-up.

## Design review 2026-10-21 (Opus, `.superpowers/b2b-design-review.md`) - rulings that SUPERSEDE or extend the Decisions above

Applied to Tasks 1-2 in migration `20261028000300_b2b_identity_link_ownership_fks`, `resolve-unit-price.ts`, `price-resolver.service.ts`, `lib/buyer-identity.ts`. Where this block and an earlier Ruling disagree, this block wins. Each is copied into `docs/RULINGS.md` in Task 8.

- **Ruling B2B-1b - Restrictions survive a downgrade; benefits do not.** MOQ and `audience = wholesale_only` stay enforced whatever the plan; tier prices (public AND group) and group pricing switch off. The merchant can still clear MOQ / audience on a downgraded store. Cost if wrong: a downgraded merchant who wants MOQ gone has one extra click; the opposite failure (single-unit orders a merchant forbade) costs stock and margin.
- **Ruling B2B-2c - A wholesale price is granted only through `customers.user_id`** (the link between the CRM row and the registered shopper), never through an email or phone match. `assignByIdentity` matches phone first and overwrites email, and `User.phone` is self-editable and unverified, so a match on either can be steered by typed input. The link is set only by (a) Task 5 approval, from `wholesale_applications.user_id` (which came from the session), or (b) the merchant's group dropdown on a REGISTERED shopper's profile (upsert by `user_id`). Guest / CRM rows written by `assignByIdentity` never confer a price. The composite FK `(store_id, user_id) -> users(store_id, id) ON DELETE SET NULL (user_id)` makes a cross-store link impossible. Cost if wrong: one merchant click moves a wholesaler's group to an attacker's account and the real wholesaler silently drops to retail.
- **Ruling B2B-2d - An admin order or payment link prices as the Customer the merchant explicitly selects BY ID**, never from a typed phone or email; with nothing selected it is retail. Record `priceSource` per line, `Order.priceGroupName` and an audit entry with the acting staff id. Cost if wrong: a merchant who types a phone expecting auto-pricing gets retail and must pick the customer.
- **Ruling B2B-3b - Lowest merchant-authored price visible to this buyer at this quantity; specificity decides only within one audience; no stacking** (replaces the selection step of B2B-3). (1) `pub` = best PUBLIC tier (variant-level beats product-level, then the lowest price, then the smaller minQty); (2) `gTier` = the same over the buyer's active-group tiers; (3) `gPct` = group percent off base; (4) `unit = min(pub, gTier, gPct)` clamped to `[0, base]`; (5) provenance tie-break gTier -> gPct -> pub; `unit == base` reports `base`. A tier is a candidate only if its minQty is reached, its price is `< base` (a stale / useless tier is dropped, so it cannot mask the group %), and a product-level tier applies only when `base == product.price` (a variant with its own price needs variant-level tiers). Guarantees (property tests): `0 <= unit <= base`; `unit(group buyer) <= unit(anonymous)`; unit is always one of base / a tier price / the percent price; independent of input order. Cost if wrong: a merchant who deliberately set a group tier dearer than the public break sees the cheaper public price win; the line records `price_source` so it is explainable.
- **Ruling B2B-3r - Round half-up, per unit, once.** `unit = floor((base * (10000 - bps) + 5000) / 10000)`, `line = unit * qty`, `subtotal = sum(line)`; never round a line from a fractional unit. Cost if wrong: the merchant gains at most 0.5 piastre per unit on a tie.
- **Ruling B2B-4 (extended, I4) - Only orderable, loose (non-bundle) lines are summed** into the product / variant quantity; an unavailable line must not carry a cart over a tier. **Ruling B2B-8b - bundle components do not count toward tier quantity or MOQ, and MOQ does not apply inside a bundle.** Cost if wrong: a merchant expects a bundle to count toward a reseller's 10+ break; the follow-up is a per-bundle flag.
- **Ruling B2B-7b - Public catalogue routes are always computed as anonymous.** They never read identity, never include group prices, always exclude `wholesale_only`; buyer-specific data comes only from authenticated `no-store` routes (`/public/pricing/resolve` plus a wholesale catalogue route). Cost if wrong: an approved buyer's wholesale-only catalogue needs one extra authenticated call.
- **Ruling B2B-9 - The order transaction is the only moment a price becomes binding.** Cart, PDP and pricing-resolve outputs are quotes. `POST /public/orders` re-resolves everything inside the transaction (buyer row, `customers.user_id` link, group `isActive`, UNCACHED entitlement, tiers, MOQ); the client's `expectedTotal` is used only to compare, never to charge; a mismatch is 409 `PRICE_CHANGED` with the new lines. Once created, the persisted lines are the contract: payment init reads the persisted order and does NOT re-resolve (this replaces RF6's re-resolve-at-pay). Cost if wrong: a wholesaler revoked after creating an unpaid order can still pay that one order at wholesale; the merchant can cancel it.
- **Ruling B2B-10 (Ahmad, 2026-10-21) - A partial return that drops the kept quantity below the tier threshold ADJUSTS the refund.** Refund = the paid amount of the returned units minus `(listPrice - paid unit price)` on the units KEPT, shown to the merchant before confirming, with an override. Specified in Task 8b. Cost if wrong: a buyer who returns a few units is refunded less than `price x quantity`; the merchant can override per return.
- **Ruling B2B-TEN-1 - Tier / group / application ownership is enforced by composite FKs, not only by the service** (migration `20261028000300`): tiers `(store_id, product_id)`, `(product_id, variant_id)`, `(store_id, group_id)`; applications `(store_id, user_id)`, `(store_id, group_id)`; customers `(store_id, group_id)`. The single-column FKs are kept (the Prisma relations sit on them). Cost if wrong: a service validation bug persists garbage rows that a later refactor starts charging.
- **Ruling B2B-2e (coordinator, 2026-10-21) - Group membership for promotions and coupons is decided by the SAME `BuyerIdentity` as prices.** `resolveCustomerContext(storeId, typed, buyer)` takes the group from `loadBuyerGroup(storeId, buyer)` (session via `customers.user_id`, or a merchant's explicit pick) and ignores the typed phone / email and the self-edited `User.phone`. Guest checkout has NO group benefits. First-order status keeps its typed-identity logic (it can only reduce what a typed identity gets). `assignByIdentity` never overwrites an existing row's email, phone or names; with a `userId` it matches/creates the row linked to that registered shopper (contact fields only where free), without one it matches phone then email and attaches the group only. Callers covered: `order.service` create + `createAdminOrder`, `coupon.routes` validate, `promotion.routes` preview. Cost if wrong: a guest who is a real VIP but checks out without signing in loses the VIP promo until they sign in; the merchant can issue a code instead.
- **Ruling B2B-12 (coordinator, 2026-10-21) - Task 4 rejects a variant-level tier priced above the product-level tier of the same audience** (`TIER_VARIANT_ABOVE_PRODUCT`), which closes the "price rises with quantity" corner of B2B-3b. Cost if wrong: a merchant who deliberately made one variant's break dearer than the product's is refused and must lower it.
- **Ruling B2B-13 (coordinator, 2026-10-21; supersedes the "list price" wording of B2B-10) - A partial return reprices the units the buyer KEEPS at the LOWEST tier they still reach, falling back to list price.** The merchant sees the calculation and can override it. Cost if wrong: a buyer who returns part of an order is refunded less than `price x quantity`; the merchant can override per return.
- **Ruling B2B-17 (controller, 2026-10-21, final review P1-1; amends B2B-13) - eligibility on return is judged on the PRODUCT aggregate across every loose line (variants, note-lines), exactly as the tier was awarded; the product-level adjustment is allocated over the returned items.** Text in `docs/RULINGS.md`.
- **Ruling B2B-18 (controller, 2026-10-21, final review P1-2; amends B2B-13) - kept units are repriced with the buyer's full sale-time entitlement (group percent + any tier still reached), never bare list price.** Text in `docs/RULINGS.md`.
- **Ruling B2B-20 (controller, 2026-10-21; amends B2B-14) - a shortfall the zero-refund floor swallowed is carried forward per product (`return_items.tier_carry`, migration 20261028000700) and collected FIRST by the product's later refunds (returns and the final release), never below 0 per refund, consumed exactly once, the B2B-14 release clamp intact; an override waives it (audited).** Full text in `docs/RULINGS.md`.
- **Ruling B2B-9a (money review M-1; supersedes the "inside the transaction" wording of B2B-9 and the Task 3 table) - Pricing resolves in the request, just before the money transaction opens, with no row lock.** Moving it inside the transaction would not close the race (a revoke committing after the in-transaction read still loses under READ COMMITTED unless the `customers` / `customer_groups` rows are read `FOR SHARE`). The binding mechanism is `expectedTotal` (409 `PRICE_CHANGED`), fed by the checkout's server quote. Cost if wrong: an order created within the request window after a revoke / downgrade carries the old price; the merchant cancels it.
- **Ruling B2B-M2 (coordinator, money review M-2) - Free-shipping coupons are ALLOWED on tier / group priced carts.** Shipping is not a price discount; the B2B-5 exclusion applies to the discount BASIS (percentage / fixed amounts), not to the shipping line. Cost if wrong: a wholesaler's tier cart ships free with a free-shipping code; the merchant limits such codes by scope or minimum.
- **Ruling B2B-M3 (coordinator, money review M-3) - Loyalty-point redemption is EXCLUDED on tier / group priced lines**, consistent with coupons: the redeemable base is `subtotal - nonBaseSubtotal - primaryDiscount` (`loyaltyRedeemableSubtotal`). Cost if wrong: a wholesaler cannot spend points on wholesale lines; they can on base-priced ones.
- **Ruling B2B-M8 (coordinator, money review M-8) - Payment links are retail-only (anonymous buyer + public tiers) for now.** A merchant-selected wholesale payment link is a future feature, built with an explicit Customer-id selection (never a phone lookup). Cost if wrong: a merchant cannot send a wholesale link and creates an admin order instead.
- **Ruling B2B-M9 (money review M-9) - Do not merge before Task 6.** `audience = wholesale_only` is read nowhere in `apps/api/src` until Task 6; until then a guest can cart and order a wholesale-only product at retail. The branch stays unmerged until B2B is complete.
- **Ruling B2B-I3 (money review I-3) - `assignByIdentity` without a `userId` matches only UNLINKED rows (`user_id IS NULL`); when only a row linked to a registered shopper matches the typed phone / email it refuses with 409 `IDENTITY_LINKED_TO_ACCOUNT` (the merchant assigns the group from that shopper's profile). A linked row never receives a phone copied from the shopper's self-edited profile.** Cost if wrong: a merchant assigning a guest key whose phone also belongs to a registered account sees a 409 and must use the profile.
- **Q-rulings.** Duplicate tier at the same scope+minQty: resolver takes the lower price, no throw (a throw turns a data defect into a checkout outage). Non-monotone tiers: rejected at write time in Task 4 (`TIER_NOT_MONOTONE`). Feature-read failure: propagates (5xx), never prices retail or wholesale on a failed read. Entitlement read: cached is fine for DISPLAY; order, payment-link and admin-order creation read it UNCACHED inside the transaction (`PriceResolver.forBuyer(..., { uncachedEntitlement })` is the seam, already built).

**Open item for Tasks 3-6 (found while applying C2, not decided by the review):** the review's "unit non-increasing in qty" guarantee holds inside one tier level, but because a variant-level tier beats a product-level one within an audience, a dearer variant-level tier reached at a higher quantity can replace a cheaper product-level tier (qty 10 -> product tier 7000; qty 20 -> variant tier 9000). The property test pins the one-level case and a table test pins the precedence; Task 4 write validation should therefore also reject a variant-level tier priced above the product-level tier in the same audience (`TIER_VARIANT_ABOVE_PRODUCT`).

## Global Constraints

- Arabic-first: every merchant- and shopper-facing string in `ar` and `en`; NUMERALS-1: Latin digits in the admin and emails; money through `fromMinor`/`toMinor` from `@ebda/shared` only (no float math on money, no `parseFloat` on prices).
- Money is integer piastres end to end. No new column is `Decimal`/`Float`. Percent discounts are integer basis points.
- **One resolver.** After Task 3 `grep -rn "\.price" apps/api/src` on a charge/display path must hit only the resolver, the snapshot writers, or a line in the Task 3 allow-list test. An architecture test enforces this (see Task 3), the way `no-rls-bypass-in-runtime.test.ts` does for RLS.
- **Never trust a client price.** No request body, query or header carries a price into cart, order, payment link, or WA flows; the server derives it. Existing zod schemas must be asserted to reject/ignore `price`/`unitPrice` keys on the new routes.
- Production has no Redis: `redis.service.ts` is a Cloudflare shim (KV_CACHE for `cache:*` payloads, Durable Object for strong state), so "Redis" below means that layer. Cache staleness class **NEVER-stale** for prices, MOQ, audience, group membership, approval status. Every write path that can change them calls the invalidation in the same transaction-after-commit hook (Task 4 lists them). BOUNDED-stale is NOT used for anything in this plan. An `invalidate*` with zero call-sites fails a test.
- Group-specific prices and wholesale-only products never appear in a cacheable response: no Redis, no `setEdgeCache`, no Next data-cache tag. Responses that vary by buyer send `Cache-Control: private, no-store` and `Vary: Cookie, Authorization`.
- Migrations: additive only, NEVER `lock_timeout`, new tables empty so plain `CREATE INDEX`; new columns nullable or with constant defaults (docs/DB-INDEX-MIGRATIONS.md). Names: `20261028000100_b2b_pricing_tables`, `20261028000200_b2b_product_columns_order_snapshots` (newest migration on ANY branch today is `20261025000100_merchant_webhooks`; re-check `git for-each-ref` + `ls migrations` on every branch before creating, and bump the date prefix if something newer landed).
- RLS: every new table has `store_id`, strict RLS with the canonical 3-branch policy (copy `20260721120000_customer_groups`), tenant-guard classification + regenerated snapshot (`npm run gen:tenant-guard-schema -w packages/database -- --check` exits 0). No `withRlsBypass`/`withOwnerTx` in `apps/api/src`.
- New FK on tenant tables: grep every delete/cascade handler (`ProductService.delete`, `variant.service` delete, `CustomerGroupService.remove`, store-closure, erasure/export) and check `information_schema.referential_constraints` for `NO ACTION` children (Task 1 Step 5).
- Erasure/export: `wholesale_applications` holds PII (business name, phone, commercial reg. no.): it must be in the customer export and erasure paths (`privacy-propagation.service.ts`, `store-closure.service.ts`) — Task 5.
- Route authorization: merchant routes = `authenticate → requireStoreAccess → requireFeature('b2b.wholesale') → rbac`; shopper routes = `customerUserId(req)` required; public price route is read-only and rate-limited.
- commitlint: lowercase subjects, blank line before trailers; `git add` named paths only.
- Storefront copy goes in the `apps/web/src/contexts/LanguageContext.tsx` translations map (EN + AR), never hard-coded in a theme (project rule 3 of Platform-level fixes).
- Platform-level: product-card price display is NOT changed per buyer in v1 (cards show retail / public-tier "from" price on all 8 card paths + Dahab + the 4 hand-built mappers, unchanged); buyer-specific price paints on PDP, cart and checkout only. Recorded as Ruling B2B-9; cost if wrong: a wholesaler sees retail on listing cards until a follow-up threads `BuyerPrice` through every card path.
- Tenant guard: every query on `ProductPriceTier` / `WholesaleApplication` carries a top-level `storeId` in `where`/`data`; use `withSavepoint()` for the unique-race writes (apply twice, tier minQty collision) because the request is one transaction.

- Integration tests are retry-safe (unique ids per call), run against the local Postgres described in the Test environment block.
- Do not weaken a test to make it pass; a failing money test blocks the task.

## Review Focus (money edge cases; each pinned by a named test)

1. **Cache and CDN leak.** An authenticated wholesale request for a PDP/price must never be stored by Redis, the CDN, or a Next data cache, and an anonymous request right after must see retail only. Pinned by `tests/integration/b2b-price-cache-isolation.test.ts`: hit `/public/pricing/resolve` as wholesaler, assert `Cache-Control: private, no-store` and no `s-maxage`; then anonymous `/public/products/:slug` has no group price and no wholesale-only product; assert the existing PDP route no longer calls `setEdgeCache` when `authorization` or the `token` cookie is present (this is a latent defect today).
2. **Typed phone is not identity.** Guest checkout with a wholesaler's phone/email is charged retail. `tests/integration/b2b-price-identity.test.ts`.

### Task 8b: Partial-return tier adjustment (Ruling B2B-10, Ahmad 2026-10-21)

**Rule (Ahmad, refined by Ruling B2B-13):** a partial return that drops the units KEPT below the tier threshold adjusts the refund: the kept units are repriced at the LOWEST tier they still reach, falling back to list price, and the refund is the paid amount of the returned units minus `(keptPrice - paid unit price)` on the units kept. Shown to the merchant before confirming (with the calculation), with an override.

**Definition (pure, `packages/shared/src/pricing/return-adjustment.ts`, no imports):** for an order line with quantity `N`, paid unit `b` (`OrderItem.price`), `L = listPrice`, `priceSource`, `m = priceTierMinQty`, the persisted tier ladder `T = [{minQty, priceMinor}, ...]` (see Files: snapshotted at sale time, so no live table is re-read), `returnedBefore` and `k`. `kept = N - returnedBefore - k`. `keptUnit(kept)` = the LOWEST `priceMinor` in `T` with `minQty <= kept` and `priceMinor >= b`, else `L`; and `keptUnit(kept) = b` when `kept >= m` (the tier is still reached). If `priceSource == 'tier'` and `m != null` and `L != null` and `kept > 0`: `clawback(kept) = (keptUnit(kept) - b) * kept`, else 0. `adjustment = clawback(kept) - clawback(keptBefore)` where `keptBefore = N - returnedBefore` (cumulative partial returns never double-charge). `standardRefund = b * k`; `adjustedRefund = max(0, standardRefund - adjustment)`; when the floor bites, `shortfall = adjustment - standardRefund` is reported to the merchant (NOT charged to the buyer). `kept == 0` -> no adjustment. Group-percent (`group`), `base`, a line with no snapshot and a line with no ladder -> no adjustment (a line sold before the ladder snapshot exists falls back to list, never to a guess).

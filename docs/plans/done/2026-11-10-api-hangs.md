# API hangs on cache misses (API-HANG-1)

Branch `fix/api-hangs-do-chain`. Rulings: `docs/rulings/API-HANG-1.md`, `docs/rulings/API-HANG-2.md`.

## Finish line

- **Must work:** a cold (cache-miss) public read waits on ONE AuthState round trip per cache level, not three; no rate-limit or generation-read call can hold a request longer than `AUTH_STATE_TIMEOUT_MS` (2.5 s); credential limiters fail closed, public read limiters fail open; generation bumps complete before the delete; every limit, window and 429 body is unchanged.
- **Exercised:** `GET /public/stores/:slug`, `GET /public/products`, PDP, cart add, guest order create, customer sign-in on workerd (`workers-test/latency-budget.test.ts`, `public-do-calls.test.ts`, new `api-hang-concurrency.test.ts`); unit `tests/unit/api-hang-deadline.test.ts`.
- **Must NOT change:** `apps/api/src/worker.ts`, `middleware/security.ts`, `cf/ssr-client-ip.ts`, `app.ts` (PR #514 owns them); `apps/web/**`; limiter keys/windows/bodies; the NEVER-stale generation protocol (check before put, re-check after put, delete on a bump).
- **Done:** PR open, CI green, not merged, not deployed.

## Evidence

1. **Where the serial AuthState calls come from (measured, local workerd, cold call of each path, `x-dev-io-ops`).**
   Cold store resolve = 7 AuthState calls / 20 serial waves: 1 limiter batch + **3 identical generation reads per cache level** x 2 nested levels (`public:store:<slug>` wraps `dir:slug:<slug>`). `lib/public-cache.ts` `getCached` read the generations (1) before the fetch, (2) before the KV put and (3) after the KV put, all on the request path, so a fill paid three serial DO round trips plus a KV write before answering. Product list / PDP: 5 calls (1-2 limiter + 3 generation reads).
2. **`apply`** is the only RPC method of the `AuthState` DO (`cf/auth-state.ts`): every limiter hit, generation read/bump, jti/lockout/CSRF op goes through it. Logpush logs the DO side of a call as `outcome: canceled` when the CALLER went away first, so the Nov 9 `apply` cancellations are requests that were already cut off (storefront 8 s probe / client disconnect) while waiting on that chain, not a DO-side crash.
3. **One hot instance (inferred from code + PR #514's production measurement).** Before #514, every storefront SSR fetch reached the API from `ebda-web`'s egress address, so all shoppers' limiter batches (`rl:public:<ip>`, `rl:store-miss:<ip>` peek) hashed to ONE `rl-client:<egress ip>` shard: one single-threaded AuthState instance in front of every public read. #514 keys them on the shopper's verified address and is the fix for that part; this PR does not duplicate it.
4. **No deadline.** `applyOn` / `applyOnShard` / `applyOnAll` awaited the DO with no timeout: a slow or stuck instance held the request until the caller gave up (8 s+).

Production log numbers (R2 Logpush reader, `ebda-foundation` `os/ops/ebda-logs.mjs`) are in the PR body.

## Changes

1. `apps/api/src/cf/auth-state-client.ts`: `withAuthStateDeadline` (2500 ms, `AuthStateTimeoutError` + one `logger.warn`), applied ONLY to calls made with `{ bounded: true }` (Ruling API-HANG-1 as amended after review): the rate-limit store and cache-generation reads. Bumps, jti/token-version/lockout/CSRF ops, locks and sweeps are unbounded, as before. A DEV_STATS-only fault hook (`x-dev-authstate-delay-ms`, `x-dev-authstate-stall`, read by `lib/request-timing.ts` into the io tally) gives local workerd a production-like round trip or a stuck instance.
2. `apps/api/src/cf/rate-limit-store.ts`: on a timeout a public read limiter fails OPEN, every other limiter fails CLOSED with its normal 429 + Retry-After (Ruling API-HANG-2, `RL_FAIL_OPEN_PREFIXES`). A timed-out prefetched hit is not retried directly (no second 2.5 s wait).
3. `apps/api/src/lib/public-cache.ts`: on Workers the write-back (generation check -> KV put -> re-check -> delete on a bump) runs in `waitUntil`, same order and checks. Critical path of a cold fill: 1 generation read + the fetch (was 3 reads + a KV put).

## Batching (review item 3)

The "up to 9 serial AuthState calls" on a public-read cache miss were cache-generation reads, not limiters: the public limiters were already ONE batched call (PERF-RL-DO-1; op trace: 1 `rl:` call, 6 `cachegen` reads on a cold store resolve). This PR removes 4 of them from the critical path (above). The remaining serial LIMITER chains are on sign-in (`rl:global` -> `rl:auth-ip-fail` -> `rl:auth`) and order create (`rl:global` -> public batch -> `rl:write`); collapsing them means prefetching those keys before the middleware chain in `app.ts` / `middleware/security.ts`, which PR #514 owns (open). Follow-up branch from fresh main after #514 merges.

## Not in this PR (blocked or out of scope)

- Sign-in / order-create limiter batching (above, blocked by #514).
- #514 removes the single hot `rl-client:<ebda-web egress ip>` AuthState shard every SSR public read hit; not duplicated here.
- Cold store resolve still makes 10 serial StoreDO calls (record x2, tax, FAQ, how-to, pages, abandoned-cart, WhatsApp); batch in a follow-up.

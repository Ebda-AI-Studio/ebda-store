# Help corpus and capability registry become build-time outputs (2026-11-24)

Approved by Ahmad. Ruling HELP-CORPUS-BUILD-1 below.

## Problem

`apps/api/src/cf/modules/help-corpus.mjs` (451 KB) and `apps/api/src/smart-layer/registry.generated.json` are generated by `apps/api/scripts/build-help-corpus.mjs`
from `apps/help/content/**/*.mdx` and `capabilities/*.capability.json`, and were committed. Every PR that touched help content or a capability regenerated them,
so those PRs conflicted on the generated file whenever main moved, and went stale until someone re-ran the generator by hand.

## Decision

Stop committing both files (`git rm --cached`, `.gitignore`) and generate them before every use. Nothing else about the corpus changes (same bytes from the same sources,
same Worker module name, same `rules` entry, same `help-index.ts` loader).

## Where it is generated (every consumer, one script)

| Consumer                                                                                             | Mechanism                                                                                                                  |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `wrangler deploy`, `--dry-run`, `dev`, Workers Builds (the `cf:dry-run` script, the deploy workflow) | `build.command` in `apps/api/wrangler.jsonc` (runs before bundling, in `apps/api`; the deploy config is a text copy of it) |
| every CI job that installs                                                                           | a step in the `npm-ci` composite action                                                                                    |
| `cf-api-deploy.yml` (it runs `npm ci` itself, then `tsc` + vitest)                                   | an explicit step before tsc                                                                                                |
| unit tests, workers pool tests, workers-do tests, Stryker                                            | vitest `globalSetup` (`tests/global-setup-assistant-assets.ts`) in all four configs                                        |
| typecheck                                                                                            | root `pretypecheck`                                                                                                        |
| local dev / build / lint / test of the Node API                                                      | `predev`, `prebuild`, `prelint`, `pretest` in `apps/api`                                                                   |
| by hand                                                                                              | `npm run gen:assistant-assets`                                                                                             |

The generator writes only files whose content changed, so a watcher never sees a rewrite on start.

## Things that used to fire because the file was in the diff, and now need an explicit trigger

- `cf-api-deploy.yml` `paths:` (and `deploy-plan.mjs`, which reads them): added `apps/help/content/**` and `capabilities/**`, so a help-only or capability-only merge still redeploys the API.
- `scripts/ci-affected.mjs` api Worker entry pattern: added `capabilities/` and `apps/help/content/`, so such a PR runs the API `wrangler deploy --dry-run` (which also proves the generator works on that content).

## CI sanity (freshness)

`tests/unit/build-time-assets.test.ts` pins: both files untracked and ignored; non-trivial content (both locales, > 20 capabilities); `--check` exits 0; every consumer above is wired (wrangler build.command,
four vitest configs, npm scripts, composite action, deploy workflow order and paths, ci-affected). `tests/unit/assistant-adapter.test.ts` keeps comparing the files on disk with a fresh `buildAssets()`.

## Looked at and left alone

- `apps/api/workers-test/route-table.json`: not a build output. It is a reviewed manifest the route-table test compares the live routes against; a diff there is the point.
- `apps/api/src/cf/modules/exceljs.cjs`, `pdf-lib.mjs` (generated by `scripts/ci/gen-*.mjs`) and `apps/api/src/cf/erasure/registry.generated.ts`: same class of file, out of scope for this approval; their generators need install-time package sources or are checked by `cf-schema-current`.
- `apps/api/src/cf/modules/help-corpus.d.mts` stays tracked: it is the type declaration, not an output.

## Ruling HELP-CORPUS-BUILD-1

Ruling HELP-CORPUS-BUILD-1 - the help corpus module and the capability registry JSON are generated at build time and never committed; every build, deploy, test and typecheck path generates them first and `tests/unit/build-time-assets.test.ts` fails when a path stops doing so or a file is tracked again. Evidence: a fresh clone with no corpus builds, tests and `wrangler deploy --dry-run`s (PR body). Cost if wrong: a new consumer that forgets to generate fails loudly (a missing module rejects, `registry.ts` import fails typecheck), never serves an empty corpus.

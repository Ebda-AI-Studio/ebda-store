## Finish line

- **Must work:** a Paymob / Kashier / Fawry / Geidea payout (net of fees, batched, T+n) and a courier COD statement each produce ONE balanced journal entry that moves money out of the clearing account (1000 / 1010 / 1020) into the bank (1030) and books the fee to an expense, so a bank deposit has a ledger line of the same amount to match, and the clearing balances equal "paid but not yet settled".
- **Flows exercised:** settlement-report import (gateway CSV, courier CSV) -> payout rows -> journal post -> reversal of a wrongly imported batch; COD order delivered -> `1020` debit (exists) -> statement import -> `1020` credit + `5700` fee + `1030` debit; the admin payouts page and clearing-balance tile; the integrity cron. Real StoreDO ops on workerd, not mocks.
- **Must NOT change:** the sale / COGS / refund / wallet entries and their idempotency keys; `PROVIDER_TO_CASH_CODE`; the S3-O7 rule (a statement marks a delivered COD order paid, amount-guarded, pr 735); integer piastres, DR = CR; a statement line is never refused because of an external money fact (booked in full, flagged).
- **Done =** every acceptance test below green AND red when the new op is disabled; replaying any import posts nothing; clearing-balance test ties to the order ledger on a seeded store; `npm run typecheck` + lint exit 0; docs (RULINGS, plan-feature-matrix, RETENTION) updated in the same PRs. ## 1. What the repo does today (verified by reading main at origin/main, not by running)

- Sale posting books gross cash at `paid` time: `DR 1000|1010|1020`, by `PROVIDER_TO_CASH_CODE` (paymob 1000, fawry 1000, instapay 1000, kashier 1010, geidea 1010, cod 1020) (`apps/api/src/services/accounting/posting/order-posting.ts:17`, DO twin `packages/repo/src/do/ledger.ts:21`). Nothing ever credits 1000/1010/1020 for a settlement, and no entry debits 1030 except manual ones. So the three cash accounts only grow and "Bank Main" never moves. (inferred from grep: no posting file references 1030 or a fee account)
- No gateway fee or payout data enters the system at all. `grep -i "fees|commission|net_amount|settle"` over `routes/webhook.routes.ts` and the four `payment-providers/*.provider.ts` finds no parsing of a fee or net field. The raw webhook body is kept in `PaymentEvent.providerPayload` ("lets us replay a dispute 6+ months later"), so whatever fee fields a webhook carries are stored but unread: that is the cheapest discovery path (step P0-0).
- Provider payout / settlement APIs: none integrated. `docs/plans/2026-10-07-egypt-payments-shipping-integrations.md` records fees and settlement cadence as UNVERIFIED for every gateway ("Paymob and Kashier ~2.75% + EGP 3 + 14% VAT on the fee ... Do not quote fees in the product") and "No Egyptian carrier exposes a COD remittance/settlement API". **Unknown, needs provider docs:** whether Paymob (transactions / payouts report), Kashier, Fawry (FawryPay merchant report) and Geidea expose a settlement API or only a portal CSV/Excel export; their column names; whether the fee VAT is itemised. Until verified the design takes a CSV the merchant uploads, like the COD statement import.
- COD today, three separate pieces:
  1. `order.service.ts:3104-3160` (ruling MONEYB-7): status `delivered` on an unpaid COD order completes the `cod_pending` payment and fires `order/created`, which posts the sale: `DR 1020`. So 1020 = "COD collected by the courier, not yet in the bank". This is already the correct clearing account; no new COD clearing account is needed.
  2. `cod-reconciliation.service.ts` `importSettlement` + `lib/cod-reconciliation.ts` `parseSettlementCsv`: a courier statement CSV becomes `cod_remittances` rows (gross, fee, net, remittedAt, batch_id, line_ref, source), keyed `(store_id, carrier, line_ref)`, no journal. Columns are matched by alias names (tracking, collected, fee, net, date, reference, batch).
  3. pr 735 (open, branch `feat/cod-auto-paid-on-statement`, Ruling S3-O7): in the DO `importCodRemittances`, a newly booked line whose delivered order is still unpaid and whose cash equals the COD due marks the order paid and sends the same `order/created` fan-out. Lines suspected duplicate get `source = <source>:suspected_duplicate` and are excluded from the collected sum.
     So "courier statements mark COD paid" is pr 735 (not yet merged at the time of writing); the money still never reaches a journal line. This plan builds on 735 and must be rebased on it.
- Parser gap (measured by reading `amount()` in `lib/cod-reconciliation.ts`): a negative amount is rejected ("an amount is not a valid EGP number") and `net` must equal `gross - fee`. A refused / returned-to-origin parcel normally costs the merchant a fee with zero cash (gross 0, fee > 0, net negative), so those statement lines are rejected today and the carrier's charge never reaches the books. Fix in P0-3.
- Postgres is removed in production (pr 735 text, `docs/plans/2026-11-05-nz-17-postgres-removal.md`), so the money ops live on the StoreDO (`packages/repo/src/do/*`, Ruling CF-LEDGER-1). The Prisma path is not extended; if the house still requires Prisma-schema parity for dev, step P0-1 adds the models and nothing else.
- Hard constraint found: `journal_entries.source` has a SQLite CHECK (`'order','refund','purchase_order','expense','stock_adjustment','manual','period_close','opening_balance'`, `packages/cf-schema/migrations/store/0001_init.sql:1363`) and so does `bank_transactions.match_status`. SQLite cannot alter a CHECK, so adding sources needs a table rebuild migration (create new, copy, drop, rename, recreate indexes + the DR=CR / immutability triggers from `0002_invariants.sql`). Latest store migration is `0006`; this plan's is `0007`. This is the riskiest step and gets its own PR with a migration test on a store with data.

## 2. Accounts

Existing: 1000 Cash Online, 1010 Cash Card, 1020 Cash COD, 1030 Bank Main, 5700 Courier, 5800 Bank Fees, 5990 Other. Proposed additions (COA template self-heals on first use, see `getSystemAccountIdByCode`):

| Code | Name                                                      | Type      | Why                                                                                  |
| ---- | --------------------------------------------------------- | --------- | ------------------------------------------------------------------------------------ |
| 5810 | Payment Gateway Fees (رسوم بوابات الدفع)                  | expense   | keeps card fees apart from bank charges (5800) so margin per channel is readable     |
| 2170 | Unapplied Settlement Receipts (مبالغ محصلة بانتظار الربط) | liability | statement / payout cash that has no matching sale yet; cleared when the sale appears |
| 5710 | Courier COD Fees                                          | expense   | optional split from 5700 (shipping); ruling stub R-1                                 |

Clearing accounts are the existing 1000/1010/1020, not new ones. Limitation: 1000 is shared by Paymob, Fawry and InstaPay, so per-provider clearing is NOT visible in the GL, only in a subledger report grouped by `payments.provider` (the sale lines carry `refTable/refId`; verify in P0-1). Splitting 1000 into per-provider accounts would change every existing store's COA: not proposed (open question Q4).

## 3. Journal shapes (all integer piastres, all idempotent)

Idempotency key is `(store_id, source, source_id)` as everywhere. `postedAt` = settlement date in Cairo (the payout / remittance date), never "now" (audit D-3), and subject to the period lock when D-4 lands.

**A. Gateway payout batch** (source `gateway_payout`, sourceId `payout:<provider>:<providerPayoutRef>`; if the report has no payout reference, `payout:<provider>:<sha256(provider|date|sorted line refs)[0..32]>`)

```
DR 1030 Bank Main                    net deposit
DR 5810 Gateway Fees                 fees (gross of fee VAT until input VAT exists, audit D-10)
CR 1000|1010 clearing (by provider)  gross settled = net + fees
```

- Refunds and chargebacks netted inside a payout: the payout's `gross` is sales minus refunds. Refunds are already booked at refund time as `CR <cash account>` (refund journal), so the clearing account was already reduced. The payout entry therefore credits clearing with `salesSettled - refundsSettled` only; the report line type decides. A chargeback (not a refund we booked) is `DR 5990 / CR clearing` with a flag, never silently absorbed: ruling stub R-2.
- Rolling reserve / held-back amounts: unknown if any provider does this; a held amount would be a receivable from the gateway, deferred until a provider says it exists (Q2).

**B. Courier COD remittance import** (source `cod_remittance`, sourceId `cod_import:<importId>`; one entry per upload per carrier, not per line)

```
DR 1030 Bank Main                    sum(net) over NEW, non-duplicate lines
DR 5700 (or 5710) Courier fees       sum(fee)
CR 1020 Cash COD                     sum(gross) over lines whose order is paid
CR 2170 Unapplied Receipts           sum(gross) over lines whose order is NOT paid / unknown tracking
```

- Lines flagged `suspected_duplicate` (pr 735) are excluded: they are booked in `cod_remittances` but never in a journal until the merchant confirms.
- RTO / refused parcel line (gross 0, fee F): the carrier deducts the fee from the next payout, so it nets inside the batch (the fee is in `DR 5700`, and the negative net line reduces the `DR 1030` sum). If the batch net would be negative (carrier invoices instead), the entry is `DR 5700 / CR carrier payable (new liability account; AP 2000 is supplier-only)`: ruling stub R-3, not built in v1; v1 books only batches with `sum(net) >= 0` and flags others.
- When an order later flips to paid (statement mismatch fixed, merchant "Mark paid"), a re-class entry `DR 2170 / CR 1020` (source `cod_remittance`, sourceId `cod_reclass:<orderId>`) clears the unapplied credit. A sweeper finds `2170` lines whose order is now paid.
- The bank deposit usually equals a carrier's batch net, or several batches together (reconciliation plan handles N:1; this entry gives it the `1030` line).

**C. Reversal of a bad import:** `reverseEntry` on the batch entry (exists in `ledger.ts:152`) plus a `reversed_at/by/reason` mark on the `gateway_payouts` / `cod_statement_imports` row; re-import after reversal is allowed (a new `importId`). Needs the merchant-facing reverse route that does not exist today (audit D-9): this plan adds a store_admin-only "undo this import" action (scoped to these two sources), not a general reversal route.

## 7. Plan gating, data, rollout

- **Gating proposal:** payout/remittance posting is accounting plumbing, not an AI feature: gate with `accounting.basic` (Growth and Business today per `plan-baselines.ts`; Basic has no accounting). The COD statement import page already exists on every plan with SP7; its posting runs only when the store has accounting enabled (`Store.accountingEnabled`), like sales postings. No new feature key. **Ruling stub PAYOUT-GATE-1 (for Ahmad):** keep on `accounting.basic`, or put the gateway importer in `accounting.bank_reconcile` (Business only) because its purpose is reconciliation. Default taken: `accounting.basic`. Cost if wrong: Growth stores get a feature we meant to upsell; reversible by moving the key.
- **Data/privacy:** settlement files contain order references, partial payer data (names, masked card numbers, wallet numbers) and the merchant's bank/payout references. Do not log row contents; log counts, ids and hashes only. Do not store the uploaded file; store parsed rows. `gateway_payout_lines` get a retention row in `docs/RETENTION.md` (financial record: follow the accounting retention already stated there; bank tables are NOT in that file today, a gap this plan also closes in P0-1 docs). No PII column is added.
- **Rollout:** no new flag for COD (additive entries, replay-safe, reversible). Gateway importer behind a super_admin `StoreFeature` override key `accounting.gateway_payouts` (addon tier, in no baseline) for the QA store `1bb14d0e-0cb8-4cb4-b939-e889c4bc2ebc` first, then a ruling to add it to a baseline. Backfill: none automatic; the first import after enabling is the cutover (older unsettled orders show in the clearing aging as "before cutover" and are cleared by `2170`/negative-clearing review, never auto-cleared).
- **Cost:** no LLM, no new third-party spend. Storage: one payout row + lines per batch.

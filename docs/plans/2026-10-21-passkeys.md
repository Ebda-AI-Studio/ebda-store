# Passkeys (WebAuthn) for merchants and shoppers - 2026-10-21

Finish line: a merchant and a shopper can register a passkey, list/rename/delete it, and sign in with it (no email/password
typed). Proven by unit tests (real WebAuthn ceremony against a software authenticator) + an RLS integration test.
Must NOT change: password + TOTP/backup-code login, email reset, super_admin MFA enforcement, refresh/token rules (S11-1).

## Decisions (rulings in the report)

- Library: `@simplewebauthn/server` 14.0.3 (api) + `@simplewebauthn/browser` 14.0.0 (web, admin). MIT, released <12mo, Workers-safe (WebCrypto, no native deps).
- One table `passkey_credentials`, **user-keyed** (like `refresh_tokens`/`legal_acceptances`), no `store_id` column: the user row is already
  store-scoped (shopper: `users.store_id`; merchant: NULL). RLS ENABLE+FORCE, `user_id = app.current_user_id`, ON DELETE CASCADE.
  Pre-identity lookup (discoverable sign-in knows only the credential id) goes through SECURITY DEFINER `ebda_passkey_lookup`.
- Challenges: Redis `passkey:ch:<sha256(challenge)>`, TTL 300s (floor is 120s), consumed with `DEL` (returns 1 for exactly one caller = single use).
  Fail CLOSED if Redis is down. Record binds purpose, rpId, origin, userId (registration), storeId (shopper).
- RP ID = the request **host** (per-host). Admin: host of `config.adminUrl`. Storefront: the Origin must resolve to a store
  (`<slug>.ebda.app` by slug, else a verified custom domain). Credential stores `rp_id`; a custom-domain switch changes the host, so old
  credentials stop matching (listed as "needs re-enrol", sign-in fails closed, password path unaffected).
- Passkey sign-in satisfies MFA (phishing-resistant, UV required) -> mints the session directly via `issueSessionFor`, skipping the TOTP challenge.
  `super_admin` is excluded (their MFA enforcement is TOTP-flag based; unchanged).
- Sign-in begin is credential-less and identical for everyone (no email) -> nothing to enumerate; finish returns one generic failure.
- Rate limits (as built): sign-in `/begin` = per store host + IP, 300/15 min (the real brute-force guard is the shared account
  lockout, PASSKEY-8); `/finish` = per IP, 20 failures/15 min; `/step-up` = per authenticated user, 10/15 min; registration
  writes use `writeLimiter`. The login pages start the conditional-UI ceremony on first focus of the email field, not on load.
- Audit: `passkey.added|removed|renamed|login|login.failed`. Cascade on user delete; erase deletes rows explicitly; export lists metadata (no key material).

## Added after the security reviews (rulings PASSKEY-7..16 in docs/RULINGS.md)

- Step-up (password [+TOTP] or a passkey sign-in), bound to user + session, 5 min, for add / rename / remove.
- Password login and passkey sign-in share `loginGate`; `tests/unit/login-parity-behaviour.test.ts` proves it by behaviour.
- A password change OR reset removes every passkey, atomically with the new hash, with an audit row and a notice (PASSKEY-10/13).
- Admin-namespace identities are served account endpoints only to platform origins; passkey endpoints are bound to the account's own surface (PASSKEY-14).
- Notices: merchants from the platform sender; shoppers from their STORE's sender identity (PASSKEY-16).
- Permissions-Policy pins `publickey-credentials-get/create=(self)` on web and admin.

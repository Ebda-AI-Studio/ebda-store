# Plan: storefront HTML on Workers Caching instead of `caches.default` (2026-11-11)

Status: PLAN ONLY, nothing implemented. Source: Ruling WEB-COLD-3 (docs/rulings/WEB-COLD-3.md). Needs its own reviewed PR because it changes the price / stock staleness contract.

## Goal and why

First hit per data centre per deploy is an edge MISS of 1-4 s (measured with `scripts/ops/ttfb-probe.mjs`); hits are 0.4-0.6 s. `caches.default` is per data centre and not tiered, so every data centre renders every page once per deploy. Workers Caching (docs: developers.cloudflare.com/workers/cache) is tiered by default (lower tier near the visitor, upper tier shared), read-through (a hit never runs the Worker) and collapses concurrent misses. Target: first hit under 1 s (about 0.5 s network floor plus an upper-tier read).

## Steps (each ends in evidence or `skip: <reason>`)

1. **Platform blocker first: compat date vs pinned wrangler.** The feature page names compat date >= 2026-10-13 and, for per-entrypoint control, wrangler >= 4.107. web is at compat `2025-08-16` (scripts/cf-setup-local.sh:60) and wrangler is pinned EXACTLY at 4.116.0 (Ruling DEP-WRANGLER-1: newest wrangler with a stable miniflare, `4.20260730.0`; 4.117+ pin an alpha miniflare). The api note says the pinned workerd rejects `2026-09-01`. So a 2026-10-13 compat date will probably be rejected by local workerd / `wrangler deploy --dry-run` on 4.116. Verify with `wrangler deploy --dry-run` on a throwaway copy (not the live worker). If rejected: either wait for a stable-miniflare wrangler (re-check `npm view wrangler@<v> dependencies.miniflare` for versions after 4.147) or take the Cloudflare API path (set `cache` on the Worker script settings) without bumping local tooling; decide by Ruling. Do not take an alpha miniflare into the prod tree.
2. **Compat-date audit (web).** Bumping from 2025-08-16 to 2026-10-13 flips every compat flag defaulted in between. List them from the workerd compat-flags table, then run: the workerd smoke (`scripts/ci/next-worker-smoke.mjs web`), `tests/unit` web suites, the OpenNext build, and a Sentry `https.request` check (the reason for 2025-08-16). Report each flag as no-effect / checked-with-test.
3. **Cache headers.** Today the app answers `private, no-store` to the client and the Worker caches internally. Workers Caching reads the response `Cache-Control`, so a cacheable page must carry `public, max-age=<fresh>, stale-while-revalidate=<s>` and `Cache-Tag`s, while anything ineligible keeps `private, no-store`. Eligibility stays exactly the DEMO-EDGE-1 / STORE-EDGE verdicts; only the storage moves. The client-facing header changes from no-store to short public max-age: decide the browser TTL (suggest `max-age=0` for browsers with `s-maxage` for the cache if the feature honours it; confirm in the docs) so a merchant edit is never held in a visitor's browser.
4. **Cache-Tag and purge design (price and stock are NEVER-stale).** Tag every cached page `store:<id>` plus `products:<id>` (the same tag the API already revalidates, apps/api/src/lib/public-cache.ts, guarded by tests/unit/storefront-purge-on-write.test.ts). Purge with `ctx.cache.purge()` on EVERY write path that clears the Next data cache today: product / variant / price / stock / category / theme / layout / store-settings writes, plus order paths that change stock (checkout, cancel, refund restock). Rule: an `invalidate*` with zero call sites is a bug, so add a test that fails if a stock/price writer does not reach the HTML purge. Purge rate limits are the Free tier's for Workers Caching (docs), so batch by tag and never purge per request. Open question to settle in review: a page that shows live stock must either carry a short TTL (BOUNDED-stale with the window documented at the cache site) or stay out of the cache; today the demo layer's fresh window is 300 s and demo checkout is refused, real stores use the store layer behind an allowlist. Do not widen what is cached.
5. **Cache-key re-review against DEMO-EDGE-1 and STORE-EDGE.** Workers Caching keys by request path, entrypoint, `ctx.props` and (default) Worker version, NOT by hostname. Today's key is built by us from host + a strict path allowlist + `look` + language. Required: the host must be part of the key (a store's HTML must never be served for another host): use `ctx.props` or a per-host entrypoint, then prove with a negative control per host. Re-prove each rule with a test that fails when broken: cookies (any consent / draft / auth cookie bypasses), `Authorization`, `x-forwarded-host` and friends, `Set-Cookie` never stored, non-200 and non-HTML never stored, language path vs cookie variant, the `look` allowlist, the CSP nonce renewal (csp-nonce-renew.ts), and EDGE-BUILD-1 (the HTML names `/_next/static` files of one build: default keying by Worker version keeps this; confirm). Security review required (cache poisoning, parser differential), as for #128.
6. **Size cap.** Docs: all Workers Caching responses are capped at the Free plan cacheable size at launch, regardless of plan. Measure the largest storefront HTML (home, PDP with many variants, long product list) and the RSC payloads; anything over the cap simply is not cached (a MISS every time), so list which pages that is before rollout.
7. **Rollout and kill switch.** Behind a Worker secret/var (like `STOREFRONT_HTML_EDGE_OFF`): on = new path, off = today's `caches.default` path, so a bad rollout is reverted without a deploy. Demo hosts first, then listed stores via the existing allowlist.
8. **Measurement plan.** Before (already recorded in WEB-COLD-3): `/ar` MISS 5.05 s, `/en` MISS 1.52 s and 2.96 s, `/en` MISS 3.66 s, `/ar/products` MISS 1.11 s; HITs 0.4-1.5 s. After, on the first deploy of each build: run `ttfb-probe.mjs` from at least two regions/data centres against a page nobody has requested for that build, 5 pages x 2 languages, and report p50 and p95 first-hit TTFB plus the fraction served `HIT`. Pass = first hit under 1 s on at least 90% of pairs; also confirm a price edit and a stock change are visible on the storefront within the documented window (merchant save, then probe). Report what could not be measured.
9. **Cost / risk.** Workers Caching billing was not checked (docs read for behaviour only): read the pricing page before step 7. Risk: price/stock staleness (step 4), cross-host leakage (step 5), a compat-date bump touching unrelated behaviour (step 2). Rollback: the step 7 switch.

## Not in this plan

No R2 HTML tier (superseded unless step 1 shows the platform path is closed). No change to the API Worker (it stays unplaced and uncached at this layer).

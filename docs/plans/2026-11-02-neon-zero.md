# NEON-ZERO-1: Ebda API with zero Postgres / Neon / Hyperdrive

Ruling NEON-ZERO-1 (Ahmad 2026-10-31: "I want Ebda completely off Neon"). Goal: `apps/api` (Worker `ebda-api`) serves every public
and admin request with no Postgres dependency, then `HYPERDRIVE` leaves `apps/api/wrangler.jsonc`.
Source of the numbers: `business/ebda/STATUS-AUDIT-2026-11-02.md` section 3.4 plus a model-level scan of `apps/api/src` on
2026-11-02 (non-test files that reference prisma / withStore / raw SQL / Hyperdrive: 362 incl. lib/inngest; targets from
`packages/cf-schema/model-split.json`). Counts are an upper bound (syntactic). Labels: measured / inferred / guess.

## 1. Findings that shape the work (measured unless marked)

- F1. There is no runtime client for the D1-target models. `repo-factory` serves StoreDO stores through prisma-lite
  (`packages/repo`), whose `SqlRunner` is SYNCHRONOUS (DO SQLite). Every `target: d1` model (`Store`, `StoreStaff`, `StaffInvite`,
  `SlugRedirect`, `StoreFeature`, `SystemSetting`, `Plan`, `StoreSubscription`, `BillingEvent`, `MerchantApiKey`, `WebhookEvent`, ...)
  and every `target: identity` profile read still goes through the Postgres `prisma` proxy / SQL definers. D1 holds the data (38 rows)
  but the API reads only `stores.storage_backend` (and now the directory, PR1) from it.
- F2. `Store` is split: D1 `stores` has only the 30 directory columns; branding, theme, SEO, settings live in the DO `store_profile` /
  `store_config`. The DO has NO read RPC for them (a `Store` read is `db: d1` in prisma-meta, the table `stores` does not exist in the
  DO), and `applyStoreSettings` is a write-through whose AUTHORITATIVE write is still the Postgres `Store` row. So the public store record
  (`GET /public/stores/:slug`, 62 selected columns) cannot be served without Postgres until a DO `storeRecord` read exists.
- F3. Writes to platform tables (store create, settings, staff, plans, subscriptions, billing events) are Postgres writes. A read moved
  to D1 before its write moves is split-brain (security review of 2026-11-02). Rule for every PR here: a table family moves reads AND
  writes in the same PR, or neither.
- F4. `backendFor(id)` returns `'pg'` for an id with no D1 row. Fine while PG exists; in the final PR an unknown id with D1 bound becomes
  404 `STORE_NOT_FOUND` (matches Ruling CF-PLATFORM-1 text). Tracked as N-12.
- F5. `middleware/auth.ts` (`getUserState` -> `ebda_user_state` definer, token version in the AuthState DO) and
  `middleware/store-access.ts` (`withStore(...).store.findUnique`, `storeStaff.findUnique`) both read Postgres today, consistently. They
  are consistent ONLY because both are still PG. The split-brain risk appears the moment one moves: see N-8.
- F6. Hyperdrive appears in `worker.ts`, `index.ts`, `app.ts`, `cf/dev-stats.ts`, `cf/queues.ts` (boot, pool, role guard); the Postgres
  path stays reachable lazily (#374), so `/health` does not need PG. (inferred from the audit; re-verify when removing.)

## 2. Class legend

(a) already DO/D1-routed - (b) platform data -> D1 - (c) per-store data -> StoreDO seam (`storeDb` / `storeWriter` / `storeMoney` /
`storeStock`) - (d) dead code (delete). Identity-owned data (`User`, `RefreshToken`, `VerificationToken`, `PasskeyCredential`) is
served by `apps/accounts` (D1 `ebda-identity`); the Store keeps only a profile row (see N-8).

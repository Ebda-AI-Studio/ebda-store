# NEON-ZERO-1: Ebda API with zero Postgres / Neon / Hyperdrive

Ruling NEON-ZERO-1 (Ahmad 2026-10-31: "I want Ebda completely off Neon"). Goal: `apps/api` (Worker `ebda-api`) serves every public
and admin request with no Postgres dependency, then `HYPERDRIVE` leaves `apps/api/wrangler.jsonc`.
Source of the numbers: `business/ebda/STATUS-AUDIT-2026-11-02.md` section 3.4 plus a model-level scan of `apps/api/src` on
2026-11-02 (non-test files that reference prisma / withStore / raw SQL / Hyperdrive: 362 incl. lib/inngest; targets from
`packages/cf-schema/model-split.json`). Counts are an upper bound (syntactic). Labels: measured / inferred / guess.

## 1. Findings that shape the work (measured unless marked)

- F1. There is no runtime client for the D1-target models. `repo-factory` serves StoreDO stores through prisma-lite
  (`packages/repo`), whose `SqlRunner` is SYNCHRONOUS (DO SQLite). Every `target: d1` model (`Store`, `StoreStaff`, `StaffInvite`,
  `SlugRedirect`, `StoreFeature`, `SystemSetting`, `Plan`, `StoreSubscription`, `BillingEvent`, `MerchantApiKey`, `WebhookEvent`, ...)
  and every `target: identity` profile read still goes through the Postgres `prisma` proxy / SQL definers. D1 holds the data (38 rows)
  but the API reads only `stores.storage_backend` (and now the directory, PR1) from it.
- F2. `Store` is split: D1 `stores` has only the 30 directory columns; branding, theme, SEO, settings live in the DO `store_profile` /
  `store_config`. The DO has NO read RPC for them (a `Store` read is `db: d1` in prisma-meta, the table `stores` does not exist in the
  DO), and `applyStoreSettings` is a write-through whose AUTHORITATIVE write is still the Postgres `Store` row. So the public store record
  (`GET /public/stores/:slug`, 62 selected columns) cannot be served without Postgres until a DO `storeRecord` read exists.
- F3. Writes to platform tables (store create, settings, staff, plans, subscriptions, billing events) are Postgres writes. A read moved
  to D1 before its write moves is split-brain (security review of 2026-11-02). Rule for every PR here: a table family moves reads AND
  writes in the same PR, or neither.
- F4. `backendFor(id)` returns `'pg'` for an id with no D1 row. Fine while PG exists; in the final PR an unknown id with D1 bound becomes
  404 `STORE_NOT_FOUND` (matches Ruling CF-PLATFORM-1 text). Tracked as N-12.
- F5. `middleware/auth.ts` (`getUserState` -> `ebda_user_state` definer, token version in the AuthState DO) and
  `middleware/store-access.ts` (`withStore(...).store.findUnique`, `storeStaff.findUnique`) both read Postgres today, consistently. They
  are consistent ONLY because both are still PG. The split-brain risk appears the moment one moves: see N-8.
- F6. Hyperdrive appears in `worker.ts`, `index.ts`, `app.ts`, `cf/dev-stats.ts`, `cf/queues.ts` (boot, pool, role guard); the Postgres
  path stays reachable lazily (#374), so `/health` does not need PG. (inferred from the audit; re-verify when removing.)

## 2. Class legend

(a) already DO/D1-routed - (b) platform data -> D1 - (c) per-store data -> StoreDO seam (`storeDb` / `storeWriter` / `storeMoney` /
`storeStock`) - (d) dead code (delete). Identity-owned data (`User`, `RefreshToken`, `VerificationToken`, `PasskeyCredential`) is
served by `apps/accounts` (D1 `ebda-identity`); the Store keeps only a profile row (see N-8).

Ruling NZ-10-2 - D1 has no interactive transaction, so the billing writes that were one Postgres transaction are rebuilt around D1's atomic `batch` and an explicit order of the two halves (D1 ledger / money write FIRST so every refusal fails closed, then the idempotent Postgres half; in settlement the Postgres tier precedes the subscription write because the provider has already confirmed the money): (a) caps (founding 20, referrer 3) are one `INSERT ... SELECT ... WHERE COUNT < cap`; (b) revoke / restore claims are one `UPDATE ... RETURNING`; (c) a manual payment is ONE batch (ledger INSERT guarded by a compare-and-set on the subscription row + subscription upsert that requires this batch inserted the ledger row) and it is the FIRST change, before any Postgres write (fail closed: a reference another store holds is refused 409 REFERENCE_USED_ELSEWHERE, a lost CAS 409 retryable, a D1 error aborts, all with stores.plan, the claim and the receipt untouched); the idempotent Postgres half (stores.plan, claim confirm, receipt approve) follows with an event id derived from the idempotency key, a failure there raises a P1, and a same-store retry is a replay that repeats the half while the subscription is still on that payment's plan (a stale replay never drags stores.plan back); (d) free-month grants are ONE batch (subscription move guarded by the period read AND by every grant still pending, then every grant claim guarded by the subscription now ending where the chain ends): all or nothing, a miss leaves the grants pending for the next sweep (P1 names it); (e) settlement of a SUCCESS takes a lease on the ledger row (`failure_reason = 'settling'`, 120 s), applies the Postgres half (stores.plan) then the subscription, THEN flips the status (`succeeded` is final by trigger); a failure releases the lease, a crash lets it expire and the next settle sees `alreadyApplied` and only finishes the flip; `expireStaleCheckouts` skips leased rows; (f) the webhook dedupe row is a CLAIM (`processing`), finalised after the settlement, deleted on failure, taken over when stale: a throw after the claim can no longer turn the provider's retry into a "replay"; (g) cross-store scans are ONE query (no `acrossStores` fan-out). ## 7. Scale rules (Ruling NEON-SCALE-1, Ahmad 2026-11-02: "we could go viral any time")

Binding on every NEON-ZERO-1 PR. Copied from the controller's rules file (business/ebda/plans/2026-11-02-neon-zero-scale-rules.md).

Ahmad, 2026-11-02: "make NEON-ZERO-1 scalable from the start; we could go viral any time."
Owner: Ebda controller. Applies to every NEON-ZERO-1 PR. A PR that breaks a rule here needs a written ruling, not a silent exception.
Folds SCALE-READY-1 items 2 (platform lookups cached) and 3 (hot-store protection) into NEON-ZERO-1 so the new paths are built once, scale-ready.

### Why

- D1 is one database with one writer, queries run one at a time per database, 10 GB cap. If every request reads it, it becomes the single bottleneck for every store.
- Each StoreDO runs one request at a time. A viral store's traffic all lands on one object.
- So the request path must touch D1 rarely, touch a store's DO only for writes and live state, and serve everything else from cache.

### Request budgets (per request, steady state, cache warm)

| Path                                                                                 | Postgres | D1                  | StoreDO calls                          | Cache                |
| ------------------------------------------------------------------------------------ | -------- | ------------------- | -------------------------------------- | -------------------- |
| Public storefront page / catalogue / PDP / search                                    | 0        | 0                   | 0                                      | edge cache or KV hit |
| Store resolution (slug, custom domain, id)                                           | 0        | 0 on hit, 1 on miss | 0                                      | KV_CACHE             |
| Cart / checkout / stock / order write                                                | 0        | 0                   | 1 (batched RPC, never a loop of calls) | —                    |
| Authenticated merchant read (admin)                                                  | 0        | ≤1                  | ≤1                                     | per-request memo     |
| Auth check on a normal request                                                       | 0        | 0                   | 0                                      | signed token claims  |
| Auth check on a sensitive write (money, staff, plan, payout, settings, store delete) | 0        | 0                   | 1 (AUTH_STATE)                         | none                 |

Each PR states the budget of every route it touches and adds a test that counts calls (mock bindings that count invocations) so a regression fails CI.

### Rules

1. **Store directory cached.** slug / custom domain / id → `{storeId, status, backend}` in KV_CACHE. Unknown → cache a short negative entry (so a bot hitting random slugs never reaches D1), then 404. Staleness class: `status` (suspend, delete) is NEVER-stale → every write path that changes slug, domain or status deletes the KV keys in the same handler. Document the class at the cache site. A read with `status=suspended` from cache is honoured immediately.
2. **Auth state is strongly consistent, but not read per request.** Access tokens are short-lived (≤15 min) and carry `tokenVersion`. Normal requests trust the signed token. Refresh, and every sensitive write, reads the live `tokenVersion` + `status` from the AUTH_STATE Durable Object (strongly consistent, one object per user or per user shard). Revocation (logout-all, password change, staff removal, suspend) bumps AUTH_STATE in the same handler. Unknown user = blocked, never tokenVersion 0. No KV for revocation (eventually consistent).
3. **Store access (owner + staff) from ONE source.** Membership lives with the store (StoreDO) or with D1, never split. The gate and every staff/owner mutation use the same source, and the gate's answer is memoised per request only. Owner/staff changes bump the member's AUTH_STATE so stale tokens lose access within one request on sensitive writes.
4. **Hot store protection.** Storefront reads (store record, catalogue, PDP, collections, search results, settings for rendering) are served from the edge cache, tagged per store (`store:<id>`, `product:<id>`). Every write path that changes price, stock, publish state, settings or theme purges the matching tags in the same handler (price/stock = NEVER-stale → purge on EVERY write path, including imports, bulk edits, AI edits, jobs, webhooks). The StoreDO is reached only for cart, checkout, stock reservation, orders, payments and live state.
5. **D1 is for platform truth that changes rarely.** Plans, subscriptions, features, store directory, billing accounts, grants. Append-heavy data (audit log, billing events, analytics, webhook deliveries, job runs) does NOT grow inside the single platform D1: write it through a queue to Analytics Engine / R2 (or a per-store DO table where it belongs to one store), keep only a bounded summary in D1. State the 10 GB plan for every new D1 table (expected rows per store × stores at 100k stores).
6. **D1 reads use read replication where a read may be slightly stale.** Admin lists and dashboards read through the D1 Sessions API (replica-friendly); writes and read-after-write use the primary session bookmark. Never use a replica for auth, billing state or the store directory miss path.
7. **No fan-out on the request path.** Nothing loops over stores or DOs inside a request. Cross-store work (platform admin lists, rollups, billing runs) is a queue/workflow job that writes a summary.
8. **Every write is idempotent.** Payment, order, webhook and job writes carry an idempotency key checked inside the owning DO/D1 transaction (retries from queues and clients are normal at scale).
9. **Batching.** One RPC per request to a DO, carrying everything the request needs (a `getStorefrontState(...)` shaped call, not ten getters). D1 statements batched with `db.batch()`.
10. **Fail closed, cheap.** D1 unreachable on the directory miss path → 503 (already in #377). Cache unreachable → fall through to the source with a per-isolate circuit breaker, never an error storm.

## 8. Design note: rules 1-5 on the existing bindings (for controller review; no keystone code beyond the D1 client until approved)

Measured today (apps/api, main + #377):

- M1. Every anonymous edge-cache hit is validated by reading the cache generations from ONE Durable Object (`idFromName('cachegen')`,
  `lib/edge-gens.ts`, `cf/auth-state-client.ts`). That is a global single-object hot spot on every public read, and it breaks the
  "0 DO on cache hit" budget. (measured, code)
- M2. `authenticateAccounts` calls `Accounts.isRevoked(sid)` (service binding) AND `getUserState` (Postgres definer) on EVERY
  authenticated request, and `resolveTokenVersionAndStatus` caches `tokenVersion 0` for an unknown user. (measured, code)
- M3. AUTH_STATE is already sharded: 32 user shards (`shard-N`) plus `cachegen`. KV_CACHE is a 60 s TTL-floor L1 under `getCached`.
  STORE_REALTIME is per store. One analytics dataset exists (`CI_OUTCOMES`). Queues: jobs, ci-events, email, sms, wa-events.

### 8.1 Rule 1 - store directory (KV_CACHE, no D1 on hit)

- Keys `dir:s:<slug>`, `dir:h:<host>`, `dir:i:<id>` -> `{id, status, backend}`; negative `dir:n:<kind>:<key>` for 30 s. Fill from D1 (the
  #377 functions) on a miss only. The same entry carries `backend` so `backendFor` needs no D1 read on a hit.
- The reserved-slug check and a slug-shape check run BEFORE the cache so random strings never allocate keys.
- Invalidation: slug / domain / status / backend writes delete the keys in the same handler (store create, settings, domain verify,
  billing suspend, `flip-backend.mjs`). KV has no purge-all-colos primitive: a KV delete reaches other data centres within ~60 s.
  So `status` is NEVER-stale only on the paths that matter for money: every WRITE path (cart, checkout, admin, webhooks) re-reads
  `status` from the authoritative place (D1 for the gate, DO for orders) and never trusts the directory entry. For a pure READ of the
  storefront a suspended store can be served from a stale KV entry for <= 60 s. Decision needed (D-1): accept that residual for
  reads, or pay one StoreDO-free check via a per-store generation (see 8.4). Cost if wrong: a just-suspended store renders for up to a minute.
- Staleness class documented at the cache site; an `invalidate*` with zero call sites is a CI failure (test greps the call sites).

### 8.2 Rule 2 - auth (signed claims; AUTH_STATE only on refresh and sensitive writes)

- Source of truth for user existence, status and tokenVersion: the identity service (`Accounts`, D1 `ebda-identity`). AUTH_STATE
  (32 user shards) holds the strongly consistent copy `{tokenVersion, status}`, written by the identity service's revoke / suspend /
  password-change / staff-removal handlers in the same request (their existing `pushTokenVersion` path).
- Normal request: verify the ES256 / HS256 signature and `exp` (<= 15 min); trust claims. NO `isRevoked`, NO profile read.
  This replaces ID-9's "isRevoked on every request" -> Decision D-2: a revoked session keeps working on READS for <= 15 min.
- Refresh and every sensitive write (money, payout, staff / owner change, plan, settings, store delete, MFA / password): one
  AUTH_STATE read on `shard(userId)`. A MISS is not "tokenVersion 0": it asks the identity service once; if the identity does not
  exist the answer is BLOCKED and nothing is cached; if it exists the value is written to AUTH_STATE. Never filled from a
  non-authoritative backend (Postgres leaves this path entirely).
- The store keeps no credential profile row in Postgres; the `users` profile used by `getUserState` (role, deletedAt) moves into the
  token claims (role is already derived in `accountsUser`) plus the D1 `store_staff` / `stores.owner_id` gate (8.3).

### 8.3 Rule 3 - store access (one source: D1, per-request memo)

- Source: D1 `stores` (owner_id, status, billing_suspended_reason) + `store_staff`. Not the StoreDO: the gate runs before any DO is chosen,
  and platform-admin lists need cross-store membership. One query: `SELECT ... FROM stores s LEFT JOIN store_staff m ON ... WHERE s.id=?`
  = 1 D1 read per admin request, memoised on the request, via the D1 client (8.6).
- Every owner / staff mutation (staff add / remove, invite accept, owner transfer, store delete) writes THAT D1 row set and bumps the
  affected member's AUTH_STATE tokenVersion in the same handler, so on a sensitive write the stale token fails within one request.
  Reads and writes ship in ONE PR (Ruling NEON-ZERO-2). `readStoreForAccess` / `checkStoreAccess` and `StoreStaff` writes in
  `staff.routes`, `staff-invite.routes`, `store-members.ts`, `store.service` all move together.

### 8.4 Rule 4 - hot store protection (edge cache, tag purge, generations)

- Store record, catalogue, PDP, collections, search results, render settings are served from the existing public edge cache
  (`cf/public-edge-cache.ts`); the StoreDO is reached for cart, checkout, stock reservation, orders, payments, live state only.
- Cloudflare tag purge is a zone-cache feature; the Worker's `caches.default` is per data centre and cannot be purged by tag. So the
  existing generation scheme stays the invalidation mechanism, with two changes (Decision D-3):
  (a) shard the generation counters per store (`gen:<storeId mod 64>`) instead of one global `cachegen` object;
  (b) memoise generations per isolate for 2 s (reads then cost <= 1 DO read per isolate per store per 2 s, not per request).
  Residual: a price / stock figure on a read-only listing is up to 2 s stale in a data centre; checkout re-reads both authoritatively.
  Tags `store:<id>` / `product:<id>` map onto the generation names `generationNamesFor` already derives; every write path
  (imports, bulk, AI edits, jobs, webhooks) already calls `invalidateCached*` - the PR adds a test that enumerates writes of price,
  stock, publish, settings, theme and asserts a bump (zero-call-site check).
- The store record read inside the cache fill is ONE batched StoreDO RPC `storeRecord` (profile + config + disabled CMS slugs + footer
  locations + faqs), not the 12 queries `GET /public/stores/:slug` issues today.

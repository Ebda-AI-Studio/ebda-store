# CI-1 capture: implementation plan (Store, pre-launch)

Spec: `2026-10-28-customer-intelligence.md` (sections 1.1 to 1.8). This is the build order for the part that ships before launch. Stacked on #218 (`feat/wa-store-contract`): `buyerKeyFor` / `toE164` / `BUYER_KEY_VERSION` come from `@ebda/shared` there, nothing is duplicated.

**Finish line.** (1) Each outcome in the task list produces ONE `commerce_outcomes` v1 envelope with a deterministic `eventId` (a retry or a double carrier poll never makes a second row). (2) A batch on Queue `ebda-ci-events` lands as `outcomes/v1/store=<id>/dt=<day>/<ulid>.ndjson.gz` in R2 `ebda-ci` (with `buyerKey`, no phone, name, address) plus the buyer index, and as one Analytics Engine point per event WITHOUT `buyerKey`/`orderId`. (3) The existing G10 `ciSurface` erases and exports what this writer wrote (proved by a test that runs the real writer, then the real surface). (4) 24-month lifecycle on `outcomes/`. Must NOT change: order and shipment state machines, any checkout/booking path (a CI failure never blocks or delays one: advise-never-block). Done = unit tests green, full suite green via the heavy lock, CI green, `/health` commit == main tip after merge.

## Decisions

- **One port, many adapters.** `lib/ci/port.ts` `CommerceOutcomesPort.emit(inputs)` is the only thing emit sites know. Today's adapter enqueues to `ebda-ci-events`. After the Cloudflare cutover the StoreDO adapter writes `ci_outbox` in the domain transaction and its alarm flushes to the SAME queue; planners, envelope, consumer and sink do not change. The migration agent's repo layer only has to call the port from its status writes (`ci:` waiver comments mark the sites).
- **Event-fed, no scans.** One Inngest function `ci-outcomes` (triggers `order/created`, `order/status-changed`, `shipment/status-updated`, plus `shipment/created-ci`) reads ONE order/shipment row by id and plans envelopes. No table scan anywhere.
- **First-time-only** shipment events are decided where the state is written: `applyTrackingEntries` stamps `pickedUpAt` / `deliveredAt` / `returnedAt` only when null, bumps `deliveryAttempts`, and passes `firstTime` in the event; envelope ids are also deterministic (`shipment:<id>:<type>[:attemptNo]`) so a replay is the same row.
- **WhatsApp COD (contract section 8).** A COD outcome that arrived from WhatsApp (audit row `order.cod_outcome` with `source: whatsapp`) is NOT re-emitted as `order.cod_confirmed/unconfirmed`. The Store emits those two only for manual confirmation (`confirmedVia: call`) or a cancel with no confirmation (`none`).
- **Consumer dedupe**: KV `ci-seen:<eventId>` (7 d TTL), written AFTER the sink, best effort; the compaction/CI-2 reader dedupes on `eventId` too (at-least-once is the honest guarantee; the D1 `ci_seen` of the spec arrives with D1).
- **Privacy**: envelope `data` is built from a closed allow-list per type (no spread of a row), `returnReasonRaw` goes through `scrubFreeText` (200 chars, phones/emails/URLs masked). The consumer re-validates and rejects any key named like `phone|email|name|address` (Ruling CI-2 guard). `buyerKey` only when the order has a valid phone; never invented.
- **Contract deltas vs the v1 table (all inside `data`/enums, minor):** `byActor` gained `unknown` (no actor is recorded for system/cron status changes); there is no `order.returned` (the contract's `shipment.returned` plus the order's `order.cancelled` with reason `returned_to_sender` carry it); `payment.failed` is not emitted yet (no single provider-webhook failure path; its emit site is a follow-up against the same port).
- **Postgres-path erasure/export** (until the cutover turns on the G10 job): `eraseAccount` collects the buyer keys on the shopper's orders into the `account/erased` event, the propagation job erases them from R2 and verifies, the export bundle gains `customerIntelligence`, `orders.buyer_key`/`area_key` are nulled, and `redactOrderForCustomer` never returns them.
- **Scope cut, stated:** `cart.*`, `merchant.onboarding_step`, `customer.erased` are not in the task list; their emitters are later steps against the same port. The `ciSharing` onboarding question and privacy text stay with the controller; this PR adds the column and stamps `xstore` from it.

## Steps (TDD, touched tests only while working)

1. Schema: Shipment `returnReasonRaw/Code`, `pickedUpAt/deliveredAt/returnedAt`, `deliveryAttempts`, `areaKey`; Order `areaKey`, `buyerKey`; Store `ciSharing`, `ciSharingChangedAt`; CHECK on the code list; migration + tenant-guard regen.
2. `packages/shared` geo: `areaKeyFor(state, city)` with a pinned governorate list + alias table (AR/EN).
3. `lib/ci`: `envelope` (Zod, v1), `return-reason` (per-carrier mapper + scrub), `port`, `planner` (order, payment, shipment to envelopes), `consumer` (validate, dedupe, R2 + index with conditional put, AE), alert on `other` above 20%.
4. Emit wiring: `applyTrackingEntries`, shipment booking, the Inngest function, `worker.ts` queue routing, `wrangler.jsonc` (queue, DLQ, `CI_BUCKET`, AE dataset), boot assert.
5. Erasure/retention: writer-then-`ciSurface` test; `scripts/ops/ci-r2-lifecycle.sh` (730 d on `outcomes/`); guard test that every `shipment.status`/order status write path has an emit or `// ci: not-an-outcome`.
6. Docs: ENVIRONMENT, RULINGS, DEPLOYMENT (bucket/queue creation), then PR, Opus PII review, merge, deploy check.

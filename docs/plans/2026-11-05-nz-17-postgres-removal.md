# NEON-ZERO N-17: Postgres removal from the repo (plan + slice 1)

Date 2026-11-05. Branch `chore/nz-17-postgres-removal`. Prod has had no Postgres since #437: the Worker has no Hyperdrive,
its Prisma client throws `POSTGRES_REMOVED`, all data is on D1 `ebda-platform` + StoreDO. This plan inventories what still
names Postgres and says what happens to each part. Gate: `node scripts/cf/decommission-neon.mjs residue --strict`.

Finish line. Must work: Worker unchanged, local dev + Node integration tier unchanged. Exercised: tsc (shared, database, repo,
api, admin, web), the full unit suite, the strict route sweep (`SWEEP_STRICT=1`, HYPERDRIVE absent). Must NOT change:
production behaviour, any DO/D1 path. Done: slice 1 merged-ready with the numbers below, the rest tracked here.

## The key fact that shapes the plan

"Prisma" is not only Postgres. `packages/repo` (prisma-lite) answers the Prisma client API on the StoreDO, and the whole
domain layer (`@prisma/client` types, `Prisma.Decimal`, the DMMF) is shared by both backends. So the residue pattern
(`@prisma/client`, `$queryRaw`, `DATABASE_URL`...) matches live DO-serving code, not only dead Postgres code. The `'pg'`
backend is also not dead in the repo: `backendFor()` returns `pg` for Node, unit tests and local dev (D1 unbound), and 112
`backendFor`/`storeRepo` call sites keep a `pg` arm because the 144 Node integration tests drive it. On the Worker the `pg`
arm is unreachable (`backendFor` 410s a `pg` row, the client throws). Deleting those arms before the Node tier has a DO/D1
replacement would delete the only test coverage of the service logic, so it is NOT slice 1.

## Replacement for the Postgres integration suite

The DB-less lanes already exist: `apps/api/workers-do/*` (28 files: stock, orders, payments, returns, wallet, erasure,
backup, jobs, books, gold pricing, cutover...) on a real StoreDO + D1 + R2 under workerd, `workers-test/` (entry, route
sweep over the whole route table with `SWEEP_STRICT`, impersonation, platform D1, queues/cron, `pg-unreachable`), plus
the unit tier. Assertions with NO DO/D1 equivalent yet (must be ported before their Postgres test is deleted):

1. Tenant isolation as a property: StoreDO.bind refuses another store (spike-level only in `store-do-spike`), but there is
   no sweep-style test that every route with a `:storeId` returns 404/403 for a foreign store on the DO. (Replaces RLS
   "cross-tenant read/write denial". This is why NZ-17-RLS-1 names it as the residual.)
2. Search ranking/lexical + trigram index behaviour (`search-lexical-rls-index`, `order-customer-search-rls-index`):
   Postgres planner assertions, no FTS5 equivalent test; `palette-search` covers only the palette.
3. Accounting reports on large ledgers (journal/period close SQL aggregates) vs the DO SQLite path: only money/books
   happy paths in `books.test.ts`.
4. Request-transaction semantics (commit-before-response, savepoints, `COMMIT_TIMEOUT`): DO has atomic `mutate` instead;
   the invariants differ, so these tests are deleted with category A, not ported.
5. Super-admin cross-store reads (`acrossStores`, definers): D1 directory covers listing (`store-directory-d1`), not the
   per-store fan-out of analytics.
6. Impersonation + audit sink to Postgres (`audit-sink` targets `pg`): D1 target is covered by `impersonation.test.ts`.

Slice 2 ports 1, 3 and 5 into `workers-do`; 2 and 6 are decided there (port or accept loss as a Ruling).

## Local dev story (unchanged by slice 1)

`npm run dev:api` (`tsx watch src/index.ts`) is the Node server: it still needs the docker Postgres (`docker-compose.yml`,
pgvector pg17) plus `DATABASE_URL`/`DIRECT_URL`, `npm run db:migrate`, `npm run db:seed`. The Worker path needs no Postgres:
`npm run cf:test` / `cf:test:do` (workerd + local D1/DO/R2), and `scripts/ebda-dev-api.sh MODE=worker` is the only script
that still passes a Hyperdrive string (slice 2 removes that branch). Slice 3 retires the Node server and `dev:api` becomes
`wrangler dev` over local D1/DO.

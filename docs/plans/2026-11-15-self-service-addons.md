## 3. State model (derived from the ledger, nothing new stored; ADDON-2 kept)

Per SKU the API returns exactly one `state`, computed server-side from `billing_events` (newest `addon:<sku>` row + running terms + cancel markers + feature map):

| state                     | rule                                                                            | merchant sees                                                   | action                                                         |
| ------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------- |
| `available`               | no running term, no recent attempt, not on plan                                 | price + what it does                                            | Buy                                                            |
| `pending_payment`         | newest `addon:<sku>` row is `pending`, created < 30 min ago                     | "Waiting for your payment to be confirmed"                      | none (poll); after 30 min row is treated stale and Buy returns |
| `failed`                  | newest row `failed` within 7 days, no running term                              | "Payment did not go through" + reason code, nothing was charged | Buy again                                                      |
| `active` / `renewing`     | running term, no cancel marker (feature SKUs renew; AI packs are `active` only) | "Active, renews on <date> for <amount>"                         | Cancel renewal                                                 |
| `cancelled_at_period_end` | running term + latest marker is `addon-cancel:`                                 | "Active until <date>, will not renew"                           | Resume                                                         |
| `expired`                 | latest succeeded term ended within 30 days                                      | "Ended on <date>"                                               | Buy again                                                      |
| `refunded`                | newest succeeded row became `refunded`                                          | "Refunded on <date>, turned off"                                | Buy                                                            |
| `included`                | feature on via plan baseline with no running term (source `plan`)               | "Included in your plan"                                         | none                                                           |
| `granted`                 | super-admin override `enabled=true`, no running term (source `grant`)           | "Turned on for you by Ebda support"                             | none                                                           |

A paid term and an override can coexist: precedence is override off > running term > override on > plan, unchanged from #775 (ADDON-3).

## 4. Data flow (card, unchanged from #775; stated so the review can check each hop)

1. Merchant opens Settings -> Add-ons (`/stores/:id/billing/addons`), `GET .../addons` returns catalogue + state per SKU.
2. Buy -> `POST preview` (read-only, nothing charged) -> dialog shows total, VAT, renewal terms.
3. "Yes, charge" -> `POST checkout` with `Idempotency-Key` (browser `crypto.randomUUID()` per click-through, reused on retry of the SAME dialog) + confirm token. Server: `withIdempotencyKey` (required) -> consume token (single use) -> `claimEvent` UNIQUE key `addon:<store>:<sku>:<key>` -> one `pending` row -> hosted card page. A double click or replay returns the same result / `CHECKOUT_IN_PROGRESS`; never a second row.
4. Card page -> webhook (signed) -> `settleInTx`: guarded pending->succeeded update (single-shot) + `applyAddonGrant` in the SAME transaction -> effect `addon_granted` -> cache bust. A duplicate webhook finds the row already settled and the grant marker already there: no second grant (#788/#791).
5. Browser returns to `?checkout=return`: the page polls `GET addons` every 3 s for up to 90 s until the SKU leaves `pending_payment` (G3). Nothing is enabled client-side, ever.
6. Failure at any point: row `failed` (checkout error or declined webhook), no grant, state `failed`.

## 5. Entitlement source of truth and cache (G2, NEVER-stale)

Source of truth: ledger rows (section 1). Read path: `FeatureService.readFromDb` -> `rowsToMap` -> Redis `features:store:<id>` (plus the per-request in-process map; verify in `featureService.getStoreFeatures`).

Staleness class: **NEVER-stale** (entitlements). Every change path and its invalidation:

| path                            | event                                | layers cleared                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| grant (settle)                  | `addon_granted` effect               | Redis feature key + product caches (`invalidateCache`) - exists                                                                                                                                                                                                                                                                                                                                                                          |
| refund succeeded                | inline in refund settle              | same - exists                                                                                                                                                                                                                                                                                                                                                                                                                            |
| super-admin set/remove override | `feature.service` write paths        | same - exists                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **expiry (term end passes)**    | none today                           | **new: cache entry is written with TTL = min(300 s, seconds until the earliest running term end)**, so the entry dies exactly at the end of the paid term. A running-term-aware TTL is an event (time of expiry is known at write time), not a sampling window. Plus the existing daily billing job calls `invalidateCache` for every store whose term ended since the last run (belt and braces for entries written before this ships). |
| cancel at period end            | no entitlement change until term end | covered by expiry row above                                                                                                                                                                                                                                                                                                                                                                                                              |
| renewal succeeds                | new `upgrade` row -> `addon_granted` | exists                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| renewal fails                   | term simply lapses                   | covered by expiry row                                                                                                                                                                                                                                                                                                                                                                                                                    |

Guard test: a unit test enumerates every writer of `billing_events` with an `addon:` plan code and asserts each one pushes an effect or is listed as no-entitlement-change; a second asserts the Redis `set` TTL never exceeds the soonest term end (mutation-checked: drop the clamp -> red).

## 6. Idempotency, refunds, plan interaction, super-admin

- Double click / double submit: two layers already (Idempotency-Key + single-use token); the delta adds a test that fires both concurrently and asserts one `pending` row and one provider call.
- Duplicate webhook: guarded status transition + D1 predecessor marker (#788); delta adds an end-to-end test across `settleInTx` twice -> one term.
- Failed payment: no grant, state `failed` (G3), #797 keeps the failed row out of the term chain.
- Refunds: unchanged mechanism (`refundCharge`: succeeded -> refunded, entitlement off at once, cache busted). Policy: super admin issues refunds (money-out stays staff). The page shows the `refunded` state and the refund line in history (G4). Self-service refund is OUT of scope (open decision D3).
- Plan interaction: if the plan baseline already includes the feature, state is `included`, Buy is hidden, `quote` returns ALREADY_INCLUDED. A merchant who bought and later upgrades to a plan that includes it keeps the paid term but renewal is skipped (exists: `resolveWithoutAddons` in renewal) - a notice is added to the card.
- Super-admin grant: the override endpoint is untouched and still audited (`auditLog` actions in `feature.routes.ts`). The delta adds `source: 'plan' | 'grant' | 'purchase'` so the page can say "turned on for you by Ebda support" (G7), and a test asserts a grant never creates a ledger row and a purchase never writes `StoreFeature`.

## 7. InstaPay (G6) - DECIDED by Ahmad 2026-11-15: allowed now, manual approval

Reuse of the existing plan path (no second flow): the merchant transfers the quoted total (VAT included) and uploads the receipt through the existing `POST /billing/receipts`; the add-on submit (`POST .../addons/:sku/instapay/receipts/:id/submit`) calls the same `submitSubscriptionReceipt` with the add-on code, which creates a `manual_payment_claims` row (planCode `addon:<sku>`). That claim IS the entry in the existing super-admin "Payment claims" queue. NOTHING turns on until a super admin approves (`POST /admin/billing/claims/:id/approve-addon`): the claim becomes a ledger row (key `addon-instapay:<claimId>`, provider `instapay`) settled by the same guarded pending -> succeeded transition as a card payment, so the grant is exactly once and a replay resumes the same row. The plan path (`recordManualPayment`) refuses an add-on claim (USE_ADDON_APPROVAL). Reject or silence: nothing active; a claim older than 7 days shows `available` again but stays in the queue. A pending claim blocks a second purchase of the same add-on (card or InstaPay). States added: `waiting_confirmation`, `rejected` (ar + en). When InstaPay auto-confirm ships it calls `approveAddonClaim` with the machine as actor.

InstaPay terms are NON-RENEWING (Ruling ADDON-SS-6): `renewDueAddons` skips provider `instapay` and sends one "pay again by InstaPay" notice; `refundCharge` refuses provider `instapay` (staff refund outside the gateway, revoke with a super-admin feature override off); the stuck-charge sweep never asks the card gateway about an `instapay` row.

## 10. Rulings

Ruling ADDON-SS-1 - no second purchase path: this work extends #775..#798 and merges after them. Cost if wrong: two billing flows to reconcile; mitigated by building nothing in parallel.
Ruling ADDON-SS-2 - states are derived from the ledger, no new table/ledger type (ADDON-2 kept). Cost if wrong: history queries scan `billing_events` by planCode prefix; bounded by the 50/200 row limit and the existing index on store.
Ruling ADDON-SS-3 - expiry is closed by a running-term-aware cache TTL, replacing the BOUNDED 5-minute residual of ADDON-3 with NEVER-stale. Cost if wrong: an expired add-on is served for as long as the cache clamp fails; the daily sweep caps that at 24 h and it errs in the merchant's favour.
Ruling ADDON-SS-4 - InstaPay is IN, with manual super-admin approval per payment (section 7). Cost if wrong: approval latency; nothing is ever on before a human approves.
Ruling ADDON-SS-6 - InstaPay terms never renew, refund or poll the card gateway. Cost if wrong: a free extension or a wrong-gateway refund; closed by tests.
Ruling ADDON-SS-5 - self-service refund is out of scope; refunds stay a super-admin money-out action. Cost if wrong: a merchant who bought by mistake files a request.

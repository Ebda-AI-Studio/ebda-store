# FWB "Vibecode Lens" Perf Audit — 2026-07-12

Source: an Instagram reel making 5 blanket claims that "Claude-coded apps are
slow" (artificial UI delays, unbounded third-party fetches, cold serverless
caches, naive per-row DB writes, and blocking spinners on optimistic-eligible
actions). Scope: `apps/api` (Express+TS on Railway), `apps/web` (Next.js on
Cloudflare Workers via OpenNext), `packages/database` (Prisma+Neon). Each
claim was verified against the actual codebase before any fix landed — this
is not a blind pattern-match against the reel's talking points.

## Per-claim verdict

| #   | Reel claim                                                                                                           | Verdict against this codebase                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | "Buttons have fake `setTimeout` delays to fake a loading state"                                                      | **Confirmed.** `ProductDetailClient.tsx` had a literal `await new Promise(resolve => setTimeout(resolve, 300))` before `addItem()` in `handleAddToCart` — a pure, artificial 300ms tax on every add-to-cart click.                                                                                                                                                                                                                           |
| 2   | "Outbound API calls have no timeout, so one flaky vendor hangs the whole request"                                    | **Confirmed.** All four Kuwait payment-provider clients (`myfatoorah`, `tap`, `hesabe`, `upayments`) called `fetch()` with no `signal` — a hung gateway would hold the connection (and Node's event loop capacity) open indefinitely instead of failing over to the existing fail-soft error path.                                                                                                                                           |
| 3   | "Serverless deploys have no persistent cache, so every page recomputes from origin"                                  | **Confirmed.** `apps/web/open-next.config.ts` passed an empty config to `defineCloudflareConfig({})` — OpenNext's default incremental cache is in-memory only, which is cold on every Cloudflare Worker isolate restart. The R2 bucket for this (`force-web-isr-cache`) already existed but was never wired as the `NEXT_INC_CACHE_R2_BUCKET` binding.                                                                                       |
| 4   | "Bulk operations do N sequential single-row writes instead of one batched write"                                     | **Confirmed, in three places.** Variant import (`bulk.service.ts`) created options, option values, variants, and variant-option junction rows one `.create()` at a time inside a transaction. Order placement (`order.service.ts`) wrote one `inventoryHistory.create()` per cart line. The nightly analytics rollup (`analytics-rollup.service.ts`) wrote one cohort/funnel/RFM snapshot row at a time via `findFirst` + `create`/`update`. |
| 5   | "Actions that could be optimistic (toggle a heart icon, remove a wishlist row) instead block the UI on a round-trip" | **Confirmed, two surfaces.** The PDP wishlist toggle (`ProductDetailClient.tsx`) and the wishlist-page remove button (`WishlistClient.tsx`) both disabled/waited on the API call before updating state, unlike `CartContext.addItem`, which already updates state optimistically and rolls back on failure.                                                                                                                                  |

**Tally: 0 Critical / 3 High / 2 Medium / 4 Low** (9 findings, 9 fixes — none deferred).

- **High** — artificial UI delay (claim 1), unbounded payment-provider fetches (claim 2), cold ISR/SSG cache (claim 3). All three sit directly on the checkout/storefront critical path.
- **Medium** — batched variant import, batched order inventory-history writes (half of claim 4 — the two writes on a live request path: import and checkout).
- **Low** — batched analytics-rollup snapshots (the other half of claim 4 — an internal nightly cron, not user-facing), optimistic PDP wishlist toggle + wishlist-page remove (claim 5 — UX polish, not a broken flow), and a stale doc-path one-liner unrelated to any of the 5 claims but caught in the same pass.

## What NOT to do (guardrails re-affirmed, not touched by this pass)

- **Redis TTL floor stays ≥120s.** No cache introduced or modified here uses a sub-120s TTL. (ESLint-blocked repo-wide regardless.)
- **No network I/O inside an RLS or money transaction.** The batched writes in (d) and (f) are pure-DB `createMany`/`createManyAndReturn` calls inside the _existing_ transaction boundary — no new fetch, cache, or queue call was added inside any `tx.$transaction`/`withMoneyTx` block.
- **`headers()` stays in the store-resolver.** Tenant resolution via `apps/web/src/lib/store-resolver.ts` was not touched — that redesign is planned work, out of scope here.
- **Checkout concurrency patterns are untouched.** `withMoneyTx`, stock-decrement locking, and the serializable-transaction retry logic in `order.service.ts` are unchanged; only the trailing inventory-history _write_ (which runs after stock is already decremented) was batched.
- **Compression config was already correct** — confirmed during this audit, no change made.

# FWB i18n / RTL Audit — 2026-07-02

Scope: `apps/admin` (next-intl) + `apps/web` (custom `LanguageContext` inline
`t(en, ar)` pattern). Read-only. Worktree HEAD: `2332c4d5`.

Lens: key parity, hardcoded strings, RTL layout breakage, number/date/currency
formatting, bilingual (`*Ar`) data-column admin editability.

## Architecture note (verify-before-audit)

Contrary to the task brief's framing, only **`apps/admin`** uses next-intl with
`messages/{en,ar}.json` (`apps/admin/src/i18n/messages/{en,ar}.json`, 5,815
lines each). **`apps/web` has no messages JSON at all** — it uses a custom
`LanguageContext` (`apps/web/src/contexts/LanguageContext.tsx`) exposing
`t(en: string, ar: string) => string`, called inline at each use-site with
literal EN/AR strings (a `translations` const map exists but is legacy/mostly
unused — call-sites pass literals directly to `t()`). So "key parity" in the
JSON-diff sense only applies to admin; the storefront's i18n risk is instead
"was `t()`/`isAr` used at all for this string."

### 3. [High, CONFIRMED] Every price on the storefront (and admin) renders in English digits/format regardless of active locale — inconsistent with the newer Arabic-Indic discount-savings text

`packages/shared/src/utils/index.ts:51-65`:

```ts
export function formatPrice(
  amount: number,
  options?: { unit?: 'fils' | 'kwd'; currency?: string; locale?: string }
): string {
  const { unit = 'fils', currency = 'KWD', locale = 'en-US' } = options ?? {};
  ...
  return new Intl.NumberFormat(locale, { style: 'currency', currency, ... }).format(amount / divisor);
}
```

`locale` defaults to `'en-US'` and **0 of 86 call-sites repo-wide** (verified
by grep across `apps/web/src` + `apps/admin/src`) ever pass a `locale`
override. Runtime-verified in Node:

```
Intl.NumberFormat('en-US', {style:'currency', currency:'KWD', minimumFractionDigits:3}).format(12.5)
  → "KWD 12.500"
Intl.NumberFormat('ar-KW', {style:'currency', currency:'KWD', minimumFractionDigits:3}).format(12.5)
  → "‏١٢٫٥٠٠ د.ك.‏"   (Arabic-Indic digits + Arabic currency string)
```

So every price on the Arabic storefront — cart line items and totals
(`CartClient.tsx:492,579,812,871`), checkout total (`OrderSummary.tsx:275,350`,
`CheckoutClient.tsx`, `PaymentStep.tsx:217`), PDP price
(`ProductDetailClient.tsx:683-688`), order confirmation
(`SuccessClient.tsx:249,257`), account/order history
(`AccountDashboardClient.tsx:259`, `OrdersClient.tsx:161`) — always renders
"KWD 12.500", never Arabic-Indic digits, even though `document.lang === 'ar'`
and everything around it is RTL Arabic text.

This directly contradicts a sibling helper in the **same directory**:
`apps/web/src/lib/product-pricing.ts:82` (`getDiscountBadgeText`, shipped
2026-07-01 per project memory) explicitly does
`new Intl.NumberFormat('ar-KW', {...}).format(...)` to produce
`"وفّر ٢٫٠٠٠ د.ك"` for the discount-savings badge. Net effect: an Arabic
shopper on a discounted product's cart line can see the savings text in
Arabic-Indic numerals directly next to the subtotal in Western digits/English
"KWD" prefix — a mixed-locale currency display on one line. Admin has the same
gap (44 `formatPrice()` call-sites, same default), lower severity since it's
an internal tool where Western digits for bookkeeping may be an accepted
convention — flag for Ahmad to confirm intent either way.

### 6. [Low, informational] Two `*Ar` columns have no admin editor AND no storefront render — not an EN/AR asymmetry, but an orphaned-data smell

Systematic check (script diff of all 65 `*Ar` Prisma columns against
`apps/admin/src` / `apps/web/src` grep hits) found **no case of "rendered on
storefront but not editable in admin"** — the specific bug class in the task
brief. Two fields have neither editor nor storefront render:

- `Product.citationCopyAr` (`packages/database/prisma/schema.prisma:729`) —
  AI-generated GEO/citation text (`apps/api/src/lib/inngest/functions/bulk-ai-geo.ts`).
  Admin's `GeoResultsPanel` shows fill-rate/counts only, never the generated
  text itself (EN or AR) for merchant review.
- `JournalLine.lineMemoAr` (`packages/database/prisma/schema.prisma:2713`) —
  accounting ledger line memo; no admin field, no storefront surface (expected,

Both are symmetric (neither EN nor AR side is exposed), so this isn't an
i18n-parity bug — flagged as a minor "every data needs UI" gap for
`citationCopy`/`citationCopyAr` specifically (a merchant currently cannot see
what GEO copy the AI wrote for their product in either language).

## Confirmed-fixed / no-action items (verified against actual code, not assumed from memory)

These are exactly the bug classes the project's own memory files warn about
(`feedback-tailwind-tracking-breaks-arabic.md`,
`feedback-card-cta-ai-balancer-plp-filters-batch.md`'s `dir="ltr"` rule,
`feedback-fwb-rtl-select-min-width.md`) — verified **already mitigated**, not
re-flagged as findings:

- **Arabic letter-joining / `tracking-[X]`.** 79 `tracking-[X]` instances
  exist (mostly in `elegant`/`classic` templates), but
  `apps/web/src/styles/globals.css:209-213` globally neutralizes them:

  ```css
  :lang(ar),
  :lang(ar) * {
    letter-spacing: normal !important;
    text-transform: none !important;
  }
  ```

  `lang`/`dir` are set both server-side (`apps/web/src/app/layout.tsx:692`,
  `<html lang={lang} dir={dir} suppressHydrationWarning>`) and client-side
  (`LanguageContext.tsx:60-61`), so there's no FOUC window where tracking
  briefly renders before the override applies. This is a smarter, more
  comprehensive fix than the original per-component gating pattern the memory
  file describes for a different (Om Hassan) project — no action needed.

- **RTL scroll-snap / negative `scrollLeft`.** `ProductDetailClient.tsx:570`
  forces `dir="ltr"` on the swipeable PDP image-gallery track (images are
  direction-agnostic, matching the standing rule exactly).
  `ProductCarousel.tsx:157-158,185,205` takes a different but equally correct
  approach for content where direction DOES matter (product order should
  follow reading direction): `Math.abs(el.scrollLeft)` for position math plus
  an explicit `isRtl ? -1 : 1` sign multiplier on `scrollBy`/`scrollTo` calls.
  `CategoryStrip.tsx` and `BlogCarousel.tsx` use pure CSS `snap-x` with no JS
  `scrollLeft` reads at all, so the negative-scrollLeft bug class doesn't
  apply to them. No action needed.

- **Select truncation in horizontal toolbars.** The PLP's Show/Sort controls
  (`apps/web/src/app/products/ProductsFilterSidebar.tsx:229-266`) are native
  `<select className="w-full">` stacked vertically inside a fixed-width
  sidebar column (not competing in a horizontal toolbar row), so the
  wrapper-squeeze truncation bug documented in
  `feedback-fwb-select-wrapper-stack-toolbars.md` /
  `feedback-fwb-rtl-select-min-width.md` doesn't apply here. No action needed.

- **Admin `en.json`/`ar.json` structural parity.** 0/5,173 keys missing either
  direction — see key-parity tally above.

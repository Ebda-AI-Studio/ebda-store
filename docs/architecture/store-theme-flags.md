# Per-store visual configuration — flags, owners, invariants

Moved verbatim from `CLAUDE.md` (2026-07-11). Canonical reference for StoreTheme flags, canonical editors after the Page-Builder consolidation, and the product-card customization system. Update in the SAME session as any change to these systems (documentation-parity rule).

**Page Builder + Smart Palette are the CANONICAL design system** for all color, font, hero, and per-section layout controls as of 2026-06-09 (PRs #86–#90). The Branding tab's manual color pickers (`ColorPalettePicker`), global font-family picker (`TypographyPicker`), and `backgroundPreset` selector are **retired inputs** — "edit in Page Builder" pointers or read-only swatches. Any code or doc referencing those as the primary color/font editors is stale.

**Section keys and the layout write path (visual builder Phase 1, 2026-10-07):** the section registry (`packages/shared/src/builder/registry.ts`) owns the homepage section keys and their settings schemas; `LEGACY_HOME_SECTION_KEYS` is the one copy of the 8 orderable keys, and the layout Zod schema lives in `packages/shared/src/builder/layout-schema.ts` (re-exported by the API route). `stores.layout_settings` is written by builder publish / rollback (`apps/api/src/services/page-builder.service.ts`, back-write) and by the legacy layout PUT, which now records a published revision in the same transaction so the two never diverge. `hideOnTablet` (unset = legacy two-way visibility) is the only new section knob. Details: `docs/architecture/page-definition.md`.

## Look-owned keys and the compose path (2026-10-14)

Looks (`docs/ebda/templates/looks.md`) own a set of `StoreTheme` keys, `LOOK_TOKEN_KEYS` in `packages/shared/src/looks/types.ts` (the colour keys, `headingFont`, `bodyFont`, `borderRadius`, `bgPage`, `bgSectionAlt` and three new ones). A stored value for one of them is a **merchant override**.

| Key          | Type                                 | Default | Owner                                                                                                |
| ------------ | ------------------------------------ | ------- | ---------------------------------------------------------------------------------------------------- |
| `density`    | `'compact' \| 'regular' \| 'airy'`   | unset   | set only by a look (`lookTheme`); `--space-unit` 0.875 / 1 / 1.25; scales UNSET section spacing only |
| `imageRatio` | `'1/1' \| '4/5' \| '3/4' \| '4/3'`   | unset   | set only by a look; `--image-ratio`; product card media `aspect-[var(--image-ratio,4/5)]`            |
| `motion`     | `'none' \| 'subtle' \| 'expressive'` | unset   | set only by a look; `--motion-duration` 0 / 180 / 280ms; forced to 0ms under reduced motion          |

All three are optional and absent from `DEFAULT_THEME` (Ruling LOOKS-6): a legacy store (`stores.look` null) emits none of the look CSS variables and renders byte-identical.

- **`composeStoreTheme({ template, look, theme })`** (`@ebda/shared`) is the single compose path for every resolver site: `DEFAULT_THEME < TEMPLATE_THEMES[skin] < look tokens < stores.theme`. Do not spread `getTemplateTheme(...)` and `stores.theme` by hand; an unknown/null `look` is ignored.
- **`PUT /stores/:id/theme` null-deletes.** `StoreService.updateTheme` shallow-merges the payload into the stored theme, and a `null` value DELETES that key (it is never persisted as `null`). That is how a merchant resets one look override back to the look's value. No admin surface wrote an intentional null before this (audited 2026-10-14). Builder reset also removes the key from the draft theme first (Ruling LOOKS-11).
- **`overriddenLookKeys(theme, look)`** lists look-owned keys whose stored value differs from the look; it drives the override badges in the builder's `ThemeSettingsPanel`.
- Switching look is `PUT /stores/:id/look` (`StoreService.applyLook`): `design: 'keep'` leaves overrides, `'reset'` deletes every `LOOK_TOKEN_KEYS` key from `stores.theme` and the draft theme.

## Product-card CTA + OOS-label + name-case (2026-06-24)

`ProductCardDefaults` (store layout JSON, Page Builder → "Product cards (everywhere)") carries an opt-in CTA/label system applied across ALL 8 render paths (7 product-render-paths + `ProductListItem`): `ctaShape` (rounded/pill/square/soft), `ctaSize` (sm/md/lg), `ctaColor`/`ctaTextColor`, `ctaLabel`+`ctaLabelText{En,Ar}`; `oosLabel`+`oosLabelText{En,Ar}`, `oosLabelShape`, `oosLabelPlacement` (top/bottom × start/end), `oosLabelColor`/`oosLabelTextColor`, `oosDimColor`; `productNameCase` (normal/uppercase). All optional + neutral-default EXCEPT `productNameCase` defaulting to **normal** (intentionally removed forced ALL-CAPS on elegant/minimal/bold).

Invariants:

- Class helpers live in `apps/web/src/templates/shared/card-size.ts` (`ctaShapeClass`/`ctaSizeClass`/`labelShapeClass`/`oosPlacementClass`); Zod-validated in `packages/shared/src/builder/layout-schema.ts` `productCardDefaults` (re-exported by `store-layout.routes.ts`) (silent-strip trap — every key must be listed).
- Cards read via `useStore().layout?.productCardDefaults` with prop fallback (the #380 "T.ProductGrid threads zero props" lesson).
- **`ctaShape`/`ctaSize` MUST merge via `cn()` (tailwind-merge), NOT string concat** — base buttons hardcode `rounded-2xl`/`rounded-xl` + padding/`min-h`, and Tailwind's fixed source order makes those win over later-in-string classes; plain concat silently dropped every shape except `pill`. Fixed across all 8 paths.
- **The PDP carries the OOS system too** — `ProductDetailClient.tsx` mounts `OosImageDim` + `OutOfStockRibbon` on the main image from the same `productCardDefaults`, honoring backorder (`orderable = !outOfStock || canBackorder`).
- **Backorder-aware CTA**: cards compute `orderable = product.inStock !== false || product.acceptsBackorder === true`; CTA pressable + OOS label hidden when orderable. `inStock` still used separately for NEW-badge suppression / BrandPill.

## Custom product badge (2026-09-07)

A **per-product, merchant-authored** chip rendered in the same visual language as the computed discount badge. Two nullable columns on `Product` (`badgeLabel` / `badgeLabelAr`, `VARCHAR(32)`, migration `20260907120000_product_custom_badge`) plus a `customBadge` block on `ProductCardDefaults` that carries only styling (`position` + `color`).

The distinction that drives every decision below: `getDiscountBadgeText()` **derives** its text from the pricing maths and cannot say anything the numbers do not; this one is the merchant's own words ("عرض" / "Offer" on a School's Offer product), which nothing else in the platform could produce.

**Where each half lives**

| Half                              | Owner                                              | Surface                                                                                                            |
| --------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| The text (per product, bilingual) | `Product.badgeLabel` / `badgeLabelAr`              | Admin → Products → edit → **Product Flags** card (`EditSidebar.tsx`), and the new-product form                     |
| The look (per store)              | `productCardDefaults.customBadge.{position,color}` | Page Builder → "Product cards (everywhere)" → **Custom product badge**, sibling to the Discount / sale badge block |

There is **no enable toggle by design** — an empty label already means off, which is why this satisfies "new visual features default OFF" structurally rather than with a flag. A store that has typed nothing renders byte-for-byte what it rendered before the feature existed (asserted, see below).

**The badge mutex — `apps/web/src/templates/shared/custom-badge.ts`, `resolveCardBadges()`**

Sister systems are a runtime mutex, not a merchant decision (same rule as the `SectionDivider` ↔ `backgroundPreset` precedent below). Three rules, one implementation, called by all nine surfaces:

1. **No label → nothing changes.** `customBadgeText` is null, `discountBadgeAllowed` is true. The additive contract.
2. **Not orderable → the custom badge is suppressed.** Out-of-stock is a hard state signal that must not compete with a promotion, and an "Offer" chip on something nobody can buy is a promise the store cannot keep. The **discount badge is deliberately NOT suppressed** here — it is factual pricing information and has rendered in both stock states since the 2026 "BUG 2" fix. This rule also collapses the three-way case (label + discount + OOS) to today's exact rendering, which is why there is no fourth rule for it.
3. **Same physical corner → the custom badge wins, the discount badge yields.** The merchant _typed_ the custom label; the discount badge is _derived_. Explicit beats derived, same direction as the SectionDivider precedent. Different corners → both render. The comparison is on RESOLVED corners, so an unset position and its explicit twin count as the same corner.

Two badges never stack on one corner, and the merchant is never asked to resolve the clash.

**Invariants**

- **Position is PHYSICAL, never RTL-mirrored** — identical rule and identical class mapping to `getDiscountBadgePosition` (`discount-badge.ts`). "bottom-right" is the physical bottom-right on an Arabic storefront too. The badge's _text_ follows the locale; its _placement_ does not.
- **Defaults differ on purpose**: custom = `bottom-right` (`CUSTOM_BADGE_DEFAULT_POSITION`); discount = the image's **top corner on the reading-START side** (`pinDefaultDiscountBadge`, owner decisions 2026-10-01 / 2026-09-30, #1998), or the legacy `bottom-left` (`DISCOUNT_BADGE_DEFAULT_POSITION`) for a store whose theme sets `saleBadgeLegacyCorner: true`. A store that configures neither gets both badges on different corners, not a suppression. A custom chip the merchant put in a TOP corner never suppresses the pinned sale chip either (issue 2343, Ruling OD-9e): the pin moves to the free top corner or the row below the custom chip; rule 3's suppression applies only when the merchant chose both corners.
- **`StoreTheme.saleBadgeLegacyCorner`** (boolean, unset = false): per-store DATA that keeps the pre-#1998 bottom-left default. Every corner-chip surface passes `saleBadgeTopCorner: store.theme?.saleBadgeLegacyCorner !== true` into `resolveCardBadges` (pinned by `tests/unit/sale-badge-top-pin.test.ts`, which also proves `saleBadgeTopCorner: false` resolves identically to omitting it). Toggle: **Page Builder → Product cards → Discount / sale badge** → "Keep the original sale-badge corner" (ThemeTab is at its 7-toggle ceiling); saved through the theme shallow-merge PATCH. pecannbee is set to legacy by `scripts/set-sale-badge-legacy-corner.mjs` BEFORE the #1998 code deploys (owner: pecannbee must not change).
- **The unset sale badge is pinned to the top edge — never lifted** (#1998; not on a legacy-corner store). The old default (physical bottom-left) was lifted ~96px on the five theme cards to clear the mobile add-to-cart band; on desktop that band is `lg:opacity-0` until hover, so at rest the chip floated mid-image with nothing under it. The band only covers the bottom edge, so the pinned chip is never covered. It takes the reading-start top corner when free; else the reading-end corner when free; else it stays on the side with the shallower occupant and sits one row below it — `top-12` under a NEW/brand pill, `top-16` under a heart/compare button, `top-[min(6rem,…)]` under the out-of-stock corner ribbon (`!orderable` reserves top-start on every surface). On PecannbeeProductCard (heart at top-start) that puts it top-END, matching the card's § 4.3 spec. A corner the merchant CHOSE is unchanged: physical, avoided and lifted exactly as below. Pinned by `tests/unit/sale-badge-top-pin.test.ts`; before/after screenshots on the PR.
- **Corner-collision avoidance** (issues #1609/#1611/#548/#1997): a merchant-configured top corner that coincides with a reserved action button (heart via `topEndReserved`, compare via `topStartReserved`) or the platform's own NEW badge / brand pill (`newOrBrandBadgeReserved`, always logical top-start) moves to the other top corner, or to the bottom edge if that one is reserved too — `avoidReservedCorner()` in `badge-collision.ts`. `newOrBrandBadgeReserved` is a per-surface platform fact (the exact expression that surface renders its NEW badge/brand pill on), same contract as `topStartReserved`/`topEndReserved`. Every surface that renders a NEW chip passes it — the 5 themes (minimal since #2092, with its own `isProductNew` expression), PecannbeeProductCard and ProductCarousel; ProductListItem renders no NEW chip. A bottom corner under a CTA band / quick-add is **lifted** 96px (144px when stacked), CLAMPED to the image box (`bottom-[min(6rem,calc(100%-2.25rem))]`, #1996) so a short 16:9 image keeps the chip inside instead of clipping it away.
- **Colour** resolves `token:*` via `resolveColor` and falls back to `hsl(var(--primary))` (rule 15). Primary, not the discount badge's destructive red, so a promotion chip is never mistaken for a price cut.
- **Locale fallback is two-way**: the current language's field wins, the other is the fallback. A merchant who fills only one box still gets a badge in both storefront languages. The label is merchant DATA — it is deliberately NOT in `LanguageContext`; only the admin's own field labels/hints are (`products.{new,edit}.fields.badgeLabel*` in `apps/admin/src/i18n/messages/{en,ar}.json`).
- **`minimal` and the PDP pass `discountOccupiesCorner: false`.** minimal renders its discount as inline text under the price with no corner; the PDP renders both badges as inline `<Badge>`s in a flex row. Neither can collide, so rule 3 must not fire and steal their discount indicator. minimal's custom badge is still a corner overlay, styled in that pack's extra-quiet idiom (no shadow, micro-tracking) to match its NEW chip.
- **Length is capped in three places** off one constant (`PRODUCT_BADGE_LABEL_MAX_LENGTH = 32`, `@ebda/shared`): the DB column (`VARCHAR(32)`), the Zod `badgeLabelSchema` (which **trims first**, so a padded max-length label is accepted and a whitespace-only value becomes `null`), and the admin inputs' `maxLength`. Over-length is **rejected**, never truncated — truncating ships a label the merchant never wrote.
- **Clearable**: `null` clears, an omitted key leaves the stored value alone. The admin routes it through `productTextFields(form, 'update')` (`apps/admin/src/lib/form-text.ts` convention), which the `scripts/check-update-payload-clear.mjs` Lint gate enforces.
- **Every data hop is an explicit allowlist and each one was widened**: `STOREFRONT_PRODUCT_SELECT`, the recommendation service's `productSelect` (FBT + "You might also like" render through the same canonical cards), `toTemplateProduct`, the wishlist route's two hand-written projections, and the three recommendation components' inline maps. A field missing from any of these reaches no card, with no error anywhere.

# ADR 0001 — Ebda Store tenant isolation: Postgres Row-Level Security

Status: Accepted (2026-06-07)

## Context

Ebda Store is a multi-tenant storefront platform — every merchant ("store") shares one database and must never see another store's data.

## Decision

Tenant isolation is enforced at the **database layer** with PostgreSQL Row-Level Security, on top of application-layer `where: { storeId }` scoping (defense in depth):

- A dedicated **non-owner role (`ebda_app`)** that the application connects as, so RLS is not bypassed (table owners bypass non-`FORCE` RLS).
- `runInTenantContext(storeId, fn)` (`packages/database`) opens a transaction and runs `SET LOCAL app.current_store_id = '<uuid>'` before any query; the per-request middleware `apps/api/src/middleware/tenant-context.ts` wraps every tenant-scoped route in it.
- RLS policies on all tenant tables compare `store_id::text = current_setting('app.current_store_id', true)`.
- Super-admin / cross-tenant operations use an explicit bypass (`runWithBypassRls`) that sets `app.bypass_rls`.
- UUID format is validated before being interpolated into `SET LOCAL`.

Migrations: `packages/database/prisma/migrations/*_rls_*` (`add_rls_policies`, `rls_for_8_missing_tables`, `force_rls_enforcement`, `fix_ai_usage_rls_bypass`, `complete_force_rls_coverage`).

## Complete FORCE coverage (2026-06-09)

A coverage audit found that, of the public tables, only a subset had RLS `ENABLE`'d and fewer were `FORCE`'d. `ENABLE`-without-`FORCE` is acceptable for the live app _today_ (it connects as the non-owner `ebda_app`, for which `ENABLE` already applies) but it is NOT defense-in-depth: any owner/superuser connection (a stray `psql`, a Neon owner query, a future role change) skips non-`FORCE`'d RLS entirely. Migration `20260609000000_complete_force_rls_coverage` closes the gap:

- **Newly protected (had NO RLS):** 16 tenant tables — 4 with a direct `store_id` (`affiliate_events`, `bulk_import_jobs`, `payment_events`, `whatsapp_templates`) and 12 child tables isolated through a parent FK via an `EXISTS` join (`cart_items`→carts, `order_items`/`payments`→orders, `return_items`→returns, `wishlist_items`→wishlists, `product_images`/`product_options`/`product_categories`/`product_tags`/`product_variants`→products, plus 2-hop `product_option_values`→options→products and `product_variant_options`→variants→products).
- **Newly FORCE'd (were ENABLE-only):** the remaining tenant tables — including the 4 that the earlier `force_rls_enforcement` migration _missed because it listed non-existent table names_ (`anomalies`→`profit_anomalies`, `dead_stock_flags`→`deadstock_flags`, `inventory_logs`→`inventory_history`, `notifications` [no such table]).
- **Intentionally LEFT without tenant RLS (documented in the migration):**
  - _User/identity-scoped, isolated at the auth layer not the store boundary_ — `users` (store_id is NULL for admins; auth lookups are contextless), `addresses`, `customer_addresses`, `refresh_tokens`, `verification_tokens`, `onesignal_subscriptions`. A store predicate here would 0-row auth. Same precedent the codebase set for `onesignal_subscriptions` in `rls_for_8_missing_tables`.
  - _Global / tenant-root_ — `stores` (resolved by slug/domain in `store-access.ts` _before_ any tenant GUC is set — a store predicate would break store resolution + login; the migration also `DISABLE`s the inert FORCE the prior migration left on it), `system_settings` (platform-global config, no store_id).

### Policy idiom — hybrid (superset of both historical generations)

Ebda Store accumulated two policy shapes: the **old** `current_store_id() IS NULL OR store_id = current_store_id()` and the **new** `store_id = current_setting('app.current_store_id', true) OR current_setting('app.bypass_rls', true) = 'true'`. `withRlsBypass()` sets BOTH `app.bypass_rls='true'` AND `app.current_store_id=''`, so it satisfies both. New policies use the **hybrid** predicate so they are safe across every access pattern:

```
current_store_id() IS NULL                          -- no tenant ctx (webhook, super-admin)
OR current_setting('app.bypass_rls', true) = 'true' -- explicit bypass (Inngest/cron)
OR store_id = current_store_id()                    -- tenant match
```

**Contextless-read caveat (load-bearing):** the payment webhook at `/api/v1/webhooks` reads/updates `orders` and `payments` _without_ a `:storeId` and _without_ `withRlsBypass` — it relies on the old idiom's "context unset ⇒ allow" escape (`current_store_id()` is NULL when the GUC is unset). The hybrid predicate's first branch preserves this, so adding FORCE'd RLS to `payments` does NOT 0-row live payment confirmation. The regression test `tests/integration/tenant-isolation.test.ts` ("contextless read (payment webhook) still sees payments") guards this property.

> **Role-scoping note:** all Ebda Store policies are `FOR ALL TO ebda_app`, so a table _owner_/superuser still bypasses them even under FORCE. This is intentional — prod connects as `ebda_app`. The integration test issues `SET LOCAL ROLE ebda_app` to exercise the policies on the CI superuser connection.

## Consequences

- Every tenant-scoped query MUST run within `runInTenantContext` (the middleware guarantees this for HTTP routes). A query outside the tenant context returns zero rows **by design** — that is the safety property, not a bug.
- **A statement error inside the request transaction poisons the whole request.** Because the middleware puts the entire request in ONE interactive transaction, Postgres aborts that transaction on the first statement error, and every later statement — including any in-place recovery query — fails with SQLSTATE `25P02` ("current transaction is aborted"). So the ordinary `try { create() } catch (P2002) { findFirst() }` idiom is INOPERATIVE inside a request: it turns a recoverable unique race into a 500. Any write that can lose a unique race must be wrapped in `withSavepoint()` (`apps/api/src/lib/savepoint.ts`), which brackets it in a Postgres SAVEPOINT so the failure rolls back only that statement. `services/accounting/journal.service.ts` uses the same bracket through `withSavepointOn(tx, …)` (it receives an explicit `tx` rather than the ambient proxy). The bracket always rethrows the ORIGINAL error: a `ROLLBACK TO SAVEPOINT` that itself fails (closed transaction, dropped connection) is logged and swallowed, so the caller's P2002 recovery still sees the P2002 (#1595). Regression guard: `tests/integration/cart-session-race.test.ts`.
- **`tenantContext` COMMITS BEFORE THE RESPONSE IS SENT (changed 2026-09-08).** The lifecycle lives in `apps/api/src/middleware/request-transaction.ts` and has two explicitly enforced lanes:
  - **Buffered** (every JSON / redirect / `res.send(buffer)` response, which is nearly all traffic): `res.end` is intercepted, the transaction settles (commit on <500, rollback on >=500), and only then are the bytes written. So a 2xx that reaches the client is a COMMITTED 2xx, a COMMIT that fails becomes a 500 the client actually sees instead of a silent lost write behind a 201, and a strictly sequential caller can no longer race its own previous write. **Cost of that trade (recorded 2026-09-26, #1608):** every buffered store-scoped response — including pure reads — now pays one COMMIT round-trip before its bytes go out; it is measured on every response as `Server-Timing: request-tx;desc="commit";dur=<ms>` and a settle slower than 1s logs a warning. The wait is **bounded** by `REQUEST_COMMIT_TIMEOUT_MS` (default 10s): Prisma's transaction `timeout` does not cover the COMMIT and `server.requestTimeout` bounds request receipt, not the response, so without it a stalled COMMIT held the client's socket open with no status line. On expiry a would-be 2xx becomes a 503 `COMMIT_TIMEOUT` (outcome unknown — never the 2xx), a 5xx is sent as-is, and a P1 alert (`request-transaction.commit_timeout`) fires; if the COMMIT lands later that is logged so the outcome is resolvable.
  - **Streaming** (`res.write` / `res.download` / `res.sendFile` / `res.flushHeaders` / `pipe(res)`): ESCALATES out of the buffered lane and keeps the old commit-on-`res.on('finish')` semantics, because a streaming handler keeps querying between chunks — committing first would drop those queries out of the tenant transaction (losing the RLS GUC) and there is no single "handler is done" moment to capture. **Accepted residual, bounded to this lane:** a COMMIT that fails after a streamed 200 has started still cannot be reported to the client. Exactly one route inside a request transaction streams today: `GET /stores/:storeId/bulk/export.xlsx`.
  - **A client that disconnects before the handler answers ROLLS BACK (issue 1604).** Node keeps running the handler after the socket closes, but the transaction is closing, so its later statements fail; committing on `close` (the original middleware's behaviour) persisted whatever half of the handler had run. `request-transaction.ts` now rejects with an `AbandonedRequest` sentinel on a premature `close`: all-or-nothing, and the request's deferred post-commit work is dropped like any rollback's. The guarantee is therefore symmetric — a 2xx the client receives is committed, and a request the client never got an answer for is not.
  - **Accepted residual, both lanes — an AMBIGUOUS COMMIT (#1603):** a COMMIT that succeeds in Postgres but whose acknowledgement is lost (connection reset after the COMMIT is on the wire) is indistinguishable from a failed one, so the client sees a 500 for a durable write. On the cart checkout (`POST /stores/:storeId/orders`) a retry cannot double-order: the committed order cleared the cart in the same transaction, so the retry fails `EMPTY_CART`. The merchant manual-order path (`POST /stores/:storeId/orders/admin`) carries its items in the payload, so a human retry there can create a second `pending`/`unpaid` order — it moves no money and reserves no stock (admin orders do not decrement inventory at creation), and it is visible in the order list to cancel. No idempotency key is added for that (Ruling M2-3 in `docs/RULINGS.md`).
  - The lane split is asserted by observed event ORDER (commit-before-flush vs flush-before-commit) in `apps/api/src/middleware/__tests__/request-transaction.test.ts`, and end-to-end through the real router table in `tests/integration/export-response-lifecycle.test.ts`.
  - **Superseded:** the old behaviour was commit-after-flush for every shape, measured at ~1 in 30 sequential add-then-read pairs racing on a developer machine (far more on a loaded CI runner). `tests/helpers/bundle-fixtures.ts`'s `awaitCartCommitted()` barrier existed only for that race and has been deleted; the cart suites pass without it.
- **Post-response work runs AFTER that commit and AFTER the response, in a FRESH tenant transaction.** A fire-and-forget promise started inside a handler inherits the request's AsyncLocalStorage context, so once the transaction settles its Prisma calls die with `P2028` ("Transaction already closed") inside a swallowed `.catch` — that is what silently stopped every return-confirmation email, dropped affiliate audit rows, and leaked R2 objects. `deferAfterTenantCommit(name, run)` (`apps/api/src/lib/after-tenant-commit.ts`) is the supported way to do such work; outside a request it simply runs inline, so adopting it cannot regress an Inngest/cron/script path. The full per-request order is:

      COMMIT  →  response released to the client  →  deferred work drains

  `withDeferredWork` wraps the transaction and receives `request-transaction.ts`'s own `releaseResponse` callback, which is what pins the middle step. Draining before the COMMIT would be the P2028 defect; draining before the release would put an email round-trip on the request's latency path (a regression the old commit-on-`finish` wiring did not have). Each drained task runs in its own `runInTenantContext(storeId, …, userId)` — up to `DRAIN_CONCURRENCY` (5) at once per request, and never more than `DEFERRED_TX_GLOBAL_LIMIT` (a third of `DB_CONNECTION_LIMIT`, default 5) pooled CONNECTIONS across the whole process, since each holds a pooled connection for its transaction (a task that nests a second transaction, like the R2 orphan check's `withRlsBypass`, declares and takes two) — so **both** GUCs — `app.current_store_id` and `app.current_user_id` — are re-established rather than dropped; reaching for a bare Prisma client to escape the closed transaction would trade a transaction bug for a tenancy bug. A transaction that ROLLS BACK (5xx handler) or whose COMMIT FAILS drops its queued work entirely — the rows it would react to do not exist. On the streaming lane the response is already on the wire when the transaction settles, so `releaseResponse` is a no-op and the drain still runs after the commit; streaming exports keep their deferred work. Failures of deferred work are loud (error log + Telegram alert), and `packages/database`'s closed-transaction detector names any call site that still touches the committed transaction directly.
  - The combination is asserted by ORDER on a real socket in `apps/api/src/middleware/__tests__/deferred-work-lifecycle.test.ts`, and against a real Postgres — fresh transaction, both GUCs read back with `current_setting(...)`, read-your-own-committed-write, non-blocking, rollback drops — in `tests/integration/deferred-work-lifecycle.test.ts`.

- A regression guard test asserts cross-store reads return zero rows under tenant context.
- After any Neon snapshot restore, RLS policy state must be re-verified (the runtime depends on the policy shape being intact).

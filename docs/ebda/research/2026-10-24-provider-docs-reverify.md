# Provider docs re-verification, 2026-10-24

Ruling PROVIDERS-3. Payment adapters (Paymob, Kashier, FawryPay) re-checked against each provider's current official docs. No test accounts exist; the first merchant with real credentials is the live test, so every point below is a docs-to-code comparison, not a runtime proof.

## Method

- Fetched the live official docs with `defuddle` (and `curl` where a page hides code samples): developers.paymob.com, developers.kashier.io (including `/openapi.yaml` and per-page `.md`), developer.fawrystaging.com.
- Used the official published collections: `PaymobAccept/API-Postman-Collections` (commit of 2026-09-15) and `PaymobAccept/Paymob-AI-Integration-Skill` v3.4.1 (2026-10-14). Paymob's API-reference pages are an interactive explorer that did not render through the fetch tools or the browser, so the Postman collection is the source for request shapes.
- Each discrepancy got a failing contract test first (confirmed red), then the fix (green). Tests: `tests/unit/{paymob,kashier,fawry}-official-contract.test.ts`.
- `verified` / `sandboxVerifiedAt` flags are NOT changed. Kashier was verified on a real test account on 2026-10-08 and was only re-read for doc changes.

## Security follow-up: signed-fields-only classification (Paymob, Kashier, Fawry)

Review finding (HIGH): Paymob `is_refund` / `is_void` are not in the documented HMAC field list, so they must not drive money classification. FIXED: refund-vs-payment is decided only from signed `has_parent_transaction` (and signed `is_capture` to exclude auth captures); the classification is part of the `eventId` and of the inbox idempotency key. Tests: tampered unsigned `is_refund`/`is_void` stays a payment; a differently classified replay has a different eventId. Kashier: `event` is unsigned by design, the applied kind comes from Kashier's own transaction record (`confirmWebhookEvent`), eventId deliberately omits `event`: OK. Fawry: kind comes from signed `orderStatus`, eventId only signed fields: OK.

### Second security pass (type confusion, replay window, legacy keys)

- FIXED: the Paymob HMAC text stringifies, so `"true"` or `1` could verify yet classify differently. Any present signed boolean that is not a JSON boolean is now refused (`WEBHOOK_MALFORMED`) before the HMAC check; the route dedupe key reads values exactly as the HMAC text does, so a type-flipped replay maps to the same key.
- FIXED: Kashier `data.status` must be a JSON string (was stringified from anything).
- Key shape: parent-less Paymob keys are byte-identical to the legacy `paymob_<id>_<4flags>`; a child (refund/void) delivery gets `_p` and the route also dedupes on the legacy key (`legacyIdempotencyKeys`). Adapter eventId: `paymob:<id>:<4flags>[:p]`.
- Freshness: callbacks whose signed `created_at` is older than 38 days (36-day max checkout expiry + 2) or more than 24 h ahead are rejected (zone-less timestamp read as UTC; the margins absorb the offset). UNCONFIRMED: Paymob's documented retry horizon and timestamp zone.

Ruling PROVIDERS-3a - Paymob callback window is 38 d past / 24 h future. Docs do not state the retry horizon; a genuine delivery older than 38 d would be dropped and recovered by the status poll. Cost if wrong: a very late genuine callback is ignored until reconciliation.

Parity sweep (webhook entry paths): dedupe now goes through one helper, `checkWebhookIdempotency`, used by `POST /payment/:provider`, `/payment/:provider/s/:storeId` and the auto-detect `POST /payment`; a test replays a legacy-keyed Paymob refund through all three. Kashier and Fawry key shapes are unchanged by this PR (no legacy keys to look up). The Bosta carrier webhook route and billing/alert webhooks have no `webhookRefs` keying and are untouched.

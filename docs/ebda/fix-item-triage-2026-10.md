### FIX-007 — define merchant MCP write scope (security/business scope call)

**Current state:** `merchant-mcp-server.ts` registers read-only tools (store reporting, customer/marketing read). No write/destructive tools exist. Default-off; a super-admin must enable it per store (per `architecture/merchant-mcp.md`, not re-read this session for budget).

Options:

1. **Keep read-only indefinitely** — cheapest, lowest risk, but undersells "AI controls your store" positioning (pillar 1/2 of Ebda's strategic positioning in this repo's CLAUDE.md); merchants asking an agent to "update this price" get nothing.
2. **Add a narrow, confirmable write surface first** — e.g. price/inventory/order-status updates only, each requiring an explicit confirmation round-trip (the audit's own acceptance criteria: "permitted update works; wrong-store/unauthorized/destructive-without-confirmation requests fail"). Smallest blast radius, reuses the existing tenant-guard + RLS layers already proven for HTTP routes; still meaningful effort (new tool registrars, confirmation UX, revocation testing).
3. **Full write parity with the admin UI** — highest value, highest risk; needs an entitlement gate (which plans get it), a destructive-action confirmation protocol, and probably a narrower "what can an agent do unattended" policy than a human admin has. Largest effort (L in the audit's own estimate), should not be scoped in the same pass as anything revenue-critical.

### FIX-008 — WhatsApp bot launch scope (business call)

**Current state:** only free wa.me click-to-chat is shipped. `plan-limits.ts` sets `whatsappAutomation: false` on all three locked public plans (confirmed in `tests/unit/locked-pricing.test.ts`: `expect(pick(l => l.whatsappAutomation)).toEqual([false, false, false])` pattern) — so even the entitlement flag for a future bot is currently off everywhere, consistent with "wa.me only" being the real launch scope today.

Options:

1. **Ship wa.me-only at launch, revisit WhatsApp Cloud API bot post-launch** — matches current entitlements exactly, zero extra work, defers WABA onboarding complexity (Egyptian business verification, template approval, per-message cost) to a later release.
2. **Build Cloud API bot as a Growth/Business-tier add-on before launch** — meaningful differentiation (pillar 2: AI-as-default) but is an L-effort item per the audit (self-service WABA provisioning, inbound message → product/price/stock resolution, duplicate webhook replay, consent/template/error/human-handoff) that would need its own research pass on Meta's current Egyptian pricing/policy (the existing WhatsApp brief is explicitly flagged non-authoritative, FIX-010/D7).
3. **Soft-launch a manual/semi-automated middle ground** (e.g. notify-only order confirmations via Cloud API, no inbound bot) — smaller than full automation, bigger than wa.me, but risks half-shipping a WABA integration that still needs the same approval/compliance overhead as the full bot.

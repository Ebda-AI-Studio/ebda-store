# Demo store (looks showroom)

`stores.is_demo = true` marks the showroom store (`storedemo`, seeded by `scripts/storedemo/seed.mjs`). It does four things and nothing else:

1. **Previews looks.** `?look=<id>` on a demo store renders that look. Applied only when the store `isDemo` AND the look is `status: 'built'` in `@ebda/shared`'s registry (since Phase B1 Task 10 that is exactly the three Qamar looks; the other twelve are `designed`, so `?look=souq.night` etc. is ignored and the bar lists Qamar only). The preview goes through the one composition path every store uses: `applyDemoLook` (`apps/web/src/lib/demo-look.ts`) replaces `template` (the look's skin), `look` and `theme` (`composeStoreTheme`, no merchant overrides) on the resolved store, so `layout.tsx` (`data-look`, font link, CSS vars) needs no parallel mechanism.
2. **Refuses every order.** `assertOrderAllowed` (`plan-limit.service.ts`) throws `403 DEMO_STORE` first, before the entitlement read. Every order-creating path calls it: `OrderService.create` (storefront checkout, public routes, MCP order tools), `OrderService.createAdminOrder`, and the WhatsApp payment link (`payment-links.routes.ts`). `tests/integration/demo-store.test.ts` proves no `orders` / `order_items` row and no stock movement. (There is no separate stock-hold table: a hold is the inventory decrement inside the order transaction.)
3. **Renders the home through the look's mix (Ruling B1-8).** The showroom keeps ONE superset home document; `demoHomeDefinition` (`apps/web/src/lib/demo-home.ts`, called by `HomePageBody`) runs it through `applyTemplateFamily(def, look.template, look)` at request time, so each look shows its own section order, design keys and `lookTag` hero (C10). Pure: the stored document is never changed and nothing is written. A non-demo store, or a look without a mix, gets the same object back.
4. **Collects no visitor data and is not indexed (Rulings B1-13, B1-14).** `assertNotDemoStore` (`plan-limit.service.ts`) refuses with the same `403 DEMO_STORE`: customer register with the demo `storeId`, `POST /public/newsletter/subscribe`, `POST /public/contact` (store from the store headers, else from the storefront's `Origin` host, so a client that drops the headers on the demo host is still refused; a request with no store at all is the platform path it always was, with no demo identity to refuse, under `writeLimiter`), `POST /auth/forgot-password` and `/auth/resend-verification` with the demo `storeId`, and, through `middleware/demo-store.ts` before the feature gate, `POST /public/:storeId/affiliates/apply` and `/public/:storeId/push/subscribe` (C13). The seeded owner (`storedemo-owner@ebda.app`, no mailbox) is never mailed: a reset or resend for it answers exactly like an unknown address and issues no token (`ownsDemoStore` in `auth.service.ts`). The forms show the API's sentence ("ده متجر تجريبي — الخاصية دي مقفولة هنا") via `lib/demo-refusal.ts`. Carts stay allowed. `robots.txt` asks `/public/store/resolve` and disallows `/` with no sitemap for the demo host (C14), the sitemap is empty, and the root metadata is `noindex, nofollow`. `tests/unit/demo-order-guard-coverage.test.ts` parses `apps/api/src` and pins exactly three `order.create` owners (`OrderService.create`, `OrderService.createAdminOrder`, `router.post('/')` in `payment-links.routes.ts`), each calling `assertOrderAllowed` first, and fails on `order.upsert` / `createMany` / nested `orders: { create }` / raw `INSERT INTO orders` (C12). At checkout the pay button is replaced by the demo notice and the payment-method card is not rendered (nothing to choose), unless loading the methods failed, whose error and retry still show. Guards with a mutation record entry (`docs/security/defence-mutations.json`): `demo-store-refuses-orders`, `demo-store-every-order-path-gated`, `demo-store-collects-no-visitor-pii`, `demo-owner-never-mailed`.

## Request flow and caching

- Middleware forwards a well-formed `?look=` (`^(qamar|souq|jasmine|lamma|dahab)\.[a-z]+$`, the `stores_look_format` CHECK) as request header `x-demo-look`. The header is in `MIDDLEWARE_ASSERTED_HEADERS`, so a client-sent copy is stripped.
- Such a request never takes the shared tenant-tree rewrite (`/tenant-store/<host>/<locale>`, the only full-route-cache path) and its response is `Cache-Control: private, no-store`. Middleware is synchronous and cannot ask whether the store is a demo, so the header is set for any store host carrying a well-formed `?look=`; the page of a non-demo store is identical to the one without the param.
- The look is applied after the cached store fetch, per request; the in-memory store map and Next's tagged data cache only ever hold the base store.
- **Edge cache caveat.** The Worker emits `private, no-store`, which a standards-following CDN honours. If a Cloudflare Cache Rule on the zone ever sets "Cache everything" or an edge TTL override for `*.ebda.app` / custom domains, it must bypass when the query string contains `look=`; a rule that ignores origin `Cache-Control` would defeat the header. Not verifiable from the repo (zone rules live in the dashboard).
- The bar (`DemoLookBar`, Ruling B1-12) is the inverse surface (page colour on ink) with select boundaries in the page colour at 70% (>= 3:1 on every look, measured 5.49-9.34:1 on the Qamar looks); it is two selects, template then look; only templates with a built look are listed, and changing the template opens its first built look. It writes nothing: the preview lives in the URL only (no cookie by design: a cookie would put the look in a shared-cache key).
- While a preview is showing (`?look=` that the server applied), a capture-phase click handler adds `look=<id>` to every same-origin link and does a full document load (Ruling B1-11), so a product opened from a Lookbook preview renders Lookbook. External, new-tab, download and modified clicks are untouched. Programmatic navigations (`router.push`, e.g. cart → checkout) still drop it; checkout is refused on the demo anyway.

## Seeding

`DATABASE_URL=<owner url> [QAMAR_DEMO_ASSET_BASE=<url or /path>] npx tsx scripts/storedemo/seed.mjs [--yes-production] [--local-look-stores]` prints the plan first. It refuses a non-loopback database unless `--yes-production` (Ahmad's STOP 3, never an agent), and with `--yes-production` it refuses any asset base other than `https://media.ebda.app/demo/qamar` (Ruling B1-16). Idempotent: owner, store, categories and products upserted; the store declares cash on delivery (one `payment_configs` row, found by provider then updated or created) and a 14-day return window, so the shared PDP trust line renders on every look (W2b, Ruling B1-64); size charts and the shipping zone found by name then updated or created; variants found by SKU (built from the FULL option-value slugs, e.g. `LINEN-ABAYA-ROSE-M-56`) and never deleted, because cart lines may point at them.

What it writes (Phase B1 Task 6):

- **Catalogue**: the Qamar demo boutique, `scripts/qamar-demo/catalogue.mjs` (18 products, 160 variants, 7 categories incl. the three occasion categories, which are hidden from the home category row). Every B0 feature appears once: hex and image swatches, a 7-colour scarf (`+2` on the card), Colour x Size x Length with a sold-out combination, facts (at most 2 on the card), a made-to-order lead time, a personalisation field, size charts by category, a sale, a backorder, a product with no photo and very long names. `tests/unit/qamar-demo-catalogue.test.ts` enforces it.
- **Photos**: AI-generated illustrative samples (Ruling TPL-3, `scripts/qamar-demo/CREDITS.md`), committed as WebP under `scripts/qamar-demo/assets/` (each <= 140 KB, total <= 7 MB incl. the one `hero.mp4`, Rulings B1-9/B1-10 as amended by C18) and served from `QAMAR_DEMO_ASSET_BASE` (production: R2 `ebda-media` under `demo/qamar/`, uploaded at STOP 3). The announcement bar says "الصور توضيحية / Illustrative photos"; "demo store" is said once, by the demo bar above it.
- **Archive**: the Phase S placeholder families (fashion, electronics, beauty, home and kitchen, jewellery) are set `status: 'archived'` and their categories `is_active = false`. Never deleted (Ruling B1-15, C3).
- **Home**: the Qamar superset document (`scripts/storedemo/qamar-home.mjs`): one hero per look tagged with `lookTag` (Atelier still + hero clip, Lookbook three-photo slider, Vitrine window), chips category row, new-in collection, full-bleed image break, abayas carousel, occasion collection list, testimonials (render nothing until there are verified reviews), brand story. Lookbook adds a `shop-the-look` section (tagged `qamar.lookbook`: three looks from `QAMAR_LOOKS_STORY`, pieces by product id; the seed fails if a piece is missing from the catalogue) and its collage hero uses the three Lookbook slides. The four home-strip categories carry a product photo (`QAMAR_CATEGORIES[].image`) for Lookbook's photo category row. Each occasion block carries its band `tone` from `QAMAR_OCCASIONS` (wedding primary, engagement accent, evening the champagne line), which Vitrine's mix renders as full-width bands (`tileShape: 'band'`); the Vitrine hero (`hero-vitrine`, tagged `qamar.vitrine`) renders framed with its drawn hairline.
- **Store settings**: `defaultLanguage: 'ar'`, `deliveryDays {2, 4}`, a "Greater Cairo" shipping zone (60 EGP, 1-3 days).
- `--local-look-stores` (refused with `--yes-production`) also seeds three non-demo stores `qamar-atelier` / `qamar-lookbook` / `qamar-vitrine` on the `qamar` skin with Western digits (the default, NUMERALS-1), each switched to its look with `StoreService.applyLook(..., { design: 'reset' })` and the resulting draft published, for local review.

Local review: copy `scripts/qamar-demo/assets/*` into an untracked `apps/web/public/__qamar-demo/` and seed with `QAMAR_DEMO_ASSET_BASE=/__qamar-demo` (a relative base also satisfies the hero video's https-or-relative rule and the storefront CSP's `media-src 'self'`; `localhost:9000` is often taken by a local MinIO). Delete the folder afterwards.

## Plan, scenario stores and the browser suite (Phase B1 Task 10)

- **The showroom runs the Professional plan** (`plan: 'professional'` in the seed, Ruling B1-112). The catalogue's backorder is `inventory.backorder`, a Professional feature (`plan-baselines.ts`); on a starter store the cart/PDP gate (`gateBackorder`) switches backorder off and the demo's pre-order product reads "Out of stock" with every size disabled. - **Scenario stores** (`scripts/storedemo/scenario-stores.mjs`, local only, no production flag): `qamar-empty` (0 products), `qamar-one`, `qamar-500` (500 generated products, every 5th without a photo), `qamar-edge-wide` / `-tall` / `-nologo` (logo shapes, Arabic-Indic numerals ON, merchant `primaryColor` at `0 0% 98%` / `60 100% 50%`). - **Browser suite** `tests/qamar/` with `playwright.qamar.config.ts` (projects phone-390, tablet-820, desktop-1280): `qamar-matrix.spec.ts` (stores x ar/en x 12 pages, plus reduced motion, 200% zoom, keyboard, slow 3G, variants/OOS/backorder/sale/personalisation/size chart/delivery chip/hero video) and `qamar-demo.spec.ts` (the showroom). ## The second demo store: `storedemo-souq` (Phase B2 Task 6, Ruling B2-7)

One demo store per template. `storedemo` stays the Qamar showroom; Souq gets **`storedemo-souq`**, a second `is_demo` store with its own owner (`storedemo-souq-owner@ebda.app`, `passwordHash '!seed-no-login'`, no mailbox, never mailed: `ownsDemoStore` is keyed on `isDemo`, not a slug), its own catalogue and its own R2 prefix `demo/souq/`. The alternative (scoping one store's catalogue by look) would be a filter on every catalogue query; a second store is isolated by construction and reuses every guard that reads `is_demo`: it refuses orders and visitor PII exactly like `storedemo` (`assertOrderAllowed`, `assertNotDemoStore`, `middleware/demo-store.ts`), with no slug-keyed branch anywhere. The Qamar catalogue never appears on the Souq demo or the reverse.

**Host map.** `apps/web/src/lib/demo-hosts.ts` is the single map `{ qamar: 'storedemo', souq: 'storedemo-souq' }` (host label; the apex and port come from the host the visitor is on). `DemoLookBar` lists only templates that have a built look AND a demo host; choosing another template leaves this store for that template's demo store with its first built look (`https://storedemo-souq.<apex>/?look=souq.catalogue`), and on a host that is not a demo host (a local look store) it applies the look on the same host as before. The unknown-store 404's demo link reads `DEMO_HOSTS.qamar`. `?look=` previews still go through `applyDemoLook` and only for a BUILT look, so the Souq looks appear in the bar after Task 7 flips them to `built`.

**Seed.** `DATABASE_URL=<owner url> [SOUQ_DEMO_ASSET_BASE=<url or /path>] npx tsx scripts/storedemo/seed.mjs --template souq [--yes-production] [--local-look-stores]`. `TEMPLATE_SPECS` in `seed.mjs` holds everything that differs per template (slug, owner, catalogue, asset env var, production asset base, local look stores, home builder, settings); the catalogue writer reads only the spec. What it writes: **catalogue** `scripts/souq-demo/catalogue.mjs` (20 unbranded Egyptian electronics products, 24 variants, 7 categories: Colour (hex) x Storage (chip) with price STEPS on 4 products, two `onCard` facts + a warranty and a condition fact on every product, a refurbished and a used-in-excellent-condition product, 8 sale prices (one 45 % off), a backorder, a sold-out combination, a product with no photo, a long Arabic and a long English name, a made-to-order lead time; `tests/unit/souq-demo-catalogue.test.ts` enforces each by count); **photos** 21 AI-generated illustrative WebP (`scripts/souq-demo/assets/`, 256 KB in all, `CREDITS.md`, `orange-probe.py` measures every file, `tests/unit/souq-demo-assets.test.ts`); **store** cash on delivery, a 14-day return window, `deliveryDays {2, 4}`, a Greater Cairo zone, and `settings.instalments = { enabled: true, months: 12, markupPct: 0 }` with no provider name (Ruling B2-9); **home** the Souq superset (`scripts/storedemo/souq-home.mjs`): one hero and the curated "من السوق" carousel tagged `souq.night`, the category grid, a deals row (`on_sale`), the newest grid, three one-product stages (distinct products), a hand-picked collection list, trust strip, newsletter, brand story.

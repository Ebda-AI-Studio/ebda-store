# Demo store (looks showroom)

**Production homes since Postgres was removed (Ruling DEMO-SEED-DO-1):** `DEMO_SEED_TOKEN=<worker secret> node scripts/storedemo/seed-home-do.mjs --api-url https://api.ebda.app [--template <tpl>|all] [--apply]` builds each demo home with the same `build<X>Home` builders and publishes it through `PUT /api/v1/internal/demo-home/:slug` on the store's DO. Dry run by default, `--apply` writes, a home already equal to the built one is skipped, every write is read back; only the five `storedemo*` slugs, and the Worker refuses any store that is not `is_demo`. Catalogues are not touched. The `seed.mjs` commands below are Postgres-era and run locally only.

`stores.is_demo = true` marks the showroom store (`storedemo`, seeded by `scripts/storedemo/seed.mjs`). It does four things and nothing else:

1. **Previews looks.** `?look=<id>` on a demo store renders that look. Applied only when the store `isDemo` AND the look is `status: 'built'` in `@ebda/shared`'s registry (since Phase B1 Task 10 that is exactly the three Qamar looks; the other twelve are `designed`, so `?look=souq.night` etc. is ignored and the bar lists Qamar only). The preview goes through the one composition path every store uses: `applyDemoLook` (`apps/web/src/lib/demo-look.ts`) replaces `template` (the look's skin), `look` and `theme` (`composeStoreTheme`, no merchant overrides) on the resolved store, so `layout.tsx` (`data-look`, font link, CSS vars) needs no parallel mechanism.
2. **Refuses every order.** `assertOrderAllowed` (`plan-limit.service.ts`) throws `403 DEMO_STORE` first, before the entitlement read. Every order-creating path calls it: `OrderService.create` (storefront checkout, public routes, MCP order tools), `OrderService.createAdminOrder`, and the WhatsApp payment link (`payment-links.routes.ts`). `tests/integration/demo-store.test.ts` proves no `orders` / `order_items` row and no stock movement. (There is no separate stock-hold table: a hold is the inventory decrement inside the order transaction.)
3. **Renders the home through the look's mix (Ruling B1-8).** The showroom keeps ONE superset home document; `demoHomeDefinition` (`apps/web/src/lib/demo-home.ts`, called by `HomePageBody`) runs it through `applyTemplateFamily(def, look.template, look)` at request time, so each look shows its own section order, design keys and `lookTag` hero (C10). Pure: the stored document is never changed and nothing is written. A non-demo store, or a look without a mix, gets the same object back.
4. **Collects no visitor data and is not indexed (Rulings B1-13, B1-14).** `assertNotDemoStore` (`plan-limit.service.ts`) refuses with the same `403 DEMO_STORE`: customer register with the demo `storeId`, `POST /public/newsletter/subscribe`, `POST /public/contact` (store from the store headers, else from the storefront's `Origin` host, so a client that drops the headers on the demo host is still refused; a request with no store at all is the platform path it always was, with no demo identity to refuse, under `writeLimiter`), `POST /auth/forgot-password` and `/auth/resend-verification` with the demo `storeId`, and, through `middleware/demo-store.ts` before the feature gate, `POST /public/:storeId/affiliates/apply` and `/public/:storeId/push/subscribe` (C13). The seeded owner (`storedemo-owner@ebda.app`, no mailbox) is never mailed: a reset or resend for it answers exactly like an unknown address and issues no token (`ownsDemoStore` in `auth.service.ts`). The forms show the API's sentence ("ده متجر تجريبي — الخاصية دي مقفولة هنا") via `lib/demo-refusal.ts`. Carts stay allowed. `robots.txt` asks `/public/store/resolve` and disallows `/` with no sitemap for the demo host (C14), the sitemap is empty, and the root metadata is `noindex, nofollow`. `tests/unit/demo-order-guard-coverage.test.ts` parses `apps/api/src` and pins exactly three `order.create` owners (`OrderService.create`, `OrderService.createAdminOrder`, `router.post('/')` in `payment-links.routes.ts`), each calling `assertOrderAllowed` first, and fails on `order.upsert` / `createMany` / nested `orders: { create }` / raw `INSERT INTO orders` (C12). At checkout the pay button is replaced by the demo notice and the payment-method card is not rendered (nothing to choose), unless loading the methods failed, whose error and retry still show. Guards with a mutation record entry (`docs/security/defence-mutations.json`): `demo-store-refuses-orders`, `demo-store-every-order-path-gated`, `demo-store-collects-no-visitor-pii`, `demo-owner-never-mailed`.

## Request flow and caching

- Middleware forwards a well-formed `?look=` (`^(qamar|souq|jasmine|lamma|dahab)\.[a-z]+$`, the `stores_look_format` CHECK) as request header `x-demo-look`. The header is in `MIDDLEWARE_ASSERTED_HEADERS`, so a client-sent copy is stripped.
- Such a request never takes the shared tenant-tree rewrite (`/tenant-store/<host>/<locale>`, the only full-route-cache path) and its response is `Cache-Control: private, no-store`. Middleware is synchronous and cannot ask whether the store is a demo, so the header is set for any store host carrying a well-formed `?look=`; the page of a non-demo store is identical to the one without the param.
- The look is applied after the cached store fetch, per request; the in-memory store map and Next's tagged data cache only ever hold the base store.
- **Edge cache caveat.** The Worker emits `private, no-store`, which a standards-following CDN honours. If a Cloudflare Cache Rule on the zone ever sets "Cache everything" or an edge TTL override for `*.ebda.app` / custom domains, it must bypass when the query string contains `look=`; a rule that ignores origin `Cache-Control` would defeat the header. Not verifiable from the repo (zone rules live in the dashboard).
- The bar (`DemoLookBar`, Ruling B1-12) is the inverse surface (page colour on ink) with select boundaries in the page colour at 70% (>= 3:1 on every look, measured 5.49-9.34:1 on the Qamar looks); it is two selects, template then look; only templates with a built look are listed, and changing the template opens its first built look. It writes nothing: the preview lives in the URL only (no cookie by design: a cookie would put the look in a shared-cache key).
- While a preview is showing (`?look=` that the server applied), a capture-phase click handler adds `look=<id>` to every same-origin link and does a full document load (Ruling B1-11), so a product opened from a Lookbook preview renders Lookbook. External, new-tab, download and modified clicks are untouched. Programmatic navigations (`router.push`, e.g. cart → checkout) still drop it; checkout is refused on the demo anyway.

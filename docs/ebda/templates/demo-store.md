# Demo store (looks showroom)

`stores.is_demo = true` marks the showroom store (`storedemo`, seeded by `scripts/storedemo/seed.mjs`). It does four things and nothing else:

1. **Previews looks.** `?look=<id>` on a demo store renders that look. Applied only when the store `isDemo` AND the look is `status: 'built'` in `@ebda/shared`'s registry (all 15 are `designed` until Phase B, so the bar and the preview are inert in production until then). The preview goes through the one composition path every store uses: `applyDemoLook` (`apps/web/src/lib/demo-look.ts`) replaces `template` (the look's skin), `look` and `theme` (`composeStoreTheme`, no merchant overrides) on the resolved store, so `layout.tsx` (`data-look`, font link, CSS vars) needs no parallel mechanism.
2. **Refuses every order.** `assertOrderAllowed` (`plan-limit.service.ts`) throws `403 DEMO_STORE` first, before the entitlement read. Every order-creating path calls it: `OrderService.create` (storefront checkout, public routes, MCP order tools), `OrderService.createAdminOrder`, and the WhatsApp payment link (`payment-links.routes.ts`). `tests/integration/demo-store.test.ts` proves no `orders` / `order_items` row and no stock movement. (There is no separate stock-hold table: a hold is the inventory decrement inside the order transaction.)
3. **Renders the home through the look's mix (Ruling B1-8).** The showroom keeps ONE superset home document; `demoHomeDefinition` (`apps/web/src/lib/demo-home.ts`, called by `HomePageBody`) runs it through `applyTemplateFamily(def, look.template, look)` at request time, so each look shows its own section order, design keys and `lookTag` hero (C10). Pure: the stored document is never changed and nothing is written. A non-demo store, or a look without a mix, gets the same object back.
4. **Collects no visitor data and is not indexed (Rulings B1-13, B1-14).** `assertNotDemoStore` (`plan-limit.service.ts`) refuses with the same `403 DEMO_STORE`: customer register with the demo `storeId`, `POST /public/newsletter/subscribe`, `POST /public/contact` (store resolved without throwing, so a request with no resolvable store keeps today's behaviour), and, through `middleware/demo-store.ts` before the feature gate, `POST /public/:storeId/affiliates/apply` and `/public/:storeId/push/subscribe` (C13). The forms show the API's sentence ("ده متجر تجريبي — الخاصية دي مقفولة هنا") via `lib/demo-refusal.ts`. Carts stay allowed. `robots.txt` asks `/public/store/resolve` and disallows `/` with no sitemap for the demo host (C14), the sitemap is empty, and the root metadata is `noindex, nofollow`. `tests/unit/demo-order-guard-coverage.test.ts` parses `apps/api/src` and pins exactly three `order.create` owners (`OrderService.create`, `OrderService.createAdminOrder`, `router.post('/')` in `payment-links.routes.ts`), each calling `assertOrderAllowed` first, and fails on `order.upsert` / `createMany` / nested `orders: { create }` / raw `INSERT INTO orders` (C12). At checkout the pay button is replaced by the demo notice and the "no payment methods" alert is not shown.

## Request flow and caching

- Middleware forwards a well-formed `?look=` (`^(qamar|souq|jasmine|lamma|dahab)\.[a-z]+$`, the `stores_look_format` CHECK) as request header `x-demo-look`. The header is in `MIDDLEWARE_ASSERTED_HEADERS`, so a client-sent copy is stripped.
- Such a request never takes the shared tenant-tree rewrite (`/tenant-store/<host>/<locale>`, the only full-route-cache path) and its response is `Cache-Control: private, no-store`. Middleware is synchronous and cannot ask whether the store is a demo, so the header is set for any store host carrying a well-formed `?look=`; the page of a non-demo store is identical to the one without the param.
- The look is applied after the cached store fetch, per request; the in-memory store map and Next's tagged data cache only ever hold the base store.
- **Edge cache caveat.** The Worker emits `private, no-store`, which a standards-following CDN honours. If a Cloudflare Cache Rule on the zone ever sets "Cache everything" or an edge TTL override for `*.ebda.app` / custom domains, it must bypass when the query string contains `look=`; a rule that ignores origin `Cache-Control` would defeat the header. Not verifiable from the repo (zone rules live in the dashboard).
- The bar (`DemoLookBar`, Ruling B1-12) is two selects, template then look; only templates with a built look are listed, and changing the template opens its first built look. It writes nothing: the preview lives in the URL only (no cookie by design: a cookie would put the look in a shared-cache key).
- While a preview is showing (`?look=` that the server applied), a capture-phase click handler adds `look=<id>` to every same-origin link and does a full document load (Ruling B1-11), so a product opened from a Lookbook preview renders Lookbook. External, new-tab, download and modified clicks are untouched. Programmatic navigations (`router.push`, e.g. cart → checkout) still drop it; checkout is refused on the demo anyway.

## Seeding

`DATABASE_URL=<owner url> [QAMAR_DEMO_ASSET_BASE=<url or /path>] npx tsx scripts/storedemo/seed.mjs [--yes-production] [--local-look-stores]` prints the plan first. It refuses a non-loopback database unless `--yes-production` (Ahmad's STOP 3, never an agent), and with `--yes-production` it refuses any asset base other than `https://media.ebda.app/demo/qamar` (Ruling B1-16). Idempotent: owner, store, categories and products upserted; size charts and the shipping zone found by name then updated or created; variants found by SKU (built from the FULL option-value slugs, e.g. `LINEN-ABAYA-ROSE-M-56`) and never deleted, because cart lines may point at them.

What it writes (Phase B1 Task 6):

- **Catalogue**: the Qamar demo boutique, `scripts/qamar-demo/catalogue.mjs` (18 products, 160 variants, 7 categories incl. the three occasion categories, which are hidden from the home category row). Every B0 feature appears once: hex and image swatches, a 7-colour scarf (`+2` on the card), Colour x Size x Length with a sold-out combination, facts (at most 2 on the card), a made-to-order lead time, a personalisation field, size charts by category, a sale, a backorder, a product with no photo and very long names. `tests/unit/qamar-demo-catalogue.test.ts` enforces it.
- **Photos**: AI-generated illustrative samples (Ruling TPL-3, `scripts/qamar-demo/CREDITS.md`), committed as WebP under `scripts/qamar-demo/assets/` (each <= 140 KB, total <= 7 MB incl. the one `hero.mp4`, Rulings B1-9/B1-10 as amended by C18) and served from `QAMAR_DEMO_ASSET_BASE` (production: R2 `ebda-media` under `demo/qamar/`, uploaded at STOP 3). The announcement bar says "Demo store · illustrative photos".
- **Archive**: the Phase S placeholder families (fashion, electronics, beauty, home and kitchen, jewellery) are set `status: 'archived'` and their categories `is_active = false`. Never deleted (Ruling B1-15, C3).
- **Home**: the Qamar superset document (`scripts/storedemo/qamar-home.mjs`): one hero per look tagged with `lookTag` (Atelier still + hero clip, Lookbook three-photo slider, Vitrine window), chips category row, new-in collection, full-bleed image break, abayas carousel, occasion collection list, testimonials (render nothing until there are verified reviews), brand story. Saved and published through the page-builder service. Lookbook adds a `shop-the-look` section (tagged `qamar.lookbook`: three looks from `QAMAR_LOOKS_STORY`, pieces by product id; the seed fails if a piece is missing from the catalogue) and its collage hero uses the three Lookbook slides. The four home-strip categories carry a product photo (`QAMAR_CATEGORIES[].image`) for Lookbook's photo category row. Each occasion block carries its band `tone` from `QAMAR_OCCASIONS` (wedding primary, engagement accent, evening the champagne line), which Vitrine's mix renders as full-width bands (`tileShape: 'band'`); the Vitrine hero (`hero-vitrine`, tagged `qamar.vitrine`) renders framed with its drawn hairline.
- **Store settings**: `defaultLanguage: 'ar'`, `deliveryDays {2, 4}`, a "Greater Cairo" shipping zone (60 EGP, 1-3 days).
- `--local-look-stores` (refused with `--yes-production`) also seeds three non-demo stores `qamar-atelier` / `qamar-lookbook` / `qamar-vitrine` on the `qamar` skin with Western digits (the default, NUMERALS-1), each switched to its look with `StoreService.applyLook(..., { design: 'reset' })` and the resulting draft published, for local review.

Local review: copy `scripts/qamar-demo/assets/*` into an untracked `apps/web/public/__qamar-demo/` and seed with `QAMAR_DEMO_ASSET_BASE=/__qamar-demo` (a relative base also satisfies the hero video's https-or-relative rule and the storefront CSP's `media-src 'self'`; `localhost:9000` is often taken by a local MinIO). Delete the folder afterwards.

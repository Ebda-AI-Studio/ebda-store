# Template quality bar (binding for every template and every look)

Every template (Qamar, Souq, Jasmine, Lamma, Dahab) and every look inside it must pass these rules before a look moves to `built`. The rules extend the **B0 taste bar** (`docs/plans/2026-10-14-phase-b0-platform-commerce.md` § Taste bar: leave-out limits, the three motion moments, Arabic-first, the taste gate) and the shared bar in `2026-10-14-directions.md`. Neither is repeated here.

- **Source:** the B1 Qamar audits (`.superpowers/sdd/2026-10-15-phase-b1-qamar/taste/consolidated.md`). Ids in brackets point there.
- **Check column:** `test` = unit/integration · `lint` = a grep or ESLint gate in CI · `shot` = the screenshot matrix below · `critique` = the impeccable pass.
- **Labels:** **[gate pending]** = the gate is planned in `fix-waves.md` and does not exist yet; until it lands, a reviewer checks the rule by hand. **[ruling pending]** = waits on a decision listed in `consolidated.md`.

### Egyptian copy style guide (Rulings FU46-Y02a/b/d, review 2026-10-16)

Every shopper-facing full sentence is Egyptian Arabic. Labels and buttons use neutral forms. Legal text is formal.

- **Address:** masculine singular, generic ("اختار", "جرّب", "إنت"). Never "حضرتك", and never mixed forms of address on one page.
- **Spellings:**
  - "إنت", with the hamza (never "انت" or "وانت").
  - "عشان" (never "علشان").
  - "مفيش", "معرفناش", "ملقيناش".
  - "نتايج" in sentences; "نتائج" only in labels and counted nouns.
- **Negation:** one joined style. Write "منفعش", "متبعتش", "موصلش", "مضفتش", "متحسبتش", "مكملش", "متمش", "مفتحش" — never "ما نفعش" / "ما اتبعتش".
- **Toasts that name a product:** use the gender-free "we" form: "شيلنا ‹الاسم› من السلة", "ضفنا ‹الاسم› للمفضلة". Never "‹الاسم› اتشال", which takes the gender of an arbitrary name.
- **Status and toast titles:** short Egyptian past forms ("اتنسخ", "اتشحن", "اتسلّم", "اتضاف"), never "تم …" / "تمت …".
- **Loading states:** "بنحمّل…", "بنبعت…", "لحظة…". Use "بنسجّلك…" for joining and "بنسجّل اشتراكك…" for subscribing (the subject is the shopper, not us).
- **Retry:** "جرّب تاني" in sentences and on buttons; never "حاول مرة أخرى".
- **Phone:** "تليفون" in sentences; "رقم الموبايل" as the field label.
- **Counted nouns:** go through `countText` with Egyptian forms ("قطعتين", "يومين", "١٤ يوم"). Legal text uses `DAYS_FORMAL` ("١٤ يومًا"), and only inside a `legal-register` fence.
- **AI copy shoppers read:** `EGYPTIAN_ARABIC_REGISTER` in every generator; the cache key carries the instruction.

**Enforced mechanically:** `tests/unit/storefront-arabic-register.test.ts`.

- It reads every string literal, template text, JSX text node and JSX attribute (TypeScript AST), and every `messageAr` value at any depth or line count. An indirect `messageAr` must come from a listed message table, and those tables are scanned in full.
- It bans:
  - the MSA-only markers ("هذا", "لم", "يرجى", "كن", "مرة أخرى", "تم", "تعذّر", "أدناه", "بنجاح", "الخاص بك", …);
  - "انت" without the hamza;
  - "ما …ش" split negation;
  - "حضرتك" and "علشان".
- The only exceptions are the named legal files and fenced regions.
- `tests/unit/legal-formal-counts.test.ts` and `tests/unit/ai-arabic-register.test.ts` cover the legal counts and the AI prompts.
- **Shopper messages outside the storefront bundle** go through the same gate (`shopper messages` block in the same test): every file in `apps/api/src/services/email-templates/` (shopper-facing by default; merchant emails are listed in `MERCHANT_EMAIL_TEMPLATES`), `packages/shared/src/notifications.ts` (SMS + web-push), `apps/api/src/lib/wa-templates/definitions.ts` (WhatsApp template bodies), the email footer and the newsletter footer. Merchant-facing messages (merchant emails, merchant push in `onesignal.service.ts`, the admin) and the tax-invoice document (`invoice.service.ts`, `fiscal-document-render.ts`, a legal record) are not scanned. Changing the Arabic body of a WhatsApp template needs a Meta re-approval; keep the template `name` and the `{{n}}` variables stable. Canonical names are `ebda_<purpose>_v<n>` (renamed from `force_*`); a store still approved under an old name keeps sending under it until the new name is approved (`lib/wa-templates/legacy-names.ts`). SMS and push follow the shopper's locale (order/customer locale, else the store default, else ar).
- `tests/unit/toast-semantic-tokens.test.ts` keeps the toast and the added-to-cart state on semantic tokens (success / destructive / warning / info), never a palette colour.
- The critique owns everything else: wording, tone and gender-safe toasts.

## How to run the taste gate

Run it at the end of every template or look task, after the tests pass and before the commit. The B0 taste bar's gate still applies; this adds the order and the bar.

1. **Screens:** home, PLP, PDP (with an unselected size), cart (qty 1), checkout success and the filter sheet. Add OOS, empty-cart and failed-coupon states when the change touches them.
2. **Widths, in this order:**
   - **390×844 Arabic first** (full page + fold);
   - **820 Arabic**;
   - **1280×800 English**.

   Shoot each look changed, plus one no-look `minimal` store to prove its defaults did not move. Save the shots in the task's report directory.

3. **Skills, in this order:**
   1. `impeccable` **critique**, then **polish** (Nielsen score, anti-patterns, the polish checklist);
   2. `accessibility-review` + `impeccable` **audit** (WCAG AA tables, measured contrast);
   3. the design-craft lenses (`design-critique`, `apple-design`, `emil-design-eng`) for hierarchy, response and motion.

   Each pass judges the 390-ar shots first. Merge the findings with a dedupe step.

4. **Pass bar:**
   - **no open P0 or P1**;
   - impeccable critique **≥ 28/40** (Atelier scored 21/40 on 2026-10-15);
   - every rule above is `done (evidence)` or carries a Ruling with cost-if-wrong.

   A P2 left open is written as a Ruling, never left only in chat.

5. **Re-check:** list which earlier findings still hold, so a fixed item is not silently re-opened.

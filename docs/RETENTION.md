# Data retention policy

How long every PII or PII-adjacent column lives, and what enforces it.
Companion document to:

- `~/.claude/CLAUDE.md` § Production Reality gates rule 9 (GDPR erasure).
- `docs/superpowers/plans/2026-05-13-iceberg-audit-v2.md` § Tier 1 item #16
  and Tier 3 item #15.
- `docs/privacy/data-map.md` — the third-party-destination companion to
  this table (PostHog / OneSignal / pixels & CAPI / Sentry / Resend / R2 /
  backups), plus the erasure-propagation and backup-boundary writeups.

The policy reconciles two opposing pressures on Ebda:

- **Storage limitation**: keep PII no longer than the business need it was
  collected for. Egypt's Personal Data Protection Law (Law No. 151 of 2020,
  "PDPL") states this principle (personal data is kept only as long as the
  purpose requires), and GDPR Art. 5(1)(e) states the same for any EU data
  subject. Ebda's merchants and shoppers are in Egypt; the older GCC
  analysis is in `docs/privacy/data-map.md`.
- **Tax and accounting records**: invoice and order financial records must
  be kept for the period the Egyptian Tax Authority requires. This policy
  operates on 5 years. **FLAG (not verified by counsel):** the exact
  statutory period and the article that sets it have not been confirmed
  for Egypt; this document previously cited Egypt's Electronic
  Transactions Law No. 20/2014 and the Egypt MOF, which were carried over
  from Ebda Store and do not apply to Ebda. Confirm the Egyptian period and the
  PDPL article numbers with counsel before quoting them to a merchant.

The rule is: financial records survive at the table level, but the PII
attached to them gets stripped on schedule.

## Erasure paths

There are three ways PII leaves the system, all routing through the
same `AuthService.eraseAccount(userId)` transaction so the wipe shape
is identical regardless of trigger:

1. **Self-serve**: `POST /auth/me/erase`, authenticated. Customer
   clicks "Delete my data" in the account UI.
2. **Retention cron**: `soft-deleted-user-anonymize` monthly. Catches
   soft-deleted users whose 12-month window has elapsed without
   them returning.
3. **Merchant/admin-initiated**: `POST /stores/:storeId/customers/:customerId/erase`
   (`store_admin`/`super_admin` only, blocked while impersonating,
   type-to-confirm in the admin UI at `/stores/[id]/customers/[customerKey]`).
   Merchants are data controllers for their own shoppers and must be able
   to fulfil a data-subject request even when the shopper doesn't use the
   self-service flow themselves. Strictly tenant-scoped: `customerId` must
   resolve to a `customer`-role `User` row whose `storeId` matches the
   calling merchant's own store, or the endpoint 404s — a merchant can
   never act on, or even detect the existence of, another store's shopper.
   Export has the same shape: `GET /stores/:storeId/customers/:customerId/export`.

   **One difference from the self-service path, deliberately handled.** On this
   route the request's `app.current_user_id` GUC is the MERCHANT's id, not the
   shopper's — `tenantContext` sets it from `req.user?.userId`. `addresses` is
   the only erasure target with a USER-scoped RLS policy (`rls_addresses_user`:
   `user_id = current_user_id()`), so under the earlier app role a plain delete would
   match ZERO rows and return `{count: 0}` with no error, leaving the shopper's
   name, phone and street behind an audit row claiming a completed erasure; the
   export would likewise ship an empty `addresses` section. The erase therefore
   brackets that one delete with `SET LOCAL app.bypass_rls` on the AMBIENT
   transaction (not `withRlsBypass`, which opens a second, independently
   committing connection), and the export reads addresses through
   `withRlsBypass` (safe there — it is read-only). Guarded by
   `erasure-addresses-escapes-user-rls` in `docs/security/defence-mutations.json`.
   Inert until the the earlier app role cutover, since prod still connects as
   `neondb_owner` (BYPASSRLS) — see `docs/plans/2026-07-02-rls-cutover.md`.

**Sessions die with the erasure.** `eraseAccount` bumps `tokenVersion` in the
same write that anonymizes the user row and pushes the new version into the tv
cache after COMMIT, so every access token already issued stops authenticating
on its next request — including the shopper's own session on the
merchant-initiated path, where nothing clears their cookies (#1871). If that
cache write fails the key is deleted instead (the next request reads the bumped
version from Postgres); if the delete fails too, the old tokens keep working for
up to their 30-minute life and a P1 alert fires (`auth.eraseAccount.revoke-sessions`)
— the erasure itself still completes (issue 1964).

**CRM scrub outcome.** The `customers` CRM row has no FK to `users` and is
matched by email/phone, so the scrub is NOT unconditional: it can match nothing
(CRM rows only exist for shoppers a merchant has grouped, or the contact details
differ) or refuse a match that hits more than one row rather than erase another
data subject. `eraseAccount` returns `{ crmChecked, crmRowsScrubbed,
crmAmbiguous }`; all three callers write it (plus `crmReviewNeeded`, true only
for an ambiguous match) into the audit row's `details`, and the merchant route
returns it so the admin UI shows a warning for an ambiguous match and a note
for no match instead of an unqualified success (#1880). The ambiguous-match
warning does not auto-dismiss, and the Customers list the merchant is sent to
repeats it as a banner (`?erasureReview=1`) until dismissed (#2229) — the audit
row itself is readable only in the super-admin viewer.

**Storefront search log (`search_query_daily`).** A row is a normalised search term and daily
counts for one store; it is never linked to a user, session, IP, user agent or order, and keeps no
time of day. Phone / email / national-id / order-number / id / link shaped terms are dropped before
insert (`isPersonalDataTerm` in `@ebda/shared` `search/personal-data-term.ts`), but free text can
still contain a name or a place a shopper typed. There is no subject key, so a per-customer erasure
or export cannot find such a row and none is attempted (Ruling SEARCH-T5-6); the merchant view (admin
`/stores/[id]/insights/searches` and the "searches with no results" card on Analytics, both
through `getSearchInsights`) lists only terms searched by at least two distinct searchers in the window (the same searcher's
sort/category changes and retries count once: a salted, daily-rotated IP+UA hash that lives only as a
30-minute Redis key, never in the table or a log), and every row ages out after 90 days. A store
deletion removes it (FK `ON DELETE CASCADE`, proven in `tests/integration/search-log.test.ts`).

**Merchant webhook delivery log (`webhook_deliveries`).** One row per event per merchant endpoint,
holding the exact JSON that was signed and sent. By default the payload has no customer identity
(order id/number, totals, status, line items); only an endpoint the merchant switched
`includeCustomer` on carries the customer's name, email and phone, and then the merchant is the
controller of what their own server receives. The last 50 rows per endpoint are kept, every row ages
out after 30 days (`webhook-delivery-purge-daily`, each store in its own tenant transaction), the
response body is kept only as a 200-character snippet, and a store deletion removes it (FK `ON DELETE
CASCADE`). A customer erasure strips `data.customer` from the stored payloads of that shopper's orders and
email (`redactWebhookCustomerData`, Ruling WH-7); payloads already delivered to the merchant's own
server cannot be recalled, and the 30-day purge bounds our copy. `webhook_endpoints` holds the endpoint URL and the signing secret encrypted at rest
(`encryption.encrypt`); it is deleted with the endpoint or the store.

## Export path

`GET /auth/me/export`, authenticated. Returns the full JSON bundle
of every PII row tied to the user (every table in the matrix above
that references their `userId`/`customerId`). Required by GDPR
Art. 20 (data portability); the PDPL (Law 151/2020) also gives the data
subject a right of access (see the legal-basis note at the top).

| `search-log-purge-daily`              | `30 4 * * *`   | daily 06:30 (DST 07:30) | Deletes `search_query_daily` rows >90d                                              |
| `instapay-receipt-retention-daily`    | `30 4 * * *`   | daily 06:30 (DST 07:30) | Deletes InstaPay receipt screenshots and scrubs receipt personal fields on schedule |

Three Sunday-morning passes are intentionally staggered an hour apart
to avoid Neon connection-pool overlap during the heaviest cleanup
window. The monthly user-anonymize lands a separate day from the
weekly sweeps so its retries (`retries: 2`) don't compound the Sunday
load.

`search-log-purge-daily` runs every day at 04:30 UTC, after the 04:00 Sunday sweep; it is one
small indexed DELETE per store (`store_id, date`), so it adds no meaningful load to that window.

## Future work

- **Guest-origin CRM erasure path** (audit-followup #1878): `eraseAccount`
  starts from `prisma.user.findUnique` and 404s when no matching `users` row
  exists. A `customers` row created from a guest checkout (no account, e.g.
  via `customer-group.service.ts`) has no `userId` to erase by, so its PII
  (email, name, phone, notes) and its `customer_addresses` rows have no
  self-service or admin erasure path today — a real gap given this is a
  majority-guest-checkout market. Needs a product decision on how a guest
  proves they are the data subject before a CRM-row-keyed erasure is added
  (e.g. un-hiding the admin privacy card for guests, or a verified
  self-service flow keyed on phone/email) — not solved here.
- **5y order anonymizer**: when the first Ebda Store orders hit 5 years
  (earliest in 2026-12), add a cron that scrubs `shippingAddress` +
  `billingAddress` JSON to `{anonymized:true}` on `orders` whose
  `createdAt` is >5 years AND `customerId` IS NULL (already-erased
  customer). Until then there are no orders old enough to trigger.
- **Per-store retention overrides**: some merchants may want shorter
  retention for compliance with stricter regional regs. Today every
  store inherits the platform defaults above.
- **Backup retention** (corrected 2026-07-11 — the previous "9 commits via
  `prod-<sha>` branches" description was stale; per-commit Neon snapshots
  were retired 2026-06-08): recovery today is **Neon PITR (7-day window)**
  as the primary near-zero-RPO path, plus **daily encrypted `pg_dump`s to
  local Mac + R2 (30-day retention on both)** as the belt-and-suspenders
  layer. Full detail: `docs/DB-BACKUP-RESTORE.md`. Both layers mean an
  erased user's PII can persist in a backup for up to 30 days after
  erasure (the dump layer) — see `docs/privacy/data-map.md` § "Deletion &
  backups" for the full erasure-boundary writeup. The source of truth for
  live retention enforcement is still the DB columns above.

# PDPL erasure and export on Cloudflare storage (G10)

Law: Egypt Personal Data Protection Law 151/2020 (article numbers not yet counsel-verified, see `docs/RETENTION.md`). Code: `apps/api/src/cf/erasure/`. Plan lineage: `business/ebda/plans/2026-10-28-store-on-cloudflare-detailed.md` addendum G10, `docs/plans/done/2026-10-28-customer-intelligence.md` section 1.7.

**Status: built and tested, flag-gated.** `PDPL_CF_ERASURE_ENABLED` is unset everywhere, so `runErasure` / `runExport` throw `ErasureDisabledError`. While the flag is off the merchant/staff closure API (`POST /auth/me/close-account`) is honest about it: it records an `account.closure.requested` audit row, sends a P1 alert and returns `503 ERASURE_NOT_ENABLED` (bilingual message, nothing erased), and the flag state is reported as `checks.pdplErasure` in the super-admin deep health check (S3, 2026-11-12). Until the Store cuts over to StoreDO the Postgres path (`POST /auth/me/erase` -> `AuthService.eraseAccount` + `privacy-propagation.service.ts`) stays the one that runs. At cutover: set the var, wire the trigger (below), and delete the Postgres path with the rest of Neon.

## One job, five surfaces

`runErasure(env, surfaces, subject)` runs every surface even when one fails, records a ledger entry (`ebda-private/erasure-ledger/<requestId>.json`, subject stored only as a sha256, never the phone/email), fails the job when any surface reports `remaining > 0` after its erase, alerts P1, and is idempotent per `requestId` (a `done` entry short-circuits a queue redelivery; a `failed` one retries). `runExport` writes one NDJSON per surface plus a manifest to `ebda-private/exports/<requestId>/` (the bucket expires `exports/` after 7 days, `scripts/ops/cf-logs-setup.sh` step 2).

| Surface                                | Customer erase                                                                                                                                                                   | Merchant erase                                                                  | Export                                                  | Test (`apps/api/workers-do/erasure.test.ts`)                                                                      |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `store-do` (StoreDO rows)              | registry-driven delete or scrub of rows matching buyerKey / email / phone / userId (`registry.ts`); orders keep money history, identity columns are overwritten                  | `deleteAll()` + alarm cleared, verified by an empty `sqlite_master`             | merchant: every table; customer: matching registry rows | "surface: store-do" (3 tests)                                                                                     |

| `media` (R2 `ebda-media`)              | none (customers own no media)                                                                                                                                                    | deletes exactly `stores/<storeId>/` (prefix is exact, `m1` never matches `m10`) | key list                                                | "surface: media"                                                                                                  |

Analytics Engine holds no buyer key and no order id by design (CI plan 1.5), so there is nothing to erase there; aggregates already published stay (they are not personal data after the k-threshold). Backups: an erased row survives in the 30-day R2 and Mac copies until they rotate; the boundary statement in `docs/privacy/data-map.md` ("Deletion & backups") is the one to quote, and it now also covers `store-do-backups/`, `d1-backups/` and the Mac copy (30 days).

## Live flows after Postgres removal: D1 + StoreDO coverage (FOLD-ERASURE, Rulings FOLD-ERASURE-1/2)

The flag-gated job above is not the path that runs today. These are, and `tests/unit/platform-subject-coverage.test.ts` enforces that every personal table of BOTH databases is reachable from them (it reads the real migrations; a new personal table with no export + erase path, or an engine that no flow calls, fails the PR):

| Flow                                                                       | StoreDO                                                                                                                                                                | Platform D1 (`ebda-platform`)                                                                                                                                                                                                                                | Identity (D1 `ebda-identity`)    |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| Customer erase (`POST /auth/me/erase`, merchant/admin erase of a customer) | `eraseShopper` (registry: delete or scrub, orders keep money and lose the person)                                                                                      | none by construction (a shopper has no D1 row)                                                                                                                                                                                                               | `eraseCustomer` (in the DO)      |
| Customer export (`GET /auth/me/export`)                                    | `exportSubject` (registry customer-pii rows)                                                                                                                           | none                                                                                                                                                                                                                                                         | profile + passkey labels         |
| Merchant / staff erase (`POST /auth/me/erase`, `DELETE /admin/users/:id`)  | `StoreDO.scrubActor` on EVERY DO store: actor ids (`created_by`, `approved_by`...) replaced                                                                            | `eraseUserAccess` -> classification engine: memberships, push devices, legal acceptances (IP, UA), notice deliveries, API keys DELETED; actor ids on audit / approval / invitation rows replaced; invitations by address revoked and the address overwritten | `eraseUser` (sessions, passkeys) |
| Merchant / staff export (`GET /auth/me/export`)                            | not included (actor ids are pseudonymous, listed in the classification)                                                                                                | every row above, plus the actor-id rows as `rowid + column`; API key HASHES are never exported                                                                                                                                                               | `exportUser`                     |
| Store deletion (`StoreService.delete`, after the delete commits)           | `eraseSubject({kind:'merchant'})`: buyer + merchant contact data anonymised, account / cart / consent / marketing rows deleted, fiscal / VAT / payment / ETA rows KEPT | `eraseStorePlatformData`: store staff + API keys deleted, invitee addresses overwritten, card reference + provider customer id removed; payer fields via `paymentsErasurePort` (anonymised, amounts and references kept)                                     | owner via the existing flow      |

Rules this encodes (nothing new was invented): money and order records keep their legally required fields and lose the person (Ruling RETENTION-1/2, Law 206/2020 Art. 37, Law 17/1999 Art. 26); erasure of a user who still owns stores is refused (409 `USER_OWNS_STORES`); platform administrators are removed by the operator only; every erase is idempotent, read-back verified, and throws (503) rather than report done with rows left.

**Ruling FOLD-ERASURE-1** - the user-keyed D1 engine (`cf/erasure/platform-subject.ts`) is driven by `erasure-classification.json`, replacing the never-called `scrubUserFromPlatform`; the StoreDO actor scrub fans out to every DO store because the user's past stores are not recorded once the membership row is gone. Cost if wrong: an erasure wakes every StoreDO (cheap UPDATEs, rare operation); at thousands of stores move the fan-out to a queue.

**Ruling FOLD-ERASURE-2** - a deleted DO store is anonymised right after the delete commits (not before: a failed delete reopens the DO and an anonymisation cannot be rolled back). Each of the three steps retries 3x and raises a P1 alert naming the store when it cannot finish; re-running the delete converges. Cost if wrong: a store whose anonymisation alert is missed keeps customer PII in a closed DO until someone acts on the alert.

Not covered here, on purpose: a merchant-wide portability bundle for a whole store (the `runExport` job above stays flag-gated; the business export is `GET /stores/:id/bulk/export.xlsx`), and R2 media leftovers of already-deleted stores (a separate approved step). Audit-log `meta` JSON is free-form and is not scanned for personal values; the admin delete route no longer writes the erased address into it.

## Contracts other work must honour

1. **Phase-1 schema owner:** `registry.ts` must classify EVERY StoreDO table. The unit test "every StoreDO table is classified" fails the PR that adds a table without deciding `no-pii`, `store-owned` or `customer-pii`. When phase 1 adds customer, address or buyer-key columns, replace the `orders`/`order_items` entries with a `customer-pii` scrub (orders stay, identity goes). A scrub entry must overwrite every column it matches on (also tested).
2. **Identity owner (contract addendum v1.1, DELIVERED on feat/identity-store-verify):** the identity service provides a Service Binding RPC pair on `accounts.ebda.app`: `Accounts.eraseUser(userId, requestId?) -> { erased: boolean, remaining: number }` (a repeat is `erased:false, remaining:0`; deletes User, RefreshToken, VerificationToken, PasskeyCredential, sessions; revokes every `sid`) and `Accounts.exportUser(userId) -> Record<string, unknown[]>`. `IdentityPort` in `cf/erasure/types.ts` is the consumer side. The contract text lives in `business/ebda/plans/2026-10-24-ebda-identity-token-contract.md` (v1.1); `workers-do/erasure.test.ts` pins the same fixture shape.
3. **Email owner (G6):** implement `SuppressionPort` over the suppression table (tombstone = HMAC of the lower-cased address with `SUITE_BUYER_KEY_SECRET`-class secret, status kept).
4. **CI owner (DONE, CI-1):** the layout in the CI plan (store-first prefixes and the buyer index) is what the CI surface reads, and the writer (`apps/api/src/lib/ci/sink.ts`) maintains the index (index first, compare-and-set; Ruling CI-5). `tests/unit/ci-sink.test.ts` and `apps/api/workers-do/ci-capture.test.ts` run the real writer and then this real surface. On the Postgres path (until cutover) `AuthService.eraseAccount` collects every buyer key on the shopper's orders and the `account/erased` job erases them from R2 (`eraseCiOutcomes`), the export bundle carries `customerIntelligence`, and `orders.buyer_key` / `area_key` are nulled.
   4b. **At cutover (Ruling CI-8):** the customer-erase trigger must call `apps/api/src/lib/ci/erase.ts` (`eraseCiForOrders`, `eraseCiBuyerInStore`), not `ciSurface.eraseSubject`, whose buyer-key-wide, tombstone-less erase is unsafe for a typed phone.
5. **WhatsApp:** emit `customer.erased { buyerKey }` on the `ebda-wa-events` queue when a customer erase completes, so Ebda Chat deletes the contact and messages (contract section on `customer.erased`). Wiring lives with the trigger below.

## Trigger (not wired, on purpose)

**Merchant / staff closure trigger (M-024, Ruling M024-1): `POST /auth/me/close-account` calls the job; flag off records the request (audit row `account.closure.requested`) and erases nothing.** The job is a library plus a flag. The trigger belongs with the jobs work (G5): an `erasure.requested` queue message, or the existing `/auth/me/erase` route and the merchant-delete flow calling `runErasure` when the flag is on. Bindings needed on the consuming Worker: `STORE_DO`, `MEDIA_BUCKET` (ebda-media), `CI_BUCKET` (ebda-ci), `STORE_BACKUPS` (ebda-private), `ACCOUNTS` (identity service binding).

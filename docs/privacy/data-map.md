# Data map (Record of Processing Activities)

What personal data Ebda Store collects, where it goes, why, how long it lives, and
how it's deleted. This is the artifact that makes the cookie-consent banner
(`apps/web/src/components/CookieConsentBanner.tsx`) and the erasure endpoint
(`POST /auth/me/erase` → `AuthService.eraseAccount`) defensible under a
GDPR / Egyptian PDPL (Law No. 151 of 2020) audit (the older GCC
analysis is in `docs/privacy/data-map.md`; the PDPL article
numbers are not yet counsel-verified, see `docs/RETENTION.md`) — a regulator (or a
client's counsel) can point at any category of data and get a straight
answer: where it lives, on what legal basis, for how long, and how it's
purged.

Derived directly from the code (grepped, not guessed) on 2026-07-11. Companion
to `docs/RETENTION.md` (which is the authoritative per-Postgres-table
retention matrix) — this document adds the piece RETENTION.md doesn't cover:
**every third-party destination** the data also flows to.

## How to read this

- **Legal basis** follows GDPR Art. 6(1): `contract` (needed to deliver the
  order/account), `consent` (cookie-banner opt-in, revocable), `legitimate
interest` (fraud prevention, security, service operation).
- **Deletion path**: `eraseAccount` = covered by `AuthService.eraseAccount`
  (customer-initiated `/auth/me/erase`, merchant-initiated
  `POST /stores/:storeId/customers/:customerId/erase` — store_admin/
  super_admin only, strictly scoped to that merchant's own store, see
  `customers.routes.ts` — or the monthly retention cron). Export is the
  same split: `/auth/me/export` (shopper) and
  `GET /stores/:storeId/customers/:customerId/export` (merchant), both
  backed by `AuthService.exportAccount`. Exactly one implementation of
  each; the two routes differ only in who's allowed to call them and for
  which shopper. `propagated` = additionally pushed to the third party by the
  `account/erased` Inngest event (see "Third-party erasure propagation"
  below). `never collected if declined` = consent-gated, so a customer who
  never opts in never generates the row in the first place. `not deletable
per-user` = see the specific note.

### Cloudflare Workers Logs — request URLs (accepted residual, Ruling SEARCH-T5-8)

- **What is stored:** `apps/api`, `apps/admin` and `apps/orders` run with Workers observability
  on (`"observability": { "enabled": true }` in each `wrangler.jsonc`), so Cloudflare keeps one
  invocation log per request whose message is `<method> <full URL>`, query string included
  (Cloudflare docs, Workers Logs → Invocation Logs). A storefront search reaches the API as
  `GET /api/v1/public/products?search=<term>`, so whatever a shopper typed (a phone, an email)
  can sit in that log. Code cannot scrub it: it is written by the platform before our handler
  runs. Our own log lines (pino) and Sentry redact these values (`sentry-url-scrub`).
- **Admin routes (Ruling SEARCH-P2-9):** the admin ⌘K palette, the Customers and Orders search/export
  and the Orders PWA list send the typed term in the `X-Search-Query` request header, not in the URL,
  so a merchant's customer-phone lookup does not enter this log. Request headers are not part of the
  invocation log. The storefront → API term is closed too (Ruling SEARCH-URL-1): `GET
/public/products` and `GET /public/:storeId/search/suggest` read it from the same header, and the
  search PAGE address is `/search` with the term in the browser's history state. Still open: an older
  admin/PWA/storefront build that still sends `?search=`/`?q=` (accepted by the API for one release,
  then removed), and an old `/search?q=` link a shopper opens (that one request is logged before any
  code runs).
- **Retention:** the platform's Workers Logs window, at most 7 days (3 days on Workers Free,
  7 on Workers Paid; the plan in use was not verified from this repo), then deleted by
  Cloudflare. Not exported (no Logpush).
- **Who can read it:** Ebda operators only (members of the Cloudflare account). Merchants and
  shoppers have no access.
- **Why accepted:** pre-launch these logs are our only production request trace; turning
  `invocation_logs` off would lose it.
- **Done (Ruling SEARCH-URL-1):** the storefront → API search term moved out of the URL into the
  `X-Search-Query` header. After the first deploy, re-check that the `api` Worker's invocation log has
  no `search=` / `q=` values from the new storefront. Cost if wrong: a shopper's typed phone number
  retained in operator-only logs for up to the retention window.

### Ad pixels receive the search term (accepted residual, Ruling SEARCH-T5-9; URL half closed by PIXEL-CONSENT-1)

- **What is sent:** after the shopper gives marketing consent, the storefront's search page calls
  `trackSearch` (`apps/web/src/components/MarketingPixels.tsx`), which SENDS the typed term as an
  event parameter to the merchant's own pixels: Meta (`Search`, `search_string`), TikTok
  (`Search`, `query`), Snap (`SEARCH`, `search_string`), Google gtag / GA4 / Ads (`search`,
  `search_term`) and Pinterest (`search`, `search_query`). X (`Search`) carries no term.
- **What is withheld:** when the term is personal-data shaped (`isPersonalDataTerm` from
  `@ebda/shared`, the same test the first-party search log uses: a phone or national id in any
  digit script, an email, an order number, an id/token, a link), the Search event still fires but
  WITHOUT the term.
- **Residual:** a term that is not PII-shaped (a name, a street) still reaches those networks for
  a consenting shopper, as an event parameter. The pixels' own PageView used to read the page URL
  (`/search?q=<term>`); that is closed (Rulings SEARCH-URL-1 and PIXEL-CONSENT-1): the search address
  carries no term, and no pixel loads or fires on any URL with a `q` / `search` / `email` / `phone` /
  `token` / `restore` / `waToken` query. Cost if wrong: a name typed into search reaches the
  merchant's ad networks for consenting shoppers.
- **Why accepted:** consent-gated, merchant-configured, and the standard behaviour of commerce
  pixels; our own capture paths (PostHog, Sentry, the search log) scrub or drop these terms.
- Related: the PostHog `$elements_chain` string (`a:attr__href="/search?q=…"`) is scrubbed too;
  a query value stops at a double quote (never at an apostrophe, which `encodeURIComponent`
  leaves raw and Franco-Arabic terms use as a letter) so the inner `?q=` is not swallowed by the
  first pair.

## 4. Two intentional "won't erase" categories — and why

Not every category above is erasable on request, and that's a defensible
design choice, not an oversight:

1. **Audit logs (`audit_logs` table + R2 JSONL archive).** These exist
   specifically to be tamper-evident proof of what happened, including
   who did it — erasing an entry on the erased user's own request would
   defeat the purpose (imagine a fraud investigation where the suspect
   could delete their own trail by clicking "delete my account"). GDPR
   Art. 17(3)(b) explicitly carves out an exception for legal-obligation /
   legitimate-interest records like this. They still expire on their own
   schedule (90 days hot → 7 years archived, then gone — see
   `docs/RETENTION.md`).
2. **Advertising-platform copies (Meta/TikTok/Snap pixels + CAPI, §3).**
   Ebda Store never stores a queryable "this is customer X's ad-platform profile"
   record — it only ever SENDS pseudonymized events outward. There is
   nothing in Ebda Store's own systems to delete beyond what `eraseAccount`
   already removes (the local order/customer link). A shopper who wants
   their data removed from Meta's or TikTok's own ad systems needs to use
   THOSE platforms' own subject-access tooling — that's a relationship
   between the shopper and Meta/TikTok as independent data controllers of
   their advertising data, not something reachable through Ebda Store's API.

### Customer Intelligence outcomes (CI-1, capture only)

What: one append-only record per commerce outcome (order placed/paid/cancelled/refunded, COD confirmed/unconfirmed, shipment created/picked up/attempted/delivered/returned) in the private R2 bucket `ebda-ci` (`outcomes/v1/store=<id>/dt=<day>/*.ndjson.gz`), plus one content-free point per event in Analytics Engine (`ebda_commerce_outcomes`: store id, type, carrier, area key, amounts, hours; NO buyer key, NO order id). The buyer appears only as `buyerKey` = HMAC-SHA256(secret, E.164 phone); never a name, phone, e-mail or address. The one free-text field is the carrier's return reason, scrubbed (phones, e-mails, links masked) and cut to 200 characters. `areaKey` is governorate plus district only (`EG-C-nasr-city`).
Purpose: improving delivery, courier choice and fraud signals (internal first; merchant hints later behind minimum samples, advise-never-block). Basis and wording: the privacy-policy and terms update the controller drafts and Ahmad signs (not in this repo's code).
Retention: raw envelopes 24 months (R2 lifecycle rule `expire-ci-raw-24m` on `outcomes/`, `scripts/ops/ci-capture-setup.sh`); Analytics Engine 90 days (Cloudflare); aggregates (later) indefinite and k-anonymous.
Erasure/export: customer erasure removes the account's own orders' rows in its store (and, for a proven phone, that key's rows in that store only) via the buyer index (`index/buyer/`) and a second prefix pass, nulls `orders.buyer_key`/`area_key`, and is verified by re-reading the partitions (`eraseCiOutcomes`, `cf/erasure/surfaces.ts`); merchant erasure deletes the store's whole prefix. Erasure tombstones (`tombstone/`, 30 days) stop in-flight events re-creating erased data; parked dead letters (`dlq/`, 14 days) are erased with the account. The account export includes the buyer's own rows (`customerIntelligence`).

### Customer Intelligence aggregates and hints (CI-2 / CI-3, Rulings CI-9 to CI-12)

What: derived counters only. Per store and day, and a 90-day window per store, in R2 `ebda-ci` under `aggregates/v1/store=<id>/` (counts by carrier, area key, COD amount band; no buyer key, no order id, no person); a cross-store cohort (`aggregates/v1/<metric>/dt=<day>.json`, `aggregates/v1/xstore/latest.json`) built ONLY from stores that switched `ciSharing` on, with every cell under 100 outcomes / 5 stores / 40% single-store share written as suppressed and no store id in the file. `ci_insights` (Neon; findings over the cohort, no identifier) and `ci_hint_logs` (Neon; per order: a band, a sample size, later whether it was delivered or returned; no buyer key, phone or text).
Purpose: show the merchant advice (COD risk note, courier suggestion, COD-amount card) and let a super-admin review platform-wide findings. Advice only: nothing holds, delays or cancels an order.
Retention: aggregates indefinite (k-anonymous cohort) / store-level files until the store closes; `ci_hint_logs` 400 days.
Erasure: customer erasure needs nothing here (counts only; `ci_hint_logs` rows leave with the order); merchant erasure deletes `aggregates/v1/store=<id>/` with the outcome prefix. Published cohort cells stay (k-anonymous).

## 5. Deletion & backups — the honest erasure boundary

`eraseAccount` (+ its third-party propagation, §3) only ever mutates the
CURRENT, live copy of the data. Ebda Store also keeps point-in-time recovery and
backup copies of the whole database for disaster recovery
(`docs/DB-BACKUP-RESTORE.md`), and those copies are, by construction, taken
at a moment in time — an erasure that happens today doesn't retroactively
edit a backup that was already taken yesterday.

**Cloudflare storage (from the cutover, G8/G10).** The same boundary applies to the new copies: nightly StoreDO exports (`ebda-private/store-do-backups/`), D1 exports (`d1-backups/`) and their copy on the Mac (`_backups/ebda-cloudflare/`, 30 days) keep a pre-erasure row until they rotate, and StoreDO PITR / D1 Time Travel keep 30 days. A restore from any of them must be followed by re-running the ledger's erasures (`erasure-ledger/<requestId>.json` lists every request; the job is idempotent). Erasure design and per-surface tests: `docs/privacy/erasure-export.md`.

Concretely, as of 2026-07-11 (`docs/DB-BACKUP-RESTORE.md` is the live
source of truth if these numbers ever change):

- **Neon PITR (point-in-time recovery): 7-day window.** If production is
  ever restored to a timestamp from BEFORE an erasure, that customer's
  pre-erasure PII reappears until the erase is re-applied (or re-run — it's
  idempotent). This window is short and only used for genuine incident
  recovery, never a routine operation.
- **Daily `pg_dump` backups (local Mac + R2, encrypted): 30-day retention
  on both layers.** An erased user's PII persists in progressively older
  dumps until they roll off this 30-day window. This is the LONGEST
  possible reappearance window across all backup layers today.

**Plain-language boundary statement:** once a customer's data is erased,
Ebda Store's live systems reflect that immediately, and the third-party
propagation in §3 runs within minutes (best-effort). Standing backups mean
a genuinely complete purge — including every backup copy — takes up to
**30 days** (the longer of the two backup layers above) to fully roll off,
and up to 7 additional days of PITR exposure if a disaster-recovery
restore happens to land on a pre-erasure timestamp during that window.
This is disclosed here, in `docs/DB-BACKUP-RESTORE.md`, and should be the
answer given to any data-subject request that asks specifically about
backup persistence.

## Third-party erasure propagation — how it's wired

`AuthService.eraseAccount` fires an `account/erased` Inngest event
immediately after its anonymization transaction commits (see
`apps/api/src/services/auth.service.ts`). A dedicated consumer,
`apps/api/src/lib/inngest/functions/account-erased-propagation.ts`, then
calls `apps/api/src/services/privacy-propagation.service.ts` to best-effort
delete the user's copy at each configured third party (§3). This is
deliberately decoupled from the erase transaction and from the HTTP
response the customer receives:

- The Postgres anonymization is the transaction that MUST succeed — it's
  synchronous, in the request path, and already committed by the time any
  propagation runs.
- Every propagation step is independently retried by Inngest and logged on
  failure, but a failure can never roll back the anonymization or surface
  as an error to the customer who requested erasure.
- Nothing here ever logs the user's email, name, phone, or other PII —
  only the opaque `userId` (already the established logging convention
  across this codebase) and provider-issued opaque ids (OneSignal player
  id, PostHog person id).
